# 痕迹验收（`scripts/trace_verify/`）

## 这个目录现在验什么

**一件事**：正文渲染改走 Markdown 之后，痕迹靠「**往源文本里插控制字符标记**」实现
（`app/lib/services/trace_markdown_source.dart`）—— 本目录验这条注入路径。

它只有**一个脚本**：`bin/verify_trace_markdown.dart`（10 组 · 43 项）。

```bash
cd scripts/trace_verify
DART=/d/flutter/bin/cache/dart-sdk/bin/dart.exe    # 官方版 Dart 3.11.0（PATH 里那个是鸿蒙版）

$DART run bin/verify_trace_markdown.dart
```

**退出码 0 = 全过；1 = 有失败** → 可挂 CI / pre-commit。

## 为什么需要它：这条路上全是**静默**错误

| 往哪插 | 后果 | 会不会报错 |
|---|---|---|
| **围栏代码块**里 | 代码内容被污染（代码块本该原样呈现） | ❌ 不报错 |
| **行内代码**里 | 同上；且控制字符会被当代码显示出来 | ❌ 不报错 |
| **链接 URL** 里 | 🔴 **链接直接失效**（点不开） | ❌ 不报错 |
| 重复调用 | 双层标记 → 多渲染一层 | ❌ 不报错 |

⇒ 这类「不抛异常、肉眼也难发现」的缺陷，只能由断言锁死。

🔑 **本脚本最强的一条是【0】**：**剥掉控制字符后必须与原文完全相同** ——
一句覆盖了「只加不清、不改内容」这整类风险。

## 为什么是「零依赖」脚本

被验的 `trace_markdown_source.dart` 是**纯字符串处理、零 import**（连 token 层都不引），
所以本脚本 `pubspec.yaml` **不拉任何包**。

理由同 `tokens_verify` / `fsrs_verify`：本机 `flutter analyze` 会因 Windows 管道耗尽崩溃
（`CreateFile failed 231`，见 `scripts/static_check/README.md`），
**只有纯 Dart 才能本地独立验证**。

🔑 **这条约束反过来影响了架构**：为了让「痕迹怎么注入」可验证，
它必须**不碰 Flutter** —— 于是「判定 / 编码 / 渲染」被强制分成三层
（`trace_locator.dart` / `trace_markdown_source.dart` / `trace_markdown.dart`）。
**可验证性促成了更好的分层。**

## 十组断言（43 项）

| 组 | 内容 |
|---|---|
| 【0】🔑 **核心不变量** | 剥掉控制字符后与原文**完全相同**（只加不清、不改内容）|
| 【1】基本注入 | 词被包住，且档位正确（fresh / reviewing 用不同控制字符）|
| 【2】🔴 跳过围栏代码块 | ``` / ~~~ 内的词**不得**被标记 |
| 【3】🔴 跳过行内代码 | `` ` `` 内的词**不得**被标记 |
| 【4】🔴🔴 跳过链接 URL | `](…)` 里插字符会让**链接失效** |
| 【5】词边界与大小写 | `\b` 判据（`art` 不标 `start` 里的 art）· 大小写不敏感 |
| 【6】🔑 幂等 | 重复调用不产生双层标记 |
| 【7】边界 | 空输入 / 空词表 / 无命中 / 空词 |
| 【8】🔑 **与渲染端一致** | 注入的标记能被渲染端的 `pattern` 匹配回原文 + 档位 |
| 【9】词表顺序无关 | 词表顺序不同 → 结果相同；控制字符数一致 |

## 能力边界（重要）

| 能查 | 不能查 |
|---|---|
| ✅ 标记注入的全部逻辑边界（跳过区 / 幂等 / 词边界）| ❌ **`gpt_markdown` 是否真的把它渲染成带样式的 span**（需 Flutter 环境）|
| ✅ 「只加不清」这一整类不变量 | ❌ **两档在 15/18/24px 下是否真的可辨**（肉眼）|

⚠️ **脚本末尾会主动打出这两行提醒** —— 避免「跑绿了就当没问题」。
另：token 层（三档 × 两态 · 读法递减 · `forReps` 映射）**不在本目录验**，
已并入 `scripts/tokens_verify/`（【4】组「痕迹 token」，断言到具体数值，比这里更严）。

## 历史：`bin/verify_trace.dart` 已于 2026-10-02 删除

S4 之前，痕迹是「**词 → 字符区间 → 逐 span 上色**」，那个脚本验的就是这条路径
（8 组 · 97 项：切分边界 / 确定性 / 不变量 / token / 定位）。

**删除理由（逐组交代，不是整块丢弃）**：

| 原组 | 处置 |
|---|---|
| 【1】切分边界 · 【2】确定性 · 【3】核心不变量 | 🔴 **随死代码作废** —— 测的 `splitTraceSpans` 只在「字符区间」表达下有意义，而 Markdown 渲染后**偏移全变**，这条路径已整体删除 |
| 【8】痕迹定位 | 🔴 同上 —— `locateTraceMarks` 已删 |
| 【4】token 完整性 · 【5】读法递减 · 【6】三档语法 · 【7】`forReps` | ✅ **已被 `tokens_verify`【4】组覆盖且更严**（那里断言到具体数值：墨 `p.right=3`/`r=3`、格线宽 `2.5→1.5`、夜暖度 `r−b` 递减…；而删掉的这几组只验「已显式给出」）|

📌 **判据：删断言前先逐组交代「它的价值去哪了」** ——
是「随被删的实现一起作废」，还是「已被别处覆盖」。
两者都不成立时才叫**真的丢覆盖**，那时不该删。
🔑 顺带清掉的两条**恒真断言**（`check(desc, true, detail)` —— 第二个参数写死 `true`，
实际只是打印信息）：它们永远绿，是「看起来有覆盖」的假象。
