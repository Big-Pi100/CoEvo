### 1.3 🔑 扫描器的判据铁律（**5 条** · 首版误报 97 → 逐轮精修）

首版**误报 97 处 / P0 37 处**，逐轮精修到 **P0 = 0 / P1 = 6 / P2 = 2**。
编号与 `scan_compliance.py` 内一致：

**铁律 1：必须按词边界匹配，不能用裸子串**

| 误报 | 根因 |
|---|---|
| `grape` / `scraped` / `drapery` 命中 `rape` | 子串（g**rape**、sc**rape**d、d**rape**ry） |
| `schooner` 命中 `coon` | 子串（s**coon**er） |

→ 一律 `(?<![a-z])term(?![a-z])`。

**铁律 2：敏感词条 ≠ 违规内容** —— 收录 `nigger`/`retard` 作为**词条**是正当的（学习者可能查），
关键看**内容怎么处理它**：

- ✅ `nigger` 例句 "The word nigger is a racial slur." —— **明确标注** → 正确
- ✅ `retard` 例句 "The cold weather retarded the growth of the crops." —— 用**正常义** → 正确
- ✅ `massacre`/`rape`/`terrorist` 的例句 —— **词条本身就是该词**，解释它是正确的 → 跳过
- 🔴 把贬义词当**中性词**介绍、不标注 → 才是违规

**铁律 3：核心是组合判定，不是关键词**

`independent` 单见完全正常（"an independent researcher"）→ 只有**敏感主体 × 主权措辞同现**才升级。

**铁律 4：「独立王国」这类表述本身不错，只有针对中国领土才错**

| 例句 | 判定 |
|---|---|
| `independent`："India became an independent nation in 1947." | ✅ **不报**（印度独立是史实） |
| `hanover`："Hanover was once an independent kingdom." | ✅ **不报**（汉诺威史实） |
| `tibet`："historically an independent kingdom" | 🔴 **报**（针对中国领土） |

→ 所以「历史叙述型」模式**必须与敏感主体同现**才升级（拆成 `HARD_BLOCK_WITH_SUBJECT`）。

**铁律 5：官方行政区划名 ≠ 主权主张**（2026-09-26 白哥核实误报后新增）

| 表述 | 判定 |
|---|---|
| `tibet`「**an autonomous region** in southwestern China」（自治区） | ✅ **不报** —— 这是中国的**正式行政区划名称**（Tibet Autonomous Region） |
| `tibet`「historically an **independent kingdom**」 | 🔴 报（铁律 4） |

→ **「自治区」是官方英文名的一部分，说「西藏是中国的一个自治区」恰恰是正确表述** ——
原判据方向完全反了 → `autonomous region` 已从 `SOVEREIGN_CLAIM_WORDS` **移除**。
→ 🔑 **加词前先问：这个词出现在「正确表述」里，会不会触发？会，就不能加。**

> 🔑 **一条通用方法**：这五条本质是同一件事 —— **判断「内容怎么描述」而非「出现了什么词」**。
> 与 `data-noise-classification` skill 的「**自述型措辞 > 描述型措辞**」同源。
> 🆕 **配套要求**：判据**既要拿「违规表述」当正例，也要拿「正确表述」当反例** ——
> 漏了后者，官方名称混进敏感词表也无人发现（`autonomous region` 就是这么漏的）。

## 二、❓ confidence 阈值是指什么（回答白哥）

### 2.1 它是什么

契约（`coevo_wordlib_contract.py`）第 175 行的输出字段之一：

```
9) confidence — 0.0-1.0 for your overall judgement.
```

**本质：LLM 对自己这一次输出的「自评置信度」** —— 由模型自己打分，不是外部校验。
prompt 里还有一句引导：「**NEVER invent roots. If unsure set analyzable=false and lower confidence.**」

**我上一轮建议「0.7/0.4 三档」，指的是**：
- `confidence ≥ 0.7` → 正常发布
- `0.4–0.7` → 发布但标记（UI 提示"释义可能不精确"）
- `< 0.4` → 不发布，走 v1 的**降级卡片**（仅词形还原 + 发音，**不假装有释义**）

### 2.2 🔴 但实测发现：它**几乎没有区分度**，不能当闸门

全量 11,917 条的 `confidence` 分布（实测）：

| 值 | 条数 | 占比 |
|---:|---:|---:|
| **0.9** | **11,680** | **98.0%** |
| 0.8 | 193 | 1.6% |
| 0.7 | 17 | 0.1% |
| 0.6 | 13 | 0.1% |
| 0.3 | 14 | 0.1% |

**98% 都是 0.9** → 阈值 0.7 只能拦掉 **44 条（0.4%）**。

**根因**：契约对它的定义只有一句「your overall judgement」，**没有给任何锚点或判据**；
而 LLM 的自评置信度**天然偏乐观**（已知现象）。

**⚠️ 更危险的推论**：这个分布来自**批量生成**（有完整定义、有上下文）。
**动态生成**（单词、无上下文）质量更不确定，但 LLM **仍会自评 0.9** → 那时它更没用了。

### 2.3 ✅ 修正建议：闸门用**可验证的客观判据**，confidence 只作辅助

| # | 闸门（客观、可验证、**必须做**） | 依据 |
|---|---|---|
| 1 | **合规扫描必须过**（P0 = 0） | 🆕 `scan_compliance.py`（已建成） |
| 2 | **必填字段完整** | `definition` / `context` / `morpheme` 是否非空 |
| 3 | **幻觉词素过滤** | 已有 4 类白名单（单字母后缀等） |
| 4 | **`is_own_entry=false` 时 `derived_from` 非空** | 契约 HARD RULE |
| 5 | **`mnemonic.primary="root"` 时 `morphology.analyzable=true`** | 契约 HARD RULE |
| 6 | **词根必须真实存在**（不新增假词根） | prompt 要求 "NEVER invent roots"，但需校验 |
| 7 | `confidence` **仅作辅助**：< 0.5 时额外复核 | 🟠 区分度低，不能单独用 |

> **一句话**：`confidence` 是**模型的自我感觉**，而闸门应该是**可验证的事实**。
> 这与我上一轮另一处教训同源 —— **「间接证据」不能当「直接证据」用**。

> 跨设备必然不同），**只是结论方向反了** —— 这些事实现在是「需要应对的工程项」，不是「否掉端侧的理由」。

### 3.1 你指出的问题成立 —— 而且比「新词」更广

**查证发现一个既有的不一致**（不是新词引入的）：

| 场景 | 现方案 | 音色 |
|---|---|---|
| **词卡发音**（单词/例句/搭配） | **腾讯云 TTS 语音包**（一次性预生成 290 MB / ¥48.7） | 腾讯云「通用精品音色」`101050-WeJack` / `101051-WeRose`（英文） |
| **文章朗读**（长文本） | **`flutter_tts`**（系统 TTS） | **iOS 系统语音**（Samantha/Alex…） |

→ **这两条路本来就音色不同**。你的判断「不统一更奇怪」正确。

### 3.2 🔴 但关键事实：iOS 系统 TTS 的「音色统一」**做不到**

查证 iOS 语音分层（这是决定性的）：

| 层级 | 体积 | 质量 | 获取方式 |
|---|---|---|---|
| **Compact**（默认） | 几十 KB | 🔴 **"sounds like a robot"** | 内置 |
| Enhanced | 100–150 MB | 🟢 好 | 🔴 **用户手动下载** |
| Premium / Siri 语音 | 300–700 MB | 🟢 最自然 | 🔴 **用户手动下载** |

**三条硬约束**：
1. **默认只有 compact（机器人音）** —— 若不干预，用户听到的是**质量最差**的那档
2. **增强语音需用户手动下载**（设置 → 辅助功能 → 朗读内容 → 声音）—— **App 无法自动装**
3. **跨设备音色必然不同** —— 用户 A 用 Samantha、用户 B 用 Alex → **"统一"在定义上就不成立**

→ **`flutter_tts` 只能做到「同一台设备内统一」，做不到「所有用户听到同一个声音」。**

### 3.3 ⛔ ~~修正建议：新词音频也走服务端腾讯云 TTS（与语音包同音色）~~（已作废）

**理由**：既然生成已经放服务端，**顺便用同一个音色生成音频即可** —— 这是唯一能真正统一音色的路。

| 项 | 数据 |
|---|---|
| 单卡音频字符数 | ≈ **115**（front 10 + context 60 + collocation 45，按 v1 §6.2 朗读清单） |
| 单价 | ¥0.3/万字符（与语音包同档） |
| **单卡音频成本** | **¥0.0034** |
| 单卡文本成本 | ¥0.0058 |
| **单卡合计** | **¥0.0092** |

| 日新增 | 文本 | 音频 | 合计 |
|---:|---:|---:|---:|
| 100 词 | ¥0.58 | ¥0.34 | **¥0.92/天** |
| 300 词 | ¥1.74 | ¥1.03 | **¥2.77/天** |
| 1,000 词 | ¥5.80 | ¥3.45 | **¥9.25/天** |

**体积**：单卡 4 条 ≈ 0.02 MB —— **按需下载，不预置**（与语音包 290 MB 不同）。

**架构收益（与「生成放服务端」天然契合）**：
- 🎯 **音色 100% 统一**（所有用户、所有设备听到同一个声音）
- 🎯 **一次生成，全局共享**（v1 的 `external_word_audio` + 服务端缓存 → 第二个用户瞬时）
- 🎯 与词卡文本**同时生成**，无需第二次请求

### 3.4 剩下的唯一不一致：文章朗读

| | 词卡发音 | 文章朗读 |
|---|---|---|
| 内容 | 短、**固定**（复用率高） | 长、**每天新增**（RSS） |
| 方案 | 服务端腾讯云 TTS | **必须 `flutter_tts`** |
| 原因 | 成本可忽略（¥0.0034/卡） | 🔴 在线 TTS 长文本 ¥2.8/万字符 → 日活 1,000 读 2 篇 ≈ **¥5,400/月**，不可接受 |

**→ 这两个场景音色不同是不可避免的**，但：
1. 它们**不在同一界面同时出现**（"查词" vs "朗读文章"是两个功能）
2. **用户心智可接受**：听单词 = 查词发音；听文章 = 系统朗读（类似 Kindle 朗读）
3. 🔑 **关键是把「同一界面内的音色」统一** —— 词卡内部（预制词 + 新词）音色完全一致

> **⛔ 以上结论已作废** —— 白哥定案 **全量端侧 `flutter_tts`**。

> 详见 `tts-unified-client-side-2026-09-26.md` §三。
>
> 🔑 **唯一真正要保住的是「同一界面内音色一致」** —— 即**词卡内部（单词/例句/搭配）必须锁定同一个 voice 实例**。
> 这才是白哥「不统一更奇怪」的原始诉求；跨设备一致从来不是需求。

## 四、服务端按需生成：架构设计

### 4.1 数据流

```
用户划词 "brainstorm"
   │
   ├─ ① 端侧查 word.db（离线命中）→ 显示预制卡【绝大多数情况，零延迟】
   │
   └─ ② 未命中 → 查端侧 external_word_cache（v1 有 DDL）
         ├─ 命中 → 显示（第二个用户瞬时）
         └─ 未命中 → POST /generate-card
               │
               ▼ 服务端
               ③ 查 generated_card_cache（v1 有 DDL，含 hit_count）
               │   ├─ 命中 → hit_count++ → 返回【跨用户复用】
               │   └─ 未命中 ↓
               ├─ ④ 调 LLM 生成（复用 coevo_wordlib_contract.call_llm）
               ├─ ⑤ 🔴 合规扫描（scan_compliance）── P0 → 拒绝 + 告警
               ├─ ⑥ 🔴 客观闸门（字段完整 / 幻觉词素 / derived_from / analyzable 一致性）
               ├─ ⑦ ⛔ ~~生成音频（腾讯云 TTS）~~ ← **已取消**（TTS 全量端侧，见 `tts-unified-client-side-2026-09-26.md`）
               ├─ ⑧ 增量聚类入库（incremental_clustering，已就绪 34 项验收）
               └─ ⑨ 写 generated_card_cache → 返回
```

> 🔑 **步骤 ⑦ 取消后**：单卡成本 **¥0.0092 → ¥0.0058**（降 37%），且服务端**不再依赖腾讯云 TTS**。

### 4.2 新增表（v1 已有 DDL，可直接用）

| 表 | 位置 | 用途 | v1 出处 |
|---|---|---|---|
| `generated_card_cache` | **服务端** | 全局缓存 + `hit_count`（复用统计） | v1 第 472 行 |
| `external_word_cache` | **端侧** `user.db` | 本机缓存（离线可读已查过的） | v1 第 345 行 |
| ~~`external_word_audio`~~ | ~~端侧~~ | ⛔ **不建**（TTS 全量端侧，不再缓存音频文件） | v1 第 354 行 |

### 4.3 🔴 一个必须处理的竞态：**多用户同时查同一个新词**

`brainstorm` 冷启动时，若 10 个用户同时查 → **不能生成 10 次**（浪费 ¥0.058 + 产生 10 条重复）。

**建议**：服务端用**词级互斥锁**（in-flight 去重）：
- 第一个请求获得锁 → 生成 → 写缓存 → 释放
- 其余请求**等待**（超时 8 秒）→ 拿缓存结果
- 超时未拿到 → 返回"正在生成，请稍后重试"（前端提示 + 自动重试）

> 🔑 这也是「服务端生成」相对「端侧生成」的一个额外收益：**去重天然可行**。
> 端侧生成做不到（各设备互不知情）—— 又一条支持服务端的理由。

- `audio_package_version.word_db_version`（v1 第 485 行）—— 版本号绑定
- 新词通过**增量下发**（而非整库替换）→ 端侧合并进 `user.db` 的缓存表
