三、聚合页条目「点进词库」 已实施

3.1 通路已具备，而且是干净的

不会污染生词本 —— lookup() 是纯查询； 写库（_writeBackLookup）是阅读器显式调用的。
→ 从聚合页点开一个词，不写生词本、不记 lookup 事件 —— 语义正确 （「看看这个词」≠「我要学它」）。
  • 界面直接复用查词浮层 LookupSheet.show()（阅读器里划词的那个）
  • 浮层里没有 ①② 入口 → 不会套娃（聚合页 → 浮层 → 聚合页…）
  • 🔑 这是设计里双向链路缺的一半：卡片 ⇄ 聚合页（已有）· 浮层 → 聚合页（未做）· 聚合页 → 词条（本次要补）

3.2 一种实现，两种外观

「能不能点」与「看起来能不能点」必须一致（否则又是静默无效）。三种形态：

选项行外观可点信号说明
② 平坦 + ›
推荐		 无底色、细下分隔线 › + 按下时浅底反馈 与目标形态（§二 第 1 处）一致 —— 一次改到位
① 粘土行 + onTap 凸起粘土卡 凸起本身 保住「凸起 = 可点」的一致语义，但 20+ 行仍显重
③ 不可点 平坦无箭头 无 维持现状语义，但你已明确要「能进词库」

4.1 第 4 项的实质：一句话

mnemonic_type.priority 的前四级是 root(1) → etymology(3) → collocation(4) → image(5)。 etymology（词源）与 collocation（搭配）谁在前，只影响一件事：

词型词数搭配优先（曾用）✅ 词源优先（生效）
有词根可拆5,484（47.6%） root + 搭配 root + 词源
无词根可拆6,039（52.4%） 搭配 + 词源 词源 + 搭配
代价是镜像对称的（各约 5,479 词）—— 这个顺序决定「哪一段被挤掉」，两张表只能选一张：
口径段的上卡率被挤掉的是
搭配优先（当前） collocation 99.3% · etymology 51.4% 有词根的卡看不到词源故事
词源优先 etymology 99.0% · collocation 51.7% 有词根的卡看不到搭配
🔑 所以要定的是一个产品判断，不是技术判断： 卡片第二段该给「怎么用它」（搭配）还是「它从哪来」（词源）？
（两个段的语料覆盖率几乎相同 —— 各有 11,407 / 11,437 个词带段 —— 所以不是「谁的料多」，是「谁更该被优先看到」。）

五、20:1x–21:0x 真机反馈修正（已实施）

#白哥原话改动
1 「每个词条应该有左侧的竖线区分，不然很难阅读」 成员行加 2px accentBright 左竖线（保留底边线 —— 前者归组、后者分隔）
🔑 为什么用 accentBright 而不是 line： 项目已定判据「左侧色条用 line（#EFE9DE）在浅纸上几乎看不见 = 白设」
🔄 20:2x 修正：竖线必须「分段」（白哥：「左侧的竖线是用来分割聚合页中的词条的， 我看你在草稿中都连起来了」）
原做法是 border-left —— 它必然从行顶贯穿到行底， 而行与行紧挨（无间距）→ 上一行的尾接下一行的头 = 一条贯穿全列表的长线， 看着像「列表的左边框」而不是「词条之间的分隔」。
→ 改用 ::before 并在上下各缩进 6px：相邻两行之间自然形成 12px 间隙 = 一段一段。 （实现同口径：Stack + Positioned(top/bottom: _barGap)； ⚠️ CSS 里 ::before 在 display:flex 容器内会成为 flex item， 必须 position:absolute 才能脱离 flex 流。）
2 「右上角有个小的单词这个用来干什么的，应该取消吧」 取消顶栏族名 —— 锚点 .pbar 里本来有它， 但它与页头 .agg-src 的 cept 大字 + meta 重复显示同一信息
4 「搭配整记的搭配词组应该保证显示在一行，可以中文一行、搭配词组一行这样， 现在的排列方式把词组分成了两行」
（词卡 —— 不属聚合页，但同批改）		 搭配段：Row（词组 ｜ 中文同行）→ Column（词组一行、中文一行）
🔑 根因是布局容器不是文案：Flexible 默认 fit: loose 允许子项被压窄，而 Text 被压窄时会软换行 → 词组自己折成两行。
· 词组不再被 Flexible 包 → 独占整行宽（≈300pt）
· 词组 ↔ 中文 2px；条 ↔ 条 7 → 10px （每条从 1 行变 2 行 → 两档必须拉开差距，否则分不清「哪两行是一条」）
📊 实测 31,334 条搭配：词组 p99 = 29 字符 → 99.7% 一行放得下； 余 0.3%（103 条 > 32 字符，最长 44）仍会折行 —— 有意保留（截断会看不到完整搭配，更糟）
3 「全部/已到期两个状态的大小应该统一，最好和阅读页面的收藏大小一致， 同时……应该一个凹陷一个浮起，而不是都一样」 HeaderChip 加两个可选参数：
· active → raised（浮起）/ pressed（凹陷）
· minWidth → 84 🔄 21:0x 已废弃（口径错，见下）

🔄 21:0x 修正（白哥：「药丸太宽」「内容看起来不居中」）
两个错都被指出：
① 宽度口径错：84 是「整宽」（含 padding，见我当时写的算式 padding 24 + icon 13 + gap 6 + …），却传给了作用在 padding 内部的 minWidth → 实际整宽 = 84 + 24 = 108，比目标宽 24（内容只占药丸 39% → 看着空）。
② 文字偏右：把「图标 + 文字」整块居中时，文字必然偏右 (13+6)/2 = 9.5px —— 图标只占左边，右边没有对称物。

修法：不再撑「整块内容区」，改为文字区定宽（labelMinWidth）， 并按「让文字落在药丸正中」反推内边距：
药丸宽 = L + labelW + R ｜ 文字区中心 = L + labelW/2 ｜ 药丸中心 = (L+labelW+R)/2
令两者相等 → L = R　（L 含图标 → 右内边距要故意比左内边距大）
📐 实测尺寸：8(左) + 13(图标) + 6(间距) + 36(文字区) + 27(右) = 90； 文字区 27…63 中心 45 ＝ 药丸中心 45 （精确相等）。药丸 108 → 90。
⚠️ 取舍：「图标+文字整块居中」与「文字居中」数学上不能同时成立（差 9.5px）， 你选了后者 → 图标会看起来靠左（这是必然结果）。仍略宽于「收藏」（≈84）， 因为文字居中要求右侧留出与图标等量的空间；要更窄只能缩小图标前留白或去掉图标。

🔄 21:3x 定案（白哥：「右上角按钮更不对了，还不如原来的」）→ 去掉图标
21:0x 那版也被推翻了：它虽让文字精确居中（偏移 0.00）， 却在右侧留了 27px 纯空白（左 8 / 右 27 不对称）→ 视觉重心压在左边， 比「文字偏右 9.5px」更不平衡。
🔑 一条数学结论，决定了可选范围：
药丸内容 = [图标 13][间距 6][文字]　→　 「图标+文字」整块居中时，文字必然偏右 (13+6)/2 = 9.5px
图标只占左边、右边没有对称物 —— 这是数学必然，调参消不掉。想消掉只有两条路：
· ① 右侧留出与图标等量的空白 → ✅ 文字正中，但 ❌ 右侧一大块空（＝ 21:0x，实测更差）
· ② 不要图标 → ✅ 文字正中，且 ✅ 左右留白对称

🔴 第 2 条纠正了我两处错误（都记下来）
错误一 · 引用 class 名不精确：我上一轮写「锚点 .agg-bar 右侧就是族名」—— 锚点里的顶栏其实是 .pbar（.agg-bar 是我自己在设计稿里造的 class）。
错误二 · 把「我没找到」当成了「不存在」（更值得记）： 刚才我 grep .agg-bar 找不到，就下结论「锚点里根本没有顶栏，是我编的」—— 🔴 这句才是错的。实测锚点第 715 行原样是：
<div class="pbar"><span>‹ 返回</span><b>cept 词根族</b><span></span></div>
→ 锚点里确实有族名，我上一轮加它的依据是成立的。
白哥这次取消它，是新的设计决定（理由：顶栏 .pbar 的族名与页头 .agg-src 的 cept 大字 + meta 重复显示同一信息），不是纠正我的编造。

✅ 两条判据（都已有先例，我这次又踩）：
  • 「找不到 ≠ 不存在」—— 项目原有：「我找不到原文」≠「原文不存在」≠「可按转述做」 → 换个 class 名/说法再搜一遍，再下结论
  • 引用文档内容时要「复制」，不要「凭印象写」（class 名、字段名、路径尤其） —— 我两次栽在「凭印象引用」（第一次：.agg-bar；这次又用错名去搜）
关于第 3 条：我选的方向（若不合意，一句话就能反转）
「已到期」（筛选生效）→ 浮起；「全部」（无筛选）→ 凹陷。
🔑 依据 = 项目既有语汇：BookmarkButton 是 「已收藏 = selected 凸起，未收藏 = pressed 凹陷」 → 「**生效/激活的状态浮起**」。
✅ 且凸起时给的是 raised（亮底）而不是 selected（强调色填充）—— 后者会与 _SortChip 的选中态撞脸（项目已定禁忌）。
