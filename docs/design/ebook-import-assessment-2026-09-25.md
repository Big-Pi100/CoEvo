- 性质：**可行性评估**，不改代码、不动生产环境

## 〇、结论

| # | 判断 | 结论 |
|---|---|---|
| 1 | 🟢 **合规可行，但风险等级上调** | 原判「RSS 绕开出版许可」仍成立；**用户导入自带文件 ≠ 平台提供书籍内容** —— 已用中国区 App Store 实证（大量**个人主体**阅读器）验证。⚠️ **但 Apple 审核措辞是「includes or *accesses* book content」，比预想宽** → 必须严守「本地导入」定位（见 §二） |
| 2 | 🟢 **技术上比原设想简单** | **不需要 EPUB 阅读器包**（那些维护状态都是 `Poor`）—— 我们只要**纯文本**，用 `archive` + `html` 两个成熟基础包自研即可 |
| 3 | 🟢 **零边际成本不变** | 纯端侧本地解析，**无服务端、无 API 调用** → 不破坏零边际成本模型 |
| 4 | 🟢 **对产品定位是加强而非稀释** | RSS 提供「每日新鲜短内容」，EPUB 提供「我想读的长内容」—— **两者互补**；且「想读原著」正是英语学习者的核心需求 |
| 5 | 🔴 **有一个必须处理的体验坑** | **DRM 保护的 EPUB 无法解析**（绝大多数付费电子书有 DRM）—— 不做提示会收到大量「为什么导入失败」 |
| 6 | 🟠 **工作量** | 解析器约 **930 行 / 5–7 天**（原方案预估的 500 行偏乐观，见 §四）；**「用 CoEvo 打开」已实施**（约 70 行 Swift + 185 行 Dart，见 §六） |
| 7 | 🟢 **与「TTS 朗读文章」天然协同** | 导入的书也能朗读 → **听原著** 是高价值场景（见 §五） |
| 8 | ✅ **对订阅转化是加速器** | 长文本**累计查词量远高**（书 12 万词 vs 文章 400 词）→ 用户**更快撞到 200 词上限** → 更早触发订阅（见 §3.2.1） |
| 9 | ✅ **「用 CoEvo 打开」已实施** | 用户在「文件」App 长按 EPUB → 选「用 CoEvo 打开」即可导入。**不需要 Share Extension**（省一整个 extension target）；EPUB 的 UTI 是系统内置，**不需要自定义声明**（见 §六） |

## 一、先解决最要命的问题：会不会触发 NPPA 出版许可？

### 1.1 原判断链（仍然成立）

| 环节 | 判断 |
|---|---|
| Apple 条款 | 「**提供書籍與雜誌內容的 App**」必须持 NPPA《网络出版服务许可证》 |
| RSS 为何安全 | RSS 文章**不是「书籍」** → 不触发 |
| 电子书导入为何也安全 | **内容不由我们提供** —— 是用户自己的文件 |

**核心区分**：

| 形态 | 内容来源 | 是否触发 NPPA |
|---|---|---|
| **在线书城 / 内置书库** | **平台提供** | 🔴 **触发** —— 这就是「提供书籍内容」 |
| **本地文件阅读器** | **用户自己导入** | 🟢 **不触发** —— 平台是工具，不是出版方 |

> 类比：播放器 App 能播用户自己的音乐，不需要唱片公司资质。工具中立。

### 1.2 ⚠️ 但风险比原评估高：Apple 的实际措辞

**Apple 官方审核拒绝原文**（真实案例，DCloud 社区）：

> your app **includes or accesses** book or magazine content and is intended for distribution on the App Store in China mainland. However, you have not provided a permit...

**关键在 `accesses`（访问）这个词** —— 它比「提供」宽得多。理论上，「能访问书籍内容」的 App 都可能被要求。原文更明确：

> 图书和报刊杂志 App 必须持有中国国家新闻出版署(NPPA)颁发的《网络出版服务许可证》

**→ 这意味着审核结果高度依赖「App 如何自我表述」，而不只是「实际上做了什么」。**

### 1.3 🟢 实证：中国区有大量个人主体的本地阅读器

**我用 iTunes Search API 扫了中国区 App Store**（2026-09-25），发现个人主体（卖家名为「名 姓」格式）的本地阅读器**大量存在且规模化**：

| 卖家 | App | 评价数 |
|---|---|---:|
| 三英 郑 | 山丘阅读器-本地文档收纳整理神器 | **33,978** |
| 鸣飞 王 | 小说下载阅读器-txt小说大全阅读神器 | 25,256 |
| 添欢 谢 | PureLibro阅读器-图书小说漫画神器 | **17,356** |
| 俐 马 | Epub阅读器 - 阅读txt,chm,epub,pdf小说 | **14,024** |
| 冬梅 杨 | 小书亭—热门小说TXT阅读器 | 9,423 |

**为什么这条实证有力**：**个人主体不可能拿到 NPPA 许可**（该许可要求出版单位资质 + 专职编辑人员）。所以这些 App 能长期在架且规模不小 → **证明「本地导入」形态不被要求 NPPA**。

### 1.4 🔑 安全模式的措辞（从实证里提炼）

我抓了「快阅」的描述原文，它的定位措辞很值得学：

> 「快阅是一款非常简洁优秀的**本地文档管理软件**，具有完善的**文件夹管理**功能和各种阅读设置……支持 **wifi 传递、iCloud 导入**……自动分章节」

**它把自己描述成「本地文档管理软件」，而不是「电子书阅读平台」。** 这就是安全模式。

| 维度 | ✅ 安全做法 | 🔴 危险做法 |
|---|---|---|
| **App 定位** | 本地文档/文件阅读器 · 阅读工具 | 电子书平台 · 阅读社区 · 书库 |
| **App 名称/副标题** | 「XX 阅读器 - 本地文档导入」 | 「XX 书城」「XX 小说大全」 |
| **内容来源表述** | 「导入**你自己的** EPUB / TXT 文件」 | 「海量书籍」「免费下载」 |
| **功能边界** | 本地导入、读本地文件 | 内置**书源**、在线书城、书籍推荐、排行榜 |
| **描述关键词** | 本地 · 导入 · 离线 · 文档管理 | 书库 · 下载 · 免费看书 · 资源 |

> ⚠️ **注意实证里的反面案例**：「小说下载阅读器」这类名称（含「下载」「大全」）虽然存在，但**属于擦边**，且这类 App 更可能内置书源。**我们不该学这半边** —— 我们只需要「导入自己的文件」这一个干净功能。

### 1.5 🔴 与我们产品叠加后的额外风险（必须知情）

我们是「RSS 内容流 + 电子书导入」**双重身份**，比纯本地阅读器多一层被审视的可能：

| 风险点 | 说明 | 缓解 |
|---|---|---|
| **有 RSS 内容流** | 审核员可能认为「这个 App 有内容分发」 | RSS 已确立「不是书」，且是**第三方源聚合 + 只存摘要 + 跳原文**（Flipboard 模式） |
| **有订阅收费** | 「收费 + 有内容」可能引起额外关注 | 订阅权益是**工具功能**（无限生词本 + 朗读），**不是内容访问权** —— 文案必须这么写 |
| **App 描述可能被误读** | 如果描述里同时强调「每日内容」+「导入书籍」，可能被归为内容 App | **描述分层**：主打「英语学习工具」，内容源与导入都作为**工具能力**描述 |

> **一句话原则**：**永远不说「我们有书」，只说「你可以导入你的文件」。**

> ⚠️ **我不是律师**。以上是基于 Apple 官方文档 + 真实审核案例 + 商店实证的核实，**不构成法律意见**。建议上线前请专业人士过一遍 App 描述与文案。

## 二、技术方案（比预想简单）

### 2.1 🔑 关键判断：不要用现成的 EPUB 阅读器包

`fluttergems.dev` 的维护状态评级（2026-05 更新）：

| 包 | Likes | 维护状态 | 评价 |
|---|---:|---|---|
| `epub_view` | 161 | **Poor** | 主流选择，但评级差 |
| `vocsy_epub_viewer` | 98 | Average | 封装 folioreader（原生） |
| `epubx` | 74 | **Poor** | 下载量最高（2.4K/30天），dart-epub fork |
| **`cosmos_epub`** | 44 | **Good** | 功能最全（翻页动画/高亮/连字符/主题） |
| `flutter_epub_viewer` | 30 | **Good** | 基于 epub.js + WebView |
| `epub` / `epub_kitty` | 54/32 | **Poor** | — |

**但它们都不适合我们**，原因是：

1. **它们是「阅读器 UI 组件」** —— 自带阅读界面/排版/翻页。而我们有**自己的设计系统**（粘土视觉 + 三档主题 + 自建字体子集），**不可能把一个第三方阅读器组件嵌进来**
2. **我们只需要「纯文本」** —— 不需要保留原书排版、图片、CSS
3. **避开 Poor 维护生态** —— 原方案正是为规避这个才选择不上电子书；现在功能需求不同了，可以绕开

### 2.2 ✅ 推荐方案：只用成熟基础包 + 自研解析

```
EPUB（本质是 zip）
  ├── archive（成熟，纯 Dart zip 解压）
  ├── xml（解析 OPF / NCX，标准库级）
  ├── html（HTML → 纯文本，成熟包）
  └── 自研：spine 顺序 → 章节切分 → 段落化
```

| 环节 | 方案 | 说明 |
|---|---|---|
| **解压** | `archive` | `.epub` = zip；纯 Dart，无原生依赖 |
| **元数据** | 自研解析 `content.opf` | 取标题/作者/语言/封面（XML，不复杂） |
| **章节顺序** | 自研解析 `<spine>` | EPUB 的章节顺序以 spine 为准（不是文件名） |
| **正文提取** | `html` 包 | HTML → 纯文本段落 |
| **TXT 编码** | UTF-8 优先 + **GBK/GB18030 兜底** | 中文 TXT 常见 GBK；英文 TXT 基本 UTF-8 |
| **TXT 分章** | 自研正则 | 识别「Chapter 1」「第X章」等常见章节标记 |
| **存储** | 复用 `content_cache` 表 | **不新建书籍模型** —— 一本书 = 一个 content，一章 = 一条记录（见 2.4） |

> **`cosmos_epub` 可作为参考实现**（它状态好），照它的 OPF/spine 解析思路写，但**不引入它的 UI**。

### 2.3 🔴 DRM 问题（必须提前处理）

| 情况 | 占比 | 处理 |
|---|---|---|
| **无 DRM 的 EPUB** | 公版书 / 自出版 / 部分电子书 | ✅ 可解析 |
| **有 DRM 的 EPUB** | **绝大多数商业付费电子书** | ❌ **无法解析** —— Adobe ADEPT、Apple FairPlay、Kindle 等 |

**DRM 检测**：检查 `META-INF/encryption.xml` 是否存在（EPUB 的 DRM 标志文件）。

**UI 必须做的事**：检测到 DRM → **明确提示**：「这本书受 DRM 保护，无法导入。请使用无 DRM 的 EPUB 文件。」

> ⚠️ **不做这个提示的后果**：用户会以为 App 坏了，大量差评。**DRM 是「导入功能」最高频的失败原因。**

**可以给用户的提示**（合法无 DRM 的来源）：Project Gutenberg（7 万+ 公版书）、Standard Ebooks、部分出版社无 DRM 版本。

### 2.4 数据模型：不新建「书籍」模型

**原电子书方案有 `book` / `book_chapter` / `reading_progress` 三张表**，但那是为「平台书城」设计的。**我们不需要。**

**推荐复用现有内容模型**：

| 概念 | 映射 |
|---|---|
| 一本书 | `content_cache` 的一条记录（`source = 'import'`） |
| 一个章节 | `content_cache` 的一条记录（`parent_id` 指向书）—— 或章内分段 |
| 阅读进度 | `content_cache.progress`（**已有字段**） |
| 生词 | 复用现有生词本 + `word_form` 词形还原 |

**理由**：查词、痕迹、生词本、复习队列、生词密度统计 —— **全部现有逻辑可以原样复用**，因为它们都基于 `content` 概念而非 `book` 概念。

> ⚠️ 需要改的是 `content_cache` 加一个 `source_type` 区分 `rss` / `import`，以及 `is_local` 标志（导入内容不需要联网同步）。

### 2.5 性能：大文件必须分块

| 场景 | 大小 | 风险 |
|---|---|---|
| 英文小说（如 *Pride and Prejudice*） | ~700 KB / 12 万词 | 🟢 可控 |
| 大部头（如 *War and Peace*） | ~3.3 MB / 58 万词 | 🟠 需分章存储 |
| 中文长篇小说 TXT | 5–20 MB | 🔴 必须分章 |

**策略**：
1. **导入时一次性解析 + 分章落库**（不每次打开都解析）
2. 阅读时**按章加载**（不整本载入内存）
3. 解析在 **Isolate 中执行**（避免阻塞 UI，大文件可能解析数秒）

## 三、产品判断：这个功能该不该做

### 3.1 🟢 支持做的三个理由

| # | 理由 | 说明 |
|---|---|---|
| 1 | **正中核心需求** | 「想读原著」是英语学习者的**最强动机之一**。RSS 只能给短新闻，**无法满足「读一本书」的诉求** |
| 2 | **与 RSS 互补而非竞争** | RSS = 每日新鲜、轻量、低门槛；EPUB = 长期投入、深度、高粘性 |
| 3 | **深度阅读的学习效率更高** | 长文本**词汇复现率高**（同一作者反复用词）、上下文连贯 → 对记忆更友好。这正是 FSRS「同一词条多次重复」的理想场景 |

### 3.2 🟠 三个必须想清楚的问题

| # | 问题 | 我的判断 |
|---|---|---|
| 1 | **会不会让产品定位变模糊？** | 🟢 **不会，只要是「导入」而非「书库」** —— 定位仍是「英语学习工具」，导入是工具能力 |
| 2 | **会不会拖慢生词积累（影响订阅转化）？** | 🟢 **不但不拖慢，反而加速** —— ⚠️ 但要分清**两个不同指标**（见下方说明） |
| 3 | **会不会引入新的边际成本？** | 🟢 **不会** —— 纯端侧解析，零服务端调用。⚠️ **但有一个例外**：导入内容里的**词库外生词**会触发 LLM 兜底 → **已有全局缓存设计可化解**（成本随唯一词数收敛） |

#### 3.2.1 ⚠️ 必须区分两个指标：单位密度 vs 累计量

初稿我写「读长文本查词密度低于新闻」—— 这句话**容易被误读**（与 §3.3 的「更快撞上限」不矛盾，但必须说清楚）。

| 指标 | 长文本（书） | 短文本（新闻） | 原因 |
|---|---|---|---|
| **单位生词密度**（每百词几个生词） | 🟢 **更低** | 🟠 更高 | 书**词汇复现率高**（同一作者反复用词、上下文连贯） |
| **累计查词量**（读完总共查多少） | 🔴 **远高** | 🟢 低 | 一本书 **12 万词** vs 一篇文章 **400 词**（差 300 倍） |

**净效果：累计量占绝对优势 → 读长文本的用户更快积累到 200 词 → 更早触发订阅。**
即使密度低一半，总量差距是 300 倍量级。

> **🔑 这对订阅是正向的**：读原著的人是**粘性最高、最愿意付费**的用户，而导入功能让他**更早遇到上限**。
> **所以：导入功能不仅不削弱订阅，反而是转化加速器。**

### 3.3 ✅ 原「生词上限是否统一」是个伪问题（白哥指出，2026-09-25）

**我先承认一个概念错误。** 本节初稿我提的问题是「**导入的生词要不要也计入 200 词上限**」，并给了「导入内容的生词不计入」这个选项。

**白哥一句话点破**：

> 「生词不是按查询算吗？生词为什么可以导入？」

**我错在两处**：

| # | 我的错误 | 事实 |
|---|---|---|
| 1 | 把「**内容来源**」投射到了「**生词**」上 | **生词的产生路径只有一条：用户查词**。导入的是**书**（内容），不是词 |
| 2 | 以为「导入」是一条新的绕过路径 | **RSS 本身就是无限内容**（每天更新几十篇）—— 导入并没有引入任何新的绕过可能 |

**所以「导入的生词」这个东西在数据上不存在。**

#### 生词本的真实机制

```
用户划词 → 词形还原（word_form → lemma）→ 生词本
                ↓
     生词本 = 一个词集合，按 lemma 唯一
     （一个词一条记录，与它在哪里被查到无关）
```

**关键推论（实现时必须遵守）**：

| 场景 | 生词本条数 | `content_lookup` 条数 |
|---|---|---|
| 在 RSS 文章里查 `received` | **1 条**（lemma = `receive`） | 1 条 |
| 之后在导入的书里又查 `received` | **仍 1 条**（同一 lemma） | **2 条**（两个语境） |
| 再查 `receive`（原形） | **仍 1 条** | 3 条 |

> **一个词只有一个归属** —— 生词本按 **lemma** 唯一，`content_lookup` 只是附在它下面的**语境记录**（而且 `content_lookup.sentence` 正是卡片例句的来源，多一条语境是**好事**）。

**「按来源分别计数」在逻辑上不成立** —— 除非给生词本加 `source` 字段，然后面对这个荒谬问题：同一个词从文章查的算一个、从书里查的算另一个？

#### 「200 词上限」的真实含义

| 项 | 说明 |
|---|---|
| **计的是什么** | **生词本里的唯一 lemma 数** —— 与内容来源、查询次数**都无关** |
| **唯一变量** | 用户查了多少个**不同的词** |
| **导入的真实影响** | 🟢 **长文本查词密度更高 → 用户更快撞到 200 词** |

**→ 而这是对转化有利的，不是问题。** 读原著的人生词密度本来就高，他会**比只读新闻的人更早**遇到上限 → 更早成为订阅用户。

> **结论：导入功能不仅不削弱订阅，反而可能促进转化**（更快达到上限 = 更早触发订阅决策）。
> **原「防绕过」的担心是多余的** —— 上限本来就按生词数量计，天然防绕过。

**所以这一项不需要任何额外设计**，也不需要在 UI 上做任何区分。**原 §六 的待确认项 1 作废。**

#### ⚠️ 但有一个真正的实现细节（值得写进规格）

**同一个 lemma 有多条 `content_lookup` 时，卡片的「首要例句」用哪条？**

| 建议 | 说明 |
|---|---|
| 默认取**首次查词的那条**（`MIN(looked_up_at)`） | 第一次遇到它的语境，记忆编码最强 |
| 允许用户在词卡里**切换/选择**语境 | 长文本用户可能遇到更好的句子 |
| 不做自动覆盖 | 每次查词都覆盖会让例句不断跳动，干扰复习 |

> **原则**：`content_lookup` 是**追加**的语境库，不是「最新语境字段」。**生词本记录的是「我学过这个词」，语境是它的附属素材。**

### 6.3 🔴 冷启动 / 热启动时序（本功能最容易出错的地方）

```
冷启动（App 未运行）
  iOS 启动 App → didFinishLaunchingWithOptions 带 launchOptions[.url]
  ⚠️ 此刻 Flutter engine 还没就绪，MethodChannel 无法推送 → 只能缓存
  → Dart 侧启动后主动 invokeMethod("getPendingFiles") 拉取

热启动（App 已在运行）
  iOS 调 application(_:open:options:) → 缓存 + 推一个"有新文件"信号
  → Dart 侧收到信号后同样走 pull
```

**采用「信号不带数据、统一走 pull」而非「直接推数据」的理由**：

| 方案 | 问题 |
|---|---|
| 直接推送数据 | 冷启动时推送丢失；且 `launchOptions` 与 `open:options:` 可能对同一文件**都触发** → 重复处理 |
| **信号 + pull（采用）** | Swift 侧 `getPendingFiles` **取出即清空** → **天然幂等**，重复调用无副作用；推送丢失也有 lifecycle 兜底 |

**Dart 侧三条取值路径（互为兜底）**：
1. `start()` 时首次拉取 → 覆盖冷启动
2. iOS 推送的 `onFileAvailable` → 覆盖热启动
3. **App 回到前台时（`AppLifecycleState.resumed`）再拉一次** → 兜底信号丢失

### 6.4 🔴 两个必须处理的实现细节

**① Inbox 必须清理（否则 App 体积持续膨胀）**

iOS 传入的外部文件落在 `Documents/Inbox/`。Apple 要求 App **自行处理后清理**。
→ 实现：【复制到 `Documents/imports/` 成功后，删除 Inbox 原文件】。

> **顺序不能反** —— 必须先确认复制成功再删除，否则复制失败会导致用户文件丢失。

**② 🐛 只清理 Inbox 文件，绝不删除其他来源的文件（我核对时发现的一个真实 bug 隐患）**

初稿的 `_ingest()` 对**任何来源**的文件都执行 `source.delete()`。
**这在导入器后续支持「App 内选文件」时会删掉用户自己的书**（例如从 iCloud / 文件 App 选的原始 EPUB）。

→ 修正：**仅在路径位于 `Inbox/` 时才删除**。

```dart
if (_isInboxPath(source.path)) {   // path.contains('/Inbox/')
  try { await source.delete(); } catch (_) {}
}
```

**③ 并发拉取必须串行化（我核对时发现的竞态）**

`onFileAvailable` 信号与 lifecycle `resumed` 可能**几乎同时**触发 `_drain()`。
若两次 `getPendingFiles` 交错（都发生在 Swift 侧清空之前）→ 同一路径拿到两次 → 复制出 `book (1).epub`。

→ 修正：用 in-flight Future 串行化，并发调用复用同一个 Future。
