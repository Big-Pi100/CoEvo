## 四、重设计方案

### 结构（按 §6.1 定稿 + 现役视觉语言）

```
我的                            ← 自绘顶栏（23px/w600/−0.345），副标题「白哥 · 免费版」
├ 顶部统计卡（Clay 大卡）        ← **只放统计**：连续天数 + 掌握词数 + 「分享我的学习记录」
│                                 （成就列表**移出**，「查看全部成就 ›」跳 /achievements）
├ 账号                          ← 🆕 两态（见 §六）：未登录 / 已登录（昵称 + 绑定邮箱）
├ 内容偏好                       ← 🆕 兴趣筛选（§6.3 定「留在我的页」）
├ 订阅                          ← 订阅状态 / 管理订阅 · **恢复购买** / 历史订单
├ 其他                          ← 主题风格（留）· 朗读设置（留，等阅读面板）· 联系工作人员 · 🆕 关于
└ 退出账号                      ← 🆕 页尾独立项（带文字，危险色，二次确认）
```

> 🔑 **决策 1、2 的落地**：主题风格与朗读设置**仍在「其他」组内**（本次不搬家）。
> 它们现在还是**唯一**入口 —— 阅读面板没做之前搬走 = 用户没地方调（§七）。
> ⚠️ 原「账号」组只有「改昵称」一项 → 决策 4 后扩成**完整账号区块**（含登录态、绑定邮箱、退出）。

### 与现状的差异（逐项）

| 项 | 改动 | 依据 |
|---|---|---|
| 外壳 | `AppBar` → **自绘顶栏**（与信息流/复习页逐字一致） | 现役页统一写法 |
| 容器 | `Container` → **`Clay`** | 同上 |
| 分区 | 直堆 → **分组 + 分组标题** | 复习页语汇 |
| 间距 | 手写值 → **`CoSpacing`** token | 现役页统一 |
| 底部 | 补 `tabBarClearance = 100` | `_ShellScaffold` 开了 `extendBody:true` |
| 删 | 推广二维码 · 推广统计 · 真实姓名 · 手机号 · 跳过概念 · trial 弹窗 | §4.2 / `:456` / `:457` / `:386` / `:391` |
| 加 | 兴趣筛选 · 关于 · 恢复购买（显式一行） | §6.1 |
| 调 | 成就区 → 「统计区 + 分享入口」 | §4.2 / `:396` |

### 三档主题都成立

原型里三档（墨/格/夜）**用真实 token 值**（照 `coevo_tokens.dart` 实测），可实时切换验证。
⚠️ **夜档最容易出问题** —— 粘土「内亮」在深底被压到 `rgba(255,255,255,.062)`，
所以**务必切到夜档看一遍**再定。

## 六、🆕 新增需求：账号区块（登录 / 退出 + 绑定邮箱）

### 6.1 规格依据（09-25 已定，不是我发明的）

`docs/design/english-app-implementation-plan-v2-2026-09-25.md` **§10.1.1** 原文：

> **模式：匿名可用 → 需要同步或购买时引导注册。**
>
> | 平台 | 主登录 | 兜底 |
> |---|---|---|
> | **iOS（现在只有 iOS）** | **Sign in with Apple** | 邮箱 + 密码 |
>
> **不做手机号**：短信有真实成本（约 ¥0.04/条）+ 模板审核 + 运营商报备；英语学习**不是实名强制场景**。

### 6.2 实测现状（🔴 缺口比预期大 —— 用户说得对）

| 项 | 实测现状 | 结论 |
|---|---|---|
| 端侧**登录 UI** | **完全没有**（无 `/login` 路由、无 `LoginScreen` 文件） | 🔴 **缺** |
| 端侧登录方式 | `auth_client` 5 方法 = `register`/`login`/`verifyToken`/`trialStart`/`trialClaim` → **username + password** | 🟠 与规格不符（规格要 Apple 主登录） |
| **Apple 登录** | 🔴 **无**（全库无 `sign_in_with_apple` 依赖、0 命中） | 🔴 **缺** |
| **邮箱** | 🔴 **端侧无**；后端 `users` 表**无 `email` 列**；全后端 `email` **0 命中** | 🔴 **缺**（是**新增**，不是复用）—— 与 `implementation-plan` §10.1「email 全后端 0 命中」一致 |
| 匿名试用 | ✅ `home_screen` 启动时自动 `trialStart` 建 `trial_*` 账号 | ✅ 已有 |
| **退出登录** | 🟠 **有**，但只是 `AppBar` 里一个 logout **图标**（`profile_screen.dart:416`，无文字、无确认、无账号信息） | 🟠 **需重做** |
| 账号信息展示 | 有 `username` + **`real_name`（实名）** + `phone` | 🟠 实名本次删；缺邮箱 |

### 6.3 账号区块设计

**① 未登录（匿名试用）**
```
账号
 ┌───────────────────────────────
 │ 👤  未登录                    ›
 │     登录后可跨设备同步 · 找回订阅
 └───────────────────────────────
        ↓ 点击 → 登录页（新增页面）
```

**② 登录页（🆕 新页面）**
```
        ← 返回
      登录 / 注册
 ┌─────────────────────────┐
 │      用 Apple 继续        │   ← 主登录（sign_in_with_apple）
 └─────────────────────────┘
            ── 或 ──
   邮箱  ┌─────────────────┐
         └─────────────────┘
   密码  ┌─────────────────┐
         └─────────────────┘
           [ 登录 ]  [ 注册 ]
```

**③ 已登录**
```
账号
 ┌───────────────────────────────
 │ 👤  白哥                      ›   ← 点击改昵称
 │     已登录 · 试用账号          │
 ├───────────────────────────────
 │ ✉️  绑定邮箱                  ›   ← 未绑时；已绑则显示邮箱
 │     用于找回账号 · 跨设备同步
 └───────────────────────────────
```

**④ 退出账号（页尾独立项）**
```
 ┌───────────────────────────────
 │          退出账号              │   ← 二次确认；文字按钮，危险色
 └───────────────────────────────
```
🔑 从 `AppBar` **图标**移到页尾**带文字**的独立项 —— Apple 审核红线要求「账号**注销**通道」在隐私政策与 App 内可见，藏在图标里不合格。

> 🔴 **「退出账号」≠「注销账号」**：**退出** = 清本地凭证（本次做）；**注销** = **删服务端账号**（Apple 审核指南 5.1.1(v) 要求 App 内可发起删号）→ 需后端接口，见 §6.4。

### 6.5 ✅ 白哥定：**本次只做 UI 骨架**

> 「账号区块是否只做 UI」→ **是**（只做 UI）

**本次落地范围**（`profile_screen.dart` 内）：

| # | 内容 | 数据来源 |

| 5 | 🔔 **通知入口保留**（右上角） | ✅ 已有，见 §6.6 |

### 6.6 ✅ 白哥定：**通知入口保留**

> 「**右上角**的通知按钮保留，保留发给用户通知的接口」

**现状实测**：

|---|---|
| 端侧入口 | `profile_screen.dart:406` 在 `AppBar.actions` —— **`Badge` + `IconButton(Icons.notifications_outlined)`** |
| 端侧页面 | `pages/user/distribution/notification_panel.dart`（`/notifications` 路由） |

  label: '通知',

· label 11.5/w600 · count 10.5/`opacity .7` · 前景 `accent` · 凹陷态底 `sunken`。
✅ 原型已按此复刻（渲染级校验：`.chip` **82.7px** · 无溢出 · 无折行）。

> 🔴 **一处语义残留待清**：`notification_panel.dart` 放在 `pages/user/distribution/`（**分销**目录）下，
> 而分销已定「不做」。它**正在被现役引用**（`app.dart:22` + `profile_screen.dart:30`）→

## 七、🆕 顶部统计加「阅读篇数」（白哥 2026-09-29）

### 7.1 ✅ 原型已改（三列）

顶部统计卡从两列 → **三列**（连续天数 / 掌握词数 / **阅读篇数**），三个数字**都左对齐、各占 1/3**。

🔑 **为什么要改 `text-align:right`**：两列时「掌握词数」靠右对得很齐；三列后
每列仅 **70.3px**，若仍靠右，「阅读篇数」会紧贴边界 → 改为全部左对齐（实测渲染级校验通过）。

| 项 | 值（实测） |
|---|---|
| `.hero .stats` 内容宽 | 235px |
| 每列宽 | **70.3px**（`(235 − 12×2) / 3`） |
| 三列数字是否同行 | ✅（6 个 `.n` 的 `top` 全等） |

## 十、🔴 原型页的布局 Bug 与修法（白哥真机打开后发现）

**白哥反馈**：「预览页面就已经有很多错误了 —— 顶部统计卡的『掌握词数』已经在区域外了，底部的『退出账号』四个字是竖排」。

**均属实。** 我交付时 `check-prototype.js` **全绿**，但那是**源码级**校验 —— 它只看字符串，
看不见「语法完全正确的 CSS 造成的布局错」。三个 bug 的根因是**同一类**：

| # | 现象 | 根因（都是合法 CSS） | 实测证据 |
|---|---|---|---|
| ① | **掌握词数被挤出区域** | `.hero .row2` 里左侧 div **漏写 `flex:1`** → 按内容宽（圆点 220px）+ gap 26 = 246px，超过容器可用宽 → 右侧被挤出 | `.row2` **`scrollWidth 298 > clientWidth 235`，溢出 63px** |
| ② | **「退出账号」竖排** | `<span class="tx" style="flex:0">` —— `flex:0` = `flex:0 1 **0%**`（flex-basis 为 0）+ `.tx{min-width:0}` → **宽度坍缩** → 每字换行 | 该元素 **`w=0.0` h=80.0**（4 字 × 20px 逐字） |
| ③ | **「兴趣筛选」胶囊也竖排**（白哥未提，我自查发现） | 胶囊组写在 `.item .tx` **内部** → `.item .tx span{display:block}`（优先级 **0,2,1**）盖掉 `.pills{display:flex}`（**0,1,0**）→ 每个胶囊独占一行 | `.pills` 高 **138px**（5 个胶囊各一行） |

### 修法（都是「改结构/优先级」，不是加 hack）

| # | 修法 |
|---|---|
| ① | 新增 `.hero .stats{display:flex}` + `.stat{flex:1 1 0;min-width:0}`（**两个数字各占一半**）；圆点移出 ── 不再依赖某一列的宽度 |
| ② | 改用独立类 `.danger-tx`（**不再借 `.tx`** —— 它有 `flex:1`，本来就不适合装居中文本） |
| ③ | 把胶囊组**移出 `.tx`**，与 `.item` 平级（左缩进 `padding-left:45px` = item 15 + 图标 19 + 间距 11 对上） |

### 🔑 教训：源码级校验看不见布局错 → 补「渲染级校验」

我原以为「脚本全绿 + 我肉眼看过截图」就够了 —— **不够**。这次的三个 bug，脚本全绿、截图上我也没看出来
（手机框 `height:668px` + `overflow:hidden`，**超出部分被裁掉了，截图里根本看不到**）。

→ 已把方法固化成 skill `design-prototype-page` 的新工具 **`scripts/measure-render.html`**：
用 headless Chrome 量**真实几何**（`getBoundingClientRect` / `scrollWidth`），抓四类错：
① 横向溢出 ② 宽度坍缩（竖排）③ 样式作用域覆盖 ④ 并排元素不同行。

**双向受控实验**（用我**实际交付过的坏版本** `0194b75` 跑）：

|---|---|---|---|
| 坏版本 `0194b75` | 🔴 `.row2` **+63px** | 🔴 「退出账号」**w=0 h=80** | 🔴 不同行 |

另固化了三条判据：**「没检查」≠「通过」**（选择器 0 命中必须报 ⚠️）·

### 11.7 🔴 按钮改用粘土（白哥 2026-09-29：「续费」不符合设计语言）

**问题**：订阅卡的「续费」用的是 Material `FilledButton.tonal`。

**规格依据（不是我的偏好）** —— `design-system-spec` §6.1 组件清单：

> | 交互 | **粘土** | 卡片、**按钮**、标签、排序药丸、徽章、进度环 |

→ 所以按钮本来就该是粘土；`FilledButton` 是**没清掉的 Material 残留**。

**为什么不能只「换个皮」**：Material 那套与粘土**不同源** ——
它没有 `accentOut` 那层「染自身色相」的外阴影、没有内暗/内亮，
按下反馈也不同（水波纹 vs `scale(.97)` + `elasticOut` 回弹，§3.8）。
混在一堆粘土卡片里会读作「这不是这个体系里的东西」。

**产出**：🆕 `app/lib/widgets/clay_button.dart`

🔑 **关键实现点：必须用 `ClayState.selected`，不能用 `raised` + 显式 `fill: accent`。**
两者看起来等价，其实差在**外阴影的颜色**：

| 写法 | 填充 | 外阴影 | 结果 |
|---|---|---|---|
| `selected` | `accent` ✅ | `clay.accentOut` ✅ | 正确 |
| `raised` + `fill` | `accent` ✅ | `clay.out`（**中性灰**）❌ | 「格」档**冷灰阴影配暖朱砂 → 发脏**（§3.2 规则 1 / §3.3.1） |

→ `ClayPainter` 里 `isSelected` **同时**决定这两件事，绕过它就必然写错一件。
**这里借用的是它的「视觉定义」，与「选中/激活」的业务含义无关** —— 按钮是无状态的。

**尺寸**：不传 `borderRadius` 也不传 `scaleSize`，让 `Clay` 按**真实高度**自动选档
（§3.5「阴影参数必须随元素尺寸缩放」）。实测 `w=53 h=33` → **sm 档**。
⚠️ 硬写 `borderRadius` 会**跳过尺寸阶梯**，让「格」档拿不到它那个「不缩放」的例外（§3.5.1）。

**改动范围（2 处，不只白哥指的那 1 处）**：

| 处 | 原因 |
|---|---|
| `profile_screen.dart` 订阅卡「续费」 | 白哥指出的 |
| `order_history.dart` 订单行「支付」 | 🔑 **与订阅卡同屏**（订阅卡正下方就是订单历史）—— 只改一处会让一屏内出现**两种按钮体系**。判据：**补丁 ≠ 修法**，要问「这洞还有哪儿有」 |

已去掉。粘土需要 inset 表现体积（§3.5 硬规则：< 24px 就得去掉 inset），

#### 11.7.1 🔴 顺带在原型里查出 3 处「假粘土」（**与真机不一致**）

核对原型时发现 `.clay` / `.chip` / `.clay.flat` 的 `box-shadow` 写的是
`var(--clay-i1)` —— 而变量值 `-3px -3px 8px` **不含 `inset` 关键字** →
被浏览器解析成**外阴影** → 原型里的粘土卡片**根本没有内亮/内暗**，
是「扁平卡片 + 三个外阴影」。浅色档肉眼难辨，所以一直没被发现。

| 处 | 修法 |
|---|---|
| `.clay` / `.clay.flat` | 后两层加 `inset`（粘土三层 = 外阴影 + **内暗** + **内亮**） |
| `.chip` | 更严重：真实组件是 `ClayState.pressed`（`active` 默认 `false`，`header_chip.dart:141`）→ 应读作**凹陷**（两个 inset **方向互换** + **无外阴影**），而原型画的是外阴影 |

**验证我是用 computed style 做的**（`getComputedStyle().boxShadow`），不是肉眼看截图 ——
漏 `inset` 不报错、只静默退化，眼睛分不出来：

```
.claybtn : rgba(180,67,44,.4) 2px 3px 5px, -2px -2px 5px inset, 2px 2px 4px inset  ✅
.clay    : rgba(150,125,95,.24) 0 4px 5px, -3px -3px 8px inset, 3px 3px 7px inset  ✅
.chip    : 2px 2px 5px inset, -2px -2px 4px inset（无外阴影 = 凹陷）              ✅
```

同时按 §3.5 补了 **sm 档**变量（`--clay-o1-sm` / `--clay-i1-sm` / `--clay-radius-sm`），
并落实 §3.5.1 的例外：**「格」档 `--clay-radius-sm: 14px`（不缩放）** ——
因为它的基准 14px 已等于目标值，再乘 0.5 会得 7px，违反「圆角 ≥ 偏移 × 3」。

🔑 **一般化判据**：**「变量拼出来的值」不会报错，只会静默不生效。**
`box-shadow: var(--i1) var(--color)` 少了 `inset` 时，CSS 完全合法、无警告，
但视觉效果变了。**这类问题只能用 computed style 验证，不能靠读源码或看截图。**

## 十四、🔴「恢复购买」为什么不能省（白哥 2026-09-29 质疑后的查证）

> 白哥问：「**恢复购买 / 换设备后找回已购订阅 —— 这个不应该存在吧？
> 订阅状态跟着账号，还需要一个额外按钮吗？**」

### 14.1 结论：按钮**必须存在** —— 但白哥的质疑抓到了一个真问题

**白哥对的部分**：如果订阅真的「完全跟我们的账号走」，那**登录本身**就等于恢复，
按钮确实冗余 —— 这个推理是成立的。

**前提错的部分**：订阅的**源头不在我们的账号**，而在 **Apple ID**。是**两个**东西：

| | 归属 | 存放 |
|---|---|---|
| Apple 的订阅记录（权威源） | **Apple ID** | Apple 服务器（StoreKit `currentEntitlements`） |
| 我们记的副本 | **我们的 `user_id`** | `users.subscription_expires`（靠 Apple 收据校验后写入） |

→ 「恢复购买」解决的是「**Apple ID 有订阅，但我们这个 `user_id` 上没记录**」。
**若订阅真只跟我们的账号，它就不叫「恢复购买」，而叫「登录」了。**

### 14.2 🔴 三个真实场景 —— 我们的产品恰好**全部命中**

| # | 场景 | 为什么「登录」解决不了 |
|---|---|---|
| **1** | 🔴 **匿名订阅者换设备** | 我们的「匿名」其实是**设备级 trial 账号**（`username LIKE 'trial_%'`，`home_screen` 启动时自动建，见 `campaign_scheduler.rs:79`）。**换新设备 → 全新 `user_id`** → 后端订阅记录找不到。而用户**不知道账号密码**（是自动生成的）→ **唯一路径 = 恢复购买**（从 Apple ID 读，不依赖我们的账号） |
| **2** | 🔴 **产品原则本身** | 白哥定的「**除生词表上限外不验证登录态**」→ 用户可以**永远不登录**。一个从不登录的订阅者，换设备后靠什么找回？**没有账号可登** |
| **3** | **后端记录与 Apple 不一致** | 后端数据丢失 / 用户在我们这儿换了账号 → `AppStore.sync()` 能**强制从 Apple 重新拉取**，那是**唯一权威来源** |

🔑 **所以「恢复购买」恰恰是为「没有我们账号」的用户准备的。**
我们的产品允许匿名使用到底 → 它的必要性**比一般 App 更高**，不是更低。

### 14.2b 🔑 「登录」与「恢复购买」解决的是**两件不同的事**（这是白哥疑问的正面回答）

白哥的推理里隐含了一个假设：**「登录」能恢复订阅**。实际上两者分工明确、**互补不可替代**：

| 机制 | 恢复的是 | 数据源 |
|---|---|---|
| **登录** | **学习数据**（生词本 · 复习进度 · 收藏） | 端侧 `user.db` → 需同步到后端 |
| **恢复购买** | **订阅权益** | **Apple ID**（不经过我们的账号） |

→ 所以答案是：**不是「有了登录就不需要按钮」，而是「按钮管订阅、登录管学习数据」。**
两者覆盖的是**不同的丢失**。要「换设备后一切都在」，**两个都需要**。

### 14.3 Apple 的官方原文（**如实引用，含与第三方说法的差异**）

🔴 **重要**：多个第三方审核工具称「3.1.1 **explicitly requires**」，
但 Apple 官方原文的措辞是 **`you should`**，且句子主要讲「可恢复的内购项目」：

> **3.1.1 In-App Purchase**：
> "Any credits or in-game currencies purchased via in-app purchase may not expire, and
> **you should make sure you have a restore mechanism for any restorable in-app purchases.**"

⚠️ **诚实标注**：官方用的是 **`should`**（不是 `must`），且**未提及**「能否通过账号恢复」。
但两点值得注意：
- 多个独立来源（审核工具、上架服务）都把它当**常见自动拒审原因**对待
- 官方原文里**没有**「有账号就无需恢复机制」这类豁免

另有 **4.9 Apple Pay 定期付款**的披露要求（精神一致，虽不直接适用）：
续订期限 + 持续至取消 + 每期提供什么 + 实际收费 + **如何取消**。

### 14.4 我们自己的规格（早已写死）

| 出处 | 原文 |
|---|---|
| `implementation-plan-v2:1713` | 「**「恢复购买」入口**（Apple 硬性要求，**订阅页 +「我的」页两处**）」 |
| `ui-ux` §4.4.3 标题 | 「**「恢复购买」按钮（🔴 Apple 审核强制项，最容易漏）**」 |
| 同上 | 「**不能只在订阅页放**」—— 用户订阅后订阅页就不再进入，得从「我的」页也能恢复 |

### 14.5 ⚠️ 另需区分：**「管理订阅」≠「恢复购买」**（白哥可能混了这两件事）

| 功能 | 作用 | API |
|---|---|---|
| **管理订阅** | 取消 / 改套餐 | `manageSubscriptionsSheet`（跳到 Apple 的订阅管理页） |
| **恢复购买** | 把 Apple ID 的订阅拉回当前本机/本账号 | `AppStore.sync()` |

规格 §4.4.4：「**已订阅** → 「我的」页显示「订阅中 · 到期日 X 月 X 日」+ **「管理订阅」**」。
→ 完整形态应是**按状态切换**：未订阅 → 「恢复购买」；已订阅 → 「管理订阅」（可两者都在）。

### 14.6 🔴 顺带查出：**「换设备」场景的两条恢复路径，一条都没实现**

白哥的问题表面是「按钮要不要」，实际指向的是**「换设备后，用户会丢什么」**。查证：

| 丢的东西 | 恢复路径 | 现状 |
|---|---|---|
| **订阅权益** | 「恢复购买」（从 Apple ID 拉） | 🔴 **全库零实现**（§11.6.2 #5） |
| **学习数据**（生词本 / 复习进度 / 收藏） | **登录 + 同步** | 🔴 **同步机制完全未实现** |

**同步机制的实测状态**：
- 后端**无任何** `sync` / `push` / `pull` 接口（`grep` 0 命中）
- 端侧 `pending_push` 列**只有「读待同步项」的方法**（`bookmark_repository.dart:165` `pendingSync()`），
  **无任何消费者** —— 即「准备好要同步，但没人来取」
- 那是「**存量不清理 → 持续产生新依赖**」的反面：这里是**「预留了口子，但功能从未建」**

🔑 **所以「换设备」在本产品当前是「全丢」**：匿名账号是设备级的（14.2 场景 1），
学习数据和订阅都找不回 —— 且**两条路径都还没做**。

⚠️ **这不是「恢复购买」一处的待办，而是「账号 + 同步 + 恢复购买」一组能力**
→ 建议**一起规划**（它们共用「用户身份」这一个前提），而不是逐个补。

### 15.6 🔴 两处裁决：弹窗外壳用**平面**，输入框**按 spec 不按原型**

**① 外壳 = 平面（不是粘土）** —— 依据 spec §〇 规则 1「**有体积的只可能是可点的东西**」：
弹窗本身不可点 → 它是「浮起来的平面」（`card` 底 + 外阴影）。

里面**输入框是凹陷、按钮是粘土** —— 三类元素各就各位。

**② 输入框 = 凹陷** —— 原型 `.inp` 画的是**平面 + 细边框**：
```css
.inp{background:var(--card);border:1px solid var(--line);border-radius:12px}
```
而 spec **§3.6**（「凹陷（搜索框、**可输入字段**）」）与 §6.2 都把「可输入字段」列为凹陷类。
→ 按已定裁决顺序（**设计稿与 spec 冲突按 spec**）→ 实现走凹陷。

⚠️ 这是**原型与 spec 的第一处实质冲突**（此前几处都是「原型阙漏」，不是冲突）。
📌 **建议：原型 `.inp` 那两行应修正为凹陷** —— 否则下次照原型实现又会走偏。
