## 五、⚠️ 唯一的「加」：解锁记录表

**问题**：纯计算能得出「**当前**满足哪些成就」，但得不出：
① **解锁时间**（成就的意义之一）② **「新解锁」**（没有这个就**无法弹通知**）

**三个选项**：

| # | 做法 | 代价 |
|---|---|---|
| **①** ⭐ | **端侧加一张极小的表** `achievement_unlock(key TEXT PRIMARY KEY, unlocked_at TEXT NOT NULL)` | 需 `user.db` 版本 2→3 迁移（**已有 `onUpgrade` 框架**，加表是幂等脚本，风险低） |
| ② | **不加表**，纯计算 | 🔴 **无法展示解锁时间**、**无法弹通知**；且「成就」退化为「统计」，失去激励意义 |
| ③ | 存进 `app_config` 之类的键值 | 需要一张不存在的表 → 实为 ① 的变体 |

> 🔑 **这不是「猜需求」**（我们反对的「只删不加」针对的是**为未知需求建表**）：这里需求明确（要展示解锁时间 + 弹通知），且表极小（每行 ~40 字节，20 行 ≈ 1 KB）。
> ⚠️ 但**它确实需要走 `user.db` 迁移** → 见文件末的「升级注意」：加表走 `onUpgrade` 幂等重跑（安全），**不改已有表的列**。

### 8.2 三个口径决策（**与方案草稿的差异**，都在文件头写明了理由）

| # | 方案草稿 | **实施取值** | 理由 |
|---|---|---|---|
| ① | 准确率 `rating >= 3` | **`rating >= 2`** | SRS 惯例（Anki）= 「非 Again 占比」；「困难」也是成功回忆。按 `>=3` 会让「评困难」反而降准确率，**与直觉相反** |

| ③ | —（草稿未定「1 小时查词」口径） | **先按词去重再算窗口** | 语义是「1 小时内遇到多少个**不同**的词」（重复查同一个词不算） |

### 8.3 🔴 两个自己踩出来的坑（都记进了代码注释）

**① 「大括号计数找函数结尾」被命名参数 `{` 骗了**
`Future<void> _writeBackLookup(WidgetRef ref, { ... }) async {` ——
计数从签名开始 → **参数列表的 `{` 先被当成函数体** → helper 被插进签名中间 → 编译报「未定义」。
🔑 正确做法：**从 `) async {` 之后开始计数**（真正的函数体起点）。
> 这与项目已有判据「`) async {` 会跳过真函数体」是**同一族**，只是这次是**插代码**而非**切代码**。

**② 「先插入、再定位」→ 定位到自己**
第一次修错时，我**先插了 helper**，然后重新定位函数结尾 ——
而刚插入的 helper 里**也有 `) async {`** → 计数定位到 helper 自己 → **越修越坏**。
→ 最终**回滚该文件重做**（一次完成：先定位、后插入）。

> 而那正是**纯函数层验不到**、只能靠采集层真库验证的部分。

### 8.5 修复了两条**自己写的假绿断言**（看输出发现的）

## 九、🆕 口径补定：暂停的词算不算「已掌握」（2026-09-29 · 白哥定）

### 9.1 触发：白哥问「已掌握是怎么统计的」

查证链路（5 环 · 逐环读代码）后，查出**一个此前没记录、也没测试的口径不一致**：

| 统计项 | 判据 | 过滤「暂停」？ |
|---|---|---|
| 生词本词数 / 200 上限 | `user_word WHERE deleted = 0` | ✅ 过滤 |
| 复习页列表 / 「今天该看」 | `COALESCE(uw.deleted, 0) = 0` | ✅ 过滤 |
| **「已掌握」** | `card_review_state WHERE stability >= 21` | ❌ **不过滤** |

🔴 **问题不在「哪个对」**，而在于：这处差异当时只是**代码碰巧这么写的** ——
没记成决策、没断言锁住 → 后人看到「别处都过滤、唯独这里没有」，会当成遗漏顺手补上，
**静默改变**用户看到的数字（且不会报错）。

### 9.2 白哥定：**计入**（保持现状）

> 「**掌握是历史成就** —— 暂停（先不学了）≠ 忘记。」

同族先例：「连续学习天数」也不会因为今天没学就清零（它记的是**曾经达成**）。

⚠️ **已知且接受的后果**：暂停一个已掌握的词后，生词本 −1 而「已掌握」不变
→ 两个数字**可以对不上**（极端情况：「已掌握 50」而复习页只剩 5 个词可见）。

### 9.3 落实（三处文档 + 一条断言）

| 处 | 动作 |
|---|---|
| `achievement_rules.dart` | 🆕 `kMatureStabilityDays = 21`（**唯一出处**）· 文件头 ③ 修正不精确说法 · 🆕 文件头 ④ 写明本决策 |
| `achievement_service.dart` | SQL 改用常量插值 · 注释写明「**有意不 JOIN `user_word`**」 |
| `user_db_schema.sql` | `user_word.deleted` 注释区加「各统计对暂停的处理**不一致且有意**」对照表 |
| `verify_achievement_service.dart`【3】 | 🆕 两条断言 + **证伪实测**（注入 `AND deleted = 0` → 第 1 条**变红**） |

**为什么断言是必要的**：决策只写在注释里**挡不住**「顺手补过滤」——
断言能让它当场变红。这正是本项目反复用的手法（`verifiable-core-logic`）。

### 9.4 ⚠️ 顺带修正一处**不准确**的注释

原文写「21 天是 SRS 界通用门槛（**Anki 同口径**）」——**不准确**：

| | Anki 的 mature 判据 |
|---|---|
| 用的是 | **`interval >= 21` 天**（下次复习**间隔**） |
| 而我们的 | `stability >= 21`（**稳定度**） |
| 关系 | interval 由 stability **换算**、还受 desired retention 影响 → **相关但不等价** |

→ 已改为「**不声称与 Anki 等价**」。
🔑 判据：**注释里的「同源 / 等价 / 同一口径」声明，也属「可被证伪的事实」**，
含混的类比会把一个「我们自己选的数」包装成「行业标准」，从而**免于被质疑**。
