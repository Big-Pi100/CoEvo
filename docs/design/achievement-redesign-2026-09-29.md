## 一、🔴 规格已在，不要再发明

09-25 的 `ui-ux-refactor-assessment-2026-09-25.md` 已明确写定：

| 出处 | 原文 |

| §4.2 成就页 | 「**拆分**：连续天数 / 里程碑的逻辑并入「我的」页顶部成就区；**其余 plan / 概念卡成就删除**。原独立页面取消」 |

🔑 **所以「重新规划」的实质不是设计新体系，而是**：

把**挂在已退役功能上的部分**（plan / 概念卡 / 对话 / 多学科）**删掉**。

## 二、旧体系盘点：46 个成就 / 27 个指标，哪些还站得住

来源 `backend/achievements.toml`（**521 行 · 仍在仓库**，但引擎已退役 → **现无消费者**）。

### 2.1 按「挂载行为」分类

| 旧分类 | 成就数 | 挂的行为 | 现状 |
|---|---:|---|---|
| 🌱 启程 | 6 | 制卡 / 对话 / plan | 🔴 行为已退役（对话无入口 · plan 已清退 · **无「制卡」动作**） |
| 🔥 坚持 | 8 | 连续学习 / 时段 | ✅ **可复用**（streak 是核心） |
| 📚 博学 | 8 | 卡片数 / 复习数 | ⚠️ **半复用**：「卡片数」→ **生词数**／「复习数」✅ 直接用 |
| 🎯 精进 | 8 | 准确率 / FSRS 状态 | ✅ **可复用**（`card_review_state` 有 state/stability/difficulty） |
| 🗺️ 探索 | 7 | 领域 / 学科 / 语言 | 🔴 **全废** —— 产品只有**英语一个学科**，`domain` 是 K12 多学科遗留 |
| ⭐ 特殊 | 4 | 1h 建 20 卡 / 中断回归 / 单日 100 次 | ⚠️ 半复用（「建卡」→ **查词**） |
| 📣 推广 | 5 | 分享 / 推荐 | ✅ **可复用**（推荐/分享是**后端现役**功能，未退役） |

### 2.2 指标可用性（决定性的一步）

**端侧 5 张表**（`app/assets/sql/user_db_schema.sql` · 权威定义）：

| 表 | 一行 = | 关键列 |
|---|---|---|
| `card_review_state` | 一个词的 FSRS 状态 | `state`(0-3) · `stability` · `difficulty` · `reps` · `lapses` · `last_review_at` |
| `review_log` | 一次复习 | `rating`(1-4) · `reviewed_at` · **`utc_day`** |
| `user_word` | 一个生词 | `deleted`(软删) · `added_at` |
| `bookmark` | 一篇收藏 | `bookmarked_at` |
| `lookup_event` | 一次查词 | `word_id`(可空) · `spelling` · `looked_up_at` |

**27 个旧指标的可用性**：

| 指标 | 可算？ | 端侧数据源 |
|---|---|---|
| `streak_days` | ✅ | `review_log.utc_day` 去重后连续序列（**有现成列**） |
| `total_reviews` | ✅ | `review_log` 行数 |
| `reviews_today` | ✅ | `WHERE utc_day = today` |
| `recent_accuracy_20/50/100` | ✅ | `rating >= 3` 视为通过（**端侧只有 rating，无 `verification_result`**） |
| `mature_cards` | ✅ | `card_review_state.stability >= 21`（FSRS 惯例） |
| `learning_cards` | ✅ | `state = 1` |
| `night_sessions` / `early_sessions` | ✅ | `reviewed_at` 的小时分量 |
| `days_since_last_review` | ✅ | `MAX(reviewed_at)` |
| `hard_cards_count` | ⚠️ 改口径 | 无「创建卡片」→ 改用 `difficulty >= 8` |
| `perfect_session_10` | ⚠️ 改口径 | 无 session 概念 → 改「**单日 ≥N 次且全对**」 |
| `cards_in_1h` | ⚠️ 改口径 | 同上 → 改「**1 小时内查词 N 个**」（`lookup_event`） |
| `no_skip_streak` | 🔴 | 端侧**无「跳过」概念**（队列是到期制的）→ 删 |
| `conversations_completed` | 🔴 | 对话功能已退役 |
| `plans_completed` / `subjects_count` | 🔴 | K12 已整体清退 |
| `domains_covered` / `languages_count` | 🔴 | 产品只有英语 → 恒为 1，成就无意义 |
| `share_count` / `share_days` / `referral_count` | ✅ | **后端**（推荐/分享未退役）→ 需后端提供 |

**→ 27 个指标里：12 个可直接算 · 3 个改口径可用 · 4 个需后端 · 8 个随功能退役。**

**🆕 端侧独有、旧体系没有的指标**（新产品的真实行为）：
`lookup_count`（查词次数）· `unique_lookup_words`（查过多少不同词）· `total_words`（生词本词数）· `bookmark_count`（收藏数）

## 三、建议的成就清单（精简后 · 约 20 个）

**设计原则**：① 只挂**产品真实存在**的行为 ② 指标**端侧可算** ③ 每个分类**有明确终局目标**（不让用户永远看不到头）

| 分类 | Key | 名称 | 条件 | 端侧数据源 |
|---|---|---|---|---|
| **🔥 坚持** | `streak_3` | 起步 | 连续 3 天 | `review_log.utc_day` |
| | `streak_7` | 一周达人 | 连续 7 天 | 同上 |
| | `streak_30` | 月度学者 | 连续 30 天 | 同上 |
| | `streak_100` | 百日毅力 | 连续 100 天 | 同上 |
| **📖 阅读** | `first_lookup` | 第一次划词 | 查词 ≥ 1 | `lookup_event` |
| | `lookup_100` | 常读者 | 查词 ≥ 100 | 同上 |
| | `lookup_1000` | 博览 | 查词 ≥ 1000 | 同上 |
| | `lookup_20_in_1h` | 沉浸阅读 | 1 小时内查词 ≥ 20 | 同上（`looked_up_at`） |
| **📚 生词** | `words_10` | 开始积累 | 生词本 ≥ 10 | `user_word`(deleted=0) |
| | `words_50` | 小词库 | 生词本 ≥ 50 | 同上 |
| | `words_200` | 满额 | 生词本达上限 200 | 同上（**与免费额度同数，有产品含义**） |
| **🎯 复习** | `first_review` | 首测 | 复习 ≥ 1 | `review_log` |
| | `reviews_100` | 百炼 | 复习 ≥ 100 | 同上 |
| | `reviews_1000` | 千锤 | 复习 ≥ 1000 | 同上 |
| | `mature_50` | 掌握 50 词 | `stability ≥ 21` 的词 ≥ 50 | `card_review_state` |
| | `mature_200` | 掌握 200 词 | 同上 ≥ 200 | 同上 |
| | `accuracy_90` | 精准 | 最近 50 次 `rating≥3` 占比 ≥ 90% | `review_log` |
| **⭐ 特殊** | `night_owl` | 深夜灯 | 22:00–02:00 学习 5 次 | `review_log.reviewed_at` |
| | `early_bird` | 早起鸟 | 06:00–08:00 学习 5 次 | 同上 |
| | `comeback` | 归来 | 中断 ≥ 30 天后回归 | `review_log` |
| **📣 推广**（后端） | `first_share` / `referral_3` | 分享 / 推荐 3 人 | 后端 `referral_clicks` | **需后端接口** |

**删掉的（附理由）**：
- 探索类全 7 个 —— 只有英语一个学科
- 对话类 2 个（破冰/话痨）—— 对话无 UI 入口
- plan 类 2 个（完赛/首段）—— K12 已清退 + 「不做 plan」
- 数量过多的小档位（`cards_10/50/200/500/2000` 五档 → 压成生词 3 档）

## 四、放哪 & 长什么样

**按规格**（不再发明）：

```
「我的」页
├─ 【顶部成就区】              ← 新增
│   ├─ 连续天数  N 天           ← 大字
│   ├─ 掌握词数  M 词           ← 大字
│   ├─ [分享] 入口              ← 规格里明确要
│   └─ 成就徽章墙（可展开/进入二级）
├─ 账号信息（已有）
├─ 兴趣筛选（待做）
└─ 订阅状态 / 管理订阅 / 恢复购买（已有）
```

**两级展示**（沿用旧设计文档 §4.1 的「双层模型」，它本身是对的）：
- **图标层**（成就墙）：小图标 + 名称 + 分级色 → 放在成就区
- **特效卡层**（弹窗通知）：解锁瞬间弹出（缩放弹跳 + 粒子）→ **可复用旧 `achievement_overlay` 的设计**

## 五、⚠️ 唯一的「加」：解锁记录表

**问题**：纯计算能得出「**当前**满足哪些成就」，但得不出：
① **解锁时间**（成就的意义之一）② **「新解锁」**（没有这个就**无法弹通知**）

**三个选项**：

| # | 做法 | 代价 |
|---|---|---|
| **①** ⭐ | **端侧加一张极小的表** `achievement_unlock(key TEXT PRIMARY KEY, unlocked_at TEXT NOT NULL)` | 需 `user.db` 版本 2→3 迁移（**已有 `onUpgrade` 框架**，加表是幂等脚本，风险低） |
| ② | **不加表**，纯计算 | 🔴 **无法展示解锁时间**、**无法弹通知**；且「成就」退化为「统计」，失去激励意义 |
| ③ | 存进 `app_config` 之类的键值 | 需要一张不存在的表 → 实为 ① 的变体 |

> 🔑 **这不是「猜需求」**（我们反对的「只删不加」针对的是**为未知需求建表**）：这里需求明确（要展示解锁时间 + 弹通知），且表极小（每行 ~40 字节，20 行 ≈ 1 KB）。
> ⚠️ 但**它确实需要走 `user.db` 迁移** → 见文件末的「升级注意」：加表走 `onUpgrade` 幂等重跑（安全），**不改已有表的列**。
