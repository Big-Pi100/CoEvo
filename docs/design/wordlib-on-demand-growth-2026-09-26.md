# 词库策略转向：从「预先建满」到「按需生长」

> 2026-09-26 ｜ 触发：白哥「**词库不用了，就用 LLM 兜底就行了，划线查询没有的就调用 LLM 生成新的词卡，
> 新生成的词卡要走完整表结构并更新聚类，这样用不了多久词库就会很完善了，用户体验也不会差**」
> 状态：**技术可行性已验证**（34 项断言）｜**3 个架构取舍待白哥定**

## 一、结论先行：这不是新设计，是**回归 v1 原文**

v1 权威原文**早就写明了这个机制**，而且措辞几乎与白哥一致：

| v1 原文位置 | 内容 |
|---|---|
| 第 26 行（架构图） | 「预制卡片直接展示 ↓ 词库外生词 → **LLM 兜底制卡**」 |
| 第 40 行（决策表） | 「联网场景 = 登录/同步 + **词库外生词制卡** + 语音包下载」 |
| 第 74 行（云端服务） | 「**LLM 制卡服务 + 全局缓存**」 |
| 第 85 行（能力表） | 「查词（词库外）｜离线：**排队**｜在线：**✅ LLM 制卡**」 |
| 第 807 行（接口） | `POST /generate-card  # 词库外生词兜底` |
| 第 1083–1086 行（查词流程） | 未命中 → 查 `external_word_cache` → 再未命中 → **联网 LLM 制卡** → **写入缓存** |
| 第 1202 行（核心原则） | 「离线优先、**预制为主、联网兜底**、单端同步、卡片固化、语音异步」 |

**⚠️ 关键澄清：v1 说的是「预制为主、联网兜底」** —— 所以准确理解是：

> **不是「废弃词库」，而是「不再追求预先建满，剩下的按需生长」。**
> 已建的 **11,523 词仍然在用**（命中即走预制卡，零延迟零成本），
> 新词走 LLM 生成并**并入词库** —— 词库因此**越长越全**。

这与白哥说的「用不了多久词库就会很完善」完全一致，也是 v1 设计 `generated_card_cache.hit_count` 的用意 ——
**跨用户复用**：第一个用户查 `brainstorm` 等 3 秒，第二个用户查就是**瞬时**。

## 二、✅ 可行性已验证：增量聚类（34 项断言全过）

白哥的要求里最硬的一条是「**走完整表结构并更新聚类**」。
聚类是**全局的**（一个族的成员决定族），所以这是唯一真正的技术风险点 —— 已实测验证。

### 2.1 产物

| 文件 | 内容 |
|---|---|
| 🆕 `scripts/incremental_clustering.py` | 增量聚类引擎：`match_or_create_root` / `add_word` / `remove_word` / `refresh_clusters` |
| 🆕 `scripts/verify_incremental_clustering.py` | 验收脚本（**在真库副本上跑，源库指纹校验未被改动**） |

```bash
python3 scripts/verify_incremental_clustering.py
# → 通过 34 项，失败 0 项    ✅ 退出码 0
```

### 2.2 验证了什么（真数据）

| # | 断言 | 结果 |
|---|---|---|
| 1 | 新词（`interception`）加入**已有大族**（`cept` 族 22 词）→ 复用 `root_id`、size→23、**不新建页**、成员入页 | ✅ |
| 2 | 🔑 **门槛跨越**：新词加入 `size=2` 族 → size→3 → **自动新建聚合页**（成员 3 条） | ✅ |
| 3 | 幂等：重复刷新不重复建页 | ✅ |
| 4 | **同形异源不混**：`man`（Old English·人）与 `man`（Latin·停留）→ 两条独立 `word_root` | ✅ |
| 5 | 全新词根 → 新建 `word_root` + 新族 `size=1` + **不建页**（符合门槛） | ✅ |
| 6 | 🔑 **反向**：删词 → size 跌破门槛 → **自动删页** | ✅ |
| 7 | 全库不变量：达标族数 == 页数（**596 == 596**）· 无低于门槛的残留页 · 无 `member_count` 不一致 | ✅ |
| 8 | **源库 md5 未变**（`3d56f3ea…`）· 副本写入确实落盘（独立连接复查） | ✅ |

### 2.3 增量聚类与批量落库的一致性（必须锁住）

批量版（`load_llm_results.py`）是「先建完所有族，再统一建页」—— 门槛**天然**被处理。
增量版是逐词改的，所以跨越检测是**新增的关键逻辑**。两条路必须产出同一个库：

| 规则 | 出处 | 增量版如何对齐 |
|---|---|---|
| 词根按 **`(form, type, origin)` 三元组**匹配 | 实测 **116 个同形异源**词根 | `match_or_create_root()` 带 `origin`（`origin IS ?` 处理 NULL） |
| `cognate_group` 按 **`root_id`** 成组 | 修过 110 族被污染的 bug | `UNIQUE(root_id)`，`_sync_root_group()` 重算成员 |
| 聚合页门槛 **≥3** | v1 §8.5 | `PAGE_THRESHOLD` + `_sync_*_page()` 显式检测跨越 |
| 幻觉词素过滤 | 4 类规则 | `add_word()` 内同一套白名单 |
| 词缀匹配不到则新增（`needs_review=1`） | 白哥方案 | `match_or_create_affix()` 同策略 |

### 2.4 顺带发现的技术坑

**Python `sqlite3` 的 `close()` 不提交、而是回滚未提交事务** —— 首版验证脚本因此「全部断言通过但文件 md5 未变」。
→ 每个写操作后必须显式 `commit()`；**验证「写入是否真的落盘」要用独立连接 + 文件指纹**，不能只看同连接内的读回。

## 三、🔴 必须定的架构取舍：生成放在哪？（成本差 ≈ 用户数倍）

「更新聚类」这条要求**逻辑上指向服务端**：

> 若各端独立生成 → A 设备认为某族有 2 词、B 设备认为有 3 词
> → **同一张卡的聚合页内容不同** → 聚类失去意义

v1 的设计正是**服务端**（`LLM 制卡服务 + 全局缓存`）。

| | **路线 A：服务端生成 + 全局缓存**（v1 原设计） | **路线 B：端侧生成 + 本地缓存** |
|---|---|---|
| 聚类一致性 | ✅ 全局唯一 | 🔴 各设备不同 |
| 成本 | **每词只生成 1 次** | 🔴 **每设备生成 1 次**（同一词被 N 个用户查 → 付 N 次） |
| 首个用户延迟 | 3–5 秒 | 3–5 秒 |
| 后续用户 | ✅ **瞬时**（命中全局缓存） | 🟠 仅本机瞬时 |
| 离线 | 🟠 排队（v1 已设计） | ✅ 可离线生成* |
| 密钥 | ✅ 只在服务端 | 🔴 **App 内嵌开发者 key → 可被提取** |
| 服务端成本 | 需新表 + 接口 + LLM 接入 | 零 |

\* 端侧离线生成也要调云端 LLM，实际仍需联网。

**成本模型**（实测 ¥0.0058/词，来自全量 ¥69 ÷ 11,917）：

| 场景 | 路线 A | 路线 B |
|---|---|---|
| 1,000 用户 × 各查 100 个新词（**假设 80% 重复**） | 20,000 词 → **¥116** | 100,000 词 → **¥580** |
| 日活 1,000 / 日新增 300 词 | ≈ **¥1.7/天**（¥52/月） | 取决于用户数 |

**→ 成本上路线 A 明显优**（用户越多差距越大）。
**→ 且路线 B 有密钥安全问题**：App 内嵌 key 必然可被提取（服务端无此问题）。

**⚠️ 但路线 B 有一个致命吸引力**：不依赖服务端 — 而服务端目前**还没有 LLM 制卡接口**（`POST /generate-card` 不存在）。

### 我的建议：**A 为主 + 端侧缓存与排队**（即 v1 原设计）

新增基础设施仍在可控范围：
- 服务端：`generated_card_cache` 表 + `POST /generate-card` + 复用现有 `coevo_wordlib_contract`（**已验证可复用**）
- 端侧：`external_word_cache` / `external_word_audio`（v1 有 DDL）+ 排队
- 增量聚类引擎：**已就绪**（本报告 §二）

## 四、🔴 白哥方案里**缺失的三个环节**（必须补，否则有实害）

### 4.1 合规扫描 —— 最高优先级

预制库的卡是**经过核查**的（✅ **2026-09-26 已修正** `taiwan` / `tibet` 释义的**涉主权错误** —— 见 `plan-and-progress` §3.10）。
动态生成的卡**没有人工环节**，直接给用户看 → 风险**直接暴露**。

| 风险 | 说明 |
|---|---|
| 🔴 **涉主权** | LLM 生成 `taiwan`/`tibet` 等词的词源或释义时可能出错 |
| 🔴 **涉政/涉黄暴/涉歧视** | 生僻词可能触发不当内容 |
| 🟠 **幻觉词源** | 编造词源（契约 `confidence` 可部分反映） |

**现状**：生成侧只有**词法层**校验（幻觉词素白名单 `SUFFIX_WHITELIST_1` 等），
**没有涉主权/合规的自动扫描器** —— 之前每轮核查是**手动**加维度的。

**→ 必须为动态生成建自动扫描**（生成后、发布前），否则这条路会把风险带给用户。

### 4.2 `confidence` 门槛 —— 已有字段但未使用

契约自带 `confidence`（0.0–1.0）与 prompt 指示「never invent roots… lower confidence」。
**当前落库逻辑未读它**。动态生成时应用作闸门：
- `confidence ≥ 0.7` → 正常发布
- `0.4–0.7` → 发布但标记（UI 可提示"释义可能不精确"）
- `< 0.4` → 不发布，走 v1 的**降级卡片**（仅词形还原结果 + 发音，**不假装有释义**）

### 4.3 音频 —— 新词没有语音包

> 🔑 **本节建议方向正确**（端侧），但上一轮我在别处又建议「新词音频走服务端腾讯云」—— **自相矛盾**，
> 以端侧为准。详见 `tts-unified-client-side-2026-09-26.md`。
