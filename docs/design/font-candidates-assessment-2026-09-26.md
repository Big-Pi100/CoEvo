# 字体候选评估（2026-09-26）

- **触发**：白哥问「字体是否应该先从可获得的字体里出方案，然后我们再选一次？」
- **做法**：先实测「什么是可获得的」，再用**真实数据**筛选，最后出对照页供选择
- **交互对照**：`font-candidates-2026-09-26.html`（**用真实字体渲染真实词卡，离线可看**）
- **上游**：`design-system-spec-2026-09-25.md` §四（字体）/ §4.2 / §4.3

> 本文只做「可获得性 + 实测数据 + 选项」。**未改动任何 App 代码**，也未把字体接进 `pubspec.yaml`。

## 一、可获得性：原始阻塞**已解除**

spec §4.3 曾指出「Flutter 侧不能直接用 `@fontsource` 的现成文件，必须自建子集」，
但**没解决「完整 TTF 从哪来」** —— 而本轮实测发现网络受限明显。

| 渠道 | 实测 |
|---|---|
| `cdn.jsdelivr.net` | ✅ **200 —— 且能代理 GitHub 仓库** |
| `pub.dev` / `registry.npmjs.org` / `unpkg.com` / `gitee.com` | ✅ 200 |
| `raw.githubusercontent.com` | ⚠️ 301 重定向后**取不到** |
| `github.com` · `fonts.gstatic.com` · `fonts.googleapis.com` | 🔴 不通（`000`） |
| `registry.npmmirror.com` | 🔴 不通（`000`） |
| `mirrors.tuna.tsinghua.edu.cn` | 🔴 403 |

### 🔑 关键发现：jsdelivr 的 **GitHub 代理**是唯一通道

```
https://cdn.jsdelivr.net/gh/google/fonts@main/<path>
```

**实测拿到**：

| 字体 | 结果 |
|---|---|
| `Literata[opsz,wght].ttf` | ✅ 200 · **955,132 B** |
| `CharisSIL-Regular.ttf` | ✅ 200 · **752,900 B** |

→ **spec 原选的 Literata 与 Charis SIL 都能拿到**。**「Literata 缺失」的阻塞不是真的。**

> ⚠️ **不要**把这个通道换成 `fonts.googleapis.com` 或 `npmmirror` —— 实测都不通。

**已固化为可复现脚本**：`scripts/fetch_fonts.py`（含 sha256 校验，检出上游改版）。

## 二、真实 IPA 需求：**靠猜会少 5 个字符**

spec §4.3 说子集字符集 = 「ASCII 95 + 标点 8 + IPA 32 = **131 码位**」，
但**没说这 32 个是从哪来的**。本轮从**真实数据**提取：

```sql
-- IPA 存在 card.content 的 JSON `ipa` 字段（不是 word 表的列 —— word 表根本没有 pronunciation 列）
SELECT content FROM card   -- 11,523 张，全部有 ipa
```

**实测：非 ASCII 34 种**，其中**真·音标 30 种**：

| 字符 | 频次 | 字符 | 频次 | 字符 | 频次 |
|---|---:|---|---:|---|---:|
| `ˈ` | 9,399 | `ɒ` | 1,196 | `ɜ` | 515 |
| `ɪ` | 8,967 | `ʌ` | 1,014 | `θ` | 307 |
| `ə` | 7,904 | `ɡ` | 927 | `ð` | 101 |
| `ː` | 3,764 | `ɔ` | 879 | `̃` ⚠️ | 9 |
| `æ` | 1,676 | `ʒ` | 779 | `ɚ` | 8 |
| `ʊ` | 1,580 | `ɑ` | 652 | `ʁ` `ø` `̬` `̩` `ᵊ` `ɾ` `ɐ` `̯` `œ` | 1–6 |
| `ɛ` | 1,490 | `ŋ` | 573 | | |
| `ˌ` | 1,450 | | | | |

### 🔴 一个必须点出的差异：**4 个组合符号**

`̃`(U+0303) `̬`(U+032C) `̩`(U+0329) `̯`(U+032F) —— 它们是**附加到基础字母上的**
（`鼻化`、`清化`、`成音节` 等）。**缺失时变音符号会静默消失**，
比「回退到别的字体」更糟：**读者看不到任何异常，但音标是错的**。

→ 所以「IPA 覆盖」必须按**逐字符**判定，不能抽样、不能只看 `unicode-range`。

**已固化**：`data/reports/ipa_charset.json`（可被任何后续脚本复用）。

## 三、实测：候选字体 × 真实字符集

用 **133 码位**（ASCII 95 + 标点 8 + IPA 30）**逐字符**验证：

| 字体 | 码位覆盖 | 子集后（woff2） | 字重形态 | 授权 |
|---|---|---:|---|---|
| **Charis SIL** | ✅ **133/133** | 82.9 KB（**Reg+Bold+Italic**） | ✅ **静态** | SIL OFL 1.1 |
| **Andika** | ✅ 133/133 | 50.6 KB（Reg+Bold） | ✅ 静态 | SIL OFL 1.1 |
| **Gentium Book Plus** | ✅ 133/133 | 54.7 KB（Reg+Bold） | ✅ 静态 | SIL OFL 1.1 |
| **Noto Serif** | ✅ 133/133 | **34.6 KB**（Reg+Bold） | ⚠️ 仅可变 | SIL OFL 1.1 |
| 🔴 **Literata** | **115/133** | 47.0 KB（Reg+Bold） | ⚠️ 仅可变 | SIL OFL 1.1 |
| ⚠️ **Inter** | 130/133 | 50.7 KB（Reg+Bold） | ⚠️ 仅可变 | SIL OFL 1.1 |

**Literata 缺的 18 个码位**：`ɪ ː ʊ ɛ ʃ ɒ ʌ ɔ ʒ ɜ ɚ ʁ ̬ ̩ ᵊ ɾ ɐ ̯`
→ 与 spec §4.2 的实测（IPA Extensions 3/96）**方向一致**，本轮是**按真实用量**复核的更强版本。

> ⚠️ **全部落回 `ofl/` 目录 → 统一 SIL OFL 1.1**（可商用、可嵌入、可子集化、需保留版权声明）。
> 这与 spec 的授权要求一致，**无授权风险**。

## 四、🔑 spec 没考虑的一个选项

spec 的字体架构是**三层**：

| 层 | spec 选择 | 问题 |
|---|---|---|
| 英文阅读正文 | Literata | 🔴 **无 IPA** → 必须配 fallback |
| IPA 音标 | Charis SIL | — |
| 中文 UI | 阿里普惠体 | ✅ 已有（24.2 MB） |
| 界面/数字 | Inter | — |

**但实测显示**：Charis SIL / Andika / Gentium / Noto Serif **单字体就能同时满足「正文 + IPA」**
→ 🔑 **一个字体家族可以顶掉两个**（少一层 fallback 链、少一套资源）。

这不是「spec 错了」—— spec 的设计（正文体 + IPA 兜底）**技术上完全成立**，
只是**多了一个 spec 当时没看到的简化路径**。

## 四之二、🔴🔴 **spec 的字体选择没问题，但「用法」会制造一个新的不一致**

> **这是本轮最重要的发现。** 它让「原方案可行 → 不用改」这个结论需要**补一个条件**。

### 4.2.1 spec §4.2 的接入方式是「整段用一个字体栈」

```dart
TextStyle(fontFamily: 'Literata', fontFamilyFallback: ['CharisSIL'])
// 注释：「接入方式（不需要在业务代码里判断字符）」
```

**语义**：整张卡的文本先试 Literata，缺哪个字符就逐个回退到 Charis SIL。

**后果（实测）**：因为 Literata 缺 18 个 IPA 码位、而 Charis 又有，
→ **同一条音标里会一部分字来自 Literata、一部分来自 Charis SIL**。

| 情况 | 卡数 | 占比 |
|---|---:|---:|
| 🔴 **混排**（同一条音标内两种字体都用上） | **10,823** | **93.9%** |
| ✅ 纯 Literata | 695 | 6.0% |
| ✅ 整条回退 | 3 | 0.03% |

**样例**（`L` = Literata，`C` = Charis SIL）：

| 单词 | 音标 | 逐字符来源 |
|---|---|---|
| `absurd` | `/əbˈsɜːd/` | `L L L L **C C** L` ← `ɜː` 夹在中间 |
| `achieve` | `/əˈtʃiːv/` | `L L L **C** L **C** L` |
| `agent` | `/ˈeɪdʒənt/` | `L L **C** L **C** L L L` |
| `agree` | `/əˈɡriː/` | `L L L L L **C**` |

→ 同一条音标内，**笔画粗细 / x-height / 黑色浓度**会跳变。
**这正是白哥在音频那轮提出的同一个问题**（原话：「不统一更奇怪」）。

### 4.2.2 🔑 修法：**不换字体，只改「在哪一层指定字体」**

| | 做法 | 结果 |
|---|---|---|
| ④ spec 原法 | fallback 链加在**整张卡的文本样式**上 → 逐字符回退 | 🔴 93.9% 混排 |
| **⑤ 修正法** | 音标作为**独立元素**，直接指定 Charis SIL（不挂 fallback 链） | ✅ **整条一致** |

**可行性实测**（IPA 到底出现在哪些字段）：

| IPA 所在 | 卡数 | 性质 |
|---|---:|---|
| **`ipa` 字段** | **11,477** | ✅ **独立 UI 元素** → 可显式指定字体 |
| `etymology.text`（词源正文内嵌） | 227 | ⚠️ 正文内嵌，只能靠 fallback |
| `definition.en` / `context.text` | 4 / 1 | 同上 |

→ **改用法可把混排从 93.9% 降到 2.0%，且不需要换任何字体。**

**视觉证据**：`font-candidates-2026-09-26.html` 的「🔴 但 spec 的「用法」会制造一个新的不一致」一节
（同一字体组合、两种指定方式并排）。

### 4.2.3 这条发现改变了什么

| 原判断 | 修正后 |
|---|---|
| A 方案「可行」 | ✅ 仍成立 —— **字体选得对，实测都能拿到** |
| A 方案「不用改」 | 🔴 **需补一个条件**：**接入方式必须改成「音标元素显式指定」**，否则交付的是 93.9% 混排的音标 |
| 「换字体才能解决混排」 | ❌ 不对 —— **不换字体也能解决**（这是新信息） |

> 🔑 **通用教训**：**「字体覆盖够不够」与「渲染出不出得来」是两个问题。**
> 前者靠解 cmap 验字形，后者要算**逐字符的字体归属**。
> spec §4.2 只验了前者（发现 Literata 缺 IPA 并设计了 fallback），
> **没验后者** —— 于是「有兜底」被当成了「没问题」。

## 五、候选方案（请看对照页选）

> 📄 **`font-candidates-2026-09-26.html`** —— 用真实字体渲染真实词卡，**离线可看**，
> 含 IPA 全字符条 + 三档主题演示。**选字体必须看这一页，不能只看表格。**

| # | 方案 | 构成 | 体积 | 工程复杂度 | 气质 |
|---|---|---|---|---|---|
| **A** | **spec 原案** | Literata 正文 + Charis SIL 兜底 | ~130 KB（4 文件） | 🟠 中（**双字体 + fallback 链**） | 🟢 Literata 是**为屏幕长文阅读专门设计**的书体 |
| **B** | **Charis SIL 单一** | 一字体顶正文 + IPA | **82.9 KB**（Reg+Bold+Italic） | 🟢 **最低**（无 fallback、静态字重） | 🟢 语言学出版级书体（底座 Bitstream Charter），耐读 |
| **C** | **Noto Serif 单一** | 同上 | **34.6 KB**（最小） | 🟢 低（但仅可变 → 需构建期 instance） | 🟠 通用书体，个性弱 |
| **D** | **Gentium Book Plus 单一** | 同上 | 54.7 KB | 🟢 低（静态） | 🟠 偏「古籍 / 学术」 |
| **E** | **Andika 单一** | 同上 | 50.6 KB | 🟢 低（静态） | 🔵 **无衬线**，SIL 明确为**识字初学者**设计 |

### E 值得单独说一下（它有一个**产品层**的理由）

Andika 是 SIL 专为「**beginning readers and those learning to read**」设计的 ——
**字母形刻意做得不易混淆**（`b`/`d`、`p`/`q`、`I`/`l`）。

对**英语学习产品**而言这是**特征而非缺陷** —— 目标用户正是「正在学」的人。
但代价是：**它不是「阅读体」的气质**，长文（RSS 文章）连续阅读的舒适度不如衬线体。

→ 这是个**真实的产品取舍**，不是纯审美：**「帮助辨形」 vs 「长文舒适」**。

### 我的倾向（供参考，不是结论）

> ⚠️ 以下已按 §4.2 的发现修正 —— **A 方案现在只需要「改用法」，不需要「换字体」**。

- 若**优先阅读体验** → **A'（spec 原案 + 修正用法）**：字体仍用 Literata + Charis SIL，
  但音标元素**显式指定 Charis SIL**（不挂 fallback 链）→ 混排 93.9% → **2.0%**。
  ✅ **这是最接近「不改」的选项** —— 只改一行样式的挂载位置。
- 若**优先工程简洁**（一个 family、零 fallback）→ **B Charis SIL**（静态字重、IPA 原生）
- 若**优先最小体积** → **C Noto Serif**
- 若**愿意为「辨形辅助」牺牲阅读体感** → **E Andika**（需先想清楚长文阅读的代价）

**A' 与 B 的真实差别**：

| | A' | B |
|---|---|---|
| 字体家族数 | 2（Literata + Charis SIL） | **1** |
| 音标一致性 | ✅（2.0% 残留在词源正文里） | ✅ **0%** |
| 正文阅读体感 | ✅ Literata 专为屏幕长文设计 | 🟢 Charis SIL（语言学出版级，也耐读） |
| 资源/纪律成本 | 🟠 多一套字体 + 需遵守「音标元素单独指定」 | 🟢 无 |

→ 若你的答案是「**原方案可行就不改**」，那**A' 就是它** —— 字体一个不动，
只需在接入时把「音标用哪个字体」从**整段 fallback** 改成**元素级指定**。

⚠️ 我**不建议**「正文用 Andika + 长文用衬线」这种混搭 —— 那会把字体层级从 2 层变 3 层，
换来的是「同一 App 内两套英文阅读字体」，与 spec §2.2「品牌签名靠字体组合」相冲。

## 六、产物（本轮零 App 代码改动）

| 文件 | 作用 |
|---|---|
| 🆕 `scripts/fetch_fonts.py` | **取字体源**（jsdelivr→google/fonts，含 sha256 校验）—— 可复现的基础设施 |
| 🆕 `scripts/build_fonts.py` | **子集构建**（源 TTF → 133 码位子集，TTF/woff2） |
| 🆕 `scripts/build_font_compare.py` | **对照页生成器**（内联真实字体 + 真实词卡 + **机制对比**） |
| 🆕 `docs/design/font-candidates-2026-09-26.html` | **对照页**（选型主依据 · 含「混排 vs 一致」并排证据） |
| 🆕 `data/reports/ipa_charset.json` | 从真实数据提取的 IPA 字符集（入库） |
| ✏️ `.gitignore` | 新增 `/data/fonts-src/` + `/data/fonts-build/`（源与产物不入库） |
| 📁 `data/fonts-src/` · `data/fonts-build/` | 源文件与构建产物（均不入库） |

### 🔴 无论选哪个方案，接入时都必须遵守的一条

**音标用「元素级显式字体」，不要用「整段 fallback 链」**（见 §4.2.2）。

| 若选 | 这条怎么落地 |
|---|---|
| **A**（Literata + Charis SIL） | 正文/例句 → Literata；**音标元素 → 直接指定 Charis SIL** |
| **B/C/D/E**（单一字体） | 全站一个 family → 天然无此问题 |

### 一条工程约束

**`woff2` 给浏览器，`app/assets/fonts/` 用 `ttf`。**
Flutter 不支持 woff/woff2（只支持 ttf/otf/ttc）→ `build_fonts.py --ttf` 输出 TTF。
TTF 体积约 woff2 的 2 倍，但仍在 **< 70 KB/字重**（对比：现有阿里普惠体 24.2 MB）。
