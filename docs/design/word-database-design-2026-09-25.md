# 词表数据库：产品的地址

- 日期：2026-09-25
- 定位依据：白哥指出「**词形还原是词表数据库的关键，涉及到学习体验，词表数据库是最基础的**」

---

## 一、为什么「词形还原」不是功能，而是地基

### 1.1 我之前的定位错了

我把词形还原写成了「划词查词的前置依赖」和「生词数的前置依赖」—— 都是**功能视角**：先有功能，再看缺什么。

**你的视角是数据库视角**：词表数据库是产品的地址，先有它，功能才站得住。

这个差别不是措辞问题，它决定了**排期**：功能前置可以晚做（功能可以不上），地基必须早做（地基不牢，上面盖什么都是歪的）。

### 1.2 没有词形映射，词表数据库是「碎的」

这是核心论证。看两种情况的对比：

**❌ 没有词形映射**

```
用户划到 received
  → 查词表：没有 "received" 这个词条
  → 判为「词库外词」
  → 走 LLM 兜底制卡
  → 生成一张 "received" 的卡

结果：receive 和 received 成了两个独立词条
     用户的复习队列里两词各占一位
     掌握度分裂（receive 复习 5 次，received 复习 0 次）
     痕迹显示不一致（同一篇文章里 receive 已掌握、received 还陌生）
```

**✅ 有词形映射**

```
用户划到 received
  → 词形映射：received → receive
  → 命中词条 "receive"
  → 复用同一张卡、同一份 FSRS 状态

结果：一个词条 = 一个学习对象，数据永远统一
```

**一句话**：词形映射之于词表数据库，相当于**范式化之于关系数据库**。没有它，数据库在逻辑上是冗余且不一致的 —— 同一个词的不同形态会各自成为独立词条。

### 1.3 影响面（这就是「涉及到学习体验」的意思）

| 环节 | 没有词形映射的后果 |
|---|---|
| **划词查词** | 文章中约 **26%** 的词形无法命中词表（实测四篇真实文本），被误判为「词库外词」→ 触发不必要的 LLM 制卡 |
| **复习队列** | `run` / `running` / `ran` 各占一个复习位，用户复习三遍同一个词 |
| **掌握度统计** | 「已掌握 1,203 词」这个数字是虚的 —— 实际掌握的可能只有 900 个词，其余是重复形态 |
| **痕迹** | 同一篇文章里 `receive` 已掌握、`received` 还陌生 —— **视觉签名自相矛盾** |
| **语音包** | `word_id` 是音频命名基础。若每个形态各立一个 word_id，音频会重复（`run`/`runs`/`running` 三份） |
| **词族聚合** | 838 条屈折重复立卡的问题**无法解决** —— 因为无法识别哪些卡是同一个词 |

**注意最后两行**：词形映射不只服务「查词」，它是**词库自身清理的前提**。没有它，连「838 条重复卡」都无法系统性地识别和合并。

**结论**：词形映射是**词表数据库建设的第一步**，不是「划词功能的前置」。

## 三、词形映射：设计与实测结论

> 完整调研与实测见 `docs/design/cefrj-license-and-lemmatization-2026-09-25.md`

### 3.1 做法（已定稿）

**反向生成**：`词表词 → 展开全部变形 → 建反查表`

```
"receive" (词表词)
   ↓ 规则引擎生成变形
   "receives", "received", "receiving"
   ↓ 建反查
   receives → receive
   received → receive
   receiving → receive
```

**为什么不用通用 lemmatizer**：

> 我们不需要解决「任意词形 → 某个 lemma」（难题），
> 只需要解决「**文章词形 → 我们词表里的某个词**」（受限问题）。

正向（通用库）会猜出一个**可能不在词表里**的 lemma；反向生成只映射到词表内的词，**准确率 100%**。

### 3.2 实测数据

| 项 | 结果 |
|---|---|
| 映射表规模 | **34,724 条** |
| 四篇真实文本覆盖率 | 94.8% / 98.0% / **100%** / 97.6% → **平均 97.6%** |
| **变形还原的贡献** | **约 26%** 的词形命中靠它 |
| 运行时依赖 | **零**（一张 SQLite 表） |
| 残留未命中 | 仅三类：英式拼写（`kilometres`）、词表缺失（`percent`）、专有名词（`singapore`，本就不该查） |

### 3.3 表结构

```sql
-- 预制库 word.db（只读，随 App 更新）
CREATE TABLE word_form (
  form     TEXT PRIMARY KEY,    -- received / running / cities / built
  lemma    TEXT NOT NULL,       -- receive / run / city / build
  word_id  INTEGER NOT NULL     -- 指向 word 表
);
CREATE INDEX idx_form ON word_form (form);
```

**查询路径**（三层，按成本递增）：

```
1. 直接命中        received → 查 word 表 → 有卡即返回
2. 词形映射命中    received → word_form → receive → word 表
3. 未命中          → 词库外词流程（本地缓存 → LLM 兜底）
```

### 3.4 ⚠️ 一条需要明确的产品规则

**当一个词形本身也是词表词条时，用谁的语义？**

例：`building`
- 作为 `build` 的变形（建造 → 正在建造）
- 同时是独立词条（建筑物，名词）

**定稿规则：优先用独立词条的语义。**

理由：`building` 有自己的 IPA、释义、例句，是一张完整的卡。用户划到它，应该看到「建筑物」，而不是「build 的现在分词」。

实现上：反向生成时，**若生成的变形本身就在词表里，则不建立映射**（保留其独立语义）。这样 `build → building` 不会覆盖 `building` 自身的词条。

> 实测数据佐证：12,650 个单词型卡片中，有 **838 条是屈折形式与基础词重复立卡**（`running`/`run`）。这些词条**本身是合理存在的**（有自己的语义和用法），需要处理的是**数据一致性**（`building` 的 FSRS 状态和 `build` 的关系），不是简单合并。

## 四、依赖词表数据库的功能（全清单）

这解释了为什么它是「最基础」——几乎所有功能都要经过它：

| 功能 | 依赖什么 |
|---|---|
| **划词查词** | 词形映射（命中）+ 词条属性（内容）+ 索引查询（性能） |
| **痕迹** | 词条 ID（FSRS 状态挂在 word_id 上，形态必须归一到同一 ID） |
| **复习队列** | 同上 —— 否则同一词的不同形态各占一位 |
| **掌握度统计** | 同上 —— 否则数字虚高 |
| **语音包** | word_id（音频命名基础）+ 词形（含变形的发音） |
| **词族聚合** | 词形映射（识别哪些卡是同一个词） |
| **词库外词兜底** | 先查词形映射（可能已有 lemma）再决定是否调 LLM |
| **难度/等级** | 词条属性（CEFR 等级） |

**一张表支撑八个功能** —— 这就是地基的特征。

| 3 | 剔除专有名词 | ✅ **清单已出**：**797 条**（`pos` 含 proper **445** + 释义判定 **352**）；⚠️ 原记 501/196 不准确。另含 280 条**兼类词**须保留 |
| 4 | 处理 838 条屈折重复 | 用词形映射识别，建立主卡 + 词形条目的关系 |

| 6 | 补 897 条无中文 | 部分可正则修复、其余 LLM |
| 7 | ~~补 1,885 条空 CEFR 等级~~ **→ ❌ 撤销** | 🔴 **实测该口径是日语 1,787 + 俄语 98，英语 0 条空** → 无需补 |
| 8 | 补 303 条拼写变体映射 | 英美拼写（`aluminum/aluminium`）—— 词形映射表可覆盖 |
| 9 | 索引化查询 → 🔄 **建立端侧索引化查询能力** | ~~替代 `word_bank.rs` 的 O(N) 全表扫~~ —— ✅ **已更正**：`match_text()` 是**死代码**（0 调用），划词**不走后端** |

**第 1 项是基础** —— 它排第一，因为第 4 项（屈折重复）和第 8 项（拼写变体）都要靠它。

> **但第 1 项可以并行** —— 它不需要等词库清理完成，因为反向生成只需要词表词列表（已有）。

### 5.2 编译顺序上的一个提醒

词形映射表是**预制库产物**（`word.db`），不是运行时计算 —— 意味着：

```
词表数据库构建流水线（离线）
  词条清理 → 词形映射生成 → 发音资产生成 → 打包 word.db
                ↑
           这三步都在本地，零边际成本
```

## 六、已作废的设计（避免以后重复讨论）

### 6.1 「N 个生词」标识 —— ✅ 已废弃

白哥 2026-09-25 决定：**不要这个统计**。

作废的不只是界面上那个数字，还包括它背后的整套设计：

| 作废项 | 原设计 |
|---|---|
| 卡片上的「6 个生词」 | 信息流卡片标识 |
| 三档渐进口径 | 按 CEFR 算 → 按词表算 → 按掌握度算 |
| `cefr_band_counts` 字段 | `content_item` 上按等级分档计数 |
| `user_article_stats` 表 | 用户级生词数缓存 |
| `number_of_unknown_words` 接口 | 含四类排除规则（专名/数字/停用词/词库外） |

**为什么废弃是合理的**：这个数字和「痕迹」表达同一件事（难度与掌握度），**两个表达会互相抢角色**。去掉数字后，痕迹成为唯一表达 —— 一个概念一个表达。

**保留的部分**：词形还原的调研结论（§三）**全部有效** —— 因为它服务的不只是这个被废弃的功能，而是整个词表数据库。

### 6.2 仍然成立的相关结论

以下从「生词数」调研中得到、但与它无关的发现仍然有效：

| 发现 | 为什么仍然重要 |
|---|---|
| 🔄 **词表噪声构成已实测修正** | 可删 804 条 + 待确认 278 条；原「76 个污染短词」口径被推翻（判据误伤合法词） |
| **专有名词应从词表逻辑中排除** | 学习场景本就不该把 `Singapore` 当生词 |
| **`prebuilt_cards.difficulty` 全是 0.5** | 该字段不可用，任何假设它有效的设计都是错的 |
| **`cefr_j_flat.json` 丢了 851 个词的词性** | 任何用词性的逻辑都必须用 `cefr_j_all.json` |
| **CEFR-J 可免费商用** | 授权已核实，可直接用 |
