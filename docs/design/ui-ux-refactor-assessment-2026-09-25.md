### 1.1 问题

`dart:html` 和 `dart:js` 是 **Web 平台专用库，在 Android/iOS 原生目标上不存在**。当前 App 是作为 Flutter Web 构建的（部署在 `http://<OLD_VPS_IP>/app/`），所以能用；**切到原生 App Store 会直接编译失败**。

### 1.3 一个建议：Web 版不废弃，但用途改变

- Admin 后台（`admin_screen` 1,833 行 + `pages/admin/*`）**不用改造**，Web 上用得好好的 → 省掉大量工作

## 二、【体积】字体问题

### 2.1 现状

`app/assets/fonts/` 有 **9 个** 阿里巴巴普惠体权重，共 **61.1 MB**；pubspec 只声明了 3 个（`pubspec.yaml` 无 `assets:` 段，故其余不会被打包）：

| 文件 | 大小 | 权重 | 打包 |
|---|---:|---|---|
| `AlibabaPuHuiTi-3-55-Regular.ttf` | 8,332.8 KB | 400 | ✅ |
| `AlibabaPuHuiTi-3-65-Medium.ttf` | 8,231.8 KB | 500 | ✅ |
| `AlibabaPuHuiTi-3-85-Bold.ttf` | 8,175.1 KB | 700 | ✅ |
| **打包小计** | **~24.2 MB** | | |
| 其余 6 个权重（Thin/Light/SemiBold/ExtraBold/Heavy/Black） | **~37 MB** | | ❌ 仓库死重量 |

**问题 1：24 MB 字体，占初装体积 17%**

App 总体积约 405 MB（App 基础 65 + word.db 50 + 语音包 290）。但**语音包是异步下载的**，初装体积约 139 MB —— 24.2 MB 占 **17%**，对中文 UI 标签来说是过重投入。

**优化方向见 §8.4（已定稿）**：授权核实的结论是**子集化的收益不值得冒条款风险**，建议保留全量。

**顺带**：未声明的 6 个权重共 **37 MB** 是仓库死重量，可直接从 `app/assets/fonts/` 删除（不影响打包，只减仓库体积）。

**问题 2（更关键）：没有英文字体**

`pubspec.yaml` 只声明了 `AlibabaPuHuiTi` 一个 family。**阅读界面的英文正文会用这个中文字体渲染。**

中文字体的拉丁字形通常是「有就行」的补充设计，不是为长文阅读优化的。后果：
- 字距/字重/连字不理想
- 长时间阅读英文的疲劳度更高
- 与「阅读器」的产品定位不匹配

**已解决**（见 §八）：英文阅读正文用 **Literata**，IPA 音标用 **Charis SIL**。两字体子集化后合计仅 **235.6 KB**。

**阅读排版参数建议**：

| 项 | 建议值 | 说明 |
|---|---|---|
| 正文字号 | 17–19 px（可调 14–24） | 英文比中文需要更大字号 |
| 行高 | **1.6–1.8** | 现有 bodyLarge 是 1.5，对英文偏紧 |
| 行宽 | 35–45 字符（移动端约 4–5 词/行） | 超过 60 字符阅读疲劳 |
| 字距 | 0 | 英文无需额外字距（Duolingo 的 0.053em 是为其品牌字体调的） |
| 段落间距 | 0.8–1em | |
| 背景 | **米色/暖白**（如 `#FAF8F3`）优于纯白 | 降低眩光 |

**同时必须支持**：
- 🌙 **真正的深色模式**（不是简单反色）—— 阅读场景夜间高频使用
- 🔤 **字号调节**（用户可调，且持久化）
- 📏 三种主题：白 / 米黄 / 深色（阅读类 App 标配）

#### 4.4.2 🔴 自动续费披露（法定要求，订阅制新增）

**《网络交易监督管理办法》第 18 条 +《消保法实施条例》第 10 条**要求：接受服务前 + 续费前以**显著方式**提请注意（处罚上限 **30 万元**）。

| 项 | 说明 |
|---|---|
| **必须展示** | **订阅名称 · 时长（1 个月 / 1 年）· 价格 · 「到期自动续期，可随时在 Apple ID 设置中取消」** |
| **不得默认勾选** | 月付 / 年付**不预选**；订阅按钮由用户主动点击 |
| 隐私政策 + 使用条款链接 | Apple 审核必填（订阅类 App 强制） |
| 取消途径 | ✅ 由 Apple 提供（iOS 设置 → Apple ID → 订阅）—— 无需自建，但**必须在页面上说明路径** |

> **判例提示**（中国法院网 2026-03）：某视频公司虽发了续费提醒，但「路径不明确」→ 法院认定**「难谓显著」**并判赔。**「不是发了就行，要看得见、找得到、关得掉」。**

#### 4.4.3 「恢复购买」按钮（🔴 Apple 审核强制项，最容易漏）

**Apple 对含订阅 / IAP 的 App 有硬性要求：必须提供恢复购买功能。** 缺这个会被拒审。

| 项 | 说明 |
|---|---|
| 位置 | **订阅页** + **「我的」页**（两处都要，用户可能从任一入口找） |
| 场景 | 换机、重装、多设备 —— 用户已订阅但本地状态丢失 |
| 交互 | 点击 → 调 `restorePurchases()` → 成功则提示「已恢复」并解锁；无记录则提示「未找到订阅记录」 |

> ⚠️ **这条不要漏** —— 它是 Apple 审核订阅类 App 的常规检查项，且**不能只在订阅页放**（用户订阅后订阅页就不再进入，得从「我的」页也能恢复）。

#### 4.4.4 订阅状态与降级展示（🔴 订阅制新增）

| 场景 | 界面表现 |
|---|---|
| 未订阅 | 订阅页可进入；「我的」页显示「订阅完整版」入口；生词本达 200 时提示上限；朗读按钮点击时提示订阅 |
| 已订阅 | 隐藏订阅入口；「我的」页显示「订阅中 · 到期日 X 月 X 日」+ **「管理订阅」**（跳 Apple 订阅管理） |
| 🔴 **已过期且词数 > 200** | **全部词保留可读 / 可复习**；顶部提示「生词本已超出免费上限，续订后可继续添加」；**不锁词** |
| 🆕 **已过期：朗读** | **朗读按钮停用**（功能类，无资产）→ 点击提示「订阅后可听全文」 |
| 🆕 **已过期：已导入的电子书** | 🔴 **必须保留** —— 仍可阅读 / 查词 / 复习，**只是不能听**（用户的书是资产） |
| 订阅中 | loading 态 + 禁止重复点击 |
| 订阅失败 | 明确告知原因（网络 / 账户），提供重试 |
| 退款 / 家人共享 | 以 Apple 的收据校验结果为准，端侧不做本地判断 |

> 🔴 **降级策略是本轮新增的关键设计** —— 订阅到期**不没收用户资产**，否则必然引发差评 + 退款。详见 `subscription-model-assessment` §四。
>
> **三类对象的降级处理不同**（实现时别搞混）：
> - **生词本** = 用户资产 → 保留全部，**仅冻结新增**
> - **文章朗读** = 功能（无资产）→ **直接停用**
> - **已导入电子书** = 用户资产 → **保留**（可读/可查/可复习，仅不能听）

#### 4.4.5 一个产品层面的判断

**不做「限时优惠」倒计时。** 学习工具做成促销型产品会伤害信任 —— 用户会开始怀疑「我是不是被套路了」。
**可以用年付折扣引导年付**（年付对 churn 有利），但**不做倒计时、不做假促销**。

### 6.2 复习页：合并为单一列表（✅ 白哥的方案，已定稿）

**我之前的设计是「分段控件切换两个视图」，白哥的修正更简洁也更正确：**

> 「我认为生词本就是复习管理，其实复习页面只要一个就行了，卡片按 FSRS 管理状态和排序，同时支持搜索和按时序、字母排序，默认是 FSRS 排序，这样如何，就不要移入移出了」

**这个修正的价值不只是「少一个控件」——它让一个原本无解的问题直接消失了。**

#### 6.2.1 为什么它更高明

我之前的方案里有个死结：分段控件意味着「两个视图」，而两个视图之间需要「移入 / 移出」的动作，于是必然要回答「移出时 FSRS 状态怎么处理？」—— 我在上一版花了整整一节讨论这个话题。

**白哥的洞察点破了这个伪问题：生词本本来就是复习管理本身。**

- 一个词进入列表，不是「移入生词本」，而是**它被你查到了**
- 一个词离开视野，不是「移出生词本」，而是**它的 FSRS 状态变了**（已掌握 / 暂停）

**既然没有「移入移出」这个动作，「移入移出时 FSRS 怎么处理」就不需要回答。** 一切由 FSRS 状态驱动，页面只是状态的投影。

#### 6.2.2 定稿设计

```
复习 tab（单一列表，无分段控件）
 ┌──────────────────────────────────────────┐
 │  复习                      23 个今天该看  │  ← 标题右侧是「到期数」，不是筛选器
 ├──────────────────────────────────────────┤
 │  🔍 搜索单词或释义                        │  ← 搜索框（凹陷，可输入）
 ├──────────────────────────────────────────┤
 │  [记忆曲线]  [最近]  [A–Z]                │  ← 排序三选一，默认「记忆曲线」
 ├──────────────────────────────────────────┤
 │  今天该复习                               │  ← FSRS 排序下自动分组
 │   ┌────────────────────────────────────┐ │
 │   │ vertical      /ˈvɜːtɪkl/    ●●○   │ │
 │   │ 竖直的；垂直的              今天 · 3天前│ │
 │   └────────────────────────────────────┘ │
 │   ┌────────────────────────────────────┐ │
 │   │ instead       /ɪnˈsted/     ●○○   │ │
 │   │ 代替；反而                  今天 · 1天前│ │
 │   └────────────────────────────────────┘ │
 │  之后                                     │
 │   ┌────────────────────────────────────┐ │
 │   │ traditional   /trəˈdɪʃənl/  ●●●   │ │
 │   │ 传统的                      4天后 · 3次│ │
 │   └────────────────────────────────────┘ │
 └──────────────────────────────────────────┘
```

| 元素 | 设计 |
|---|---|
| **排序** | 三选一 —— **记忆曲线**（默认，按 FSRS 到期时间） / 最近（最近加入或复习） / A–Z |
| **搜索** | 单词或中文释义都能搜（`vertical` 和「竖直」都命中） |
| **分组** | **仅「记忆曲线」模式**下自动按到期时间分组（今天该复习 / 之后）—— 让任务量可感知 |
| **列表项** | 单词 + IPA + 中文释义 + **熟练度三点** + 下次到期时间 |
| **熟练度三点** | 直接映射 FSRS 三态，与阅读界面的**痕迹**共用同一套定义（一致的心智模型） |
| **进入复习** | 点任意词条 → 进入翻卡模式（翻卡 → 自评四档 → 自动下一张），做完回到列表 |

**为什么排序能覆盖「管理」需求**：三个排序对应三种真实意图 ——
- **记忆曲线** = 「今天该做什么」（任务视角，默认）
- **最近** = 「我刚查了什么」（回顾视角）
- **A–Z** = 「我记得有个 v 开头的词」（查找视角，配合搜索）

三者 + 搜索已经完整覆盖了旧方案里「筛选器 + 批量操作」想做的事，而**不需要任何一个额外的控件**。

#### 6.2.3 唯一的例外：不想学的词怎么办

白哥说「不要移入移出」是对的。但有一个真实需求仍然存在：**误查的词（人名、专有名词）或就是不想学的词**，需要有办法让它不再出现在今天的任务里。

**解法是把它变成 FSRS 状态，而不是一个「移出」动作**：

| 旧概念 | 新概念 |
|---|---|
| 移出生词本（删除） | **暂停复习**（FSRS 状态 = `suspended`） |
| 数据被删掉 | 数据保留，只是不参与调度，可恢复 |
| 在列表里消失 | 仍可通过搜索找到，标注「已暂停」 |

这样：
- **概念统一** —— 一切都由 FSRS 状态管理，没有例外路径
- **零数据丢失** —— 学习数据是积累性资产
- **可逆** —— 想学了随时恢复

> 实施细节：这是**第一阶段之后**的功能。第一版可以先不做暂停，只做列表 + 排序 + 搜索；等有真实用户反馈「有些词真的不想学」时再加。

### 6.3 字号 / 主题 / 发音设置 → 移到阅读界面内（已定）

你已同意。落地方式：

| 设置项 | 位置 |
|---|---|
| 正文字号 / 行高 | 阅读界面：**单击屏幕中央**唤出底部面板（Kindle 模式） |
| 阅读主题（白/米黄/深色） | 同一面板内切换，全局记忆 |

### 6.4 信息流结构 → **B：流 + 沉浸阅读**（已定）

```
信息流（首页）
  · 卡片：标题 + 来源（VOA / BBC LE）+ 难度标签 + 摘要 + 发布时间
  · 无限下滑，按兴趣权重排序
     ↓ 点击卡片
全屏阅读视图
  · 沉浸排版（Literata + 可调字号/主题）
  · 长按/拖选单词 → 查词浮层（不遮挡正文）
  · 顶部极简（返回 + 标题），下滑隐藏
  · 下滑到底 → 自动加载下一篇（保持连续感）
```

**为什么选 B（而不是流内直读）**：
1. **划词是核心交互** —— 全屏时文本位置固定，长按选词的命中率和精度都更高
2. **阅读专注度** —— 流里的卡片周围总有其他内容，容易分心
3. **长文友好** —— VOA/BBC 正文一般 300–500 词，全屏更合适

**保留连续感的设计**：阅读视图**下滑到底自动加载下一篇**，不需要退回列表再点 —— 这样既有沉浸专注，又保留了「一直刷下去」的流畅。

### 6.5 关于「数据导出」—— 说明与取消

```
打开 App
   ↓
信息流（首页）—— 卡片列表，可直接阅读
   ↓ 长按/拖选单词
查词浮层（底部抽屉式，不遮挡正文）
   ├ 词卡内容（IPA + 释义 + 例句 + 搭配）
   ├ 发音
   └ 加入生词本（默认静默）
   ↓ 关闭浮层，回到原处继续读
   ↓ 读完继续下滑下一篇（无限流）
```

**核心体验原则：查词零打断** —— 浮层不遮挡当前阅读位置，关闭后回到原处。

**阅读界面保持单纯**：不放进度条占位、不放「读完回顾」页、不放高亮开关。已查过的词可用极淡的背景标记（无需开关，作为默认行为）。

## 八、字体（定稿：Literata + Charis SIL + 阿里普惠体）

### 8.1 英文字体：**Literata**（已定）

`docs/design/font-comparison.html` 视觉对比后选定的。Literata 是 **Google Play Books 的官方阅读字体**，为长文阅读专门设计——与「阅读器」定位契合。

**体积实测**（完整链路：下载 → 静态实例化 → 子集化）：

| 项 | 体积 |
|---|---|
| 完整可变字体（含 opsz + wght 两轴，一个文件覆盖全部字重） | 932.7 KB |
| `@fontsource` Latin 子集（woff2，**Flutter 不支持此格式**） | 20.0 / 21.5 KB |
| **静态实例 w400**（fontTools instancer，wght=400 opsz=12） | 264.4 KB |
| **静态实例 w700** | 265.0 KB |
| **w400 子集化**（Latin + Latin-ext + 常用标点） | **63.0 KB** |
| **w700 子集化** | **63.6 KB** |

**可用字重**：300/400/500/600/700/800/900 + 全部斜体
**度量**：unitsPerEm 1000，xHeight 0.507em，capHeight 0.700em

> **推荐路径**：可变字体 → `instancer` 出静态实例 → 子集化。两个字重合计 **126.6 KB**，比直接打包可变字体（932.7 KB）省 **86%**。
>
> ⚠️ 注意 `@fontsource` 提供的是 woff2，**Flutter 只支持 TTF/OTF**，必须走 TTF 链路（google/fonts 仓库的可变 TTF 或子集化输出）。
>
> 授权：Literata 为 **SIL Open Font License 1.1**，明确允许修改、子集化、嵌入，零风险。

### 8.2 🔴 【重要发现】Literata 不能显示 IPA 音标

**实测方法**：下载 Literata 完整 TTF（非子集），用 fontTools 解析 cmap 表逐码位检查。

**结果**：Literata 的 IPA 覆盖只有 **3 / 96** 个 IPA Extensions 字符。

缺失的关键字符（含语料出现次数）：

| 字符 | 码位 | 语料出现次数 |
|---|---|---:|
| `ɪ` | U+026A | **9,892** |
| `ː` | U+02D0 | **4,340** |
| `ʊ` | U+028A | 1,811 |
| `ʃ` | U+0283 | 1,557 |
| `ɒ` | U+0252 | 1,277 |
| `ʌ` | U+028C | 1,113 |
| `ɔ` | U+0254 | 993 |
| `ʒ` | U+0292 | 850 |
| `ɜ` | U+025C | 561 |
| `ɛ` | U+025B | 1,768 |

**影响面**：**11,585 / 12,839 张卡片 = 90.2%** 的音标含 Literata 缺失的字符。
> ⚠️ **清洗前口径**（2026-09-25 已删除 876 条噪声，基数变为 11,917，**该比例需重算**）

**后果**：若只用 Literata，90% 的词卡音标会**回退到系统字体** → 字体混排、大小不一、视觉不专业。

> 注：`/rɪˈsiːv/`（receive）、`/ɪnˈkrɛdɪbl/`（incredible）、`/biː/`（be）这些最常见的音标全部受影响。
>
> 为什么之前看 unicode-range 觉得「覆盖」？因为 `latin-ext` 声明的区间是 `U+0100-02BA`，**表面上包含 IPA 区间**，但文件里实际只有 3 个 IPA 字形 —— unicode-range 是粗粒度声明，不代表字形存在。必须解析 cmap 才能确认。

### 8.3 解决方案：阅读字体 + 专用 IPA 字体（双字体）

这是专业词典 App 的标准做法（Cambridge / Oxford 都用独立音标字体）。

**候选 IPA 字体**（均已实测覆盖我们语料的全部 **32 个** IPA 字符）：

| 字体 | 体积 | 类型 | 特点 |
|---|---:|---|---|
| **Charis SIL** | 735 KB | 衬线 | **SIL 出品，语言学专业字体 —— 与 Literata 气质相配** ★ 推荐 |
| Gentium Book Plus | 800 KB | 衬线 | SIL 出品，学术出版常用 |
| **Andika** | 654 KB | 无衬线 | SIL 出品，**专为识字教学设计**（字形极清晰） |
| Noto Serif | — | 衬线 | Google，覆盖广 |
| Noto Sans | 2,001 KB | 无衬线 | Google，覆盖最广但体积大 |
| Inter | 856 KB | 无衬线 | 缺 3 个罕见组合符（语料仅 6 次，可忽略） |

**推荐：Charis SIL** —— 两个理由：
1. **同为衬线**，与 Literata 视觉协调（IPA 和正文混排时不会突兀）
2. **SIL International 出品**，专为语言学/音标工作设计，IPA 字形是它的核心能力而非附带

**✅ 已定稿：Charis SIL**（白哥 2026-09-25 确认）。

**体积实测**（IPA 字符集 + ASCII + 标点）：

| 文件 | 完整 | 子集化后 |
|---|---:|---:|
| `CharisSIL-Regular.ttf` | 735.3 KB | **54.4 KB** |
| `CharisSIL-Bold.ttf` | 721.2 KB | **54.6 KB** |

**英文双字体最终预算**：

| 用途 | 字体 | 文件 | 体积 |
|---|---|---|---:|
| 英文阅读正文 | **Literata** | 静态实例 400 + 700，子集化 | 126.6 KB |
| IPA 音标 | **Charis SIL** | 400 + 700，子集化 | 109.0 KB |
| **合计** | | | **235.6 KB** |

> 对比现状：中文阿普 3 权重 24.2 MB。**英文两字体合计仅 0.23 MB** —— 用 3.6‰ 的体积换来了合格的阅读排版。

**Flutter 接入方式**（字体回退链）：

```yaml
fonts:
  - family: Literata          # 阅读正文
    fonts:
      - asset: assets/fonts/Literata-400.ttf
        weight: 400
      - asset: assets/fonts/Literata-700.ttf
        weight: 700
  - family: CharisSIL         # IPA 音标
    fonts:
      - asset: assets/fonts/CharisSIL-400.ttf
        weight: 400
      - asset: assets/fonts/CharisSIL-700.ttf
        weight: 700
```

```dart
// 阅读正文：Literata 缺 IPA 字形时自动回退 Charis SIL
TextStyle(
  fontFamily: 'Literata',
  fontFamilyFallback: const ['CharisSIL'],
)
```

> **为什么用 `fontFamilyFallback` 而不是手动判断**：Flutter 在渲染每个字符时按字体链查找，IPA 字符 Literata 没有 → 自动落到 Charis SIL，拉丁字符仍用 Literata。无需在业务代码里做字符判断。
>
> 授权：Charis SIL 同为 **SIL Open Font License 1.1**，允许修改、子集化、嵌入。

**IPA 对比已加入视觉工具**：`docs/design/font-comparison.html` 「IPA 音标字体」区，12 个真实音标样本 × 6 款候选，含 Literata 反例作对照。

#### 8.3.1 ⚠️ 分发陷阱：@fontsource 的分包同样不含全套 IPA

做粘土规格页时发现的**第二个字体陷阱**，与 Literata 那个**根因不同，必须分清**：

| | Literata | Charis SIL |
|---|---|---|
| 完整字体 IPA 覆盖 | **3/96** ❌ | **32/32** ✅ |
| `@fontsource` 分包覆盖 | 0–3/96 | **22/32** ❌ |
| 根因 | **字体设计上就没有 IPA** | **分发方式问题 —— 子集切得太窄** |
| 解法 | 换字体 / `fontFamilyFallback` | **自建子集**（字体本身没问题） |

Charis SIL 缺的正是最关键的几个：

| 缺的字符 | 后果 |
|---|---|
| `ˈ` U+02C8 重音符 | **每个音标都有** —— `/ˈvɜːtɪkl/` |
| `ː` U+02D0 长音符 | 极常用 —— `/riːv/` |
| `θ` U+03B8 | `think` / `thought` 必备 |
| `ˌ` `ʰ` `ʳ` `ˑ` `͡` | 部分词条 |

**对实现的影响**：Flutter 侧**不能直接用 `@fontsource` 的现成文件**，必须自建子集。
字符集 = ASCII 可打印 95 + 常用标点 8 + IPA 28 = **131 个码位**，实测每款字体子集后仅 **18–38 KB**。

**对已交付文档的影响（已修复）**：6 个设计原型页的 IPA **之前全部在静默回退** ——
它们的字体来源都指向 `@fontsource` 分包，页面上看到的是「系统衬线字体 + Charis SIL」的混排，
而这正是那几个页面要判断的东西（尤其 `font-comparison.html` 的 IPA 对比区，结论完全无效）。

**已执行的修复**：
1. 生成 5 款本地子集（`docs/design/fonts/`，共 **148.9 KB**，全部实测 32/32 覆盖）
2. 6 个页面改用 `@font-face` 指向本地子集
3. `src` 列表加 CDN 兜底（jsDelivr 上的 google/fonts 完整 TTF）—— 防 `file://` 协议下的 CORS 限制

> **方法论**：`unicode-range` 是**粗粒度声明，不代表字形存在**。
> 选字体必须走完整链路 ——「下载字体文件 → 用 fontTools 解 `cmap` 表 → 用真实语料的字符集去比对」。
> 只看 CSS 声明、只看第三方文档、只看「有几个字符」的概括描述，都会误判。

> 阿里巴巴授权个人、企业等用户在遵守本声明相关条款的前提下，可以下载、安装和使用上述阿里巴巴字体，该授权是**免费的普通许可**，用户可基于合法目的用于**商业用途或非商业用途**。

**核实结论**：

| 事项 | 结论 | 依据 |
|---|---|---|
| **App 内嵌使用**（打包进 App bundle） | ✅ **明确允许** | 官方无「禁止嵌入」条款；授权范围含商业用途；多个第三方来源将「网站和移动应用界面」列为允许场景 |
| 网络流传的「禁止软件嵌入式」 | ❌ **与官方原文不符** | 该说法来自第三方经验整理（且自注「不代表法律建议」）。其原文限定词是「嵌入到硬件或软件中**作为系统字体**」—— 指 OS 级字体分发，非 App UI 字体 |
| **子集化（subset）** | ⚠️ **可能触及「拆分/转换」** | 第 1 条明列「转换」「拆分」。子集化字面落在该范围内 |
| 减字重（3 → 2 权重） | ✅ 允许 | 不涉及拆分字体文件，只是不打包某个文件 |

> **白哥的判断正确**：阿里普惠体确实可免费商用，App 内嵌没问题。需要补的只是「子集化」这一条——它不是商用授权问题，而是**对字体文件本身的处理限制**。

#### 8.4.2 子集化收益实测

用 fontTools 对 `AlibabaPuHuiTi-3-55-Regular.ttf`（8.1 MB / 29,197 码位）实测：

| 字符集 | 字符数 | 子集后体积 | 压缩率 |
|---|---:|---:|---:|
| UI 文案 + 标点（从 `app/lib` 提取的实际用字） | 998 | 0.21 MB | 2.6% |
| 项目实际字符集 + 一级字（UI 884 字 + 词卡数据 4,496 字） | 4,853 | 1.13 MB | 13.9% |
| GB2312 一级 3755 字 + UI | 3,874 | 0.88 MB | 10.8% |
| **GB2312 全部 6763 字 + UI** | 6,877 | **1.64 MB** | **20.1%** |

三权重推算（6763 字档）：**24.2 MB → 约 4.9 MB**，省 **19 MB**。

> 附：项目实际用到的去重汉字仅 **4,498 个**（UI 文案 884 + 词卡中文数据 4,496，有重叠）。
> 但**用户笔记是自由输入**，会用到任意汉字，所以不能只按 UI 文案子集化（0.21 MB 那档会导致用户笔记缺字形）。

#### 8.4.3 定稿建议：**不做子集化，保留全量 3 权重**

| 方案 | App 体积 | 授权 | 评价 |
|---|---:|---|---|
| **A · 保留全量 3 权重（推荐）** | **24.2 MB** | ✅ 明确允许 | 完整字体文件内嵌，不触碰任何禁止条款 |
| B · 减到 2 权重（Regular + Bold） | 16.2 MB | ✅ 允许 | Bold 用 `FontWeight` 无法真正模拟，中文加粗会偏软 |
| C · 改系统字体（苹方 / Noto Sans CJK） | **0 MB** | ✅ 零风险 | 省 24 MB；但 Android 各厂商字体不统一，品牌感下降 |
| D · 换 OFL 字体（思源黑体等）后子集化 | ~5 MB | ✅ 允许（OFL 明确许可修改与嵌入） | 兼顾体积与合规，但**要换字体**，品牌观感会变 |
| ~~E · 阿里普惠体子集化~~ | ~4.9 MB | ⚠️ 条款灰区 | **不建议** |

**推荐 A**，理由：

1. **收益不抵风险** —— 子集化省 19 MB，但要把它推到条款解释的灰区。对一份「免费给你用」的字体，没必要为 19 MB 冒这个不确定性
2. **绝对值不关键** —— 24.2 MB 占 App 总体积 405 MB 的 **5.9%**（占初装 139 MB 的 17%）。在有 290 MB 异步语音包的前提下，这不是决定性体积
3. **零工作量** —— 现状即目标状态，`pubspec.yaml` 不用改
4. **回头路一直在** —— 若上线后数据显示下载转化受体积影响，方案 C / D 随时可切换

**如果你倾向压体积**，我推荐走 **D（换 OFL 字体）** 而不是 E —— 思源黑体（Source Han Sans，Adobe/Google 出品）是 SIL OFL 1.1，**明确允许修改、子集化、嵌入**，可以合法压到 5 MB 以内。代价是字形观感与阿普不同，需要重新视觉确认。

## 九、视觉系统：主题 × 质感（2026-09-25）

> 完整探索见 `docs/design/_archive/visual-direction-exploration-2026-09-25.md`
> 主题系统原型：`docs/design/visual-theme-system-2026-09-25.html`
> 粘土质感原型：`docs/design/_archive/visual-clay-direction-2026-09-25.html`

白哥的判断：「我们的功能其实很简单，所以视觉上其实非常重要。」—— 这是对的。产品能力（RSS 内容流 / 划词查词 / FSRS 复习 / 离线语音）**没有任何一项是护城河**，差异化必须来自视觉与体验。

**视觉系统由两个独立维度组成**：

```
视觉系统 = 底色氛围（墨 / 格 / 夜）  ← 主题，用户可切换
         × 质感语言（平面 / 粘土）    ← 交互元素的手感
```

### 9.1 视觉签名：痕迹

产品独有的行为链是 `读文章 → 划线查词 → 进入生词本 → FSRS 复习 → 从陌生变成「我的」`。这条链可以在页面上留下**痕迹**，且痕迹随熟练度**淡去**。

> **学习的终点，是痕迹的消失。**

竞品都没有这套语言：微信读书/Kindle 有阅读没查词记忆；欧路/有道有查词没长文；多邻国/墨墨有记忆没阅读。**只有「长文阅读 + 查词记忆」同时存在时，痕迹才有意义** —— 而这是我们的产品形态本身。

**三态与 FSRS 映射**（阈值沿用「掌握词数」口径）：

| 态 | 条件 | 视觉强度 |
|---|---|---|
| 刚查过 | `reps = 0` | 最明显 |
| 复习中 | `reps 1–2` 或 stability 未达阈值 | 中等 |
| 已掌握 | `reps ≥ 3 且 lapses = 0` | 几乎不可见 |

**它同时是功能**（不只是装饰）：区分「我的词」/ 难度预判 / 进步可见 / 把「读」与「记」在视觉上连起来。

**风险与处理**：痕迹会干扰阅读。三条原则 —— ① 已掌握态**近乎不可见**；② 界面上**不放开关**（遵守「阅读界面保持单纯」）；③ 开关放**阅读设置面板内**，默认开启。

**~~同源的第二处表达：信息流卡片的「N 个生词」标识~~ —— ❌ 已废弃（2026-09-25）**

我原想用信息流卡片上的「6 个生词」作为痕迹的「理性版表达」。**白哥否掉了**，理由是：两者表达同一件事（难度与掌握度），**两个表达会互相抢角色**。

**去掉数字之后，痕迹成为唯一的进度表达** —— 一个概念一个表达。这反而更符合视觉签名。

> 顺带作废：`cefr_band_counts` / `user_article_stats` / `number_of_unknown_words` 三处设计。
> **但词形还原本身全部保留** —— 它服务的是整个词表数据库（8 个功能依赖它），不是这个被废弃的功能。详见 `docs/design/word-database-design-2026-09-25.md`。

### 9.1b 信息流卡片最终形态

**只有 4 个元素**：

```
┌────────────────────────────────────┐
│ SCIENCE · 4 MIN                🔖  │  ← 分类·时长 / 收藏（右侧，拇指可达）
│                                    │
│ A New Way to Grow Food in Cities   │  ← 标题
│                                    │
│ In the middle of Singapore, a tall │  ← 摘要（3 行截断）
│ glass building produces more than… │
└────────────────────────────────────┘
```

| 去掉 | 加上 |
|---|---|
| ❌ 「N 个生词」（与痕迹抢角色） | ✅ **收藏**（书签两态：凹陷空书签 / 实心强调色） |
| ❌ 「已读 / 未读」标签 | — |

**两个收藏入口**：信息流卡片右上角（扫的时候收藏）+ 阅读界面顶部栏（读的时候收藏）。
**收藏清单**：从信息流标题栏「收藏 N」进入，**复用同一套卡片组件**（无新界面），有空状态引导。

> 原型：`docs/design/visual-feed-bookmark-2026-09-25.html`

> ⚠️ **区分「进度记录」与「已读标签」**：去掉的是**界面显示**，不是**数据记录** —— `content_cache.progress` 必须保留，否则用户读到一半退出找不回位置。



### 9.2 三档主题（✅ 白哥修正：不是三选一，是主题族）

> 白哥：「这三种不能用风格管理来切换吗？我觉得三种风格应该都需要」

**这个修正是对的。** 墨 / 格 / 夜 对应的根本不是三种审美，而是**三种使用场景**：

| 主题 | 场景 |
|---|---|
| **墨**（暖纸） | 白天、长时间阅读 |
| **格**（纯白） | 需要通透感、清晰度 |
| **夜**（深墨） | 夜间、暗光环境 |

Kindle / Apple Books / 微信读书都提供多档阅读主题让用户自己选。**三档全做，用户自己选。**

**副作用（好的）**：**痕迹语法跟着主题走** —— 每档底色用最适合自己的语法：

| | 墨 | 格 | 夜 |
|---|---|---|---|
| **痕迹语法** | **底色浸染** | **下划线** | **光**（熟练度=亮度） |
| 痕迹参数 | alpha `.15 / .075 / .026` | `2.5px solid / 1.5px 42% / 1px dashed` | `#FFD9B8 / #DEDCD7 / #8E939F` |
| 为什么合适 | 暖底 + 淡朱砂，最接近真实纸张 | **纯白底上底色浸染几乎看不见**，线才是对的 | 深底上「加亮」比「加色」更自然 |
| 底色 | 暖白 `#FAF8F4` | 纯白 `#FFFFFF` | 深墨 `#14161C` |
| 强调色 | **`#B4432C`** | **`#B4432C`** ← 与墨共用 | **`#DB7E6B`** |
| 行高 | 1.82 | 1.74 | 1.84 |
| 圆角 | 26px | **14px**（原 8px 几何不成立，见 9.5.6） | 24px |
| 白天 / 夜间 | **最好** / 中 | 好 / 中 | 差 / **最好** |

**实现上仍是同一段代码，只是 token 不同** —— 这一点很重要，意味着三档主题的增量成本远低于「做三套设计」。切换还应带过渡动画（约 280ms）。

**原型**：`docs/design/visual-theme-system-2026-09-25.html`（顶部切换器，五屏 + 痕迹语法实时联动）

### 9.3 品牌身份靠什么（三档都能切之后的新问题）

主题可以切，但对外形象需要稳定锚点。**关键在于区分「随主题变」和「跨主题稳定」**：

| 随主题变（token 不同，代码相同） | 跨主题稳定（品牌身份在这里） |
|---|---|
| 底色 / 纸色 / 卡片色 | **字体组合** —— Literata + Charis SIL + Inter，永不变 |
| 文字三档（主 / 次 / 弱） | **粘土质感** —— 三种底色都成立，反而是最稳的签名 |
| **强调色**（朱砂 / 青绿 / 暖橙） | **「痕迹」这个概念** —— 「学过的词在变淡」这个行为不变 |
| **痕迹语法**（浸染 / 下划线 / 光） | **内容平面 / 交互粘土 / 输入凹陷** 的三分原则 |
| 粘土的三个阴影参数 | 信息架构、交互方式、文案语气 |
| 行高与圆角 | **品牌色** —— 图标 / 启动页 / 分享图用固定色 |

> **一个反直觉的结论：粘土在这里帮了大忙。** 三套底色配三套强调色，本来会让品牌形象散掉。但粘土是**跨底色的质感语言** —— 无论用户选哪个主题，界面的「手感」完全一致。所以品牌签名从「一种配色」变成了**「一种材质 + 一套字体 + 一个行为概念」**，这比单一配色更耐得住主题切换。

**品牌基准建议**：

| 项 | 建议 | 理由 |
|---|---|---|
| 品牌色 | **朱砂 `#B4432C`** | 是默认主题「墨」的强调色；**暖色在 App Store 缩略图尺寸下比冷色更醒目**；且朱砂在中文语境的「印记」联想与「痕迹」天然呼应 |
| 品牌触点 | 用**固定色**（图标 / 启动页 / 官网 / 分享图 / 商店截图） | 应用内用主题色 —— 两者可以不同（如 Slack 图标固定但可切明暗） |
| 默认主题 | **墨 + 跟随系统** | 白天暖纸、日落自动切深墨；用户不动设置也有合适体验 |

### 9.4 框架修正：质感与配色是两个维度

白哥提出「可能还要更特殊，例如粘土拟态（claymorphism）」——**这个提议引出了一个我之前框架里的错误**。

我原本把 A/B/C 并列成「三选一」。但粘土出现后我看清了：**粘土是一种质感语言（材质），不是配色语言。** 它可以叠加在任何底色上。

正确的框架是两层（互相独立，可自由组合）：

```
视觉系统 = 底色氛围（墨 / 格 / 夜）      ← 主题，用户可切换
         × 质感语言（平面 / 粘土）        ← 决定交互元素的手感
```


真正的选项是**组合**，不只是「选一个」。

### 9.5 粘土拟态（质感语言 · ✅ 已定稿）

> **完整规格见 `docs/design/design-system-spec-2026-09-25.md`**（三档主题的粘土 token / 尺寸阶梯 / 圆角规则 / 四态 / 动效 / Flutter 映射 / 验收清单）
> 组件实时渲染：`docs/design/visual-clay-spec-2026-09-25.html`（可切三主题、可逐层开关阴影）

**注意它在这里的位置**：粘土不是一个「和墨/格/夜并列的方向」，而是一种**质感语言** —— 它可以叠加在上述任一主题之上（见 9.4 的框架修正）。

#### 9.5.1 它为什么能用（关键区别）

粘土常被和 Neumorphism 混为一谈，但**Neumorphism 死掉的真正原因是必须与背景同色**，导致对比度天花板极低。粘土没有这个限制：

| | Neumorphism | Claymorphism |
|---|---|---|
| 阴影 | 2 个外阴影 | **2 个内阴影 + 1 个外阴影** |
| 填充色 | **必须等于背景色** | **任意色，与背景无关** |
| 视觉读法 | 从页面里挤出来 | 漂浮的充气物体 |
| 对比度上限 | 低（设计性缺陷） | **高（填充色自己控制）** |

#### 9.5.2 三重阴影公式（顺序不能改）

```css
box-shadow:
  7px 9px 18px      rgba(150,125,95,.26),      /* ① 外阴影 · 浮起 */
  inset -5px -5px 11px rgba(186,166,138,.55),  /* ② 内暗 · 体积 */
  inset 4px 4px 10px   rgba(255,255,255,1);    /* ③ 内亮 · 充气 */
```

三个决定成败的细节：
1. **外阴影要染成元素自身的色相** —— 用中性灰/黑会让粘土「发脏」
2. **两个 inset 必须反向**，且与全站光方向一致（统一左上光）
3. **内亮要比内暗更亮、更透明** —— 完全对称的一对会读成塑料而非粘土

圆角 ≈ 元素短边的 **1/4 到 1/3**；**小于 24px 高的元素应完全去掉 inset**（没空间表现高光）。

#### 9.5.3 采用规则：内容平面，交互有体积

**这是整个方案最重要的一条规则：**

| 类型 | 质感 | 例子 |
|---|---|---|
| **内容** | **平面** | 正文、释义、例句、标题、IPA |
| **交互** | **粘土** | 卡片、按钮、标签、排序药丸、徽章、进度环 |
| **输入** | **凹陷** | 搜索框、可输入的字段 |

好处有两个：
- **文字永远不动** —— 阅读体验不受影响（粘土在结构上不进入阅读界面）
- **可点击性变成直觉** —— 粘土感本身就在说「按我」，不需要边框或下划线去提示

> **阅读界面必须零粘土。** 沉浸感来自「什么都没有」，不是来自「很好看」。原型里有一屏专门标注了这一点。

#### 9.5.4 深色模式的取舍（如实说明）

这是 claymorphism 公认的弱点：

| | 浅色 | 深色 |
|---|---|---|
| 内高光 | `rgba(255,255,255,1)` | **必须压到 `0.05–0.07`** |
| 结果 | 膨胀感完整 | **体积感减弱约一半** |
| 原因 | 亮部高光是粘土的核心机制 | 白高光在深底上变成「发光」而非「膨胀」 |

**不是不能做，是做不到浅色那么好。** 若选 C 夜 + 粘土，需要接受这个降级。

#### 9.5.5 Flutter 实现：有一个原生缺口

**🔴 Flutter 的 `BoxShadow` 不支持 `inset`** —— 而粘土的核心恰恰是两个 inset 阴影。

实测现成方案：`flutter_inset_box_shadow` **最新版 2022-04 发布，已 4 年未更新**，且要求 `hide BoxDecoration, BoxShadow` 替换整个类型（侵入性高）。**不建议引入。**

**推荐自研，渐进式落地，零第三方依赖**：

| 步骤 | 做法 | 覆盖度 |
|---|---|---|
| **第一步** | 外阴影用原生 `BoxShadow`；内阴影用 `foregroundDecoration` + `LinearGradient` 模拟 | 约 80% 效果，零成本 |
| **第二步**（若视觉不够） | 写 `ClayDecoration` CustomPainter —— 按 Chromium 的做法「画一个被圆角矩形挖空的矩形再模糊」 | 100%，约 150–200 行 |

**动效是粘土感的一半**：按下时缩放 0.95 并用 `Curves.elasticOut` 回弹 —— Flutter 原生强项，几乎零成本。缺了动效，粘土只是个圆角卡片。

**额外工程量：约 1 周**（组件 + 设计 token + theme 扩展），放在 Step 2「设计系统」阶段，不影响 Phase 1 清障。

> **粘土与三档主题的关系**：粘土的三个参数（外阴影色 / 内暗 / 内亮）是**主题 token 的一部分** —— 每档主题给一组值。墨偏暖棕、格偏中性灰、夜用纯黑 + 6.2% 白高光。所以「粘土」这个决定与「三档主题」不冲突，反而是叠加关系。

#### 9.5.6 定稿时发现的两件事

**① 尺寸阶梯（最容易实现时漏掉的一环）**

26px 圆角 + 8px 阴影偏移放在 180px 卡片上成立，放在 26px 高的药丸上会糊成一团。**阴影参数必须随元素尺寸缩放**：

| 档 | 高度 | 外阴影 | 内暗 | 内亮 |
|---|---|---|---|---|
| sm | 24–40px | `2px 3px 5px` | `inset -2px -2px 5px` | `inset 2px 2px 4px` |
| md | 40–72px | `4px 5px 10px` | `inset -3px -3px 8px` | `inset 3px 3px 7px` |
| lg | 100px+ | `6px 8px 16px` | `inset -5px -5px 12px` | `inset 4px 4px 10px` |

硬规则：**高度 < 24px 的元素完全去掉 inset**（没空间表现高光）。

**② 「格」主题的圆角与粘土在几何上冲突**

「格」原设计的圆角是 **8px**（Swiss 网格、硬朗、工具感），但粘土的内阴影是 `inset -5px -5px 12px` —— 影响范围从边缘算起约 **17px**，远超 8px 圆角能承载的尺度。圆角不够时，内阴影会绕过圆角形成**「月牙状」伪影**，边缘看起来发脏。

**经验规则**：`圆角半径 ≥ inset 偏移 × 3`

| 圆角 R | 可用 inset 上限 | 粘土强度 |
|---:|---|---|
| 8px | 偏移 ≤2px、模糊 ≤6px | 弱（几乎平） |
| **14px** | **偏移 3px、模糊 8px** | **中（「格」采用）** |
| 24–26px | 偏移 5px、模糊 12px | 强（「墨」「夜」采用） |

**定稿：「格」圆角 8px → 14px，参数同时降到 md 档**。它仍是三档里最「精确」的那一个 —— 更小圆角、更紧阴影、独有的等宽音标字体。

#### 9.5.7 组合推荐

| 组合 | 协调度 | 说明 |
|---|---|---|
| **墨 + 粘土**（默认） | ⭐ 最协调 | 暖沙色系与粘土的柔和感同源，气质一致 |
| **格 + 粘土** | 张力最大 | Swiss 网格的硬朗 vs 粘土的柔软，相冲但有意思；代价是圆角要放大 |
| **夜 + 粘土** | 最独特，有代价 | 深色下粘土需降级（膨胀感减半） |

> 三档主题都会做、用户可切换（见 9.2）。这里的「组合」指默认主题 + 质感语言的气质搭配倾向。

### 9.6 主题的实现路径

现有架构（`providers/theme_provider.dart` + `theme/app_theme.dart` 的 4 套变体）需要重新组织：

```dart
// 现状：一维，且混了「风格」和「明暗」两个概念
enum AppThemeMode { system, light, dark, duolingo }

// 目标：把「底色氛围」独立成主题族
enum ReadingTheme { ink, grid, night }        // 三档底色
// 「跟随系统」不再是主题之一，而是一个开关：
//   浅色 → 用户选的浅色主题（ink 或 grid）
//   深色 → night

// 主题由一组 token 生成，而不是四个手写的 ThemeData
class CoEvoTokens {
  final Color read;         // 阅读区底色
  final Color accent;       // 主题强调色
  final TraceStyle trace;   // 痕迹语法（浸染 / 下划线 / 光）
  final ClaySpec clay;      // 粘土三参数
  final double readLineHeight;
}
ThemeData buildTheme(CoEvoTokens t) => ThemeData(...);

// 持久化：ReadingTheme + followSystem 两个字段就够
```

**额外工作量不大，但验证工作是真的**：三套主题意味着三倍的视觉验证（文字对比度、痕迹三态在不同字号下的可读性、粘土深度、IPA 音标显示、深色下长时间阅读舒适度）。**建议把「三主题验收」列为一个独立里程碑**，而不是散在各功能里做。

**建议顺带做**：跟随系统 + **日落自动切换** —— 阅读类 App 的常见特性，成本很低（`MediaQuery.platformBrightness` 已够用），体验提升明显。
