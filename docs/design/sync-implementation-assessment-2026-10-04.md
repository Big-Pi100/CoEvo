## 二、🔴 四处必须裁决的冲突 / 缺口

### 2.1 🔴🔴 最硬的一条：**隐私政策与同步直接冲突**

`docs/legal/privacy-policy.md` §二 2.1 标题是「**仅保存在你的设备上（我们无法访问）**」，正文写：

> 以下数据**只存在你手机里**，**不上传到我们的服务器**：
> | **生词本** · **复习记录** · **阅读进度** · **收藏** · 兴趣筛选偏好 · 外观设置 |
>
> 删除本应用即会一并删除上述数据。

**而「跨设备同步」恰恰要把前四项上传。** ⇒ 二者不可能同时为真。

| 选项 | 说明 |
|---|---|
| **A** ⭐ | **改隐私政策**：把「生词本/复习记录/阅读进度/收藏」从 2.1 移到新的「为提供跨设备同步而上传」小节，写明用途 / 保留期限 / 删除方式（注销时随账号删除 —— 后端注销已实现）|
| B | 只同步「非 §2.1 列举」的数据 | 🟠 但 §2.1 几乎列举了所有该同步的东西 ⇒ 同步会变得没有意义 |
| C | 不做同步 | 🔴 那订阅**没有可卖的东西**（见 §2.4）|

🔑 **这条不能绕过**：
· 不改政策就上线 ⇒ **虚假陈述**（政策说不传，实际传了）
· 改政策需**重新部署**法律页（脚本已幂等，`scripts/legal/publish_legal_pages.sh`）
· ✅ **好消息**：零真实用户 ⇒ **无「已同意旧政策」的迁移问题**
· ⚠️ 另外 §2.1 末句「删除本应用即会一并删除」在同步后**也不准确**（服务端还有一份）⇒ 一并改

### 2.2 🔴 L0「单端登录踢旧」 vs 订阅权益「跨设备同步」

| 层 | 说法 |
|---|---|
| **L0**（最高权威）§7.2 | 「**单端登录机制**：登录时**踢掉所有旧会话**」；旧设备 401 → 停止写入 |
| **L2**（FSRS 文档）§五 | 「v1 原本**单端登录，踢旧**，**后来改为多端登录**」 |
| **实测** | `user_session` 表**不存在**；`tokens` 表**本就多端** |

🔴 **产品级矛盾**：**单端登录下「跨设备同步」没有意义** —— 只能一台设备在线，同步给谁用？
⇒ **订阅权益「跨设备同步」在逻辑上要求多端登录。**

**我的建议：按「多端登录」**（即 L2 / 实测现状），理由：
① L2 明确记录了「后来改为多端」—— 说明 L0 那句**是更早的决策，之后被改过**，只是 L0 未回填
② 实测 `tokens` 表本就不支持「踢旧」（无 `is_active` / 无 device 维度）
③ 订阅权益依赖多端 ⇒ 若坚持单端，则该权益**必须换掉**
🔴 **但这是 L0 条款，必须白哥确认**（按分层规则，L0 优先，改动要请示）。

### 2.3 🟠 L0「服务器权威」的前提已消失

L0 §7.1 写「同步模型：**单写者 + 服务器权威**」（工作副本 ↔ 权威副本）。

**但那条的前提是「FSRS 在服务端算」** —— 那时服务器自然持有权威状态。
而 2026-09-26 白哥已批准 **FSRS 迁到端侧**，且明确「**后端 `fsrs5.rs` 删除**」（§六）。

⇒ 服务器**不再计算** FSRS ⇒ 「服务器权威」**无物可威**。
⇒ 已批准的 L2 结论「**重放即权威**」是 L0 那条**前提变化后的自然推论**，不是违背。

🔑 结论：**不需要「权威端」** —— 任何一端用 `replay()` 都能算出同一结果（纯函数）。

### 2.4 🟠 同步「什么」需要拍板（8 张表逐一）

见 §3。其中 3 张**建议不同步**，需白哥确认（不同步 ≠ 遗漏，是有理由的排除）。

## 三、同步范围：逐表策略（**本文的核心设计**）

端侧 `user.db` 共 8 张表 + `book.db` 1 张。逐一判定：

| 表 | 同步 | 机制 | 理由（为什么是这个机制） |
|---|---|---|---|
| **`review_log`** | ✅ **是（唯一真相源）** | 增量 push（`synced = 0`）；幂等键 `(word_id, reviewed_at, device_id)` | 复习是**事件**，状态是事件的函数 ⇒ 同步事件即可精确重建 |
| **`card_review_state`** | ✅ **派生，不直接同步** | 收到他人事件后 `merge()` 重放 → **覆盖写本地** | 它是 `review_log` 的**函数值**。直接同步它会在冲突时「丢一次复习」，而那次复习的记忆增益**永久消失**（§五 原话） |
| **`user_word`（生词本）** | ✅ 是 | **并集**（按 `word_id` 唯一） | 生词本语义是「我学过这个词」的**集合** ⇒ 并集天然正确、无需消解冲突 |
| **`bookmark`** | ✅ 是（**白哥定要做**）| 🔴 **改软删**后按 `deleted` 取较新（原为并集 + 硬删，见 §3.3）| 收藏是集合；但**硬删 ⇒ 并集会把删掉的带回来** ⇒ 必须先改软删 |
| **`article_read`** | ✅ 是 | 并集（PK = `article_id`，`read_at` **取较早**） | 语义是「首次读完的时刻」⇒ 取 `min` 与本地幂等写入（`INSERT OR IGNORE`）一致 |
| **`achievement_unlock`** | ⛔ **不直接同步** | **由重放后的状态重新计算** | 成就是**纯函数**（`achievement_rules.dart`）⇒ 同步状态后各端算出的解锁集合必然一致。**同步它反而是冗余 + 易分叉** |
| **`lookup_event`** | ⛔ **不同步** | — | ① 量最大（**每次划词一条**）② 它是**本地素材**，而 `user_word.source_sentence` 已固化「首次语境」（v1 §八 定的规则）③ 同步它的边际价值极低 |
| **`external_word_cache`** | ⛔ **不同步** | — | 它是**缓存**不是资产：词卡可按需向服务端再取（`/api/generate-card` + 服务端全局缓存）；且它存的是「**转换后的形状**」（与服务端不同，别混） |
| **`book_progress`**（`book.db`） | ✅ 是（**白哥定要做**）| 🔴 需先引入 **`content_hash` 指纹** + **待认领表**（见 §3.4）| 「跨设备续读」是刚需；但**书 id 是端侧 uuid** ⇒ 同一本书两端是两个 id ⇒ 必须先有**跨设备身份** |

> ⚠️ 正文（电子书**内容**）仍**不同步** —— MB 级，且用户在新设备需自己导入。
> 同步的只是**进度**（几十字节）。

### 3.1 🔴 一个必须显式处理的问题：**删除怎么同步**

上表多条写「并集」—— 并集**只增不减**。而这两种删除**必须**能同步，否则会出现「删了又回来」：

| 删除 | 现状机制 | 同步后果 |
|---|---|---|
| **生词本「暂停」** | `user_word.deleted = 1`（**软删**，非真删） | 🔑 **天然可同步** —— `deleted` 是个字段值，并集时**取较新者**即可（不需要「墓碑」机制）|
| **收藏取消** | `bookmark` 直接 **`DELETE`**（硬删） | 🔴 **并集会让它复活** —— 另一端的行还在 |

⇒ **收藏需要「墓碑」（tombstone）**，或者**改为软删**。
🔑 项目已有一条判据与此相关：「**取消收藏 = `DELETE`** —— 收藏是**可再生的用户意图**，与「生词本不能硬删」不同」。
⇒ 建议：**收藏一期不同步**（或同步但接受「取消可能被另一端带回」）。
⚠️ 这是**取舍**，要白哥定 —— 我倾向「**一期收藏也不同步**」，因为：
· 它的价值低于生词本/复习状态
· 引入墓碑机制会显著增加复杂度（且要处理墓碑过期清理）

### 3.1.1 🔴 `user_word` 的合并是**字段级**的，不是「整行取较新」

实测 `user_word` 的字段（`user_db_schema.sql:181-215`）：

```
word_id · spelling · source_article_id · source_sentence
added_at · updated_at · deleted · pending_push
```

⇒ **不同字段的正确口径不同**，用一个「整行新胜」会错：

| 字段 | 合并口径 | 为什么 |
|---|---|---|
| `deleted` | **取较新**（按 `updated_at`）| 它表达「用户最后一次的意愿」|
| `updated_at` | 取较新 | 判定依据本身 |
| `added_at` | **取较早** | 语义是「首次加入生词本的时刻」（与 `article_read` 同理）|
| `source_sentence` / `source_article_id` | 🔴 **取较早**（`added_at` 更小那端）| v1 §八 已定死：**例句取首次查词的语境**（`MIN(looked_up_at)`），**不用最新语境覆盖**（否则例句会跳动、干扰复习）|
| `spelling` | 任取（同一 `word_id` 拼写不变）| 词库 `word_id` 一旦分配永久不变 |

📌 **判据**：**「合并」不是一种规则，是一族规则** ——
逐字段问「这个字段表达的是**最新意愿**还是**首次事实**」。
🔑 这与项目已有的「**同一件事的口径只能一处权威**」同族：
把字段级口径写进**代码常量的注释 + 断言**，而不是散落在合并逻辑里。

### 3.2 🆕 白哥已定范围（2026-10-04 追加「4、5 要做」）

✅ review_log（事件）  →  card_review_state（重放派生）
✅ user_word（生词本，含 deleted 字段）
✅ article_read（阅读篇数，取较早时间）

白哥追加 4、5 ⇒ 范围扩大，**代价是引入两处新复杂度**（墓碑语义 + 书籍身份），
两处的设计见下。📌 这不是「增加工作量」的问题，而是**新增两个容易静默出错的地方**。

### 3.3 🔴 收藏同步：把「硬删」改成「软删」（白哥定「4 要做」）

#### 3.3.1 问题的根

`bookmark` 取消收藏 = **`DELETE` 真删行**（`bookmark_repository.dart:126` 明确「硬删」）。
而并集同步**只增不减** ⇒ **另一端会把删掉的收藏带回来**（用户看到「删了又回来」，且无从解释）。

#### 3.3.2 两个方案与取舍

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 墓碑表** | 新增 `bookmark_tombstone(content_id, deleted_at)`；取消时写墓碑 + 删主表 | 🔴 多一张表 + **墓碑何时能清**（要确定「所有端都收到」才敢清，实践中只能按天数保守清）|
| **B. 改软删** ⭐ | `bookmark` 加 `deleted` 字段；取消 = `deleted = 1` | 🟠 所有查收藏清单处要加 `WHERE deleted = 0`；库里有已删行（量小）|

**⭐ 建议 B（软删）**，三条理由：

1. **项目已有先例** —— `user_word` 就是软删（`deleted` 字段），**同一模式**，不引入新概念
2. 🔑 **它让问题消失而不是绕开** —— 按上一轮确立的判据：
   「先问『这个删除是**字段值**还是**真删行**』」⇒ 把它变成**字段值**，合并规则立刻变成
   「按 `deleted_at`/`bookmarked_at` **取较新**」，**不需要墓碑、不需要清理策略**
3. **规避一个静默故障** —— 墓碑「清早了」会让已删收藏复活，而且是**间歇性**的（难复现）

#### 3.3.3 需要一并改的（不做就是「语义残留」）

| # | 位置 | 改什么 |
|---|---|---|
| 1 | `bookmark_repository.dart:10` 的注释「**取消收藏 = `DELETE`** —— 收藏是**可再生的用户意图**」| 🔴 **必须改** —— 它现在是**错的**，后人照它做会把软删改回硬删 |
| 2 | 所有查收藏清单的 SQL | 加 `WHERE deleted = 0`（用 grep 找全，**别漏**） |
| 3 | 「重新收藏」的语义 | `deleted` 1→0 且**更新 `bookmarked_at`**（时间要刷新，否则排序错） |

📌 **判据**：**「删功能/改语义要清残留」** —— 软删上线后，注释里还写「硬删」= 埋一颗雷。

#### 3.3.4 ⚠️ 一个必须注意的边界

软删后 `bookmark` 的 **PK 仍是 `content_id`** ⇒ 一行一篇，不会重复。
但**「已删行」会永久留在本地**（除非做清理）。
⇒ 一期**不做清理**（量极小：一篇文章一行，几十字节），但**在注释里写明这是有意的**。

### 3.4 🔴 电子书进度同步：先解决「同一本书在两台设备上是两本书」（白哥定「5 要做」）

#### 3.4.1 问题的根

`book_progress.book_id` 是**端侧生成的 uuid**（`book_db_schema.sql`）。
⇒ 同一本《Pride and Prejudice》在两台设备上导入 ⇒ **两个不同 uuid** ⇒ **进度对不上**。

#### 3.4.2 方案：**内容指纹**（文件字节的 sha256）

| 项 | 设计 |
|---|---|
| 指纹 | `sha256(原始文件字节)`（导入时算一次，写入 `book` 新列 `content_hash`）|
| 性能 | 50 MB 约 100–200 ms —— ⚠️ 必须在 **Isolate 里算**（导入本来就在 Isolate）|
| 索引 | `CREATE INDEX idx_book_hash ON book(content_hash)` |

**⚠️ 这个指纹的边界（必须如实说明，别假装更强）**：

| 情形 | 指纹 | 结果 |
|---|---|---|
| 同一文件拷到两台设备 | **相同** | ✅ 进度共享 |
| 同一个公版书，从**不同来源**下载（Gutenberg vs 其他地方）| 🔴 **不同**（含元数据/排版差异）| ❌ 进度**不共享** |

🔑 **这是刻意的选择**：不同来源的同一本书，**章节划分可能完全不同** ⇒
把它们当成同一本、把进度「共享」过去，会**把用户带到错误的位置** ——
**比不同步更糟**。⇒ 我们**不假装**它们是同一本。

📌 若将来要跨来源识别，需要「书名+作者+章节数」等**弱指纹**，但那会引入**错配风险**，
必须配套「用户确认」交互 ⇒ **一期不做**。

#### 3.4.3 🔴 一个必须解决的连带问题：**本地还没有这本书时，进度挂在哪**

`book_progress` 有 **FK → `book(id)` + `ON DELETE CASCADE`**。
若同步来一个远端 `book_id`，而本地**没导入这本书** ⇒ **FK 失败**（插不进去）。

⇒ 需要一张**「待认领」表**：

```sql
-- 来自其他设备的进度（此时本地可能还没这本书）
CREATE TABLE IF NOT EXISTS book_progress_pending (
  content_hash TEXT PRIMARY KEY,     -- 按指纹存，而不是 book_id
  chapter_idx  INTEGER NOT NULL,
  scroll_ratio REAL    NOT NULL,
  updated_at   TEXT    NOT NULL
);
```

**认领流程**：

```
① 同步拉取 → 写进 book_progress_pending（不需要本地有书）
② 用户在新设备导入同一本书 → 算出 content_hash → 命中 pending
   ⇒ 写入 book_progress（此时 FK 满足）→ 删掉 pending 行
③ 本地读书 → 更新 book_progress + 一并更新 pending（便于上传）
```

🔑 **为什么不做「远端进度直接丢弃」**（更简单的方案）：
用户流程是「新设备 → **导入书** → 打开」⇒ 若同步早于导入，进度就**永久丢了**。
⇒ 待认领表是**让这个功能真正有用**的必要条件，不是过度设计。

#### 3.4.4 合并口径

| 字段 | 口径 |
|---|---|
| `chapter_idx` / `scroll_ratio` | **取 `updated_at` 较新者**（进度是「我读到哪」的**最新意愿**）|
| `updated_at` | 取较新 |

⚠️ 多设备**同时**读同一本 ⇒ 取较新会丢另一端进度。
⇒ 这是**可接受的**（进度是单点状态，不是资产），但**要写明**，别让后人以为是 bug。

---

### 3.5 ⚠️ 范围扩大后的重新评估

白哥追加 4、5 后，**同步面从 3 项变成 5 项**，新增两处「容易静默出错」的地方：

| 新增项 | 新增的风险点 |
|---|---|
| `bookmark` | 遗漏某处 `WHERE deleted = 0` ⇒ 界面显示已删收藏（**静默**，不报错）|
| `book_progress` | FK 失败处理不当 ⇒ 进度丢失（**静默**）；指纹算错 ⇒ **把用户带到错误章节**（比丢失更糟）|

📌 ⇒ 这两项**必须有断言**（不只是「接口能通」）：
· 「取消收藏后，清单里不再出现」（**行为断言**，不是源码断言）
· 「按指纹能找回到正确的书」（含**碰撞/不匹配的负例**）

## 四、协议设计（形状，不含实现）

### 4.1 两个接口

```
POST /api/sync/push     # 上传本地未同步的变更
GET  /api/sync/pull     # 拉取服务端的变更
```

⚠️ **与 L0 §7.4 的差异**：L0 写的是 `/sync/pull`（**无 `/api` 前缀**），
而当前后端**全部**路由都在 `/api/*`（实测）。⇒ 按现状加 `/api` 前缀（L0 那节是示意）。
📌 判据：**「同一件事的口径只能一处权威」** —— 路径风格以现有代码为准。

### 4.2 `push` 形状（示意）

```jsonc
POST /api/sync/push
{
  "device_id": "dev_ab12...",
  "review_events": [
    { "word_id": "w00123", "rating": 3, "reviewed_at": "2026-10-04T12:00:00Z" }
  ],
  "user_words": [
    { "word_id": "w00123", "spelling": "receive",
      "created_at": "2026-10-01T...", "deleted": 0 }
  ],
  "article_reads": [ { "article_id": 42, "read_at": "2026-10-02T..." } ]
}
```

**幂等要求**（设计已定）：服务端写入必须 `INSERT OR IGNORE` 级幂等 ——
`review_log` 的 `UNIQUE (word_id, reviewed_at, device_id)` 正是为此。
⇒ **同一批 push 重放两次，结果必须一致**（§七 单测清单第 8 条已列为要求）。

### 4.3 `pull` 形状（示意）

```jsonc
GET /api/sync/pull?since=2026-10-01T00:00:00Z&device_id=dev_ab12...
{
  "review_events": [ ... ],   // 排除自己 device_id 的（已在本地）
  "user_words": [ ... ],
  "article_reads": [ ... ],
  "server_time": "2026-10-04T12:34:56Z"
}
```

### 4.4 端侧收到 pull 后做什么

```
① review_events  →  fsrsService.merge(local, remote)  →  写回 card_review_state
② user_words     →  并集（按 word_id；deleted 取较新者）
③ article_reads  →  并集（read_at 取较早）
④ 成就           →  不接收，改为**重算**（见 §3）
```

### 4.5 同步时机（沿用 L0 §7.3，按现状微调）

| 时机 | 动作 | 备注 |
|---|---|---|
| 登录成功 | `pull` 一次 | L0 原话 |
| 复习完成 | 本地写 + 标 `synced = 0` | 已有 |
| **批量 push** | 延迟合并推送（如退出复习页 / 启动时 / 每 N 分钟） | ⚠️ **不要每次复习都发请求** |
| 退出登录 | **先 flush 再 logout** | L0 原话（否则丢最后一批） |
| 订阅状态 | **push/pull 需登录 + 有效订阅？** | 🟠 **待定** —— 见 §6 |

### 5.1 🔴 阶段 0 是本方案最容易踩坑的一步（**必须专门做**）

§3.3 与 §3.4 都要求**给已存在的表加列**，而两套端侧库的既有迁移策略**都覆盖不了加列**：

| 库 | 现有迁移策略 | 对「加列」是否有效 |
|---|---|---|
| `user.db` | `onUpgrade` = **重跑全量幂等 schema** | 🔴 **无效** —— `CREATE TABLE IF NOT EXISTS` 对**已存在的表是空操作**，加不了列 |
| `book.db` | 同上 | 🟠 `book.db` 尚未上线（真机上不存在）⇒ `onCreate` 会走到。**但为将来稳妥，仍按迁移写** |

`user_db.dart` 的文件头**已经明确标注了这个能力边界**（原文）：

> ⚠️ 本实现**只覆盖「新增表 / 新增索引」**。
> 将来若需**改已有表的列**：必须在本分支里**按 `oldVersion` 写专门处理**。

⇒ **具体要做**：

| # | 动作 |
|---|---|
| 1 | `user.db`：`kUserDbVersion` **5 → 6**；在 `onUpgrade` 里加 `if (oldVersion < 6) { ALTER TABLE bookmark ADD COLUMN deleted INTEGER NOT NULL DEFAULT 0 }` |
| 2 | `book.db`：加 `book.content_hash` 列 + `book_progress_pending` 表 + 索引 |
| 3 | ✅ **验证必须包含「从旧版本升级」的路径** —— 只测「全新建库」会**假绿** |

🔑 **判据**：**「新建库跑通」≠「老库能升级」**。
项目里已有同类教训（`article_read` / `achievement_unlock` 都踩过：只测了 onCreate）。
📄 既有 skill：`sqlite-schema-migration` —— 本阶段应照它做。

⚠️ `ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT 0` 是 SQLite **允许**的形式
（带默认值的 NOT NULL 可以加）—— 但**不能**加「无默认值的 NOT NULL 列」。

### 6.1 关于 #6（同步与订阅的关系）—— 一个需要想清的点

权益是「**跨设备同步**」⇒ 免费用户**不应**享有。

| 选项 | 影响 |
|---|---|
| **A** | **push/pull 接口校验订阅状态**（后端查 `subscription_expires`）| 实现干净；⚠️ 但端侧要处理「订阅过期后同步停止」的提示 |
| **B** | 接口不校验，仅端侧**不展示**同步入口 | 🔴 协议上不设防 ⇒ 可被绕过；但「绕过能拿到什么」= 自己的数据 ⇒ 实际损失低 |
| **C** | 免费用户也能同步（把同步当通用能力，订阅换别的权益）| 🔴 那订阅**又空了**（回到本次的起点）|

⭐ **建议 A**（与「登录态是能力开关、不是可见性开关」同一思路：**服务端也要能拒绝**）。
⚠️ 但要注意：**订阅过期后不能让用户「丢数据」** —— 应停止**同步**而非**删除**服务端副本。
