## 一、架构已重组：学习状态整体迁到端侧

这是理解所有差异的**前提**。

| 层 | 库 | 内容 | 状态 |
|---|---|---|---|
| **端侧** | `word.db`（入 git · 33 MB） | 词库 11,523 词 / 19 表 | ✅ **唯一词库** |
| **端侧** | `user.db`（设备上 · 5 表） | `card_review_state`（FSRS 状态）· `review_log`（复习日志）· `bookmark` · `user_word`（生词本）· `lookup_event` | ✅ **唯一学习状态** |
| **后端** | `coevo.db` | 商业能力（登录/支付/订阅/通知/推荐/试用）+ **旧的学习状态** | ⚠️ **混合** |

**证据**：
- `app/assets/sql/user_db_schema.sql` 明文「依据 `fsrs-client-side-migration-plan-2026-09-26.md`」
  —— **FSRS 已按计划迁到端侧**，含 `card_review_state` / `review_log`
- 端侧 `review_log` 自己带 `synced` / `unique(word_id, reviewed_at, device_id)` 幂等键
  → **多端同步的最小单位在端侧**
- app 划词/复习/收藏**全部读写端侧**（`user_db_provider` · `review_list_provider`）→ 实测无网络调用

🔑 **结论**：后端的 `user_cards` / `card_memory` / `review_log` / `prebuilt_*` 是**旧架构产物**。
端侧那份才是现役。

## 三、🔴 一个必须先解决的硬矛盾：成就体系依赖已迁走的学习状态

**这不是"删几张表"能解决的，是架构问题。**

`app/lib/app.dart:728` → `const AchievementOverlay()` —— **已接线，是活功能**。
它读 `/api/user/{uid}/profile` 返回的 `achievements` 字段。

而算这个字段的 `backend/crates/api_server/src/achievement_engine.rs` 依赖：

| 依赖的表 | 状态 |
|---|---|
| `user_cards` · `card_memory` · `review_log` | 🔴 **学习状态已迁端侧** —— 后端这些表未来会空/被删 |
| `plan_runs` · `user_plan_progress` · `prebuilt_cards` | 🔴 **已在 09-29 删除** |
| `conversations` | 🔴 属 AI 对话（app 死代码） |

→ 🔴 **后端要算成就进度，但数据已经不在后端了。**

**三个可选方向**（需白哥定，这决定了 schema 形状）：

| # | 方案 | 说明 | 代价 |
|---|---|---|---|
| **甲** | **成就也在端侧算** | 端侧有全部学习数据，零上报 | 要重写成就逻辑（Dart）；后端 `achievements` 表退役 |
| **乙** | **端侧上报摘要** | 端侧算个"统计摘要"推给后端，后端只负责展示定义 | 要设计上报协议 + 新表 |
| **丙** | **暂时搁置成就** | 与待办「**成就体系重新规划**」合并做 | 现在不写相关 schema（即"不做加法"） |

🔑 **这与既有待办「成就体系重新规划」是同一件事** —— 建议合并处理，不要现在为它建表。

## 四、路线评估：为什么不建议「等开发完再清理」

### 4.1 三条判据

**判据 1：有没有真实数据要保？→ 🔴 没有**（这一条让重构成本**大幅下降**）

实测 `backend/data/coevo.db`（清除词卡前）：

| 指标 | 实测 |
|---|---|
| `users` | **91 个** —— **48 个 `test*`** + **43 个 `trial_xxx`**（系统自动生成） |
| 真实用户 | **0** |
| 时间跨度 | 2026-07-01 ~ 07-15（**仅半个月**，且是 7 月的旧内测） |
| `payment_orders` | 8 笔（¥12 × 8，**全部来自 `test*` 账号**） |
| `review_log` | 41 条 |
| `marketing_campaigns` | 4 个（测试活动） |

→ 🟢 **可以随便改 schema，不需要写数据迁移脚本。** 这是"现在做"最大的理由。

**判据 2：现在做 vs 后面做，成本差多少？→ 现在便宜得多**

| | 现在 | 等开发完 |
|---|---|---|
| 改动对象 | 只有 schema（零数据） | schema + **已完成的新功能代码** |
| 返工 | 无 | 每个依赖旧表的新功能都要改 |
| 认知负担 | 低（表少） | 高（新旧并存，分不清哪个现役） |

**判据 3（🔴 最关键）：带着旧 schema 开发会发生什么？**

```
新功能开发时，开发者看到 user_cards / card_memory 还在
  → 很自然地「复用它」（看起来是现成的学习状态表）
  → 而它其实已经是死表（端侧才是真来源）
  → 新功能上线才发现：数据永远是空的
```

🔑 **这是「等开发完再清理」的真正代价** —— 不是"以后再花时间清"，而是
**旧表会持续吸引新的错误依赖**。本项目已有同族教训：
`word_form` 补漏时，「**存量修复 ≠ 根治**」；这里是"**存量不清理 → 持续产生新依赖**"。

### 4.2 但「全量重构」也不对

| 全量重构的问题 | 说明 |
|---|---|
| **产品还在变** | 成就体系要重规划、LLM 制卡未做、变现细节未定 |
| **会白做** | 现在为"还不知道要什么"的部分建表 = 猜 |
| **风险集中** | 一次动 45 表的 schema，即使零数据也要重跑所有验收 |

## 五、⭐ 建议：**现在做减法 + 只解硬矛盾**（第三条路）

**不做「全量重构」，做「现在减到只留确定的」'**：

### 阶段一：现在做（**只删不加**）—— 本轮

| 步 | 内容 | 为什么现在做 |
|---|---|---|
| 1 | **删 AI 对话 3 表**（`conversations` · `conversation_turns` · `defer_queue`） | app 无 UI 入口，**不可能再要回来** |
| 2 | **删旧学习状态 8 表**（`user_cards` · `card_memory` · `review_log` · `card_relations` · `user_*_cards` ×4） | ⚠️ **前提：先定成就体系方向**（§三） |
| 3 | 清 admin 死路由（curriculum/guardian 约 28 个） | 依赖的表已删，路由是死的 |
| 4 | `schema.rs` 同步 | 否则新库重建（已踩过一次） |
| 5 | 清 F 类明显遗留（`debug_logs` · `debug_trackers`） | 无消费者 |

🔑 **为什么是"只删不加"**：删除的对象是「**架构已定、不可能回头**」的
（学习状态迁端侧是既定方向）→ 删了**不会错**；
而新增表要基于「还不知道的需求」→ 加了**可能错**。

### 阶段二：等需求明确再做（**现在不动**）

- 成就体系相关表（与「成就体系重新规划」合并）
- LLM 制卡 / 词库外生词（Phase 3）
- 变现细节（价格档位、发票等）

### 5.1 阶段一的前置：先定成就体系方向

`user_cards` / `card_memory` / `review_log` 在后端的**唯一现役消费者是成就体系**。
→ **不先定成就方向（甲/乙/丙），就无法安全删这三张表。**

## 六、🔴 顺带纠正一个我此前的部署假设

白哥说「VPS 没有部署」—— 这**推翻了我此前方案的几个前提**：

| 我此前的假设 | 实际 |
|---|---|
| VPS 在跑生产服务 | ❌ 没有部署 |
| `backend/data/coevo.db` 是"生产数据快照"（部署源） | ⚠️ 更准确说：是 **7 月内测的产物**（91 个测试账号） |
| 需要"部署前先改 schema，再删表"的顺序 | ⚠️ **无生产环境 → 无窗口期问题 → 可自由改** |

**好消息**：这让阶段一的执行**更安全**（无线上影响）。
**需要确认**：「VPS 没有部署」是指
① **从未部署过**，还是 ② **曾部署过（7 月 MVP）、现已停**？

→ 若是 ②，VPS 上可能还有一份带测试数据的旧库；建议问清后一并处理（或直接重建）。
