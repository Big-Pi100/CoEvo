## 〇、速查

| # | 瓶颈 | 影响 | 修法 | 收益 |
|---|---|---|---|---|
| **1** | 🔴🔴 **本地 HTTP 代理** | >250 并发即崩（300 并发 43% 失败） | 直连（内部自动探测选路） | 可用并发 **250 → 1000+** |

## 二、持续压测（真实场景，3,000–4,000 条）

短时压测不够 —— 全量是**持续跑几分钟**，会暴露「越跑越慢」：

| 配置 | 词数 | 耗时 | 吞吐 | 失败率 | 曲线 |
|---|---:|---:|---:|---:|---|
| 300 并发 · urllib 直连 | 4,000 | 43.1s | 168 | 0.03% | 平稳 ✅ |
| **100 并发 · urllib 直连** | 3,000 | **160.4s** | **18.7** | **1.83%** | 🔴 **越跑越慢**（尾部 300 条 72s） |
| **100 并发 · 长连接** | 3,000 | **47.0s** | **63.8** | **0%** | 平稳 ✅ |
| 200 并发 · 长连接 | 1,500 | 16.2s | 92.5 | 0% | 平稳 ✅ |
| 300 并发 · 长连接 | 1,500 | 12.8s | 117.4 | 0% | 平稳 ✅ |

### 🔴 「越跑越慢」的错误全是**建连阶段**

```
_ssl handshake timed out ......... 31
SSLEOFError (UNEXPECTED_EOF) .....  9
ConnectionReset (WinError 10054) ..  9
RemoteDisconnected ................  3
429 = 0                            ← 完全不是限流
```

**根因**：`urllib` **每个请求新建一条 TCP+TLS 连接**。而：

| 事实 | 数值 |
|---|---|
| Windows 动态端口范围 | **16,384 个**（49152–65535） |
| TIME_WAIT 默认保留 | 120 秒 |
| 300 并发下新建连接速率 | ≈100–200 条/秒 |
| → 120 秒内累积 | **12,000–24,000 个 TIME_WAIT** 🔴 **超过端口上限** |

→ **端口耗尽 + TLS 握手风暴**。这解释了为什么短时压测 0 失败、持续跑就崩。

**修法**：每线程持有一条长连接复用 → 连接数从 `O(请求数)` 降到 `O(并发数)`。

## 三、生产脚本的三处修复

### 3.1 🔴 `os.fsync`（**影响 30 倍速度**）

`Sink` 在**全局锁内**每批 `fsync`。Windows 上 `os.fsync` = `FlushFileBuffers`（**刷整个卷**）
—— 一次慢刷盘会阻塞**所有**完成线程的写入 → 整条流水线跟着卡。

| 200 并发 · 直连 · 长连接 | 耗时（200 条） | 重试 |
|---|---:|---:|
| 每批 `fsync` | **2.4 分钟** | 33 次 |
| 关 `fsync` | **8 秒** ✅ | **0 次** |

**折中策略**（已实现）：**每 `FSYNC_EVERY=1000` 条刷一次** + 收尾必刷。
既不被拖慢，进程被杀最多丢一批。
（`COEVO_NO_FSYNC=1` 完全关闭 · `COEVO_FSYNC_EVERY=N` 可调）

### 3.2 🔴 长连接被服务端单方面关闭

长连接有寿命（服务端 idle 超时 / 达到上限），客户端不知道 → 下次复用死连接报错。
虽有重试兜底，但**每次失败要退避 1–2 秒 → 少数线程变成长尾 → 拖慢整体**。

**两条主动策略**（避免「被动失败」）：
1. 响应头 `Connection: close` → **主动重置连接**
2. 连接复用上限 `MAX_REUSE_PER_CONN=200` → 到点**主动重建**

**效果**：300 并发 1000 条，重试 78 次 → **0 次**。

### 3.3 🟠 连接超时 = 读超时

原 `timeout=120` 同时作用于**握手** → 握手卡住时单请求要等 120 秒（尾部 388 秒的来源）。

```python
CONNECT_TIMEOUT = 15   # 建立 TCP+TLS（含握手）—— 正常应 <3 秒（实测 p99 3.6s）
READ_TIMEOUT    = 60   # 连上后的读超时（实测 p99 3.6s，偶见 22s → 60 秒留足余量）
```

## 六、方法论沉淀（可复用）

| # | 教训 |
|---|---|
| **1** | 🔴 **「吞吐不涨」≠「服务端饱和」** —— 必须看**延迟曲线**。延迟恒定就说明服务端没满，瓶颈在客户端 |
| **2** | 🔴 **失败率高时吞吐数字无意义** —— 失败请求瞬间返回会让「条/秒」虚高。**必须同时看失败率** |
| **3** | 🔴 **必须关闭重试才能测出真实上限** —— 生产用的 4 次指数退避会把限流/连接问题**掩盖成「慢但成功」** |
| **4** | 🔴 **必须区分错误类型**：`429` = 服务端限流；`SSL 握手超时 / EOF / Reset` = 连接层。**处理方式完全不同**，混为一谈会走错方向 |
| **5** | 🔴 **短时压测不足以暴露问题** —— 端口耗尽/TIME_WAIT 只有在**持续跑**时才显现。**压测规模必须接近真实规模** |
| **6** | 🔴 **「越跑越慢」是资源耗尽的信号**（端口/连接/句柄），不是「服务端变慢」 |
| **7** | 🟠 **可观测性优先于优化** —— 没有 `attempts` / 错误分类统计，输出里只有「成功 N · 失败 0」，**完全看不出正在被限流** |
| **8** | 🟠 **`os.fsync` 在 Windows 上代价极高**（刷整卷），且高并发下若在锁内会成为串行瓶颈 |
