## 一、先说清楚：这个数字现在从哪来

**从我的原型里手写来的**，没有任何数据支撑。

但白哥问得对 —— 这个标识是信息流里**信息密度最高的一个元素**。用户扫一眼就知道「这篇值不值得今天读」，它比标题和摘要更能驱动点击。

所以它值得做实。下面是我实测的能力评估。

---

## 二、实现它需要什么（三件套）

```
RSS 文章正文
   ↓ ① 分词 + 提纯
原始 token 序列
   ↓ ② 词形还原（produces → produce）
lemma 序列 + 去重
   ↓ ③ 与词表比对
「N 个生词」
```

### 2.1 ✅ 第 3 件已经现成：权威词表

| 资产 | 规模 | 字段 |
|---|---|---|
| `data/curriculum/prebuilt/cefr_j/cefr_j_flat.json` | **6,864 词** | `cefr_level` + `pos` |
| `data/curriculum/prebuilt/cefr_j/cefr_j_all.json` | **7,801 条** | headword / pos / cefr_level / core_inventory |
| `prebuilt_cards`（english） | **12,871 条**（词表型 12,650） | front + card_type |
| 两者交叉覆盖 | **6,561 / 6,864 = 95.6%** | 缺的 303 条几乎全是多词短语 + 英美拼写变体 |

> CEFR-J（CEFR-J Wordlist）是东京外国语大学投野由紀夫团队基于 CEFR 制定的英语词表，在学术与教学场景被广泛引用，可自由用于研究与非商业/教学用途。**商用需核实授权**（见 §六）。

### 2.2 ✅ 第 1 件是成熟技术

RSS 正文提纯（去 HTML 标签 / 广告 / 导航）+ 分词，都有成熟实现。英文分词尤其简单（空格 + 标点切分）。

**不需要 NLP 框架。** 英文没有中文分词那种歧义问题，正则 + 停用词表就够。

### 2.3 🔴 第 2 件是缺口：词形还原完全不存在

**全仓库没有任何词形还原实现。**

这不是小事 —— 不做还原，数字会严重偏高：

| 文章里的词形 | 词表里的原型 | 不还原的后果 |
|---|---|---|
| `produces` / `produced` / `producing` | `produce` | 算成 3 个不同的词 |
| `buildings` / `building` | `building` | 重复计数 |
| `grows` / `grew` / `grown` | `grow` | 算成 3 个 |
| `faster` | `fast` | 算不到 |

实测一篇 104 词的 VOA 风格短文：**75 个不同词形 → 其中 `building`/`buildings`、`farm`/`farms`/`farming`、`city`/`cities` 都是同一词的变形。**

> ⚠️ **准确量级**：初稿写「虚高 20–40%」，**实测约 7%**（216 词文本：107 → 100）。详见 §6.1。对「N 个生词」这个标识来说，词形还原是**锦上添花**而非阻塞项；但对**划词查词**是硬需求。

**这一条也是划词查词的同一个前置依赖** —— 用户在文章里划到 `received`，必须命中 `receive`。所以这张词形表是**两处共用**的基础设施，不是为「生词数」单独建的。

## 三、三种口径：算哪个数

| 口径 | 计算方式 | 冷启动可用 | 个性化 | 说明 |
|---|---|:---:|:---:|---|
| **A · 按难度** | 文章内容词 → 查 CEFR 等级 → 统计「超过某等级」的词数 | ✅ | ❌ | 所有人看到同一个数字 |
| **B · 按全站词表** | 统计「在词表中、但用户还没学过」的词数 | ⚠️ 需少量数据 | ✅ | 与生词本联动 |
| **C · 按个人掌握度** | 统计「用户未掌握（`reps<3`）」的词数 | ❌ | ✅✅ | 最准，但需积累数据 |

### 3.1 我的建议：**A 打底，B 逐渐接管**

```
新用户首次打开         → 口径 A：「6 个进阶词」
                        （用「进阶」而非「生词」—— 因为我们还不知道他会不会）
已查过一些词（10+ 个）  → 口径 B：「6 个生词」
有复习数据后           → 口径 C：「6 个生词」（真正的「你的生词」）
```

**文案要跟着口径变**，不能说谎：

| 阶段 | 标识文案 | 含义 |
|---|---|---|
| 无数据 | `6 个进阶词` | 客观难度，不是「你不会的」 |
| 有查词记录 | `6 个生词` | 词表中你还没学过的 |
| 有复习数据 | `6 个生词` | 你未掌握（`reps < 3`）的 |

这个「渐进个性化」设计还有一个好处：**用户能感知到 App 越来越懂他** —— 从「进阶词」变成「生词」，本身就是学习痕迹在积累的证据。

### 3.2 一个必须处理的数据问题

`prebuilt_language_cards.level` 有 **1,885 条为空**（占 10.8%）。这些词算不出难度。

| 处理 | 说明 |
|---|---|
| 用 CEFR-J 回填 | 6,561 条能对上，能补一部分 |
| 仍无等级的 | 不参与难度计数（宁少算，不乱算） |
| 长期 | 跑一次 LLM 补全，成本极低（1,885 条 × 短 prompt） |

> ⚠️ 另外：`prebuilt_cards.difficulty` 字段**全是 `0.5`**（12,871 条无一例外），是占位值，**不可用**。别指望它。

## 四、这个数字最有价值的地方：它应该**下降**

这是我最想说的部分。

同一篇文章：

```
今天读            →  「6 个生词」
一个月后重读       →  「3 个生词」
三个月后重读       →  「1 个生词」
```

**这个数字会随用户进步而减小。** 它和「痕迹」是同一个概念的两种表达：

| | 痕迹 | 生词数 |
|---|---|---|
| 感知方式 | **眼睛**（看到词变淡） | **理性**（看到数字变小） |
| 作用范围 | 逐个词 | 整篇 |
| 时间尺度 | 即时（每次阅读都在变） | 阶段（重读时才发现） |

### 4.1 它顺带解决了一个内容类 App 的老问题

内容流产品都有的困境：**旧内容会沉底。** 昨天的文章今天就没人看了，而 RSS 每天更新意味着内容永远在贬值。

但「生词数下降」给了用户一个**重读旧文章的理由**：

> 「这篇 3 个月前你遇到 6 个生词，现在只剩 1 个了 —— 再读一遍？」

这是一个**天然的召回机制**，而且是**正向的**（不是「你还没读」的催促，而是「你进步了」的邀请）。成本为零，因为它只是把已有的计算结果显示出来。

### 4.2 实现方式

在 `content_item`（或等价的内容表）上加两个字段：

```sql
-- 入库时预计算（不是前端算）
total_content_words   INTEGER,   -- 文章内容词总数（lemma 去重后）
cefr_band_counts      TEXT,      -- JSON：{"A1":12,"A2":18,"B1":9,"B2":6,"C1":2}

-- 用户级：按需计算 + 缓存
-- user_article_stats(user_id, content_id, unknown_count, computed_at)
```

**冷启动用 `cefr_band_counts`**（一次计算、全用户共用），**个性化用 `user_article_stats`**（按用户缓存，掌握度变化时失效重算）。

> **性能**：一篇文章内容词约 50–150 个，与 12,650 词表比对是毫秒级。但要在**入库时**做完，不要放在前端渲染路径上。

### 6.1 一个重要的自我纠正

**本文档 §2.3 说「不做词形还原，数字会虚高 20–40%」—— 这个估计是错的。**

用 216 词文本实测：未还原 107 → 已还原 100，**虚高约 7%**。

**为什么估高了**：我按「词形重复的潜在数量」推，没考虑真实短文本里同词根变形重复本来就少。误差 ∝ 同词根变形在文中重复次数，100–200 词级别重复很少。

**对优先级的影响**：

| 场景 | 词形还原的必要性 |
|---|---|
| **划词查词** | 🔴 **硬需求** —— 划 `received` 必须命中 `receive`，错一个就是硬伤 |
| **「N 个生词」标识** | 🟡 **锦上添花** —— 误差 7%，方向偏高（让用户觉得稍难，不是灾难） |

**但这不改变结论** —— 两者共用同一张表，做划词查词的顺带就把生词数算准了。

### 6.2 新增发现：词表有 76 个污染短词

合并词表中**长度 ≤2 的词有 115 个**，其中 **76 个疑似污染**（`ab`/`af`/`bw`/`cm`/`zg` 等，像缩写或截断残留）。**会直接污染生词数** —— 用户可能看到「6 个生词」里含 `bw`。

建议在词库梳理阶段与 501 条专有名词一并清理（同源：都来自 `brown_inferred_low` 自动抽取）。

**同时**：专有名词（如 `Singapore`）应从生词数中**排除** —— 不是「学习者该学的词」。

### 6.3 顺带确认的对接口径

`number_of_unknown_words` 应**排除**：

| 排除项 | 理由 |
|---|---|
| 专有名词 | 学习者不需「学」 |
| 纯数字 / 序数词 | 同上 |
| 停用词（the/a/of/…） | 不是内容词 |
| 词表中不存在的词（词库外词） | 单列一类，不计入「生词数」（否则遇生僻文本数字爆炸） |
