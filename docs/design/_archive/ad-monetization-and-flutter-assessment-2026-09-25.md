## 一、🔴 纠正：Flutter **可以**接国内广告 SDK

**白哥的判断基于一个流传较广的说法**（我也在上一轮引用过）：第三方资料称穿山甲「仅兼容 Android、iOS 纯原生开发 App；**Flutter、uni-app 等跨端开发项目不在官方适配范围内，提交审核极易被驳回**」。

**核实结果：这个说法不可靠，不需要因此改原生。**

### 1.1 现成的 Flutter 广告插件（都是真实存在的）

| 插件 | 覆盖 | 状态 |
|---|---|---|
| **`gtads` + `gtads_csj`（穿山甲）+ `gtads_ylh`（优量汇）** | 穿山甲 / 优量汇 / 百青藤 / Sigmob / 快手 | **`gtads_csj` 1.5.18 于 2 个月前发布**，支持 Android / iOS / **鸿蒙** |
| `flutter_universalad` | 穿山甲 + 优量汇 | 较早期，gtads 的前身 |
| `ad_klein_flutter_sdk`（AdKlein 聚合 SDK） | 优量汇 / 穿山甲 / 百青藤 / AdMob / Smaato | 有官方 Flutter 文档 |
| `ad_suyi_flutter_sdk`（ADmobile 聚合） | 优量汇 / 穿山甲 / 快手等十几家 | pub.dev 上架，**明确写「支持 Android、iOS、Flutter 开发」** |

**`gtads_csj` 还支持 `useMediation: true`** —— 即使用穿山甲官方聚合产品 **GroMore** 的广告位。这说明穿山甲官方聚合能力也能从 Flutter 侧接入。

### 1.2 原理：为什么"审核拒 Flutter"这个说法站不住

```
Flutter 工程 → flutter build → 产物是原生包（Android: APK/AAB；iOS: IPA）
                                ↓
                       内部含原生广告 SDK（穿山甲/优量汇的 .aar / .framework）
                       + Flutter 引擎（libflutter.so / Flutter.framework）
```

**广告平台审核看的是"应用内容是否合规"，不是"你用什么框架构建"。** 构建产物就是原生包，SDK 调用路径与原生开发完全一致。

**那第三方的说法从哪来？** 我判断最可能的解释是：**说这话的是聚合平台，指的是"它自己的聚合 SDK 没有 Flutter 版"**（如芒果联盟自己的 SDK）—— 这是**那家平台的服务范围限制**，不是穿山甲的限制。而 `ad_suyi` 明确支持 Flutter，正好反证。

### 1.3 但有一条要实测确认

⚠️ **我没有找到「Flutter 项目成功接入穿山甲」的第一手开发者记录**（只有插件存在这一间接证据）。

**建议**：把「用 Flutter 构建的包能否通过广告平台审核」列为**接入前的必确认项**——但**不要因为这条传闻就预设要改原生**。

**验证成本极低**：插件装上、用测试广告位跑一次真机，半小时内就知道。

## 二、✅ 聚合平台确实对个人开放（你的信息核实通过）

### 2.1 已核实的平台（官网/公开资料原文）

| 平台 | 原文表述 | 服务费/结算 |
|---|---|---|
| **硕果广告**（玖腾科技） | 「助力个人开发者 APP 接广告变现，**无需公司资质**，即可接入穿山甲、优量汇、快手、百度联盟等主流广告平台，数据透明，**给原始广告平台子账号**，可看原始数据，不偷量、不扣量」 | 未公开；提到「服务费约 12%」来自你的调研 |
| **芒果联盟** | 「**个人开发者可接入，无需软著、无需上架**」「支持日结/周结/月结，**支持对私结算**」 | 免费接入 |
| **百益聚合** | 「支持**个人或个体户**接入，**无需软著，无需上架应用市场**」 | 预付 / 日结 / 周结 |

### 2.2 中介机制（这是它为什么合法的关键）

**「给原始广告平台子账号」** 是核心 —— 说明聚合平台是**穿山甲/优量汇的授权服务商/代理商**，通过官方服务商体系给下游开发者开子账号。

> ⚠️ **为什么这一点很重要**：穿山甲官方《开发者管理规则》明确写着：
>
> > 「开发者类型：通常情况下，平台的开发者应属于企业法人，平台**暂不支持与自然人及个体工商户开展流量变现合作**。」
> >
> > 「穿山甲平台账户仅限账户原始注册人本人使用；未经穿山甲书面许可，开发者不得以**借用、赠予、出租、出售、委托管理和运营**或其他任何方式将账户有偿或无偿许可给第三方使用。」
>
> **所以「自己注册账号再转租」是明确违规的；但「通过官方授权服务商开子账号」是另一回事。**
> **选平台时必须确认这一点** —— 问它是不是穿山甲的**官方服务商**、子账号是否官方后台可见。

### 2.3 服务费参考（你的 12% 在合理区间）

行业分析（skyfalling.cn 聚合平台运作原理）给出的分润结构：

| 环节 | 参与方 | 典型比例 |
|---|---|---|
| 广告主出价 | — | 100%（起点） |
| DSP 平台服务费 | — | 扣 15–25% |
| 联盟分成 | Network | 再抽 20–40% |
| —— | **聚合平台** | **5–15%**（收益分成模式） |
| **开发者到手** | Publisher | **40–60%** |

**结论：12% 落在 5–15% 的正常区间内。** 免费接入的平台通常靠"自有流量优先"隐性获利（自家联盟在竞价中获优待）。

### 2.4 ✅ 顺带解决软著问题

芒果联盟的对比表（明确区分自营 vs 直连）：

| 平台 | 接入门槛 | 结算 |
|---|---|---|
| **芒果联盟** | **无需软著、无需上架** | 支持对私 |
| 穿山甲聚合（GroMore） | **需软著 + 上架** | 仅对公 |
| 优量汇聚合 | **需软著 + 上架** | 仅对公 |

**→ 走聚合平台可绕过软著。** 这对我们是实质利好（软著卡在 2026 新规的 AI 条款上）。

> 暗示无软著接入可能**只能接部分广告源**或**分成更低**。**这是要问清楚的**。

## 三、⚠️ 必须如实说明：个人备案 + 广告变现的性质

**这是本轮最重要的一条，它决定这条路径的"性质"。**

### 3.1 事实

| 来源 | 原文 |
|---|---|
| **ICP 备案的官方定义**（Grokipedia 整理 MIIT 口径） | 非经营性备案适用于「**不从事商业活动**（如销售、**广告收入**、付费服务）的信息服务」 |
| 备案服务商（快备网） | 「个人可以做**非经营性**备案，**仅限制盈利类业务**；电商、付费、UGC 社交类 App 必须企业主体 + 完整资质」 |
| 《互联网信息服务管理办法》 | 经营性互联网信息服务（含广告）须持 **ICP 经营许可证** |
| **Apple 官方**（App 信息帮助页） | 只要求填写 **ICP 备案号**，**不检查你是否经营性** ← 平台层的口子 |

### 3.2 所以准确的表述是

```
平台层（Apple）      → ✅ 通。个人账号 + 个人备案号，能上架中国区
广告平台层（聚合）    → ✅ 通。聚合平台接受个人，可对私结算
法律层（ICP 规定）    → ⚠️ 超范围。个人备案是非经营性的，而广告收入属经营性
```

**→ 「个人备案 + 广告变现」是事实上的灰色地带（超范围经营），不是干净的合法路径。**

### 3.3 现实情况与风险

| 项 | 说明 |
|---|---|
| 普遍程度 | **大量个人开发者这么做**（ZOL 上个人开发者的回答、各类"个人开发者避坑指南"都印证这是常态） |
| 主要风险 | **被举报或抽查**后：管局**注销备案**，且**同一主体 3 年内不能再次申请** |
| 触发概率 | 我不掌握数据。低流量阶段通常无人关注；**做大了或被同行举报会暴露** |
| 我不是法律意见 | 这条需要你自己判断，或咨询专业人士 |

**我的建议**：**可以做，但要在知情的前提下做，并且提前规划"转正"路径**（有收入后注册公司补办 ICP 经营许可证）。这条风险随规模上升而上升——**低流量测试阶段风险低，规模化后必须解决**。

> ⚠️ **更正**：本文档第一版把风险写成「责令整改、App 下架（可恢复）」——**不够准确**。
> 多来源一致的实际后果是 **「注销备案 + 同一主体 3 年内不能再次申请」**。
> **这是「归零型」风险而非「罚款型」风险** —— 一旦触发，3 年内无法在中国区以个人主体重新上架。
> 完整说明与降风险做法见 **§8.2 / §8.4**。

## 四、修正后的路径全景（新增路径 D）

| 路径 | 做法 | 成本 | 法律性质 | 适合 |
|---|---|---|---|---|
| A | 注册公司做中国区完整变现 | ¥1.5–3 万 + 2–3 个月 | ✅ 干净 | 已验证、确定要规模化 |
| B | 先上免费版（无广告无会员） | ≈ ¥700/年 | ✅ 干净 | **最保守** |
| C | 上架海外区（AdMob + IAP） | $99/年 + 收款手续费 | ✅ 干净 | 愿意放弃中国大陆用户。**🔄 性价比已上修**（见下） |
| **D ✅ 已选定** | **中国区上架 + 接聚合平台广告变现**（个人身份） | **¥0 额外成本**（服务费从广告收入里扣） | ⚠️ **超范围经营** | **← 2026-09-25 白哥选定** |

**路径 D 的价值**：它是**唯一能在个人主体下立即变现的中国区路径**，且额外成本为零（聚合平台免费接入、服务费从分成里扣）。

**白哥已选定 D（2026-09-25）**，理由：**不接广告就得卖付费 APP，而国内卖付费 APP 的门槛更高**。

**但「选定 D」不等于「一开始就带广告上线」** —— 从合规风险角度，有一个明显更优的**执行顺序**：

```
先免费版备案上架  →  上架后再加广告  →  达到阈值再转正（路径 A）
```

原因：**避免「虚假申报」**。备案时确实无广告 → 初始备案诚实；
加广告后属「备案信息未更新 + 超范围」，**比「申报时就写无广告、实际接广告」轻一档**。

完整执行方案见 **§八**。

## 五、平台选型标准（如果走路径 D）

聚合平台这个行业**营销噪音很大**：我查到的资料基本都来自平台自己的 SEO 文章，那些"9 万 APP、99% 填充率、收益 +100%"**无法验证**。

**选型时按这四条筛**：

| # | 标准 | 怎么验 |
|---|---|---|
| 1 | **是不是上游官方服务商** | 问它能否给出「原始广告平台子账号」（能在穿山甲/优量汇官方后台看到自己的数据）—— 这是"不偷量"的硬证据，也是合法性关键 |
| 2 | **结算规则是否透明** | 结算周期（日/周/月）、打款门槛、是否支持对私、有无最低金额、**分成比例写进合同** |
| 3 | 主体是否真实可查 | 查工商信息（硕果=玖腾科技、芒果=芒果互动传媒(深圳)），看成立时间与社保人数 |
| 4 | **先小额验证再放大** | 先跑一两个月、拿到一次完整结算，再考虑全量 |

**⚠️ 三个具体风险**：
- **账户/结算冻结**：资料里明确提到"结算冻结"是常见风险（原因包括流量异常、资质缺失）
- **平台跑路**：聚合平台是中间商，账期越长风险越大 → **优先选日结/周结**
- **数据不透明**：只能看平台给的数据 → **"原始子账号"是唯一的解法**

**建议**：**同时接 2 家**（主 + 备），避免单一依赖。

## 六、技术实施要点（Flutter 侧）

### 6.1 推荐方案

| 层 | 选型 | 说明 |
|---|---|---|
| 聚合层 | **`gtads`** | 一套接口管多家，切换广告源不用改业务代码 |
| 广告源 | `gtads_csj`（穿山甲）+ `gtads_ylh`（优量汇） | **穿山甲用 `useMediation: true` 可直接用 GroMore 广告位** |
| 备选 | `ad_suyi_flutter_sdk`（ADmobile） | 若走该聚合平台，用它的官方插件更顺 |

**好处**：`gtads` 是抽象层，**广告源可插拔** —— 即使将来某家平台政策变了，换 provider 即可，不动业务代码。

### 6.2 ⚠️ 三条硬性合规要求（与我们的设计直接相关）

| # | 要求 | 对我们的影响 |
|---|---|---|
| 1 | **SDK 初始化必须在用户同意隐私政策之后** | 启动流程：`启动 → 隐私弹窗 → 用户同意 → 初始化广告 SDK`。**绝不能提前初始化** |
| 2 | **隐私政策必须列明广告 SDK 及其收集的设备信息** | 我们已有"隐私政策独立网页"任务，需加上广告 SDK 清单 |
| 3 | **激励视频必须用户主动触发** | 与我们的设计一致（解锁权益、看广告换功能） |

> 📌 **第 2 条要注意**：广告 SDK 接入后，**隐私政策要更新**（列明穿山甲/优量汇/聚合平台，以及收集的 OAID/IDFA 等设备标识）。APP 备案的"SDK 名单"也要同步。

### 6.3 与既有设计的关系

我们在 `design-system-spec` 定的广告原则（**阅读过程中绝不出广告**）**不用改**，但要注意激励视频的**位置设计**：

| 位置 | 建议 |
|---|---|
| 阅读界面 | ❌ **绝对不放**（原定原则） |
| 信息流列表 | 🟡 可放原生信息流（自然插入） |
| 生词本/复习页 | 🟡 插屏可放（场景切换时） |
| **"解锁权益"场景** | ✅ **激励视频的最佳位置**（符合你的"价值交换式设计"） |
| 开屏 | 🟡 可接受，可跳过 |

## 八、✅ 路径 D 执行方案（2026-09-25 白哥选定）

**决策**：中国区上架（个人开发者账号 + 个人备案）+ 广告聚合平台变现。

**理由**（白哥）：不接广告就得卖 APP，而国内卖付费 APP 的门槛更高；既然大部分个人开发者都这么做，也只能这么做。

### 8.1 ✅ 先排除一条悬念：Apple 侧没有账号类型限制

代办服务商的文章普遍声称：

> 「个人开发者账号**仅纯离线免费工具**」「**禁止**：带用户注册、评论、付费、**广告**、社区、资讯功能」
> 「社交、电商、付费、UGC、直播、医疗、金融类**只允许企业账号上架，个人账号直接拒审**」

**这条与 Apple 官方文档直接矛盾，判断不可靠：**

| 证据 | 内容 |
|---|---|
| **Apple 审核指南 2.5.18**（官方，中英版本一致） | **专门规范了 App 内广告的规则** —— 广告只能在主二进制、须与年龄分级相符、须让用户看到定向信息、插屏须有清晰关闭按钮等。**规则的对象是「包含广告的 App」，不区分账号类型** |
| **Apple 审核指南「商务」章节** | 「在 App Store 中，**你可以通过多种方式让自己的 App 实现盈利**」—— **无账号类型限制** |
| Apple「Choosing a Membership」官方页 | Individual 与 Organization **同为 $99/年、功能完全相同**（IAP、推送、CloudKit 都有） |
| **自我矛盾** | 该说法同时称「个人账号无法使用 IAP」—— 而 **Apple 官方明确个人账号可开 IAP**。整段说法自相矛盾 |

**→ 结论：Apple 侧个人账号可以放广告。** 那些说法的来源（代办服务商）有**推销企业账号与企业认证服务**的商业动机。

**⚠️ 但建议你花 3 分钟做一次实证**（你有 iPhone）：

```
App Store 中国区 → 搜几个小众免费工具 App（背单词 / 记账 / 小工具）
   → 看「卖家」字段：
        显示个人姓名  = 个人开发者账号
        显示公司名    = 企业开发者账号
   → 看该 App 内是否有广告
```

找到「**卖家是个人姓名 + App 内有广告**」的实例，这条就完全确认了。

### 8.2 ⚠️ 但备案层的风险比我上一轮描述的更重

本文档第一版写的是：「被举报或抽查后：责令整改、注销备案、App 下架」。**这不够准确。**

**多来源一致的表述**：

> 个人备案的 APP **不能从事经营性业务**，涉及交易、**广告**、会员收费、在线支付等商业行为的一律不批。
> **一旦被检测到以个人备案身份从事商业运营，管局会直接注销备案，同一个主体三年内不能再次申请。**

**关键差别在这一句**：

```
第一版的理解：  灰色 → 被查 → 整改 / 下架     （可恢复）
实际的后果：    灰色 → 被查 → 注销备案 + 3 年禁申（归零 + 冷却期）
```

**这是「归零型」风险，不是「罚款型」风险** —— 触发后 3 年内无法在中国区以个人主体重新上架。

### 8.3 ✅ 一个重要的事实修正：收入的合法性其实有明确规范

**这一条是正面的，它把问题的范围缩小了。**

国家税务总局 **2025 年第 16 号公告**《关于互联网平台企业为平台内从业人员办理扣缴申报、代办申报若干事项的公告》（**2025-10-01 施行**）明确规定：

- 从业人员自互联网平台企业取得**劳务报酬**所得，平台按**累计预扣法**预扣预缴个税
- 平台还可接受税务局委托，**代办征增值税和附加税费**

**聚合平台的实际做法**（芒果联盟官方说明 + 好游快爆公告，二者一致）：

| 项 | 说明 |
|---|---|
| **发票** | **个人开发者无需提供或邮寄发票**（企业开发者需开增值税专用发票并邮寄） |
| **个税** | 平台**代扣代缴** |
| **增值税 + 附加** | 平台**代办申报**；小规模纳税人综合 **≈ 1.06%**（1% 征收率 + 附加减半） |
| **免征** | **月提现 ≤ 10 万免增值税**（若多平台合计超 10 万，次月补扣） |
| **汇算清缴** | 次年 3–6 月在「个人所得税」App 完成 |

**实测案例**（微博广告共享计划创作者）：提现 ¥4,210.81 → 扣增值税及附加 ¥44.64（1.06%）→ **个税为 0**（累计收入扣除 20% 费用和 5,000/月减除费用后为负）。

**对我们的实际税负（按公式推算的量级）**：

| 月广告收入 | 年收入 | 增值税 | 个税 | 到手率（已扣平台 12%） |
|---|---|---|---|---|
| ¥3,000 | ¥3.6 万 | 0（月 <10 万免） | **0**（未达起征） | **≈ 88%** |
| ¥10,000 | ¥12 万 | 0 | ¥8,800/年 | ≈ 81% |
| ¥30,000 | ¥36 万 | 0 | ¥84,200/年 | ≈ 65% |

> ⚠️ 以上为按公告公式推算的量级，**实际以平台结算单为准**。

**为什么这条重要**：

> **存在专门规范「个人从平台取得广告收入」的税务规定，说明国家层面认可这种收入形式。**
>
> 问题**不在收入本身**，而**只在备案的经营性限制**（个人备案不得从事商业活动）。
>
> → **这把问题从「整体违规」缩小到「备案信息与实际不符」这一个点。**

### 8.4 降低风险的四条具体做法

**核心原则：避免「虚假申报」，把性质控制在「超范围」而不是「材料不实」。**

| # | 做法 | 为什么 |
|---|---|---|
| 1 | **备案说明如实写**：个人工具类应用 · **无广告 · 无交易收费 · 无注册登录** · 数据存本机。**前提是备案时 App 确实无广告**（所以与做法 2 必须配套） | 🔄 **本条已修正**（原写「不写无广告」）—— 见下方「为什么修正」 |
| 2 | **顺序：先免费版上架 → 上架后再加广告** | 备案时确实无广告 → 初始备案诚实。加广告后属「备案信息未及时更新 + 超范围」，比「申报时即造假」轻一档 |
| 3 | **控制早期规模** | 低流量阶段实际触发概率低。**关键不在于「能不能做」，而在于「做到多大」** |
| 4 | **预设转正阈值 + 提前备料** | 建议阈值：**月广告收入 ≥ ¥5,000，或累计 ≥ ¥5 万** → 启动公司注册。此时你有收入数据支撑这笔投入（¥1.5–3 万） |

#### 为什么修正做法 1（2026-09-25 晚）

**原写法**：「不写「无广告/无付费功能」这类承诺性表述」。
**问题**：把「**如实陈述**」和「**承诺**」混为一谈了。

| | 性质 | 是否合理 |
|---|---|---|
| App **确实无广告**时写「无广告」 | **如实陈述**（事实） | ✅ 合理，且能**显著提高备案通过率** |
| App **已有广告**时写「无广告」 | **虚假申报** | ❌ 绝对不行 |

**依据**（一篇个人开发者实操文的总结，与其他来源做法一致）：

> 如果你是个人开发者，备注说明一定要写得**极其克制**，明确这是个人生活记录类应用，强调**无注册登录、无信息发布、无交易收费、无广告、无在线咨询**，数据主要保存在本机。这种表述更符合个人工具类 APP 的定位，**能大幅降低被误判成平台型、经营性或行业服务的概率**。

**→ 真正关键的不是「写不写」，而是「备案时 App 是否确实无广告」。**

所以做法 1 与做法 2（先免费版上架）**必须配套**：

```
① 先做「无广告、无付费」的免费版
② 备案说明如实写「无广告」  ← 此时每句都是真的
③ 备案通过 → 上架免费版
④ 上架稳定后（可选）再加广告
   ← 此时属「备案信息未及时更新」而非「申报造假」，性质轻一档
```

**这个顺序同时满足两个目标**：备案阶段如实且通过率高；加广告阶段风险性质最轻。

**⚠️ 一条我不建议做的：不要为了规避而做主体形式上的小改（如临时注册个体工商户）。**

理由：
1. 个体工商户**同样办不了 ICP 经营许可证**（增值电信业务要求企业法人，个体基本不受理）→ **根本问题不变**
2. 备案主体性质（个人 vs 企业）在各地口径**矛盾**（有来源说个体户应选企业性质，也有说只能走个人通道）→ 可能白折腾
3. 反而把风险性质从「个人备案违规」换成「**企业无证经营**」—— 后者的法定罚则更重（没收违法所得 + 罚款违法所得 3–5 倍 + 关闭网站）

**✅ 一个现在就该做、且确实有用的准备**：

把「公司注册 + 3 名社保 + ICP 经营许可证」的**材料清单与本地代办资源确认好，只备料不启动**。
这样一旦决定转正，能立刻启动而不是从头调研 —— 而转正的时间成本（2–3 个月）正是最大的隐性代价。

### 8.5 ⚠️ iOS 特有的收益提醒（不要按安卓的行业数字推算）

你查到的「1000 日活月入几千」「eCPM 比往年下降」**很可能是安卓的行业数字**。iOS 单平台有两处差异必须实测：

| 因素 | 影响 |
|---|---|
| **ATT（App Tracking Transparency）** | iOS 14.5+ 必须弹窗授权才能用 IDFA 做定向。国内聚合广告在 iOS 上依赖 IDFA → **授权率通常 20–40%** → 未授权流量 eCPM 显著更低 |
| **国内广告主预算分布** | 国内广告联盟在 iOS 侧的填充率与 eCPM 与安卓**可能不同**（更高或更低） |
| **单平台量级** | 只做 iOS → 用户量基准本身低于双平台 |

**→ iOS 的真实 eCPM 必须自己实测，不能套用行业均值。** 这是「先小额验证再放大」的另一个理由。

**顺带一条产品建议**：ATT 授权弹窗的**说明文案直接影响授权率**（授权率高 → eCPM 高）。
值得认真写（说明「允许跟踪」是为了让 App 免费，且不会用于其他用途），并做 A/B。

### 8.6 Apple 审核指南 2.5.18 的六条硬要求（官方原文逐条对照）

| # | 要求 | 我们的实现 |
|---|---|---|
| 1 | 广告只能在**主 App 二进制**内，不得出现在扩展、轻 App、小组件、通知、键盘、watchOS App | ✅ 只做主 App |
| 2 | 广告必须与 **App 年龄分级相符** | ✅ 需在聚合平台后台屏蔽成人/赌博类广告类目 |
| 3 | 用户必须能**看到用于定向他们的所有信息**（不要求离开 App） | 🟠 需做「为什么看到这个广告」入口（部分 SDK 自带） |
| 4 | **不得**基于敏感数据（健康/医疗、学校课堂、儿童）做定向或行为广告 | ✅ 我们采集的数据不含这些；需在 SDK 侧确认 |
| 5 | 插屏广告必须**清楚标明是广告**、不得操纵欺骗、必须有**易访问可见且足够大的关闭/跳过按钮** | ✅ SDK 默认满足，需验收 |
| 6 | **含广告的 App 必须提供让用户「报告不当广告」的功能** | 🔴 **容易漏掉，必须做**（审核硬要求） |

> **第 6 条是容易被漏掉的要求。** 建议入口：广告位附近的「ⓘ」气泡 → 「举报此广告」，或「设置 → 关于广告 → 举报广告」。

### 8.8 ⚠️ 一句话总结这条路径的性质

> **平台层通、广告平台层通、税务上有明确规范，唯一的问题是「个人备案不得从事经营性活动」。**
>
> 所以它不是「黑」（不是违法经营），是「**灰**」（超范围）。而「灰」的实际风险取决于**规模**与**是否虚假申报** —— 这两点都是可以主动控制的。
>
> **我不建议你因此犹豫，但建议你按 §8.4 的四条做，并且把「转正」当成一个已经排上日程的事，而不是一个万一出事才想的事。**
