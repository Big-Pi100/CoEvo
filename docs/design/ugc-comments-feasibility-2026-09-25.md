# 用户发言与讨论（UGC）可行性评估

- 日期：2026-09-25
- 问题：一篇文章下是否支持用户发言和讨论？
- 结论：**建议不做自由文本 UGC。** 它会同时（a）把刚拿到手的合规优势还回去（b）引入实名与审核的永久运营成本（c）与我们选的内容源正面冲突。
- 但**有 4 种替代设计**能保留「社区感」而几乎不增加合规负担。

---

## 〇、结论先行

| 判断 | 内容 |
|---|---|
| 🔴 **自由文本评论** | **不建议** —— 触发实名认证 + 先审后发 + 审核队伍三项义务 |
| 🔴 **特别麻烦的一点** | 我们用的是 **RSS 新闻源**，而规定明确要求「**对新闻信息提供跟帖评论服务的，应当建立先审后发制度**」→ 每条评论都要审后才能显示 |
| 🔴 **引入永久运营成本** | 需「**配备与服务规模相适应的审核编辑队伍**」—— 这是人力，不是可以一次性解决的 |
| 🟠 **实名认证与产品目标冲突** | 规定要求「后台实名」真实身份认证（手机号/身份证）→ 抬升注册门槛，而我们最需要的是 DAU |
| ✅ **替代方案存在** | 结构化交互 + 编辑内容 + ~~私密笔记~~（⛔ 2026-10-06 作废）+ 外部分享，可保留社区感 |

## 一、Apple 侧要求（Guideline 1.2）

一旦 App 包含用户生成内容，Apple 要求**四项齐备**：

| # | 要求 | 说明 |
|---|---|---|
| 1 | **内容过滤机制** | 「a method to filter objectionable material from being posted」—— 必须在**发布前**过滤 |
| 2 | **举报机制** | 可举报冒犯内容，且需**及时响应**（有资料提到 24 小时内处理） |
| 3 | **拉黑能力** | 可阻止有滥用行为的用户继续使用服务 |
| 4 | **公开联系方式** | 用户能方便地联系到开发者 |

**注意**：只有「举报按钮」而没有后端（举报表 + 管理端 + 封禁能力）**不算合规** —— 审核员会检查是否有实际的审核基础设施，没有就拒审。

另外，Apple 明确列出**不适合放在 App Store 的形态**，包括「任意或匿名聊天」等 —— 我们做学习 App，不该往这个方向靠。

**这一层是「可满足的」** —— 建举报表 + 管理端 + 封禁能力，工程工作量可控（约 3–5 天）。真正的问题在下面。

## 二、中国侧要求（《互联网跟帖评论服务管理规定》）

这条是**决定性的**。规定适用于「互联网站、**应用程序**……以评论、回复、留言、弹幕、点赞等方式，为**用户提供发表文字、符号、表情、图片、音视频等信息的服务**」——我们的场景正好落入。

服务提供者的法定义务（逐条对照）：

| # | 法定义务 | 对我们的影响 |
|---|---|---|
| 1 | **「后台实名、前台自愿」** —— 对注册用户进行基于**移动电话号码、身份证件号码**等方式的**真实身份信息认证**，**不得向未认证用户提供跟帖评论服务** | 🔴 **注册门槛大幅上升**。要么全站实名，要么「看文章不实名、发言先实名」 |
| 2 | 用户个人信息保护制度（告知处理目的/方式/种类/保存期限，取得同意） | 🟠 增加 PIPL 合规工作量 |
| 3 | **「对新闻信息提供跟帖评论服务的，应当建立先审后发制度」** | 🔴 **直接命中** —— 我们的内容是 RSS **新闻**，所以每条评论必须**审核通过后才能显示** |
| 4 | 建立健全**跟帖评论审核管理、实时巡查、应急处置、举报受理**等信息安全管理制度 | 🔴 需常设流程，不是一次性开发 |
| 5 | **「配备与服务规模相适应的审核编辑队伍」** | 🔴 **需要人力** —— 与长期成本绑定 |
| 6 | 具有舆论属性或社会动员能力的服务，上线新功能应开展**安全评估** | 🟠 上线流程增加环节 |

### 2.1 第 3 条为什么特别致命

我们刚刚选定 **RSS 新闻**作为内容源（为绕开出版许可）。但这条规定把「新闻」单独拎出来加严：

> 「对新闻信息提供跟帖评论服务的，**应当建立先审后发制度**」

对比一般 UGC（可以「先发后审」），**新闻下的评论必须「先审后发」**。这意味着：

```
用户写完评论 → 提交 → 【进入审核队列】→ 审核通过 → 才对外显示
```

**用户体验上**：评论不能即时出现，失去「讨论正在发生」的社交快感 —— 而这恰恰是你想要的那个「刷社交平台」的感觉。

**运营上**：这是持续的人力投入，高峰时段（如早晚）还会堆积。

### 2.2 第 1 条的隐性代价

「后台实名」要求真实身份认证。对广告变现模型来说，这是个**结构性矛盾**：

```
广告模型：需要大量免费用户 → 需要极低注册门槛 → 需要 DAU
实名要求：手机号/身份证验证 → 注册门槛升高 → DAU 下降
```

而且实名意味着要处理**身份证号级别的敏感个人信息**，触发 PIPL 的敏感信息条款（单独同意、更严格的安全措施、可能需等保测评）。

> 值得注意：项目历史上做过 `guardian_declarations`（家长声明）+ `real_name`/`phone`/`id_number` 字段 + AES-256-GCM 加密 —— 说明**这套负担之前已经承受过一次**，简化时正好整块删除了。现在重开 UGC 等于把它请回来。

## 三、成本影响

UGC 会引入**三类新的持续性成本**：

| 成本项 | 性质 | 估算 |
|---|---|---|
| **短信验证**（实名认证） | 按条 | ~¥0.04/条 × 注册量。10,000 注册/月 ≈ **¥450/月** |
| **内容审核** | 按条（若用 LLM） | ~¥0.001/条。10,000 条/天 ≈ **¥300/月** |
| **审核编辑队伍** | **人力（常设）** | 1 人 ¥4,000–6,000/月；先审后发下 1 人约处理 2,000–3,000 条/天 |

**关键对比**：我们的月收入模型是 **¥3.0/活跃用户**。

| 活跃用户 | 月广告收入 | 审核人力需求（假设 10% 发言率、人均 2 条/天） | 是否划算 |
|---:|---:|---|---|
| 1,000 | ¥3,000 | ~200 条/天（兼职可覆盖，¥2,000/月） | ⚠️ 紧 |
| 5,000 | ¥15,000 | ~1,000 条/天（1 人） | 🟡 勉强 |
| 10,000 | ¥30,000 | ~2,000 条/天（1 人） | 🟢 可接受 |
| 50,000 | ¥150,000 | ~10,000 条/天（4–5 人） | 🟢 可接受 |

**结论**：纯算钱，规模化之后 UGC 是能覆盖的。**但它打破了整个设计原则**：

> 我们的模型建立在「**零边际成本 + 零运营**」上 —— 内容一次性生成、阅读查词复习全本地、服务器只做同步。UGC 是唯一一个把「持续运营」强加进来的功能。

而且**早期最危险**：用户少时审核成本摊不掉，用户多时才划算 —— 但用户少的时候恰恰最需要把精力放在产品和留存上，不该分心做社区运营。

## 四、替代设计（保留社区感，规避 UGC 义务）

按合规风险从低到高：

### ✅ 方案 1 · 结构化交互（推荐）

**不做自由文本，只做点击式交互。**

```
文章卡片下：
  👍 有用 (328)
  🤔 我也不认识这个词 (156)      ← 点击标记，不是打字
  🔖 收藏 (89)

单词卡下：
  「今天 1,203 人查了这个词」
  「67% 的人和你一样，第一次见就查了」
```

**为什么合规风险低**：规定约束的是「为用户提供**发表文字、符号、表情、图片、音视频**等信息的服务」。纯点击式标记不产生用户创作内容，性质接近「数据统计」而非「评论」。

**产品价值**：其实**比评论更适合学习场景** —— 学习者不想看别人写的学习感想，但很想知道「这个词难不难、别人是不是也不会」。这是**匿名化的群体信号**，比自由讨论有用。

> ⚠️ **边界需要专业确认** —— 规定的表述里出现了「点赞等方式」，所以纯点赞是否完全豁免，我不建议自行断定。但可以确定的是：**结构化点击的风险显著低于自由文本**。上线前建议做一次合规确认。

### ✅ 方案 2 · 编辑内容（PGC，不是 UGC）

由运营/编辑产出的注释，不是用户发言：

```
文章下：
  📝 编辑解析
     · 本文难度：B1（约 320 词，生词率 8%）
     · 重点词：forecast / severe / evacuate
     · 语法点：过去完成时（3 处）
```

**零合规负担**（不是用户内容），且对学习有实际价值。成本是编辑时间，但可以半自动生成（LLM 初稿 + 人工过一遍）。

注意：这类内容本身也需**引用规范** —— 但已经是「学习材料」定位，比展示用户发言安全。

### ⛔ 方案 3 · 私密笔记 —— **2026-10-06 作废**（白哥定「不做，没有用」）

> 以下内容仅作历史记录。当初评估结论是「零风险、零成本」，但**从未出过 UI 稿**，
> 2026-10-06 白哥最终判定「没有用」⇒ 不实施、不建 `user_note` 表。

用户自己的笔记，**仅自己可见**：

```
我在这个词下写：这个词在《经济学人》里见过
→ 只存本地/自己账号，不公开
```

**不是公开发言 → 不构成 UGC**（Apple 1.2 与我们无关），也不触发跟帖评论规定。

**产品价值高**：符合 FSRS 的「主动回忆」原理 —— 自己写的联想比系统给的例句记得牢。

### ✅ 方案 4 · 学习成果外部分享

用户把学习数据生成图卡，**分享到微信/小红书等外部平台**：

```
「我已经连续学习 47 天，掌握了 1,203 个词」
→ 生成分享图 → 用户自己发到外部社交平台
```

**合规优势**：**内容不在我们平台承载**。App 只生成图片，风险在用户和外部平台。

**顺带解决另一件事**：这是天然的**获客渠道**（用户主动分享 = 免费曝光），对广告模型是正向的。

### 🔴 方案 5 · 自由文本评论（不推荐）

如果一定要做，必须前置：

| 前置项 | 工作量/成本 |
|---|---|
| 服务器端实名认证（短信验证） | 集成 + ¥0.04/条 |
| 先审后发队列 + 审核后台 | 开发 + 常设人力 |
| LLM 预审（减轻人工负担） | 按条成本 |
| 举报 + 拉黑 + 24h 响应流程 | 开发 + 运营 |
| 社区规范文档 + 公开联系方式 | 文档 |
| 舆论属性安全评估（视情形） | 流程 |
| PIPL 敏感信息合规（若收身份证） | 法律 + 技术 |

**建议：至少推迟到产品验证之后。** 如果真要做，也只是「文章下的一句话短评」（限字数），而不是完整论坛。

## 五、我的建议

**第一版不做自由文本 UGC。** 理由三条：

1. **合规上**：会把刚解除的出版许可阻塞，换成更难处理的实名 + 先审后发 + 审核队伍
2. **成本上**：引入常设人力，打破「零边际成本 + 零运营」的设计原则（也是你最看重的）
3. **产品上**：先审后发让评论无法即时显示，**恰恰杀死了你想要的那个「社交感」**

**但社区感值得保留** —— 用**方案 1（结构化交互）** 替代：

```
文章下：  👍 有用 (328)   🤔 这篇有点难 (56)
词卡下：  「今天 1,203 人查了这个词」「67% 的人和你一样第一次见」
```

这个设计有三个好处：
- **零合规负担**（非文本发表）
- **对学习更有用**（群体难度信号 > 别人的感想）
- **零运营成本**（纯统计，不需要审核）
