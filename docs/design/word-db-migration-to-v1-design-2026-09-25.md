## 一、我的 3 条修正建议 + 2 条补充（都有实测依据）

### 🔴 修正 1：v1 的 `UNIQUE(lemma)` 会与 **1,375 张卡片**冲突 —— 必须先做 #5

**v1 原文**：
```sql
CREATE TABLE word (
  id              INTEGER PRIMARY KEY,
  spelling        TEXT NOT NULL,
  lemma           TEXT NOT NULL,
  ...
  UNIQUE (lemma)          -- ← 一个 lemma 只能一条记录
);
```

**实测冲突规模**：

| 项 | 数量 |
|---|---:|
| 英语词表卡片 | **11,917** |
| 归一化后会「撞 lemma」的卡片 | 🔴 **1,375 张**（涉及 1,130 个 lemma） |
| 样例 | `be` ← are/am/being · `have` ← had/having/has · `run` ← running/ran · `sing` ← singing/sang/sung · `tooth` ← teeth |

**→ 如果直接建 `UNIQUE(lemma)` 并灌入现网数据，会插入失败 1,375 次。**

**这不是 v1 的错，而是「v1 假设词表已归一化」** —— v1 §3.1.1 要求 `word` 表存 **lemma**，词形归 `word_form` 之类机制。**但 v1 忘了给出词形映射表的设计**（见修正 2）。

**解法**：**先做 Phase 1 #5 词形聚合**，逐个决定 1,375 张卡的归属：

| #5 分组 | 数量 | 迁移动作 |
|---|---:|---|
| A 纯屈折 | 884 | **合并** → 不建 word 记录，只在 `word_form` 留映射 |
| B 有独立义 | 338 | **保留** → 建独立 word 记录（`lemma` = 它自己） |
| C 灰区 | 161 | 🟠 **待你判断**（决定这批是否建 word 记录） |

**→ 结论：Phase 1 #5 从「优化项」升级为「v1 设计的必需前置」。** 完成后的 word 表规模：
`11,917 − 884（合并）− (161 中判定合并的部分)` ≈ **10,900–11,030 条**

> ⚠️ **这也回答了此前的问题**：Phase 1 #5 的名字必须从「词族聚合」改为「**词形聚合**」—— 它做的是 **inflection 归一化**（v1 的 `UNIQUE(lemma)` 要求），不是 v1 的 **cognate 词源族**。

### 🔴 修正 2：v1 缺 `word_form` 表 —— 必须补，否则查词查不到变形

**v1 的检索路径**：`idx_word_spelling ON word (spelling)` —— 按 `spelling` 直查。

**问题**：用户划到 `received` → 查 `word.spelling = 'received'` → **查不到**（word 表里只有 `receive`）。

**v1 无法解决这个**，因为：
- `word` 表 `UNIQUE(lemma)` → 一个 lemma 只能一行
- `spelling` 是**单值字段** → 一个词只能有一个拼写

**→ v1 的设计里，「词形 → lemma」的映射没有落点。这是真实缺口。**

**✅ 补充**：把 v2 已实现的 `word_form` 表纳入 v1 设计（**它本来就是为补这个缺口而生的**）：

```sql
-- ✅ 补充表（v1 未设计，但必需）
CREATE TABLE word_form (
  form    TEXT NOT NULL,        -- 实际出现的形态：received
  lemma   TEXT NOT NULL,        -- 归一化目标：receive
  rule    TEXT NOT NULL,        -- 生成规则：past / plural / ing / ...
  in_vocab INTEGER DEFAULT 0,   -- 该 form 是否另有独立卡片（供 #5 判定用）
  word_id INTEGER,              -- → word.id
  PRIMARY KEY (form, lemma)
);
CREATE INDEX idx_form ON word_form (form);
```

**现状**：✅ **已实现 36,856 条 / 覆盖真实文本 99.5%**（Phase 1 #1）—— **可直接复用，无需重做**。

### 🔴 修正 3：`content_hash TEXT UNIQUE` 会阻断降级卡（评审阻塞 2）

**v1 原文**：
```sql
  content_hash  TEXT UNIQUE,      -- ← 全局唯一
```

**问题**：`content_hash` 全局唯一意味着**全库不能有两张内容完全相同的卡**。这有两个必然的冲突场景：

| 场景 | 说明 |
|---|---|
| **降级卡 / 极简卡** | LLM 制卡失败时的降级卡、或内容极少的短词卡 → 多个词可能生成完全相同的 `content` |
| **释义恰好相同** | 两个不同词的释义文本恰好一致（尤其短词、缩写） |

> ⚠️ **注意**：v1 §12 的「降级卡片」场景已由白哥质疑（2026-09-25）—— **「仅释义」的释义来源在词库外场景下不成立**，见 §三.5 的重新设计。
> **但 `content_hash` 的全局 UNIQUE 依然是错的**（上表两个场景与降级卡无关）。

**v1 评审报告（阻塞 2b）已明确指出此问题**，但 v2 从未落实修正。

**✅ 建议**（评审选项 A）：
```sql
  content_hash  TEXT,                          -- 去掉全局 UNIQUE
  UNIQUE (word_id)                             -- 一词一卡（v1 §1.3 原则）
  -- 或 UNIQUE (word_id, content_hash) 若未来可能一词多卡
```

> ⚠️ **另一个 v1 DDL 问题**（评审阻塞 2a）：`§8.4` 的 `ON CONFLICT (word_id)` **没有对应的 UNIQUE 约束** → 建表后该语句会报 `ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint`。
> **→ 两个问题用同一处修正解决**：给 `card.word_id` 加 `UNIQUE`。

### 🟢 补充 1：`word_id` 用 UUID 还是 INTEGER —— 受「音频命名」制约

**v1 原文用 INTEGER 自增**，但评审阻塞 3 建议改用**现网 UUID 风格**（天然稳定、无撞号、增量合并零冲突）。

**但 v1 的音频命名规则依赖整数**：
```
audio/00001_w.opus      # {word_id:05d}_w.opus
```
→ **UUID 无法 `%05d` 格式化**。

**✅ 建议（两全）**：
```sql
CREATE TABLE word (
  id            TEXT PRIMARY KEY,   -- UUID（沿用现网风格，稳定无撞号）
  sort_seq      INTEGER UNIQUE,     -- 🔑 新增：专供音频命名与分片排序
  spelling      TEXT NOT NULL,
  lemma         TEXT NOT NULL,
  ...
);
```
- **音频命名改用 `sort_seq`**：`00001_w.opus`（保持 v1 的可读性）
- **跨表引用用 `id`**（UUID，稳定）
- ⚠️ **但 `sort_seq` 一旦分配也不可变** —— 否则音频文件名全部失效

> 备选：坚持 INTEGER + id 台账（评审建议 A）—— 也可行，但需额外维护台账文件，且增量合并时更易冲突。**我倾向 UUID + sort_seq。**

### 🟢 补充 2：v1 的 `card` 表 `UNIQUE(word_id)` 与现网 14 种 `card_type` 冲突

**实测现网 english 的 card_type 分布**：

| card_type | 数量 | 判定 |
|---|---:|---|
| `vocabulary` | **11,917** | ✅ 迁移主体 |
| `narrative` / `opinion` / `informational` / `dialogue` / `poem` / `letter` / `nursery_rhyme` / `biography` / `report` / `speech` / `review` / `play` / `instruction` | **78**（合计） | 🔴 **精读课程残留 —— v2 已取消该功能（决策 1）→ 迁移时删除** |

**→ 这 78 张卡不属于 v1 的「一词一卡」模型**（它们是「一篇课文」不是「一个词」），且对应功能已被取消 → **迁移时排除**。

### 3.3 `definitions` → `card.content.sections`（结构转换，**零 LLM**）

**现网结构**（实测）：
```json
[{"pos": "[v]", "meaning": "to exist; to have a particular quality...",
  "chinese": "存在；是，成为", "example": "To be or not to be..."}]
```

**v1 目标结构**（§4.2 + v2 §3.3 的合并——**取两者之长**）：
```json
{
  "front": "be",
  "ipa": "/biː/",
  "sections": [
    {"type": "sense", "order": 1, "pos": "v",
     "en": "to exist; ...", "zh": "存在；是，成为",
     "example": "To be or not to be, that is the question."},
    {"type": "collocation", "items": [{"phrase": "let it be", "zh": "顺其自然"}]},
    {"type": "root", "text": "...", "payload": {"parts": [...]}},       ← 🆕 LLM 补
    {"type": "family", "members": [{"form": "are", "ipa": "..."}]}
  ],
  "extra": [ {"type": "sense", "order": 2, ...} ]
}
```

**转换规则（机械，可脚本完成）**：
1. `definitions[0]` → `sections[type=sense, order=1]`（**主义项**）
2. `definitions[1..]` → **`extra[]`**（**次义项降级**，对应 v1 §5.2 的「超限转 card_extra」）
3. `pos` 规范化（`[v]` → `v`；`noun` → `n`；多值拆分）
4. `example` → 并入 `sense.example`（v2 的形态，比 v1 的独立 `context` section 更省 section 位）

> ⚠️ **一个必须注意的点**：v1 的 `sections` 只有 `root`/`definition`/`context` 三种类型；
> **v2 的 `sense`/`collocation`/`family`/`extra` 更完整**。
> **建议以 v2 的结构为基础，补回 v1 的 `root`/`cognate`/`etymology` 三种类型** —— 而不是退回 v1 的三种。

### 3.4 `related_phrases` → `collocation`（需解析）

**现网格式**（实测原文）：
```
"let it be, be that as it may, be yourself（顺其自然，尽管如此，做你自己）"
"happy birthday, happy hour, happy go-lucky（生日快乐，欢乐时光，无忧无虑的）"
```

**解析规则**：
- 英文部分：`（` 之前，按 `,` 拆分 → `collocation.phrase`
- 中文部分：括号内，按 `，` 拆分 → 与英文**按序对应**
- ⚠️ **风险**：**中英条目数可能不一致**（如 3 英 3 中是对齐的，但需实测校验）→ **校验不一致的条目单独列出**

### 3.5 🔴 「降级卡片」需要重新设计（白哥质疑，2026-09-25）

**白哥质疑**：「『LLM 失败 → 降级卡片』—— **LLM 失败难道不应该详细看，重试，降级卡片是什么意思？**」

#### 先把两个场景分开 —— 它们的正确处置**完全不同**

| 场景 | 谁在等 | 正确处置 | 现状 |
|---|---|---|---|
| **批量补内容**（如本次 1,481 条） | **没人在等** | ✅ **必须重试**：指数退避 + 断点续跑 + `--retry-failed` | ✅ **已实现**（8 线程 / 429·5xx 退避 / 失败不污染数据） |
| **实时查词**（用户查词库外的词） | **用户当场在等** | 🟠 **不能只靠重试** —— 用户不会等 30 秒 | 🔴 **未设计** |

**v1 §12 的「降级卡片」属于第二类场景**（原文：「LLM 制卡失败 → 返回降级卡片（仅释义），标记可重试」）。

#### 🔴 v1 这个设计有一个逻辑漏洞：「仅释义」的释义从哪来？

用户查的是一个**词库外的词** → 它**本来就没有任何预制内容** → LLM 制卡失败了 → 那么「仅释义」的**释义从哪里来？**

v1 没有回答这个问题。可能的隐含假设（都不成立）：

| 假设 | 为什么不成立 |
|---|---|
| 「LLM 部分成功，用已生成的部分」 | 单次调用是原子的，失败就没有任何部分结果 |
| 「有本地词典兜底」 | ❌ 项目没有本地词典（正是要靠 LLM 补） |
| 「用词形映射给出近似释义」 | ❌ 词形映射只能给出 lemma，给不出释义 |

**→ 结论：在「词库外生词」场景下，「仅释义的降级卡」没有内容来源 —— 这个设计不可实现。**

#### 🔑 而且我们的场景比 v1 更严峻

| | v1 假设 | 我们的现状 |
|---|---|---|
| 词库规模 | CEFR 全量 **1.5–2 万词族** | **11,917 条** |
| 内容源 | 未明确 | **RSS 每日新闻**（VOA / BBC / 新闻） |
| 词库外生词比例 | 边缘场景 | 🔴 **会高得多** —— 新闻里专有名词、新词、时代词多 |

**→ 「词库外生词」不是边缘场景，是日常场景。降级策略必须认真设计。**

#### ✅ 建议的三层设计（替代 v1 的「仅释义降级卡」）

```
用户查词库外的词
  ↓
L1 · 先重试（3 次，指数退避，总超时 ≤ 6 秒）
  ├── 成功 → 正常展示 + 写入 generated_card_cache
  └── 失败 ↓
L2 · 展示「可用信息卡」（不是假的「仅释义」）
  ├── 明确提示：「该词暂不在词库中，详解生成失败」
  ├── 给出**真正能给的信息**：
  │    · 词形还原结果（`received` → `receive`，若命中则**直接跳转到已有卡片**）
  │    · 发音（端侧 `flutter_tts` 可即时合成，零成本）
  │    · 该词在当前句中的位置与上下文（已在手边）
  └── 按钮：「稍后重试」
L3 · 后台重试队列
  ├── 把失败的词写入队列（本地 + 服务端）
  ├── 后台（联网时）重试，成功后写入 `generated_card_cache`
  └── 用户下次查同一个词 → 命中缓存 → 秒出
```

**关键差别**：
- v1 的降级卡 = **给一个内容不完整的卡**（且内容来源不明）
- 建议的 L2 = **给「确实能给的准确信息」+ 明确说明缺什么**，**不假装有释义**
- **L3 让「失败」不是终点** —— 这才是「详细看重试」的正确落点：**重试不必让用户等**

> 💡 **L2 有一个白得的好处**：词形还原结果如果命中词表（`received` → `receive`），**根本不需要 LLM** —— 直接展示已有卡片。
> 而词库外生词的划词，**很多是词表内词的变形**（实测：词形映射表覆盖真实文本 99.5%）→ **大部分「词库外」其实是伪需求**，L2 就能解决。

### 4.2 🟢 强烈建议走 B（补新，不重做旧的）

### 4.4 🔴 统计方法勘误（2026-09-25 白哥质疑 → LLM 抽样验证）

**白哥质疑**：「词根 4,372 词 · 词源 ≤2,000 · 记忆法画像 —— **这些统计你是怎么做的？**」

**老实交代**：原报告的 4,372 是**规则法粗估** —— 纯字符串前缀/后缀匹配（50 前缀 × 40 后缀 + 长度门控），
**不是词根分析**。已做 LLM 抽样验证，结论是**我的数字不可靠且方向是低估**。

#### 验证方法
- **分层抽样 150 词**（每 CEFR 等级 30 词，`scripts/verify_root_feasibility.py`）
- LLM 判定「是否可拆出词根/词缀」，并给出拆分结果
- 成本 **¥0.106**（150 次调用，in 50,759 / out 6,663 token）

#### 🔴 结果：规则法 vs LLM

| | LLM 可拆 | LLM 不可拆 |
|---|---:|---:|
| **规则 可拆** | 42 | **6**（误判） |
| **规则 不可拆** | **26**（漏判） | 76 |

| 指标 | 值 |
|---|---:|
| 规则法**准确率**（说可拆里真的可拆） | 87.5% |
| 规则法**召回率**（真可拆里命中多少） | 🔴 **61.8%** |
| 整体一致率 | 78.7% |
| **真实可拆率（LLM）** | 🔴 **45.3%** |
| 规则法可拆率 | 32.0% |
| **推算全词表** | **LLM ≈ 5,402 词** / 规则法 ≈ 3,813 词 |

**→ 4,372 这个数字应更正为 ≈ 5,402（低估约 19%）。**

#### 🔴 规则法的两类错误（都很有说明性）

**误判（说可拆但不可拆）**：`private` · `destroy` · `anxious` · `cotton` · `acrylic` · `contaminate`
→ 共同点：**前缀/后缀形式存在，但词源上已不透明**（`private` ≠ priv+ate 的现代可分析义）

**漏判（说不可拆但可拆）**：`subway`(sub+way) · `anything`(any+thing) · `lovely`(love+-ly) · `earthquake`(earth+quake) · `wetland`(wet+land) · `visitor`(visit+-or) · `jumper`(jump+-er) · `positively`(posit+-ive+-ly)
→ 共同点：**全部是「构词法可拆」但非拉丁词根的词**（复合词 + 日耳曼派生）

#### 🔑 由此得出一个更重要的区分：**「可拆」有两类**

| 类型 | 例 | 用的记忆法 | 学习者收益 |
|---|---|---|---|
| **① 拉丁/希腊词根词缀** | `incredible`(in+cred+ible) · `exhibition`(ex+hibit+ion) · `supermarket`(super+market) | **词根词缀法** | 中高级词（B2/C1 主力） |
| **② 日耳曼复合词 / 派生词** | `subway`(sub+way) · `earthquake`(earth+quake) · `lovely`(love+-ly) · `wetland`(wet+land) | **构词法** | 初中级词（A1/A2 也有） |

**v1 §4.1 的「词根词缀」严格指类型 ①**（因为是 priority 1 的「可分解词」）。
**类型 ② 同样可拆、同样有教学价值**（`subway` = sub+way 对初学者很好记），但**不属于「词根词缀」记忆法**。

**→ 因此：`word_root` 表的 `type` 字段（`root`/`prefix`/`suffix`）不足以承载类型 ②**。
**建议增补**：`word_root_link.relation` 增加 `compound`（复合）与 `derivation`（派生）两种关系，
或对类型 ② 使用单独的 `word_compound` 表（**待白哥定 —— 见 §七 待确认 9**）。

### 4.5 词根可行性随等级**上升**（LLM 实测，替代原规则法）

**LLM 实测（每级 30 词抽样）按等级加权推算**：

| 等级 | 词表词数 | 实测可拆率 | 推算可拆词数 | （原规则法占比） |
|---|---:|---:|---:|---:|
| A1 | 1,145 | 16.7% | 191 | 9.5% |
| A2 | 1,676 | 40.0% | 670 | 21.3% |
| B1 | 3,482 | 46.7% | 1,626 | 34.7% |
| **B2** | **4,813** | 🔴 **63.3%** | **3,047** | 49.5% |
| C1 | 801 | **60.0%** | 481 | 39.6% |
| **合计** | **11,917** | **50.5%** | 🔴 **≈ 6,015** | 36.7%（→ 4,372） |

**→ 越高级的词越可拆，且真实值比规则法估计的更高：B2 有 63.3%、C1 有 60.0%。**
**→ 可拆词总量 ≈ 6,015 词（50.5%），是原估 4,372 的 1.38 倍。**

**这直接反驳了 v2 §3.4 的论证**：

> v2 原文：「原方案把词根词缀列为 priority 1。实测这是从零建设，且**英语高频词大量是日耳曼语源单音节词**（be / new / get / make / all），**根本没有拉丁词根可拆**」→ 推出「词根不值得做」

| v2 的观察 | 适用范围 | 结论 |
|---|---|---|
| 「be/new/get/make 无词根可拆」 | ✅ **仅 A1（实测 16.7% 可拆）** | 成立 |
| 「词根整体不值得做」 | ❌ **B2 有 63.3%（3,047 词）、C1 有 60.0%** | 🔴 **不成立** |

**→ 而 B2+C1 正是「学习者的主要学习内容」（占词表 47%）。**
**→ 可拆词绝对量 ≈ 6,015 个（50.5%）—— 且其中 B2/C1 占 3,528 词，正是「学习者主要学习内容」+「最需要记忆法辅助的长词」。**
**不可拆的 ≈ 5,902 词多为高频基础词（be/get/make 类）与已不透明的词，靠复现记忆。**

**→ 所以 v1 把词根列为 priority 1 是有道理的**，v2 的「从零建设所以不做」是**工程视角的成本判断，不是教学法的效果判断**。

| 🔴 **LLM 词根幻觉** | 生成错误的词根拆分（如把 `understand` 拆成 `under-` + `stand` 而忽略它是日耳曼复合词）→ **直接教错用户** | **必须小样验证**（已做：`verify_root_feasibility.py`，150 词 / ¥0.106）；**建议全量生成后人工抽查 100–200 条** |
| 🔴 **规则法统计不可靠**（已发生） | 原用规则法估「4,372 词可拆」→ LLM 实测 **≈6,015**（低估 19%；召回率仅 61.8%） | **已改用 LLM 抽样验证**；**→ 规则：「可拆性/词根」这类语义判断不能用字符串匹配代替** |
| 🟠 **`related_phrases` 解析错位** | 中英条目数不一致 → 搭配释义错配 | 解析时**校验中英条目数**，不一致的单独列出人工处理 |
| 🟠 **`UNIQUE(lemma)` 判定错误** | 把「有独立义」的词误合并 → 用户查不到该词 | 依赖 #5 的分组（**组 C 细分后仅 18+3 条待判**，见 §4.6）；**同形异义词（`bore`/`wound`）绝不可合并** |
| 🟠 **`sort_seq` 变更** | 音频文件名全部失效 | 明确规则：`sort_seq` 与 `word_id` 同为**只增不改** |
| 🟠 **降级策略未设计** | 词库外生词查不到 → 用户流失（**我们的词库外场景比 v1 严峻**：RSS 新闻） | 采用三层设计（§3.5）：重试 → 可用信息卡 → 后台重试队列 |
| 🟢 **迁移期间数据损坏** | — | **迁移在副本上做**（`data/backups/` 已有 4 个自动备份，再建一个 `before_migration_*.db`）；**逐表校验行数 + 抽样比对内容** |

**回滚**：v1 结构与现网结构**并存于不同库文件**（现网 `coevo.db` 不动，新建 `word.db`）→ **可随时回退**。
