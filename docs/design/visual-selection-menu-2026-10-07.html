CoEvo · 划词（选区操作）重构

有选区就弹菜单；
点第一项时，才分「查词」还是「翻译」

2026-10-07 v2 · 白哥指出判定点可以后移 —— 这一改连带把整套防抖删掉了。

v1 的判断是「一个词不弹菜单、多词才弹」。但它要求在划选那一刻就判定是否单词， 而那一刻恰恰是信息最不可靠的时刻：拖手柄时文本每帧都在变，只能用 300ms 防抖去猜「用户停手了没」。

白哥的改法：把判定挪到用户点了第一项之后。于是判定的输入变成稳定的文本； 更关键的是，菜单可以交给 Flutter 自己的 contextMenuBuilder 承载 —— 而它本身就是「选择完成」的准确信号（长按结束、拖手柄松手都会触发它） ⇒ 300ms 防抖这一整套机制可以删掉。

v2 · 判定后移

判定从「划选时」挪到「点第一项时」

判定的输入从每帧都在变的选区，变成已经稳定的文本。 这才是「更容易实现」的真正来源 —— 不是少写一个 if， 而是整条防抖链可以不要了。

连带后果

菜单「总是」弹（含单词）

不判定，就无法决定弹不弹菜单 ⇒ 有选区就弹。⚠️ 这会让最高频的 「划词查词」从 0 次点击 变成 1 次 —— 与白哥 2026-09-27 「点『查词』是多余的」有张力。取舍见 §4。

删掉一整套

300ms 防抖

contextMenuBuilder 是 Flutter 在选择完成时主动调用的 （_handleTouchLongPressEnd / _onAnyDragEnd 里都会走 _showToolbar()）⇒ 它准确，不必再靠「停手 300ms」去猜。 顺带修掉一个现存毛病：拖动中停顿会弹词卡。

第一项文案动态

单词「查词」· 多词「翻译」

项数不变（3 项）、宽度不变（都是 2 字）⇒ 菜单形态稳定。 用户一眼看到会做什么，不需要理解「翻译一个单词其实是查词」。

必须加回

复制

系统菜单曾被我们显式屏蔽（contextMenuBuilder 返回空）， 所以正文其实复制不了。菜单恢复时复制必须一并回来 —— 现在它由 state.copySelection() 直接提供。

1判定：它现在决定什么

v2 变化：判定不再是「弹不弹菜单」（菜单总是弹），而是「第一项叫什么、点了走哪条路」。 判定规则本身一字未改 —— 改的只是什么时候调用它。

选中内容判定理由
attention单词 → 第一项「查词」标准情形
attention.（拖手柄带进句号）单词 → 第一项「查词」剥首尾标点后再判。标点不是用户选的，是手柄的副产物
don't · e-mail · a.m.单词 → 第一项「查词」撇号 / 连字符 / 内部句点属于词（词库里含内部标点的词共 64 个）
give up多词 → 第一项「翻译」含空白 ⇒ 两个 token。⚠️ 短语想查词请缩到单个词（见 §4 末）
attention. None of this…多词 → 第一项「翻译」含空白
123 · !! · 中文多词 → 第一项「翻译」剥标点后不含字母 ⇒ 不是可查的词
判定的形式化写法（供实现对照）：
① s = trim(选中文本) → ② t = 剥掉 s 首尾所有非字母字符 → ③ 若 t 含空白 ⇒ 多词；否则若 t 只由 [A-Za-z'\-.] 组成 ⇒ 单词；否则 ⇒ 多词。

🔑 ②只用于判定。真正送去查词的仍是原始选中文本 —— 这条边界必须守住，否则会踩到 §7 那个坑。
🔑 判定只调用一次：在 contextMenuBuilder 里判一次，结果由闭包捕获给菜单项用； 🔴 不在点击时再判一遍 —— 两处判定 = 两处口径，迟早漂移。

🔴 2026-10-07 更正（动手实现时才发现）：本菜单不用粘土。
本节原写「内阴影 inset -3 -3 8 / inset 3 3 7（md 档 · 体积）」—— 这与 spec §〇 规则 2「阅读界面零粘土」 直接冲突。

用 card 底 + 一层外阴影表达层级，不加内阴影 （无「厚度」⇒ 内边距 5px → 4px）。

菜单是中性色元素（卡面白底），所以用主题级外阴影而不是朱砂外阴影。

条内边距4px无内阴影 ⇒ 不必留「厚度」
单项图标 15px + 间距 6px + 文字文字 12.5px / 500，项内 padding: 8px 12px

3位置、动画、时序

🔴 v2 重大简化：这一节大部分由 Flutter 负责 —— 但有一件必须我们自己做。 菜单挂在 contextMenuBuilder 上、由框架的 SelectionOverlay 承载。
🔴🔴 2026-10-08 更正（真机踩到白屏后回标）：原稿写「位置、翻转、夹紧都是框架行为」 —— 这句是错的。框架只做两件事：把返回值插进 Overlay + 给出锚点 （SelectableRegionState.contextMenuAnchors）； 约束放松与定位必须由调用方补 —— CustomSingleChildLayout + TextSelectionToolbarLayoutDelegate。
⚠️ 不做会怎样：Overlay 给非定位 entry 的是 BoxConstraints.tight(size) （全屏紧约束）⇒ 菜单被撑满全屏，而它的实心底 card 色盖住整屏 ⇒ 用户看到「白屏」（三项菜单会出现在屏幕中间偏左，正是这个形状）。
📌 判据：「框架负责位置」≠「框架负责约束」。

项谁负责说明
位置 / 翻转 / 夹紧我们（用框架的 delegate） 🔴 2026-10-08 更正（原写「Flutter」是错的）：框架只给锚点， 定位要自己包 CustomSingleChildLayout + TextSelectionToolbarLayoutDelegate（anchorAbove / anchorBelow 取 contextMenuAnchors.primaryAnchor / secondaryAnchor）。 该 delegate 还负责解除全屏紧约束（getConstraintsForChild → loosen()） —— 不做就白屏
🔴 拖动把手期间隐藏Flutter 拖手柄时不显示 toolbar、松手后重新显示（_onAnyDragEnd）⇒ 「菜单抖」这个问题不存在了

菜单长什么样我们 即 §2 的全部内容 —— 尺寸、材质、图标色
出现 / 消失动画我们（可先不做） 框架直接插入 widget，无动画。若要 140ms「弹一下」，得自己包一层

4🔴 一个必须先说清的代价（v2 新增）

「菜单总是弹」的代价：划词查词从 0 次点击变成 1 次。
而白哥 2026-09-27 明确去掉过一次中间步骤 —— 「中间那个点『查词』是多余的，直接弹出底部浮窗就可以了」 （原话记在 app/lib/screens/reader_screen.dart 的注释里）。

为什么这次不矛盾：那次是单功能菜单（菜单里只有一个按钮 ⇒ 纯多余一步）； 现在有 3 个功能（查词/翻译 · 划线 · 复制）⇒ 菜单带来了可发现性。
🔑 这条还和白哥「大部分功能都在长按划词重构里」直接相关： 若单词不弹菜单，用户大多数划选都看不到菜单 ⇒ 翻译 / 划线这些新功能永远没有曝光。 ⇒ 「总是弹」不只是实现更简单，它本身就是这些功能的入口。

5扩展性：项变多了怎么办

白哥说「大部分功能都在长按划词重构里」⇒ 这一步必须现在就定。 v2 更新：本菜单是 3 项（查词/翻译 · 划线 · 复制）—— 「制卡」已并入「划线」（见 visual-generic-card-2026-10-07.html v2）。

项数呈现实测宽度 / 理由
1 – 4 项（标签 ≤ 2 字）浮动胶囊（本稿） 3 × 2 字项 ≈ 225px；即使回到 4 项（≈ 297px），iPhone SE（375 − 24 边距 = 351）仍放得下
≥ 5 项，或标签更长底部面板（与词卡同族） 再宽就会溢出；底部面板可带标题、说明、分组
🔑 两种呈现共用同一个数据源（一个「选区动作」列表）—— 这是判据「同一件事的口径只能有一处权威」的直接应用： 加功能时只改列表，呈现形式由项数决定，不需要改两处。

7一个真实矛盾（实现时必须知道）

现象：长按后拖动手柄，会把相邻标点带进来（如 vertical,）。
现在这条链的走向是：vertical, → 词库查不到 → 送去在线制卡 → 服务端 validate_spelling 以 400 参数错误拒掉（它只收纯词形）。

本方案 §1 已经「剥标点」了，为什么不顺手修掉？
因为 §1 剥标点只用于判定弹不弹菜单。真正要修的是查询层： 它需要「精确命中 → 未命中再剥标点重查」的两段查。
🔴 而不能简单地在 UI 层剥完再查 —— 反例是 a.m. 和 dr.： 剥掉尾随句点会变成 a.m，而词库里存的就是带句点的原形 ⇒ 反而查不到。

⇒ 本轮不动查询层。这条缺陷单独修（要同步改 verify_word_query 的断言）， 与划词菜单解耦。

  • 本稿按三档给了值（见 CSS --sel）：墨 rgba(180,67,44,.22)、 格 .20、夜 rgba(219,126,107,.30)。 夜档更高是因为深底上低不透明度看不见。
  • 🔑 这与「痕迹」是两个概念：痕迹 = 「我查过这个词」（持久）；选区 = 「我现在选中了这段」（瞬时）。 所以选区比痕迹重（.22 vs .15），并且不受熟练度影响。
  • ⇒ 需把 selectionColor 补进 spec §2 + theme_builder.dart，并加断言。
