## 三、`sections` 是什么

### 3.1 它装的是**卡片一页的内容分段**

`card.content` 的结构：
```json
{
  "front": "belch",
  "ipa": "/bɛltʃ/",
  "entry_type": "word",
  "sections": [
    {"type": "sense", "order": 1, "pos": "verb",
     "en": "to release gas noisily from the stomach", "zh": "打嗝，嗳气",
     "example": "He belched loudly after dinner."},
    {"type": "root", "payload": {"parts": [...], "relation": "derivation"}}
  ]
}
```

**两种 `type`**：
| type | 内容 | 上限 |
|---|---|---|
| `sense` | 一个**义项**（词性 + 英文释义 + 中文 + 例句） | 最多 4 个 |
| `root` | 词根/词缀拆解（`parts` + `relation`） | 最多 1 个 |
| （`card_extra`） | **第 5 个义项起**移到独立表 `card_extra` | 无上限 |

**为什么要分段（v1 评审 §十「不要动」第 3 条）**：
> **一页容量上限（4 sections / 300 字 / 单 section 100 字）** —— 与项目既有卡片质量评估结论一致

目的是**控制单页认知负荷** —— 一次复习只看一页，不许堆砌。

### 3.2 🔴 我此前说错了：该上限**有明确数值**，不是「未落盘」

我在 `fullrun-completed-2026-09-26.md` §七 写「该上限数值文档未落盘」，**这是错的** ——
数值就在 `docs/review/english-app-simplification-plan-review-2026-09-25.md` §十 第 3 条：**4 sections / 300 字 / 单 section 100 字**。

### 3.3 🔴 实测：**191 张卡超 4 sections 上限**

当前实现是「**最多 4 个 sense + 1 个 root = 5**」，**超了**：

| sections 数 | 张数 |
|---:|---:|
| 1 | 1,553 |
| 2 | 3,868 |
| 3 | 3,913 |
| 4 | 1,998 |
| **5** | 🔴 **191** |

（`sense` 数分布：1→3,268 · 2→4,792 · 3→2,213 · **4→1,250**；其中 191 张同时又可拆 → 4+1=5）

**修法两个选项（待白哥定）**：
| 方案 | 做法 | 影响 |
|---|---|---|
| A | **可拆词最多 3 个 sense + 1 个 root**；第 4 个义项移 `card_extra` | 191 张受影响；严格遵守上限，但 **🔴 丢内容** |
| **B**（视觉核查后我建议） | 保留 4 sense，**`root` 不计入 sections**（另开字段如 `morphology`） | 需改卡片结构 + 客户端渲染；但 **✅ 零内容损失**，语义更干净 |

> ✅ **视觉核查后明确建议 B**（见 §3.5）：`root` 在真实卡片里只占 **1 行**高度，
> 而一个 `sense`（词性 + 中文 + 英文释义 + 例句）占 **6–8 行** ——
> **两者视觉量级差 6–8 倍，却各占 1 个 section 名额，这个名额分配本身就不合理。**

### 3.4 🔴 「300 字」经核查：**两个候选口径都不可用**

**先修正我上一轮的一个错误数字**：我先前写「字符数口径中位 322 / 超 300 的 55%」——
那个算法**把词根的 JSON `payload` 也算进「字数」了**。
`payload` 是**结构化数据**（不是给用户阅读的文本），**不该计入卡面字数**。

只算**卡面展示文本**（`pos` + `en` + `zh` + `example`）后的实测：

| 口径 | 中位 | >300 的张数 |
|---|---:|---:|
| 字符数（含标点空格） | **215** | **2,406 / 11,523 = 21%** |
| 空格分词数 | 42 | 0 |

（p90 = 356 · max = 662）

**再换算成「300 字能放几个义项」**（每义项字符中位 **102**）：

| 候选口径 | 300 ÷ 每义项 | 结论 |
|---|---|---|
| **字符数** | 300 / 102 = **2.9 个义项** | 🔴 **与「4 sections」直接矛盾** —— 装不下 4 个义项 |
| **中文字 + 英文词** | 300 / 23 = **13 个义项** | 🟠 **等于无约束** —— 4 个义项只用到 92 |

**两条都走不通，只有两种解释：**
1. 原文的「字」既不是「字符」也不是「阅读单位」；**或**
2. 该约束写于**设计早期**，当时卡片比现在简略（可能未含例句）——
   现在是「英文释义 + 中文 + 例句」三项，字数自然膨胀

**🟠 更本质的发现：「4 sections」与「300 字」不是同一层的东西**

| 约束 | 所属层 | 管什么 |
|---|---|---|
| **4 sections** | **数据层** | 决定怎么分表 —— 第 5 个义项起进 `card_extra` |
| **300 字** | **渲染层** | 决定排版 —— 一屏放多少读起来舒服 |

→ **把两层的东西写进同一组约束里比，才会显得互相矛盾。**
修法不是「二选一」，而是**把它们拆回各自的层**。

**🟠 待澄清的定义：「一页」指什么？**
- **不滚动的一屏**？→ 4 个义项（含例句各约 6–8 行）确实装不下，300 字才有意义
- **一次复习展示的完整内容（可滚动）**？→ 那 `sections` 数是唯一需要管的，**300 字应废弃**

### 3.5 🖼️ 视觉对比（2026-09-26 晚 · 白哥要求「能看到才能决定」）

**白哥的判断**：「这需要视觉决定，能看到才能决定」——
数字能说「有多少超限」，但回答不了「**该不该砍内容、砍哪个**」，那是视觉判断。

**做法**：取全库最长的超限卡 **`intercept`**（B1 · 558 字符 · 4 义项 + 1 词根），
按三种规则渲染真实排版并排对比（视觉稿在会话中，非文件）。

| 方案 | 渲染结果 | 判断 |
|---|---|---|
| **现状** | 5 sections（4 义项 + 1 词根），词根那段超出上限 | 确认为问题状态 |
| **A** 砍到 4 | 第 4 义项（`n.` 拦截；截获 · 含名词例句）**整段消失**，只剩一行「还有 1 个义项」 | 🔴 **丢内容** —— 名词义是常用义，不该牺牲 |
| **B** root 移出 sections | 4 个义项**全保留**；词根降为卡片底部**一条紧凑记忆法条** | ✅ **视觉上最自然** —— 词根本来就不是「义项」 |

**视觉得出的关键数据**：

| 元素 | 真实卡片里的高度 |
|---|---|
| 一个 `sense`（词性 + 中文 + 英文释义 + 例句） | **6–8 行** |
| 一个 `root`（`inter-（在…之间）+ cept（拿取）`） | **1 行** |

→ **视觉量级差 6–8 倍，却各占 1 个 section 名额 —— 名额分配本身不合理。**

**「300 字」口径的可视化**：两种候选口径分别算出「300 字只够 2.9 个义项」与
「300 字够 13 个义项」，**一个太严（与 4 sections 冲突）、一个太松（形同虚设）**，
排除这两个候选 —— 见上图。

### 3.6 结论

| 项 | 建议 |
|---|---|
| `sections` 上限 | 保持 **≤4**，但**只数 `sense`**；`root` 移出 `sections`（**方案 B**） |
| 「300 字」 | 🟠 **建议废弃该约束**（两个候选口径都不可用）；若保留，需白哥先给「一页」的定义 |
| 受影响卡 | 191 张 → **方案 B 下零内容损失**，无需移动任何义项 |
| 实现成本 | 卡片 schema 加顶层 `morphology` 字段 + 客户端渲染调整（**不改词库数据**） |

## 四、搭配：按白哥决定**不合并现网**

已确认：`load_llm_results.py` **默认**只用 LLM 的 `collocations[]`（质量高、中文齐全、无错位）；
`--merge-legacy-collocations` 开关保留但**不使用**。

**现网 `related_phrases` 的解析产物**（`collocation_parsed.json`，25,399 条）
→ **仅作对照资产留存**，不并入 `word.db`。

**理由**（记录以免重提）：
- 两者仅 **33% 重合**，但现网解析的**中文质量参差**（含错位残留、`(none common)` 占位符等）
- LLM 的搭配**中文齐全**、无错位、与卡片其他内容同源（同一契约产出）
- 少一个数据源 = 少一处不一致来源
