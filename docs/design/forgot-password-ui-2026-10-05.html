一整体流程

全程在 App 内完成（不跳浏览器、不需要额外部署网页）—— 这正是选「6 位码」而非「邮件链接」的原因。

① 输入邮箱› ② 收 6 位码› ③ 输码 + 设新密码› ④ 完成 · 自动登录
步用户做什么后端做什么失败态
①填注册邮箱 → 点「发送验证码」 POST /api/auth/forgot-password：生成 6 位码 → 写表 → 发信。 无论邮箱是否存在都返回成功（防枚举，见 §四） 格式错 / 限流（60 秒内重复点）
②去邮箱看码（10 分钟内有效） —（邮件已发） 没收到 → 倒计时结束后「重新发送」
③填 6 位码 + 新密码（填两遍） POST /api/auth/reset-password：验码 → 改 hash → 失效全部会话 → 返回新 token 码错 / 码过期 / 尝试次数用尽 / 密码不合规
④直接进入 App （同③一并返回） —

四文案与错误态（完整清单）

所有文案一处定义（后端返回 → 前端原样显示），与 claim_dialog 的 「同一位置、同一式样」取舍一致 —— 分两处显示会让用户以为遇到两个问题。

场景文案说明
邮箱格式错邮箱格式不正确前端即时拦（与后端 is_valid_email 同一判据）
发送成功若该邮箱已注册，验证码已发送🔴 刻意含糊——防「哪些邮箱注册过」被枚举
60 秒内重复发送发送太频繁，请稍后再试后端限流（按邮箱）
码错验证码不正确不区分「错」与「不存在」
码过期验证码已过期，请重新获取>10 分钟
试太多次尝试次数过多，请重新获取验证码同一码错 5 次即作废
密码不合规密码至少6位含英文+数字与注册/改密码同一句
发信失败验证码发送失败，请稍后再试🔴 不暴露「服务未配置」等技术细节
⚠️ 一个必须如实说明的取舍：「含糊提示」的两难
含糊（推荐）→ 防枚举，但用户打错邮箱时会一直等一封不会来的邮件。
明说「该邮箱未注册」→ 体验更好，但把「哪些邮箱注册过」变成了可探测的。
🔑 本项目的现实：个人项目、用户量小、无定向攻击动机 ⇒ 两种都可接受。
✅ 本稿按含糊画（业界标准做法）；若白哥想换，改的只是一句文案 + 一个分支。

五后端设计（我已核实到可直接实施）

以下全部实测过（读代码 + 查官方 API 文档），不是设想。

项实测结论影响
新依赖零 —— reqwest · hmac 0.12 · sha2 · hex · base64 全在 Cargo.toml 风险低
签名实现🔑 tencent_asr.rs 已有完整的 TC3-HMAC-SHA256 实现 （hmac_sha256 / format_timestamp_date） 抽出公共件给 ASR + SES 共用，不复制第二份
SES 接口Host ses.tencentcloudapi.com · Service ses · Action SendEmail · Version 2020-10-02 · Region ap-guangzhou 与 ASR 同一套签名，只换 service/host/action
必填参数FromEmailAddress · Destination · Subject · Template{TemplateID, TemplateData}
TemplateData = JSON 字符串（≤800 字节，不能是 HTML）		 用模板发信（腾讯云默认只允许模板发信）
可选但有价值ReplyToAddresses → 填 support@keyievolution.fun 用户直接回信能到我们能收的邮箱（否则回复会失败）
密钥命名ASR 用 TENCENT_SECRET_ID / TENCENT_SECRET_KEY； SES 指引里写的是 TENCENT_SES_SECRET_ID / ..._KEY 🔴 两套名字必须定一个（见 §六 待定 ③）

5.1 新表 password_reset

列类型用途
idTEXT PKUUID
user_idTEXT NOT NULL指向 users(id)
code_hashTEXT NOT NULL🔴 不存明文码（bcrypt，复用已有 hash_password）
attemptsINTEGER DEFAULT 0错 5 次作废
expires_atINTEGER NOT NULL签发 +600 秒
used_atINTEGER用过后非空 ⇒ 不可复用
created_atINTEGER NOT NULL限流用（同邮箱 60 秒一条）
🔑 为什么 6 位数字码可以安全地用 bcrypt 存： 码的空间是 106；bcrypt cost=10 每次数 ~100ms ⇒ 离线穷举需 ~27 小时。 而码只活 10 分钟且错 5 次即废 ⇒ 拿到库也来不及。
🔴 表名与语义残留：本次是新增表，不涉及旧概念残留（与「删功能要清残留」无关）。

5.2 两个端点

端点入参行为出参
POST /api/auth/forgot-password email 查用户 → 生成 6 位码 → bcrypt 存 → SES 发信。邮箱不存在时也返回 200（防枚举），只是不发信 { ok: true, message }
POST /api/auth/reset-password email · code · new_password 取最新未用未过期码 → 验码 → 改 hash → 标记已用 → 删该用户全部 token → 建新 token 与 login 同形：{ user_id, token, email }（自动登录）
🔑 为什么「重置后删全部 token」而不是「保留当前」：重置密码的前提是 当前用户不在登录态（他登不进来才来重置）⇒ 没有「当前会话」需要保留。 这与「修改密码」相反（那里用户是登录的）—— 两处语义不同，不能共用同一段代码。
