# 腾讯云邮件推送（SES）开通指引 —— 给白哥的逐步操作表

> **用途**：找回密码需要「发信能力」；本指引带你开通腾讯云 SES（**国内、数据不出境**）
> **我的对应工作**：拿到 API 密钥后，我写后端发信 + 6 位码校验 + 前端页
> **预计你的耗时**：40–70 分钟（若腾讯云账号已实名，约 30 分钟）
> 🔴 **含等待**：域名验证 5 分钟–2 小时 · **邮件模板审核 1 个工作日**

## 〇、🔴 先说三个坑（我已替你查过现状，照做可避开）

### 现状实测（我刚跑的 DNS 查询）

| 项 | 实测值 |
|---|---|
| **NS** | `weston.ns.cloudflare.com` / `aitana.ns.cloudflare.com` ⇒ 🔴 **DNS 托管在 Cloudflare** |
| **MX** | 3 条 `route1/2/3.mx.cloudflare.net`（= **Email Routing，`support@` 的收信路由**）|
| **SPF** | `v=spf1 include:_spf.mx.cloudflare.net ~all` |

### 坑 ①：DNS 记录加在 **Cloudflare**，不是腾讯云

腾讯云控制台会说「若域名在腾讯云则自动配置，否则**请自行配置**」——
我们的域名在 Cloudflare ⇒ 每条记录都**手工加到 Cloudflare**。
⚠️ 别去腾讯云找「一键配置」（找不到是对的，不是出错）。

### 坑 ②：🔴 用**子域名**发信，别用主域名（否则 `support@` 会收不到信）

腾讯云 SES 要求发信域名配 **MX** 记录（用于接收退信）。而**主域名的 MX 已被
Email Routing 占用**（`support@keyievolution.fun` 靠它收信 —— 那是**隐私政策里公示的联系邮箱**）。

⇒ 若把 SES 的 MX 加在主域名上，会**覆盖/冲突**，后果是
**用户给 `support@` 发邮件你收不到**（而这正是「联系工作人员」的通道）。

✅ **正解**：发信域名填 **`mail.keyievolution.fun`**（子域名）。
所有记录都加在这个子域名上 ⇒ **主域名的 MX 与 SPF 一个字都不用动**。
（腾讯云官方文档的示例也正是子域名：`mail.qcloud.com`。）

> 📌 代价：发件人形如 `noreply@mail.keyievolution.fun`（长一点）。
> 换来的是**零冲突、可随时撤销**，很值。

### 坑 ③：SPF 一个域名**只能有一条**

若你后来改主意想用主域名发信，**不能新增一条 SPF**，必须把腾讯云的 `include` **合并进现有那条**：

```
v=spf1 include:_spf.mx.cloudflare.net include:<腾讯云给的 spf 域> ~all
```

两条 SPF 并存 = 收件方按 `permerror` 处理 = **邮件全部进垃圾箱或拒收**。

## 一、开通步骤（按顺序）

### 1.1 实名认证（若已实名可跳过）

| 项 | 内容 |
|---|---|
| 位置 | 腾讯云控制台 → 右上角头像 → **账号信息** → 实名认证 |
| 主体 | **个人**即可（SES 支持个人实名）|
| 产出 | 状态显示「已实名」|

⚠️ **时间敏感**：腾讯云 **2026-03-02 起，新开通的个人实名用户不支持 SMTP 发信**，
只能走 **API**（或控制台）。⇒ 截图里找不到「SMTP 密码」是**正常的**，别到处找。
我们**本来就用 API**（后端 `reqwest` 已在），无影响 ✅

### 1.2 开通邮件推送

| 项 | 内容 |
|---|---|
| 位置 | 搜索「邮件推送」→ 进入控制台 → **开通服务** |
| 产出 | 能进入「发信域名」页面 |

### 1.3 新建发信域名 ⭐ 关键一步

| 项 | 填 |
|---|---|
| 域名 | **`mail.keyievolution.fun`** ← 子域名，见坑 ② |
| 操作 | 提交 → 点「验证」→ 它会给出**要配置的 DNS 记录列表** |

⚠️ **记录值以腾讯云控制台实际显示为准** —— 我**不预先编造**（编了你也对不上）。
把列表**截图或抄给我**，我帮你逐条核对「加到 Cloudflare 的哪一项、有没有跟现有记录打架」。

预期会有（**名称与值都以它显示的为准**）：

| 类型 | 作用 | 加在哪 |
|---|---|---|
| `TXT` | **所有权验证** | Cloudflare → DNS → Add record |
| `MX` | 接收退信 | 同上（加在 `mail` 子域名）|
| `TXT` | **SPF** | 同上 |
| `TXT` / `CNAME` | **DKIM** | 同上（通常是 `xxx._domainkey.mail`）|
| `TXT` | **DMARC**（可选但建议）| 同上（`_dmarc.mail`）|

🔴 **Cloudflare 的两个注意点**：
1. Cloudflare 默认会给记录开**代理（橙色云朵）**⇒ **MX / TXT 记录必须设为「DNS only」（灰色云朵）**，
   否则发信验证不通过。（Cloudflare 对 MX/TXT 通常自动不代理，但要**检查一眼**。）
2. 添加完等 **5 分钟–2 小时**（腾讯云原话），再回控制台点「验证」。
   ⚠️ **别反复点** —— 生效前点多少次都是「未通过」，不是出错。

### 1.4 新建发信地址

| 项 | 填 |
|---|---|
| 发信域名 | `mail.keyievolution.fun`（选上一步验证通过的）|
| 邮箱前缀 | **`noreply`** |
| 发件人别名 | **`CoEvo`** |
| 产出 | 发信地址 = `noreply@mail.keyievolution.fun` |

### 1.5 新建邮件模板 🔴 **这一步要等 1 个工作日**

| 项 | 内容 |
|---|---|
| 位置 | 邮件推送控制台 → **发信模板** → 新建 |
| 模板类型 | **HTML 富文本** |
| 邮件摘要 | 通知类 |
| 正文 | 👉 **我已经写好了，见 §三，直接复制** |

🔴 **硬性事实**：腾讯云「**仅支持使用模板发送邮件**」，且模板**提交后需审核**：
- 工作日提交 → 通常 **1 个工作日内**完成
- 休息日提交 → 顺延到下一个工作日

⇒ **今天（10-05 周一）提交，最快明天（10-06 周二）可用。**
这是找回密码**无法当天上线**的唯一原因（其余都是我这边写代码的事）。

### 1.6 生成 API 密钥 🔑

🔴 **建议用子账号 + 最小权限**（不要用主账号密钥）：

| 项 | 内容 |
|---|---|
| 位置 | 访问管理 CAM → **用户 → 用户列表 → 新建用户** |
| 类型 | **自定义创建** → 仅编程访问（不要控制台登录）|
| 权限 | 只勾 **`QcloudSESFullAccess`**（或更细的 `ses:SendEmail`）|
| 产出 | **SecretId** + **SecretKey** |

**为什么不用主账号密钥**：主账号密钥能控制**整个腾讯云账号**（含域名、支付、所有服务）。
一旦服务器被入侵导致密钥泄露，损失是整个账号；子账号密钥**只能发邮件**，泄露面小得多。

> ✅ 交付给我时：**别贴到聊天里**（按你的隐私铁律）。我用一条命令把它写进服务器环境变量，
> 命令里用占位符，你在我给的文件里填真值即可。方案见 §四。


> 🎨 颜色 `#B4432C` = 项目品牌色「朱砂」（视觉规格 `design-system-spec`）。

### 为什么这样写（逐条对齐腾讯云的模板规范）

| 腾讯云规范 | 我们怎么满足 |
|---|---|
| 「模板必须体现实际业务」 | 明确写「重置 CoEvo 账号密码」✅ |
| 「变量与文字比例不超过 1:5」 | 只有 `{{code}}` 一个变量，比例极低 ✅ |
| 🔴 「禁止出现加 QQ / 加微信 / **加群** 等内容」| 邮件里**没有任何群/二维码** ✅<br>⚠️ 注意：App 的「关于」页有共读群入口，但**邮件模板里绝不能提** |
| 「URL 必须确定」| 我们把链接换成**6 位码**⇒ 连 URL 都没有 ✅ |
| 「触发类邮件无字数要求」| 属用户操作触发（触发类）✅ |

### 🔑 为什么用「6 位码」而不是「邮件链接」

| | 6 位码 | 邮件链接 |
|---|---|---|
| 体验 | App 内闭环，不用跳浏览器 | 要跳浏览器再跳回 App |
| 部署 | **零额外部署** | 要再部署一个重置网页 |
| 模板审核 | 无 URL ⇒ 少一个审核风险点 | 需固定 URL |
| 安全性 | 10 分钟有效 + 限次 | 同理 |

⇒ 你已选 6 位码 ✅

## 四、密钥怎么安全地给我（等你到这一步再做）

**不要**贴在对话里。我届时会给你一条命令，形如：

```bash
# 在服务器上执行（把 <...> 换成真值）
ssh -i ~/.ssh/coevo_key ubuntu@<服务器IP>
sudo tee -a /etc/coevo/backend.env >/dev/null <<'EOF'
TENCENT_SES_SECRET_ID=<你的 SecretId>
TENCENT_SES_SECRET_KEY=<你的 SecretKey>
TENCENT_SES_FROM=noreply@mail.keyievolution.fun
TENCENT_SES_TEMPLATE_ID=<模板审核通过后的 ID>
TENCENT_SES_REGION=ap-guangzhou
EOF
```

> ⚠️ 这条命令**必须抄项目文档**（判据：给用户跑的命令须抄文档，别手写）——
> 我在实施那一步会从 `maintenance-spec.md` 抄准确的服务名与路径再给你，**现在不写死**。

🔑 密钥**只进服务器环境变量**，**不进仓库**。实施时我会加一条断言：
**仓库里不得出现 `TENCENT_SES_SECRET` 的真值**（防误提交）。

## 六、可能的疑问（预判）

| 疑问 | 答 |
|---|---|
| 为什么不用 QQ 邮箱 SMTP（vibedollar 那个 mailproxy）？ | 它 **发件人会被强制成 QQ 邮箱**（QQ SMTP 要求 From = 授权账号）⇒ 用户会收到「来自 QQ 邮箱」的密码邮件，不可信。且个人邮箱有发信量限制。 |
| 为什么不用 Resend / SendGrid（更简单）？ | 🔴 **数据出境** —— 用户邮箱地址出境属个人信息出境（需标准合同/安全评估，个人不可行）。与项目已否决的「境外验单/境外广告」同一判据。 |
| 腾讯云收费吗？ | 邮件推送按量计费，有免费额度；找回密码的用量**极小**（新域名单日上限 500 封，完全够）。具体价格以控制台为准。 |
| 会不会影响现有 `support@` 收信？ | **按 §〇 坑② 用子域名发信，就不会**（主域名 MX/SPF 一个字不动）。 |
