### 坑 ①：DNS 记录加在 **Cloudflare**，不是腾讯云

腾讯云控制台会说「若域名在腾讯云则自动配置，否则**请自行配置**」——
我们的域名在 Cloudflare ⇒ 每条记录都**手工加到 Cloudflare**。
⚠️ 别去腾讯云找「一键配置」（找不到是对的，不是出错）。

### 坑 ②：🔴 用**子域名**发信，别用主域名（否则 `support@` 会收不到信）

腾讯云 SES 要求发信域名配 **MX** 记录（用于接收退信）。而**主域名的 MX 已被
Email Routing 占用**（`support@keyievolution.fun` 靠它收信 —— 那是**隐私政策里公示的联系邮箱**）。

⇒ 若把 SES 的 MX 加在主域名上，会**覆盖/冲突**，后果是
**用户给 `support@` 发邮件你收不到**（而这正是「联系工作人员」的通道）。

✅ **正解**：发信域名填 **`mail.keyievolution.fun`**（子域名）。
所有记录都加在这个子域名上 ⇒ **主域名的 MX 与 SPF 一个字都不用动**。
（腾讯云官方文档的示例也正是子域名：`mail.qcloud.com`。）

> 📌 代价：发件人形如 `noreply@mail.keyievolution.fun`（长一点）。
> 换来的是**零冲突、可随时撤销**，很值。

### 坑 ③：SPF 一个域名**只能有一条**

若你后来改主意想用主域名发信，**不能新增一条 SPF**，必须把腾讯云的 `include` **合并进现有那条**：

```
v=spf1 include:_spf.mx.cloudflare.net include:<腾讯云给的 spf 域> ~all
```

两条 SPF 并存 = 收件方按 `permerror` 处理 = **邮件全部进垃圾箱或拒收**。

### 🔴🔴 坑 0（2026-10-05 实测踩到）：**只加一条 A 记录 ≠ 配置发信域名**

白哥先在 Cloudflare 加了一条 **A 记录**（`mail` → `<VPS_IP>`，即 VPS），
以为「把子域名指向服务器」就是配置完成。**但腾讯云 SES 要的不是 A 记录。**

实测（`scripts/check_mail_dns.py`）当时的状态：

| 类型 | 实测 | 腾讯云要吗 |
|---|---|---|
| **A**（→ `<VPS_IP>`） | ✅ 有 | ❌ **不要**（这条是多余的）|
| **MX** | NODATA（缺） | ✅ 要 |
| **TXT/SPF** | NODATA（缺） | ✅ 要 |
| **TXT 或 CNAME/DKIM** | 缺 | ✅ 要 |
| **TXT/DMARC** | NXDOMAIN（缺） | ✅ 要 |

⇒ 后果：**四项验证会全部失败**，而控制台只显示「未通过」，看不出是「缺」还是「填错」。

📌 **判据**：SES 的「发信域名」是一个**邮件身份**（靠 MX/SPF/DKIM/DMARC 声明），
**不是一个网站**（靠 A/CNAME 指服务器）。两者名字都叫「配置域名」，但记录类型完全不同。
🔑 **先确认「要的是哪几类记录」，再动手** —— 别凭「配置域名 = 加 A 记录」的直觉。

**那条 A 记录要不要删？**
- 建议**删掉**：SES 不需要它；且它让 `mail.keyievolution.fun` 指向 VPS，
  访问时可能命中 nginx 的**默认站点**（暴露一个本不该存在的入口）。
- 不删也**不影响发信**（A 记录与这四项互不干扰），只是多余 + 多一个暴露面。

#### 🔴 抄成 Cloudflare 的填法（逐条照抄）

| # | Type | **Name** | **Value** | Priority | Proxy |
|---|---|---|---|---|---|
| 1 | `MX` | `mail` | `mxbiz1.qq.com` | **`10`** 🔴必填 | 灰色（MX 不给开代理）|
| 2 | `TXT` | `mail` | `v=spf1 include:qcloudmail.com ~all` | — 无此字段 | 灰色 |
| 3 | `TXT` | `_dmarc.mail` | `v=DMARC1; p=none` | — 无此字段 | 灰色 |
| 4 | `TXT` | `qcloudhk2048._domainkey.mail` | **（把腾讯云那串完整粘进去）** | — 无此字段 | 灰色 |

> 🔴 **`Priority` 只有第 1 条（MX）会出现，且必填**（不填 Cloudflare 不让保存）⇒ **填 `10`**。
> 📌 为什么是 10：它是「这条 MX 的优先级」，**只有多条 MX 时才有比较意义**。
> 我们**只有一条** MX ⇒ 填什么都能工作，**`10` 是最常规的写法**（腾讯云官方文档的示例也是 10）。
> ⚠️ 第 2/3/4 条是 TXT，Cloudflare 的表单**不会**出现 Priority 字段
> —— 若你在配 TXT 时也看到了，那是界面版本差异，填 `0` 即可（对 TXT 无意义）。

**三条要点**：

1. 🔑 **Name 一律填相对名**（不带 `.keyievolution.fun`）——
   填 `mail`、`_dmarc.mail`、`qcloudhk2048._domainkey.mail` 即可，Cloudflare 自动补域名。
2. ✅ **DKIM 是 `TXT` 而不是 `CNAME`** ⇒ 我此前反复警告的
   「CNAME 默认开代理（橙色云朵）⇒ 验证永远不过」这个坑**不存在**了
   （TXT 记录 Cloudflare 不给开代理）。🎉 少一个坑。
3. ⚠️ **MX 记录值末尾的点**：腾讯云给的是 `mxbiz1.qq.com.`（带点）。
   在 Cloudflare 里填 **`mxbiz1.qq.com`**（不带点）即可 —— 它自己会按 FQDN 处理。
   少数 DNS 商要求带点，Cloudflare 不带更稳。

腾讯云界面上那句是**针对「发信域名选的是主域名」**的场景：

**我们不适用**：

✅ 而且它与主域名的 MX（Cloudflare Email Routing）**互不干扰** ——
邮件路由按域名归属，`@mail.keyievolution.fun` 的退信走腾讯，
`support@keyievolution.fun` 照旧走 Cloudflare。**主域名一个字都不用动。**

> 📌 将来若想给 `mail.` 子域名也配 Email Routing 收信，会与这条 MX 冲突 ——
> 那时再取舍（当前没有这个需求）。

### 🔴🔴 Cloudflare 的填写规则（这是最容易填错的地方）

| # | 规则 | 说明 |
|---|---|---|
| 1 | **Name 填「相对名」，不要填完整域名** | Cloudflare 会**自动补上** `keyievolution.fun`。<br>填 `mail` → 实际是 `mail.keyievolution.fun` ✅<br>❌ 若填 `mail.keyievolution.fun` → 会变成 `mail.keyievolution.fun.keyievolution.fun` |
| 2 | 🔴 **代理状态必须「已关闭」**（灰色云朵 ☁️ / DNS only） | 记录列表右侧那个云朵图标，**点一下**要在**灰色**状态。<br>⚠️ **TXT / MX 记录 Cloudflare 不给开代理**（自动灰）—— 但 **CNAME 默认是橙色！**<br>⇒ **如果 DKIM 给的是 CNAME，务必手动点成灰色**，否则发信验证永远不过。 |
| 3 | **TTL 用默认（Auto）** | 不用改。 |
| 4 | 🔴 **只在 `mail` 子域名上加，绝不碰主域名** | 主域名现有 MX（3 条 cloudflare route）与 SPF **一个字都不改**（见 §〇 坑②）。 |

### 🔴 为什么这套配置能通过 DMARC（不是「照着填就行」）

DMARC 要求 **SPF 或 DKIM 至少一项与 `From` 域名「对齐」**。
我们发信是 `noreply@mail.keyievolution.fun` ⇒ 对齐的是 **`mail.keyievolution.fun`**：

| 检查项 | 配在哪 | 对齐吗 |
|---|---|---|
| SPF | `mail.keyievolution.fun` 的 TXT | ✅ 与 From 域名**完全相同** |
| DKIM | `xxxx._domainkey.mail.keyievolution.fun` | ✅ 签名域 = `mail.keyievolution.fun` |
| DMARC | `_dmarc.mail.keyievolution.fun` | ✅ 自己声明自己的策略 |

⇒ 这套是**自洽**的。
⚠️ **反例（别这么做）**：若从 `mail.` 子域名发信，却把 SPF/DKIM 配在主域名上，
DMARC 会因**不对齐**而失败 ⇒ 邮件大批进垃圾箱。这正是「用子域名发信」必须
**整套记录都跟着子域名走**的原因（不是可选项）。

### 1.7 🔴 策略编辑器的「条件（Condition）」**一个都不勾**（2026-10-07）

白哥在可视化编辑器里问到「选择条件键(Condition)」怎么选 —— 答案：

| 项 | 选什么 |
|---|---|
| 条件键（`resource_tag` / `request_tag`）| ❌ **都不勾** |
| 条件运算符（`for_any_value` / `string_equal` / `for_all_value`）| 不适用（留空）|
| 关联资源选项 | ❌ 不勾 |
| 「是否授予不支持标签的接口 `"resource": "*"` 权限」| ❌ 不勾 |

#### 为什么不勾

1. **我们要的是「Action 级」最小权限，与标签无关** ——
   目标是「这对密钥**只能调 `ses:SendEmail`**」，靠 **Action** 限制即可，
   不需要再叠一层标签条件。
2. 🔴 **加了标签条件反而会让发信失败**：
   - 腾讯云原文（策略生成器界面上就写着）：
     「组（`string_equal`）……**此条件键不支持列表类接口，列表将无法访问**」
   - 更实际的：**发信模板 / 发信域名如果没绑那个标签** ⇒ 请求不匹配 ⇒ **直接拒**
   - 而拒信的报错**不会指向「标签没打」** ⇒ 排查很绕
3. **收益为零**：标签级授权是为了「只能操作带某标签的**一批**资源」——
   我们只有**一个**用途（发验证码），没有「一批资源」要区分。

#### ✅ 更省事的做法：别用可视化勾选，直接粘 JSON

控制台 → 访问管理 → 策略 → 新建自定义策略 → **按策略语法创建** → 空白模板：

```json
{
    "version": "2.0",
    "statement": [
        {
            "effect": "allow",
            "action": [
                "ses:SendEmail"
            ],
            "resource": [
                "*"
            ]
        }
    ]
}
```

🔑 `resource` 用 `["*"]` —— SES 的发送类接口是**操作级**授权
（官方授权粒度表里 `BatchSendEmail` 等即标为「操作级 / `*`」），
限死具体资源反而会被判「不在授权范围」⇒ 无权限。

📌 判据：**「最小权限」= 只给到「这个用途需要的那一个动作」** ——
不是「给一整个服务、再用条件筛掉一部分」。
⚠️ 与本项目既有做法一致：`TENCENT_SES_*` 与 ASR 的 `TENCENT_*` **故意不共用**同一对密钥。

它描述的是**外部资源的实际位置**，只有控制台知道，代码不可能猜对。

**症状**：配好密钥、重启、调用接口 → HTTP 200 但 body 是
`{"error":"验证码发送失败，请稍后再试"}`，日志里是：

```
ses API error FailedOperation.SendEmailErr: 操作失败。
您的发送遇到问题，请检查Region参数是否指定准确，若Region参数无误，请联系腾讯云提交工单沟通原因并解决。
```

⚠️ 这个错误码**极其笼统** —— region 不对 / 模板未过审 / 域名未验证 都可能报它，
而 Message 只会让你「检查 Region」。**它不指向真实原因。**

**定位方法（只读，不改服务器）**：用同一对密钥对候选 region 各发一次，看哪个成功。
实测：

| region | 结果 |
|---|---|
| `ap-guangzhou` | 🔴 `FailedOperation.SendEmailErr` |
| `ap-hongkong` | ✅ 成功（返回 `MessageId`）|
| 其他 6 个（sh/bj/nj/cd/sg/tokyo）| `UnsupportedRegion` ⇒ **SES 只覆盖广州与香港** |

⇒ **靠实测二分，比读文档猜快**。

**若报 `FailedOperation.IncorrectSender`**（发件人格式不对）：
把 `TENCENT_SES_FROM` 改成**只留邮箱**（`noreply@mail.keyievolution.fun`）再试 ——

| ④ 发信本身 | 提交后失败 | `SendEmail` 的 `Error.Code`（附「错误码 → 人话」表）|

🔑 **价值**：把「收不到验证码」这个**笼统现象拆成四个可判定的检查项** ——
比在 App 里点「忘记密码」然后看不出所以然强得多。默认**不发信**（要显式 `--send`）。

✅ **签名链路已用「假密钥」验证过**：拿假密钥跑会返回 `AuthFailure.SecretIdNotFound`
（而**不是** `SignatureFailure`）⇒ 说明网络与 TC3 签名都通，只差真凭证。
📌 顺带记住这个方法论：**`SignatureFailure` vs `SecretIdNotFound` 是两条不同路径** ——
前者 = 签名算错；后者 = 签名对了、凭证无效。

## 七、💰 要花钱吗？（2026-10-05 查官网核实）

> **口语结论：不用。以我们的用量，基本是零成本。**
> 一手来源：腾讯云**国内站**官方价格页
> <https://cloud.tencent.com/document/buy-guide/1288/47930>（已核对，非二手）

### 7.1 计费方式

| 项 | 官方原文 | 我们要不要 |
|---|---|---|
| **按量付费** | 「日结后付费…单价为 **0.0019 元/封**」 | ✅ 默认方式，够用 |
| **免费额度** | 「每个腾讯云账号均享有 **1000 封**的免费发送额度，**不限有效期，用完为止**，超过免费额度的发送将会转日结后付费」 | ✅ 我们会先吃掉这 1000 封 |
| **独立 IP**（增值） | 「**900 元/个/月**」·「月结后付费」· 开通时还会**冻结**一个月费用 | ❌ **不要开**（新项目用量小，共享 IP 足够） |
| **资源包**（预付） | 官网国际站示例：60 万封起（约 144 USD / 6 个月） | ❌ **不要买**（我们是「几十封」量级，买包纯浪费） |

### 7.2 🔴 免费额度是「**总共** 1000 封」，不是「**每天** 1000 封」

这一点**特别容易搞错**，因为网上说法不一致：

| 来源 | 说法 | 可信度 |
|---|---|---|
| ✅ **腾讯云官网**（上面那条链接） | 「**1000 封**…**不限有效期，用完为止**」⇒ **总** 1000 封 | 🟢 一手 |
| ❌ 某授权代理商页面 | 「**每天** 1000 封免费…每天 1000 封约等于每月 3 万封」 | 🔴 **与官网不符** |

📌 判据：**计费/额度这类数字只认官网** —— 代理商页面的「每天」说法差 30 倍
（1000 vs 30000），按它做容量规划会出错。
（同族：本项目的「**引用要复制，不要凭印象写**」。）

### 7.3 我们的实际用量（算给你看）

「忘记密码」每用一次 = **1 封**。而且：
- 只有**忘记密码**才发信（登录/注册/日常使用**都不发**）
- 同一个邮箱 **60 秒**才能申请一次（后端限流）
- 一个用户一年能忘几次密码？撑死 2–3 次

| 场景 | 用量 | 花费 |
|---|---|---|
| 前 1000 次重置 | 1000 封 | **¥0**（免费额度） |
| 第 1001 次起 | 每封 | **0.0019 元** ⇒ 1 万封 = **19 元** |

⇒ **1000 次密码重置 = 免费**。等你要发第 1001 封时，说明已经有相当的用户规模了，
那时 0.0019 元/封 也完全可以忽略（1 万封 19 元）。

### 7.4 ⚠️ 「冻结金额」这一条要分清是冻结谁

腾讯云有**账号冻结**机制（官方《账户冻结说明》原文）：

> 开通按量计费（后付费）资源时，会冻结您账户上的部分金额（该服务 **1 个计费周期**的费用 × 购买数量），
> 代金券不可抵扣冻结费用，**余额小于冻结费用无法开通**。

听上去要预充值 —— 但**要分清冻结的是哪一项**。SES 官方价格页**只**写了一处冻结：

| 开通什么 | 会冻结吗（官方原文） | 结论 |
|---|---|---|
| **基础按量付费（邮件推送本身）** | 价格页**未提及**冻结 | 按通用规则算 = 「**1 个计费周期的费用**」；SES 是**日结**，而免费额度内当日费用 = **0** ⇒ 冻结 **0** ⇒ **不需要预充值** |
| 🔴 **独立 IP 增值服务** | 「开通【独立 IP 增值服务】时，平台会冻结您账户**一个月的**独立 IP 费用（**余额小于冻结费用则无法开通**）」 | ⇒ **900 元/月**，会**冻结一个月** ⇒ ⛔ **别开它** |

📌 **结论**：开通**基础服务**应当不需要预充值；**只要不点「独立 IP」，就不会遇到 900 元冻结**。

⚠️ **如实标注**：我没有腾讯云个人账号可开通、**没有实测过这个界面**，
所以「基础服务不需冻结」是**按官方规则推断**的，不是实测。
若控制台在你开通时要求余额，按它提示做即可（金额很小）——
这也与 §6 既有的「核实边界」原则一致：**推断与实测要分开写**。

### 7.5 🔴 一个我主动发现的风险：欠费是**账号级**的

官方《按量计费说明》原文：

> 账户欠费时…**您名下的所有后付费资源**都将进入欠费保护期

⚠️ 也就是说：**SES 欠费 ≠ 只有 SES 停**，而是**整个账号**下的后付费资源受影响。
而你的腾讯云账号上**还跑着记忆之书的 VPS**（以及 vibedollar 的资源）。

**实际风险有多大？**（算一遍，别吓自己）
1. 免费额度 1000 封内**根本不产生账单** ⇒ 谈不上欠费
2. 超出后 0.0019 元/封 —— 要把余额花成负数，得先发很多封
3. 即使余额不足，还有「**短信通知 → 24 小时内充值则不暂停**」的缓冲

⇒ **风险低**。但既然代价是「可能的账号级停服」，成本只是「放点余额」，那答案很清楚：

| ✅ 建议 | 说明 |
|---|---|
| 开通后**留 10–50 元余额** | 10 元 ≈ 5,263 封（除免费额度外）；足够撑到你有用户规模 |
| 免费额度用满**之前**不会有任何扣费 | 你可以先在控制台「费用中心」看实际用量 |
| ⛔ **不要**为了「省事」去开独立 IP | 那是 900 元/月 + 冻结一个月，我们完全不需要 |

🔑 判据应用：这属于项目既有的「**归零型 vs 罚款型**」——
「账号级停服」偏向**归零型**（可能连带影响生产 VPS），
⇒ 对归零型风险**用低成本手段主动控制**（留点余额），而不是靠「概率低」容忍。

### 7.6 一句话

> **1000 封免费 + 之后 0.0019 元/封 ⇒ 对记忆之书这种用量，等于免费。**
> **不需要**买资源包、**不需要**开独立 IP；开通前**不需要预充值**，
> 但建议开通后**留 10–50 元余额**（防账号级欠费牵连同账号的 VPS）。
