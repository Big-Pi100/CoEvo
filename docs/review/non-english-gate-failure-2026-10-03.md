## 二、原因 1：真 bug —— 区间表漏了一段（可实证）

### 2.1 用 Rust 真实实现跑那篇（`id=4260`，越南语）

```
文件: vn_4260.txt  (7920 字符)

① 生产闸门 (count_letters):  字母=5078  拉丁=5078  ⇒ 100.00%   ← 分母里【没有】越南语字符
② 全 Unicode (is_alphabetic): 字母=5851  拉丁=5078  ⇒  86.79%

被忽略的字符数: 773

字符区间分布（非 ASCII 部分）:
  Latin-1 补充                     360
  拉丁扩展 A                       188
  拉丁扩展 B                        82
  组合变音符号                      13
  🔴 拉丁扩展附加 (U+1E00–1EFF)    773   ← 越南语声调字符全在这里
```

**根因**：`is_letter` / `is_latin` 的区间表是 `0x0041–0x024F`，**不含 `U+1E00–U+1EFF`**。
而越南语的 `ạ ả ấ ầ ệ ị ọ ụ ứ ỳ`（带声调）**全在那一段** ⇒

> 它们**既不入分子（拉丁）也不入分母（字母）** ⇒ 被**完全忽略**
> ⇒ 分母只剩 ASCII + 拉丁扩展 A/B ⇒ 比值 **100%** ⇒ **永不触发**

**⇒ 这是「可实证的 bug」，不是「设计取舍」。** 那篇的真实占比 86.79% < 阈值 90%
⇒ **本该被拦**。

### 2.2 🔴 而这个 bug 我**自己写下了**，只是赌它不会发生

`content_quality.rs` 的注释原文：

```
/// # ⚠️ 不覆盖（**已知盲区**，如实列出）
/// 泰文 / 天城文 / **越南语扩展**等 ⇒ 若出现**整篇**这类文字：
/// `letters` 会偏小 → 可能低于 MIN_LETTERS → **放过**（漏拦，不误杀）。
/// 当前 23 个源（英语媒体 + 英文技术社区）里**实测未出现** ⇒ 风险可接受。
```

我**赌「没出现」**，而它出现了（Dev.to 有越南语投稿）。

⚠️ 而且我预判的失效模式是「→ 字母偏小 → 低于 MIN_LETTERS → 放过」，
**实际失效模式不同**：分母偏小 ⇒ 比值**虚高到 100%** ⇒ 连阈值都比较不上。
⇒ **我对「已知盲区」的后果也判断错了**。

### 3.1 三个新发现

1. **非英语不止来自 Dev.to** —— `id=8` 是 **NPR**（`npr.org/.../en-esta-ciudad-de-p…`）

   ⇒ **「在源这一层按语言过滤」不可行** ⇒ 只能在**内容层**判

## 四、阈值标定（方案的关键数据）

683/966 条可判（其余 token < 30，样本太小）· 英语词密度分布：

```
── 最低 6 条（全是真非英语）──
   0.0%  id=8      src=1  tok=36    En esta ciudad de Pensilvania…        ← 西语
   2.1%  id=1021   src=4  tok=708   OpenAPA: una vecchia idea militare…  ← 意语
   2.5%  id=737    src=4  tok=1392  Cómo automatizar facturas PDF…       ← 西语
   4.6%  id=1645   src=4  tok=478   Haftalık yapay zekâ özeti…           ← 土语
   5.0%  id=4260   src=4  tok=401   Hướng Dẫn Khắc Phục Lỗi…             ← 越语（你报的）
   6.3%  id=2032   src=4  tok=444   A Linux Kernel CVE Just Dropped…     ← 越语

── 下一条起就是真英语 ──
  10.0%  id=2499   src=20 tok=30    Another court blocks White House…    ← ✅ 英语
  13.3%  id=80     src=2  tok=30    China opens four high-speed rail…    ← ✅ 英语
  15.0%  id=2031   src=4  tok=574   How We Built a 30-Tool Calculator…   ← ✅ 英语

── 对照上限 ──
  48–53%  确信英语（NPR 长文）
```

| 阈值 | 会拦 | 误杀 |
|---|---|---|
| 5% | 5 条 | 0（但漏掉 id=2032 的 6.3%）|
| **8%** ⭐ | **6 条（全中）** | **0**（下一条真英语 10.0%）|
| 10% | 6 条 | 0（但安全边际只剩 0 个百分点）|
| 12% | 7 条 | ⚠️ 开始碰到真英语（10%）|
| 15%+ | 10+ 条 | 🔴 误杀真英语 |

⇒ **8% 是「全中 6 条 + 零误杀 + 2 个百分点余量」的自然分界。**

### 4.1 ⚠️ 一个必须知道的设计约束

**闸门在「入库时」只看 `title + summary`**，而很多源（NPR / ECNS）的 RSS
**只给短摘要** —— 正文是**之后补抓的**。

⇒ 语言判据要在「**正文还没抓到**」时就做判断 ⇒ **短文本是常态**。
⇒ 必须配 `MIN_TOKENS` 保护（实测 **283/966 条 token < 30**，这些不判 ⇒ 漏拦风险）。

📌 这也解释了为什么 `MIN_LETTERS=50` 那条保护是必要的 —— 但它同时是漏拦的来源。

## 五、方案（**≥2 个，供你选**）

### 🅰 方案 A（推荐）：修 bug + 把判据升级为「英语信号」

| 步 | 做什么 | 依据 |
|---|---|---|
| A1 | 补全区间表：`U+1E00–U+1EFF`（拉丁扩展附加）等 | 让带声调拉丁字符**正确参与分母** |
| A2 | 新增「**英语功能词密度 < 8%** ⇒ 非英语」 | 实测 6 条全中、**零误杀**、余量 2pp |
| A3 | 内置 ~130 词英语功能词表（纯函数、零依赖）| 与「零框架依赖」一致，可独立断言 |

- ✅ **一次性解决「所有拉丁语系非英语」**（西/意/葡/法/德/越/土…）
- ✅ 实测**零误杀**（下一条真英语是 10.0%，是阈值的 1.25 倍）
- ⚠️ 代价：多一个判据 + 一张词表；**词表要维护**（但功能词几乎不变）
- ⚠️ 风险：短文本（< 30 token）不判 ⇒ 漏拦；技术文里代码/公式多也会拉低密度（需实测）

### 🅱 方案 B（最小改动）：只修区间表

- 只加 `U+1E00–U+1EFF` ⇒ 拦下越南语（86.79% < 90%）
- ✅ 改动最小、**零新风险**
- ❌ **你的质疑只解决 1/6** —— 西语/意语/土语仍是 100% ⇒ 照样放过

### 🅲 方案 C（源级）—— ❌ **已实测不可行**

给 NPR 等源加「只取英语内容」约束 ⇒ 需要**条目级语言标记**，
而 Dev.to feed **只有频道级 `<language>en</language>`** ⇒ 做不到。

## 六、🔴 我上一轮的「523 篇实测」为什么没发现

我上轮的验证结论是「丢弃 3 篇 · 临界样本为空 · 正常文章 ≥97%」——
**它建立在错误的分母上**：

| 实现 | 字母判定表 | 那篇越南语算出 |
|---|---|---|
| **生产（Rust）** | 固定区间 `0x0041–0x024F` 等 | **100.00%** |
| **Dart 探针** | 同一张固定区间表（✅ 与 Rust 一致）| 100.00% |
| **我的 Python 复刻** | `str.isalpha()`（**全 Unicode 字母**）| 86.79% |

⇒ **三套口径里，我用「第三套」去验证「前两套」** —— 于是：
- 我看到的「86.79% < 90%）⇒ 该拦」在生产里根本不成立（它算的是 100%）
- 「正常文章 ≥97%」这个结论也**只在 Python 口径下**成立

📌 **教训（比这次的修复更重要）**：
我在注释里写了「**两处实现必须一致**」，却只对齐了**阈值**，
**没对齐「字母判定表」** —— 而判定表才是判据的核心。
更糟的是**我又引入第三套口径（Python）去做独立验证** ⇒ 三方不一致，谁也没发现。

🔑 **判据：跨实现一致性的「相等」必须落到**每一个**共享定义上（阈值 + 判定表 + 边界处理），
而不是只对最显眼的那个（阈值）。**
