# 内置源端侧化 · 与 VPN 加速评估（2026-10-07）

> **触发**：白哥问「要不要把现在的信息源也改成端侧，我们做个 VPN 加速？」
>
> ## 结论（三条，都可直接据以决策）
>
> | 问题 | 结论 |
> |---|---|
> | **做 VPN 加速** | 🔴🔴 **绝对不做** —— 法律红线（§一），且**技术上完全没必要**（§二）|
> | **内置源改端侧抓** | ❌ **不建议** —— 现役源多为境外站，改端侧会**大面积失效**（§三）|
> | **正确架构** | ✅ **保持混合**：内置源服务端抓 · 自定义源端侧抓（§四）|

---

## 一、🔴 VPN 加速：法律红线（不可做）

### 1.1 法律依据（多来源一致）

| 依据 | 内容 |
|---|---|
| 《电信条例》第 7/9/14 条 | 经营增值电信业务**须取得经营许可证** |
| 《计算机信息网络国际联网管理暂行规定》第 6 条 | 国际联网须走国家公用电信网的**专门出入口**，**不得自行建立或使用其他信道** |
| 工信部《关于清理规范互联网网络接入服务市场的通知》 | **未经电信主管部门批准，不得自行建立或租用专线（含 VPN）开展跨境经营活动** |
| 《电信业务分类目录》B13（国内互联网虚拟专用网业务）| 资质**只面向依法设立的内资企业**；**禁止向个人用户提供 VPN 服务** |

### 1.2 对我们尤其致命的四点

1. 🔴 **个人拿不到 VPN 资质** —— 该资质只发给依法设立的中国企业（注册资本 ≥1000 万全国 / 100 万省内、
   3 名计算机相关专业人员社保、工信部指定评测……）。而本项目是**个人开发者**。
2. 🔴 **即使持证，也禁止向个人用户提供 VPN** —— 只允许服务企业客户。
3. 🔴 **司法实践不是"罚款了事"**：公开案例中，未取许可搭建并销售 VPN，
   以**非法经营罪**判处**有期徒刑 5 年 6 个月 + 罚金 50 万元**（非法获利约 50 万）。
4. 🔴 **外资/VIE 架构禁止参与** —— 把这条路彻底堵死。

> 📌 判据：**这是"零容忍"类风险，不是"成本/收益"类风险** ——
> 不存在"小心一点做"的版本。**任何形式的"帮用户访问境外站"都不做。**

## 二、🔑 而且技术上**完全没必要**（这一点更关键）

### 2.1 用户设备从来不直接访问境外站

```
用户设备  ──HTTPS──▶  api.keyievolution.fun（境内·腾讯云广州）  ──▶  服务端已抓好的内容
                              ▲
                              └── 服务端自己去抓 NPR / Ars Technica / arXiv（服务器网络可出）
```

⇒ **信息流是"我们的 API 提供"的，不是让用户去拉 NPR 的 RSS。**
⇒ **用户的网络环境（能否访问境外）根本不影响信息流的加载。**

📌 所以「VPN 加速」要解决的问题**在当前架构下不存在** —— 它是为一个**不存在的需求**引入一条法律红线。

### 2.2 反过来说

真正影响加载速度的是**我们的服务端到用户的链路**，而它在境内 ⇒
优化手段是**服务端缓存 / CDN / 减少 payload**，**不是 VPN**。

## 三、内置源改成端侧抓：会让信息流**大面积空白**

现有现役源的域名（实测提取）：

| 域名 | 归属 | 用户国内网络能否直接访问 |
|---|---|---|
| `feeds.npr.org` | 境外 | 🔴 通常不能 |
| `arstechnica.com` | 境外 | 🔴 通常不能 |
| `dev.to` | 境外 | 🔴 通常不能 |
| `export.arxiv.org` | 境外 | 🔴 通常不能 |
| `hacker-news.firebaseio.com` | 境外（**已弃用**）| 🔴 |
| **`www.ecns.cn`** | **境内**（中国新闻网英文）| ✅ 能 |

⇒ **5 个非测试域名里 4 个是境外** ⇒ 改端侧抓 = **信息流基本只剩 ECNS**。

**而这正是"服务端集中抓"的核心价值**：
**服务器网络能出去 ⇒ 抓一次 ⇒ 全体用户受益**（成本 ∝ 源数，与用户数无关）。

⇒ **把内置源改端侧是纯倒退**：丢掉可达性、丢掉集中抓取的成本优势、
丢掉服务端的正文提取（1171 行）—— 换来的只有"绕开内容责任"，而内置源**版权本来已逐源审过**
（`license` / `redistributable` 两列）。

## 四、✅ 正确架构：混合（两块的理由各自成立）

| | **内置源**（现有 22 个）| **自定义源**（新增）|
|---|---|---|
| 谁选 | 我们（精选 + 许可已标）| 用户 |
| **谁抓** | **服务端** | **端侧** |
| 理由 | ① 服务器可达境外 ② 版权已审 ③ 成本 ∝ 源数 | ① **责任归属**（用户自选）② 服务器零成本 |
| 存哪 | 服务端库 | **只在用户设备**，不上传 |
| 分级 | `cefr_hint` | 标注「未分级」|

📌 **判据：抓取放在哪一端，取决于「内容是谁指定的」** ——
我们指定的 ⇒ 服务端（且版权已审）；用户指定的 ⇒ 端侧（且不托管）。

### 那"自定义源在用户网络下不通"怎么办？

**不解决，也不该由我们解决。** 那是用户自己的源 + 用户自己的网络。
我们只保证：**失败要明确提示**（不要静默），并且**不影响内置源**。

> 🔑 一句话：**内置源的境外可达性由我们的服务器负责；自定义源的网络条件由用户自己负责。**
> 两件事不该混在一起，更不该用一条违法手段去兜。
