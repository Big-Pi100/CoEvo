## 一、🔴 先纠正一个认知：**「默写」这一半已经做完了**

`app/lib/services/highlight_grader.dart` 的文件头（白哥 **2026-10-07** 定）：

> 「**复习的时候考默写，和单词一样**」
> ⇒ **动作一样**：看到提示 → 写出内容 → 判定 → 两档（`good` / `again`）。
> 差别只在**提示形式**：
> · 单词卡：提示 = **释义（中文）**
> · **划线卡：提示 = 首字母骨架**（纯算法生成 · 零成本 · 任意长度都能生成）

⇒ 划线卡**当前就是「默写原文」题型**，只是**提示给的是首字母骨架**，不是中文译文。

**所以你的需求精确地说 = 给划线卡换/加一种提示形式（中文译文）** —— 不是"从零做默写"。

### 而且扩展点**已经预留好了**

`review_session_screen.dart` 的 `_HighlightPrompt`（原文注释）：

> 「⚠️ 揭示程度目前固定「只给首字母」。它是 `skeletonFor` 的**一个参数**
> （`SkeletonReveal.none` / `firstTwo`）—— **将来要做难度档，改这里一处**。」

## 二、为什么「现在不记录翻译」—— 根因

| 事实 | 出处 |
|---|---|
| 译文**确实落库了**，存在 `translation_cache` | `user_db_schema.sql:622` |
| 但它被设计为**派生缓存**：「清掉只会让下次重新付费，**不丢任何数据**」 | 同上（DDL 注释） |
| 🔴 **不参与同步** | 同上（「设计稿：译文不写进文章、不参与痕迹、不进生词本」） |
| 🔴 **退出登录时必须清空** | 同上（「他翻过哪些句子」是行为数据，跨账号保留会泄漏） |
| **LRU 淘汰**（按 `used_at` 删最旧） | `idx_tcache_used` |

⇒ **它不是卡片资产，是缓存** —— 换设备就没了、登出会被清、还会被淘汰。
**所以「划线卡不记录翻译」不是漏做，而是它落在了一张"本就不该承载卡片数据"的表里。**

🔑 判据复用：这与 `highlight.paused` 那条注释同族 ——
「**「会被重建/会被清空的表」不能存用户意图**」（当时说的是 `card_review_state`）。

### 但好消息：它**可以被读**

```dart
Future<CachedTranslation?> get(String rawSource)   // translation_cache.dart:104
String normalizeTranslationSource(String raw)      // 规范化口径（单点）
```

⇒ **按原文就能取回译文** —— 这条让「快版方案」成为可能（见 §四 A）。

## 三、可行性：判分器**已有**，这是最省事的一点

| 需要的能力 | 现状 |
|---|---|
| 「写出原文 → 自动判对错」 | ✅ **已有** `highlight_grader` |
| 判据 | **逐词对齐 + 按错词比例**（不是「错一个全错」）；**剔除句读标点**（少个逗号不算忘）；大小写/全角/首尾空白归一化 |
| 阈值 | 默认 **5%**，**用户可调**（「我的 → 记忆」的滑动条，`MemorySettings.maxWrongPercent`）|
| 输出 | 两档 `good` / `again`（直接复用 `ratingForSpelling`）|

⇒ **改成「给译文默写原文」，判分部分一行都不用动** —— 只换提示内容。

## 四、三个必须你定的问题（技术方案取决于它们）

### ❓问题 1：提示用「**整段**」还是「**划线那一句**」？

| | 提示 = 整段译文 | 提示 = **划线片段**的译文 |
|---|---|---|
| 与答案粒度 | 🔴 **不匹配** —— 提示里含**答案之外**的内容，等于**提前给答案**（且用户不知道要写哪句） | ✅ 一致：提示什么就默写什么 |
| 体验 | 用户看到一大段中文，不知道「该写哪句」 | 目标明确 |

> ⚠️ 你原话说的是「**连整段翻译一起记录**」—— 若指的是**用整段译文当提示**，我建议**改成"划线片段的译文"**。
> 若你的意思是「划线时顺便把所在段的译文也存下来」，那是**存储**层面的选择，可以用 §四 B 方案。

### ❓问题 2：译文**从哪来**？（这决定成本）

| 来源 | 成本 | 稳定性 |
|---|---|---|
| **用户翻译过就有**（查缓存）| ✅ **零成本**（复用它已有的翻译）| ⚠️ 不稳定：没翻过 → 只能回退骨架；换设备/登出后没了 |
| **划线时自动翻译** | 🔴 每条划线一次 LLM 调用（**翻译是订阅权益：免费 10 次/月 · 订阅无限**）| ✅ 稳定 |
| **订阅用户可"批量补译已有划线"** | 🟡 一次性成本，可控 | ✅ 稳定 |

### ❓问题 3：**要不要跨设备一致**？

- **要** ⇒ 译文必须**落进 `highlight` 表**（或新表）⇒ **user.db v11→v12 迁移 + 同步扩到 12 类**（后端 schema + push/pull + 端侧 merge）
- **不要** ⇒ 查缓存即可，**零迁移零同步**

## 五、方案选项

### 🟢 方案 A（**快版 · 建议先做**）—— 译文优先，骨架兜底

```
复习划线卡时：
  译文 = translation_cache.get(highlight.text)
  ├─ 命中 → 提示显示中文译文
  └─ 未命中 → 回退首字母骨架（现状）
```

| 项 | 值 |
|---|---|
| 改动 | `_HighlightPrompt` 一处 + 一次 cache 查询 |
| 迁移 | **零** |
| 同步 | **零**（缓存仍不同步） |
| 成本 | **零**（复用用户已付费翻译过的结果） |
| 缺点 | 译文**时有时无**（取决于是否翻过、缓存是否还在）⇒ 提示形式会**跳变** |

> ⚠️ 缺点要正视：同一个划线卡，今天有译文、明天（缓存淘汰后）变骨架 ⇒ **用户会困惑**。

### 🟡 方案 B（**完整版 · 稳定**）—— 译文成为卡片数据

```
highlight 表加一列 translation（可空）
划线时 / 复习时按需写入 ⇒ 参与同步（12 类）⇒ 跨设备一致
```

| 项 | 值 |
|---|---|
| 改动 | user.db v11→v12（**加列必须写 ALTER**）+ 服务端 schema + push/pull + 端侧 merge + 同步 12 类 |
| 成本 | 若自动翻译 ⇒ 每条划线一次 LLM 调用 |
| 优点 | ✅ 提示形式**稳定**、跨设备一致 |

### 🔵 方案 C（B + 题库增强）—— 订阅用户的"批量补译"

在 B 之上：订阅用户可一键把**已有划线**批量翻译并回填 ⇒ 历史卡片也能用译文提示。

## 六、我的建议（回答「你觉得呢」）

### ✅ 赞成做，但**做成"两种提示形式"，而不是替换**

🔑 这两者**考察的能力不同** —— 这是关键：

| 提示形式 | 实际考的是 | 难度 |
|---|---|---|
| **中文译文** | 「用英文**表达**这个意思」= **产出/翻译能力** | 较易（有完整语义锚点）|
| **首字母骨架** | 「**回忆**出原文措辞」= **记忆** | 较难（只有长度与首字母）|

⇒ 你说的方向**更接近"用英语"的真实场景**（先有想法 → 再找英文表达），
但骨架那条路练的是"记住原文"，也有独立价值。

**所以建议：**
1. **译文作为默认提示**（对多数用户更友好、更有获得感）
2. **骨架保留**，放进已有的「**我的 → 记忆**」设置里（那里已经有一个阈值滑动条）
3. 顺序上：**先做方案 A**（当天可验证效果、零成本），确认体验对了再上 B（稳定化）

### ⚠️ 两个我会坚持的点

1. **粒度必须与答案一致** —— 用**划线片段的译文**，不要整段（否则提前泄题）
2. **译文提示不要"顺手自动翻译所有划线"** —— 翻译是**订阅权益**（免费 10 次/月），
   自动翻译会把免费用户的额度瞬间烧光，且成本随划线量线性增长
