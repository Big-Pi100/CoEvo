## 四、🔴 三个关键障碍

### 障碍 1：模型不一致（最大工作量来源）

**「买断 N 天」→「自动续期订阅」** 不是改字段，是**换概念**：

| 概念 | 现状（微信买断）| Apple 自动续期订阅 |
|---|---|---|
| 谁定义价格 | 我们（`subscription_plans`）| **App Store Connect**（价格点）|
| 支付后发生什么 | 加 N 天，结束 | **开始订阅，到期自动续费** |
| 续期 | 用户再买一次 | **Apple 自动扣款** |
| 退款 / 取消 | 无概念 | **有专门事件**（退款/撤销/进入宽限期）|
| 订阅的唯一标识 | 我们的 `order.id` | **`original_transaction_id`**（跨设备/跨续期的稳定 ID）|

⇒ 需要：**新表**（记录 Apple 交易 + 订阅状态）· **`original_transaction_id` 必须存**（恢复购买和查状态都靠它）。

### 障碍 2：Apple 官方 Server Library **没有 Rust**（但社区库可用）

Apple 官方支持：**Swift / Java / Python / Node.js / Go** —— 🔴 **不含 Rust**。

✅ 社区库 [`app-store-server-library`](https://crates.io/crates/app-store-server-library)（**147 万下载**）：
- 对齐 Apple 官方 API：`AppStoreServerApiClient` + `SignedDataVerifier`
- 依赖 `x509-validator` 做证书链验证 · 支持 `reqwest` transport
- ⚠️ **风险点**：仓库从 `shimastripe` **转到了 `namecare`**（维护者变更）⇒ 需评估长期维护

**🔑 有一个绕开它的办法**（见方案 §5.1）：**只做「服务端主动查」不做「验签」**。

> 原理：JWS 验签的必要性是「**收到别人发来的 JWS 时，怎么证明它真来自 Apple**」。
> 而如果**我们主动**调 `GET https://api.storekit.itunes.apple.com/inApps/v1/transactions/{id}`，
> 响应走 **HTTPS（TLS 保护）** ⇒ 中间人无法伪造 ⇒ **可以不验 JWS 签名**。
> ⇒ 这样只用 `api-client` 那一半功能，不必依赖验签实现。
> ⚠️ 但**如果要做 Server Notifications V2**（Apple 主动 POST 给我们），**必须验签** —— 那时才需要它。

### 障碍 3：🔴 **隐私政策 / 用户协议 URL 尚未确定**（**上架硬要求**）

`about_screen.dart` 里写着：

> | **隐私政策** | 🔴 URL 尚未确定。它是 **Apple 上架的硬要求**（App Store Connect 必填 + App 内应有入口）→ **待白哥提供正式 URL 后补**。**不编造链接** |

⇒ 而**订阅页也必须放**这两个链接（Apple 对订阅的额外要求）。
⇒ **这项不解决，订阅页写完了也过不了审。**

## 五、方案（两个选项）

### 5.1 ⭐ 方案 A：自建（推荐）—— 客户端权威 + 服务端只做「验证 + 对账」

**核心判断**：本 App 的订阅权益是「**无限生词本 + 文章朗读**」，**两者都是端侧功能**
（生词本在 `user.db`，朗读在端侧）⇒ **服务端不是权益判断的必经路径**。
⇒ 可以「端侧权威 + 服务端留档」，大幅降低复杂度。

**架构**：
```
客户端                          后端                         Apple
─────────────────────────────────────────────────────────────────────
in_app_purchase 买
  ↓ 拿到 transactionId
POST /api/iap/verify ──────→  AppStoreServerApiClient
  {transactionId}              .get_transaction_info(txId) ──→ GET /inApps/v1/transactions/{id}
  ←──────────────────────────  验 productId / bundleId / environment
  {expires_at, is_active}      写入 iap_transactions 表                    ←── signedTransactionInfo
                               更新 users.subscription_expires
客户端用 StoreKit2 的
Transaction.currentEntitlements
 作为**即时权威**（离线也能判）

「恢复购买」= restorePurchases()
  ↓ StoreKit 返回该 Apple ID 的交易
  ↓ 走同一路径上报后端
  ⚠️ **不依赖我们的账号**（订阅源头是 Apple ID）
```

**✅ 优点**：无第三方抽成 · 完全控制 · Rust 库成熟 · **不依赖 JWS 验签**
**⚠️ 代价**：
- 退款/续期/取消**初期处理不完整**（需二期接 Server Notifications V2）
- 初期用「客户端每次启动上报 + 后端主动查」代替推送

### 5.2 方案 B：用第三方（RevenueCat）

**✅ 优点**：服务端全托管（验证/续期/退款/跨设备）· 开发最快
**❌ 问题**：
- **抽成**（超出免费额度后按收入比例）
- 🔴 **数据出境合规**：它是境外服务，用户订阅数据出境 ——
  与本项目已核实的「境外广告平台」问题**同族**（Google 未列入数据出境白名单）
  ⇒ **很可能因合规被否**，且与「个人 + 中国区」的主体约束叠加

> 📌 **不推荐 B**：它省的工作量（服务端验证 ~几百行）不值「引入境外数据处理者」的合规成本。
> 本项目判据：**「平台允许 ≠ 法律允许」**。

### 5.3 方案对比

| | A 自建 | B RevenueCat |
|---|---|---|
| 工作量 | 🟡 中（后端 ~500 行 + 前端 ~600 行）| 🟢 小 |
| 抽成 | ✅ 无 | 🔴 有 |
| 数据出境 | ✅ 无 | 🔴 **有（合规风险）** |
| 退款/续期处理 | 🟡 二期补 | ✅ 现成 |
| 可控性 | ✅ 完全 | 🟡 依赖第三方 |

### 🔑 `order_status_handler` 的简化（有设计价值，值得记）

原实现有一段「本地 `NOTPAY` 时主动向微信查单 → 同步状态 → 延期订阅 → 分发佣金」。
**IAP 下这一整段没有对应物**：

| 微信的做法 | IAP 的对应 |
|---|---|
| 服务端**主动**向微信查单 | ❌ 不需要 —— 凭据由客户端上报（`/api/iap/verify`）|
| 「条件 UPDATE 防竞态翻倍」 | ❌ 不需要 —— 验证**幂等**（按 `transaction_id` 唯一）|
| 同步时顺带 `extend_subscription` | ❌ 移入 `iap_handlers`（由**验证**触发，不由查单触发）|

📌 判据：**「查状态」不该有副作用** —— 原实现把它做成「查着查着就改了状态」，
在 IAP 下**多余且危险**（会与验证链路争抢同一份状态）。

### 🐛 过程中的失误（如实记录）

**删除粒度不一致 → 编译报错**：两处端点删除时，一处删了内层两行、
另一处删了整块（含 `.route(` 与 `)`）⇒ 留下**空的 `.route()`** ⇒ 编译失败。

✅ **编译器抓到了**（不是静默失败）—— 这正是「删完必须编译」的价值。
📌 判据：**批量删除时，每处的「删除边界」必须一致**（否则留下语法残缺）。
   更稳的做法：每处匹配**完整表达式**（含外层括号）。

#### 11.0.1 🔴 官方硬性资格（任一不满足 → 报「Apple ID 暂时不符合使用此应用程序的条件」）

来源：Apple 官方 [`developer.apple.com/programs/enroll`](https://developer.apple.com/programs/enroll) + 中文帮助页《使用 Apple Developer App 注册》+ Apple Developer Support 答复。

| # | 要求 | 排查方法 | 为什么 |
|---|---|---|---|
| **1** | 🔴🔴 **Apple 账户必须是「邮箱格式」**，不能是手机号 | `appleid.apple.com` 登录看账户名 | **Apple 支持原文**：「your **phone number Apple ID** cannot be used for the Apple Developer Program. You must create an **email-based** Apple ID」|

**9 条里最可能踩的是 #1 和 #2**（中国区用手机号注册 Apple ID 很常见；2FA 与 two-step 易混）。

### 11.3 等级：为什么月/年同为等级 1（决策点）

Apple 的规则是**按「提供多少服务」排等级，不按时长排**：

> 官方原文：「如果有多个订阅产品提供的内容或服务相同，只是时限、价格等有所差异，你可以将此类产品设置为同一等级。」

本 App 月度/年度**权益完全相同** ⇒ **同一等级** ⇒ 用户月↔年切换是「同级转换」（**不会重复扣费**）。
- 代价：**时限不同**的同级转换**从下一个续期日生效**（不是立即）
- 若想让「月 → 年」立即生效，才需拆成两个等级（年度=1、月度=2）—— 但那会让「年 → 月」变成降级
- ✅ **本轮决定：同等级**（符合官方推荐）
