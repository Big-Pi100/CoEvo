# 内容解析/渲染问题调查报告（2026-10-02）

> **触发**：白哥真机（Android）验证 A2 时反馈「内容有解析错误」，并举了三篇例子。
> **方式**：**只调查，未改任何代码**（按铁律）。所有结论都有实测数据或代码位置支撑。
>
> **先说好消息**：A2 本身**通了** —— 内容能连上（`--dart-define` 生效、API 全链通）。
> 本报告的问题**不在 A2**，而在**更早就存在的内容管线**（提取 → 存储 → 渲染）。

## 一、结论摘要（结论前置）

**三个症状，根因分属三层，不是同一个问题** —— 所以不能用一个修法通吃：

| # | 白哥看到的 | 根因 | 层 | 影响面 |
|---|---|---|---|---|
| 1 | GTFS 那篇「图表渲染错误」 | 原文是 `<pre>` 里的 **ASCII 树形图**，`collapse_ws` 把**换行与缩进全折叠** → 树压成一行 | **后端提取** | 🔴 **技术类文章普遍**（已确认 1 篇含树图，但代码块同理）|
| 2 | OpenRive「只有半句话」 | `body` 为 NULL → 端侧**兜底到 summary**，而那篇的 summary 是**源站自己的报错**（`Liquid syntax error`）| 源数据 + 端侧兜底 | 🟡 **2 篇**（Dev.to）—— 个案 |
| 3 | accessibility「有 HTML 代码」 | 原文用 **32 个 `<code>`** 标出 `<img>`/`alt`/`<label for>`（作者在**讨论标签**）；提取丢样式 → 端侧纯文本渲染 → **像裸代码** | **提取 + 渲染** | 🟡 **5 篇**（全是技术文）|

**一句话**：**「内容能取到，但取到的是「被压平的纯文本」，丢失了「哪里是代码、哪里是图」的结构信息」** ——
1 和 3 是同一个病（**结构丢失**），2 是另一个病（**坏数据没被拦**）。

## 二、逐个案例：症状 → 证据 → 根因

### 案例 1 · GTFS（`content_pool.id=1303`）

**白哥描述**：图表渲染错误。

**实测数据**：
```
body = 12225 字（提取是完整的！）
url  = https://dev.to/suign/what-happened-when-we-loaded-madrids-gtfs-data-...-1ngh
```

**body 里的实际内容**（第 36 行）：
```
gtfs ├── services │ ├── service_1 │ ├── service_2 │ └── ... │ ├── routes │ ├── route_1 ...
```

**根因**：原文里这是一个 **`<pre>` 代码块里的 ASCII 树形图**（用 `├──` `│` `└──` 画的层级树）。
提取时 `content_extract.rs:236` 的链路是：

```rust
collapse_ws(&decode_basic_entities(&buf))   // ← collapse_ws 把「连续空白」折叠成单个空格
```

`collapse_ws`（同文件 `:240`）对**所有空白**（含 `\n`、缩进）一视同仁地折叠 ⇒
**树的换行与缩进全没了**，`├── services` 与 `│ ├── service_1` 被拼成一行。

🔑 **它不是「图没渲染出来」，是「图被压成了乱码般的一行」** —— 白哥的「渲染错误」描述准确。

**为什么这是普遍问题**：任何**含代码块/预格式文本**的文章都会这样。
Dev.to（技术博客）是主要来源，`src=4` 共 96 篇。

**一个反证（证明我没被表面数据骗）**：
我用 `[^\S\n]{2,}\S`（**段内**多空格）统计，结果是 **0 篇** ——
这不是「没问题」，而是 **`collapse_ws` 把痕迹抹掉得太干净，所以检测不到**。
（判据：**「检测不到」不等于「不存在」—— 要先问「我的判据有没有被上游清理动作掩盖」**。）

### 案例 2 · OpenRive（`id=1307`）

**白哥描述**：内容只有半句话。

**实测数据**：
```
body    = NULL
summary = "Liquid syntax error: 'raw' tag was never closed"    ← 这正是白哥看到的「半句话」
```

**根因链（两段，缺一不可）**：

**① 源数据坏**：那篇文章正文里含 **Liquid 模板语法**（`{% raw %}`），Dev.to 渲染失败 →
它给 RSS 的 `description` 就是这条报错。

**② 端侧把兜底当正文**（`app/lib/api/content_client.dart:65`）：

```dart
String? get readableText {
  if (body != null && body!.trim().isNotEmpty) return body;
  final s = item.excerpt.trim();      // ← 兜底到 summary
  return s.isEmpty ? null : s;
}
```

而 `reader_screen.dart:328` 用 `hasReadableBody(paragraphs)` 判断「有没有正文」：

```dart
bool hasReadableBody(List<String> paragraphs) => paragraphs.isNotEmpty;   // article_text.dart:57
```

🔴 **paragraphs 来自兜底之后的文本** ⇒ 那句报错被算作「1 段」⇒ 判定「有正文」⇒ **直接显示**。

🔴 **而代码注释明确写了正确做法**（`content_client.dart:62-64`）：
> ⚠️ 退到 `summary` 时语义是「**只有摘要**」而不是「全文」——
>    调用方（阅读器）要按 `FeedItem.hasBody` 决定是否提示「正文未就绪」，
>    **不要**把这里的兜底当成「有正文」。

⇒ **注释里的约束没有被实现** —— 这是「注释 ≠ 实现」的又一例。
根因是**信息在传递中丢失**：`readableText` 返回 `String?`，**表达不出「这串是全文还是摘要」**，
调用方只能猜。

**影响面比看起来小（重要）**：body 为 NULL 共 **59 篇**，其中：

| 情况 | 篇数 | 端侧表现 | 好不好 |
|---|---|---|---|
| summary **也空** | **42** | 正确显示「这一篇还没有正文」 | ✅ 对 |
| summary 非空 → 显示 summary | **17** | 显示摘要 | ⚠️ **多数是对的** |
| ↑ 其中 src=2（图片新闻）| 15 | 摘要内容正常（如「Chinese athlete … took the gold」）| ✅ **显示摘要比空着好** |
| ↑ 其中 src=4（Dev.to）| **2** | 🔴 其中 1 篇是源站报错 | ❌ **错** |

⇒ 「兜底到 summary」这个设计**大体是对的**；真正要修的是**「源站报错被当内容存下来」**。

### 案例 3 · accessibility（`id=1168`）

**白哥描述**：里边有 HTML 代码。

**实测数据**：
```
body = 5173 字，含 `<img>` / `<label for>` / `<h1>` / `<title>` / `<html>` / `<iframe>` / `<th>` 等
```

**关键验证（直接抓原文对比）** —— 原文里这些是什么形态：

| 抓源站结果 | 数量 |
|---|---|
| `HTTP 200` · `<article>` ×1 | ✅ 页面正常 |
| **`<code>`**（内联代码）| 🔴 **32 个** |
| `<pre>` | 0 个 |
| 含 `<code>` 的段落 | **12 / 17 段** |
| 代码内容 | `'<img>'`、`'alt'`、`'alt=""'`、`'<label for>'`、`'aria-label'` … |

⇒ **原文是「等宽字体 + 底色的内联代码」**，读者一眼能看出「这是在讨论标签名，不是真的标签」。

**我们的链路**：`normalized_text` 只取**文本节点** → `<code>` 的**样式信息丢失** →
端侧 `splitParagraphs` + **纯文本渲染** → 用户看到 `<img>` 就是一段裸文字。

🔑 **所以这不是「HTML 没剥干净」** —— HTML 剥得很干净（`body` 里 `<xxx>` 形态的只有 5 篇，
且都是**文章在讨论标签**）。真正的问题是：
**「内联代码」这个语义没有被保留**，从「有样式的代码」退化成「普通文字」。

**影响面**：`body` 含标签形态的 **5 篇**，全是技术文：
`What TLA+ can and can't check`（src=5）· `Why Photos Leak Your Home GPS Coordinates` ·
`Structs Aren't on the Stack. How C# Actually Manages Memory` · `A "3% fee" that's really 27% APR` ·
`The 12 HTML checks my accessibility scanner runs`（均 src=4）

## 四、修复方案（三个选项，分层 · 未实施）

### 选项 A · 只修「坏数据兜底」（最小改动）

| 改什么 | 文件 | 代价 |
|---|---|---|
| ① 后端：存 summary 时**过滤明显的源站报错**（如含 `syntax error` / `Liquid … never closed`）→ 存 NULL | `content_pool` 写入侧 | 小 |
| ② 端侧：让「这段是摘要还是全文」**显式化**（如返回 `(text, isExcerpt)` 或加 `hasBody` 判断），摘要时给「**仅有摘要**」的提示而不是当正文 | `content_client.dart` + `reader_screen.dart` | 中 |
| ③ 断言 | `verify_article_text` 等 | 小 |

✅ **好处**：改动面小、风险低，**修掉「用户看到报错信息」这个最刺眼的问题**
❌ **不解决**：案例 1 与 3（代码/预格式仍会丢）—— 白哥看到的「图表」「HTML 代码」**依然存在**

---

### 选项 B · 保留「结构标记」（推荐）

**核心思路**：提取时**不产出「压平的纯文本」，而产出 Markdown**
（内联代码 → `` `<img>` ``；代码块 → ` ```…``` `），**端侧用已有的 `GptMarkdown` 渲染正文**。

| 改什么 | 位置 | 代价 |
|---|---|---|
| ① 提取器：`<code>` → 反引号包裹；`<pre>` → 三反引号块（**保留换行缩进**）| `content_extract.rs` | 中 |
| ② 正文渲染：从 `splitParagraphs` 纯文本 → `GptMarkdown`（**组件已在项目里**，现在只给词卡用）| `reader_screen.dart` + `article_text.dart` | 中 |
| ③ 存储格式：`body` 从纯文本 → Markdown（**TEXT 列，无 schema 迁移**）| 无需改表 | 小 |
| ④ 断言 + 老数据兼容 | 新脚本 + 决策 | 中 |

🔑 **关键风险（必须处理）**：`body` 语义从「纯文本」变成「Markdown」→ **老数据怎么办**？
- 纯文本是 Markdown 的子集 ⇒ 大多数老数据渲染正常
- 🔴 **但**：老正文里若含 `*` `_` `#` `[` 等字符，**会被当 Markdown 语法**（如 `2*3*4` 变斜体）
- ✅ 对策：**给老数据加「不解析 Markdown」标记**（或一次性重新抓取存量）

✅ **好处**：一次解决案例 1 + 3（**结构的语义被保留**），且**复用已有组件**（`GptMarkdown`）
❌ **代价**：改动跨后端+端侧，需处理老数据

---

### 选项 C · 改成「存 HTML 片段」

保留原文的**富文本 HTML**（`<p>` / `<code>` / `<pre>` / `<figure>`），端侧用 HTML 渲染。
- ✅ 信息最完整（图、表、代码全保）
- ❌ **代价最大**：端侧要引入 HTML 渲染器、要处理安全（XSS 式注入）、要处理样式适配（深色模式）
- ❌ 与项目「阅读器保持简洁」「不做 Web」的定位不符

**我的建议：不选 C。**
