📌 建议先确认：用**已订阅账号**登录 → 收藏一篇文章 → 换一台设备登同一账号 → 看收藏是否出现。  
**这一步能直接区分「没做」和「没订阅」。**

### 收藏那一环值得单独说（它比看起来讲究）

`bookmark_repository.dart` 里三处硬约束，都是踩过坑之后钉下的：

| 约束                            | 若不这么做会怎样                                               |
| ----------------------------- | ------------------------------------------------------ |
| **软删**（`deleted` 而非 `DELETE`） | 同步是**并集** ⇒ 硬删会被别端**并回来** ⇒ 用户看到「删了又自己回来」              |
| **取消收藏也要刷新 `bookmarked_at`**  | 服务端按「较新胜」判（`>`）⇒ 时间戳不变 ⇒ 取消**被丢弃** ⇒ 同上                |
| **时间戳必须毫秒**                   | 秒精度下「收藏 → 立刻取消」同秒 ⇒ `t > t` 为假 ⇒ **取消丢失**，且**只在多设备可见** |

⇒ 收藏的同步是**已经做扎实**的，不是半成品。

## 四、🔴 修正：书架正文**要上云**（白哥 2026-10-07 定）

> 白哥原话：「**收费服务哪有完全因为成本就不做的**」「用户之所以付费就是买个**云端储存空间**，
> 怕本地丢失，你跟用户说还在你本地，这不是白痴吗」—— **对，我上一版错了三处。**

### 4.1 错在哪

| 我写的 | 实际 |
|---|---|
| 拿**成本**当否决理由 | 成本是**定价与分层的输入**，不是「做不做」的理由 |
| 只凭「**随用户数线性增长**」下结论 | 🔴 **根本没算单价** → 见 4.2：实测占收入 **0.12%** |
| 「书在本地，请重新导入」 | **把我们要省的成本转嫁给用户**；而用户付费买的就是「云上有、换机不丢」 |
| 「上传正文 = 在线书库」 | **过度推导**。真分界线是**「是否向公众提供」**，不是「是否存储」→ 见 4.3 |

### 4.2 成本量化（腾讯云 COS 官方价 · 2026-10 核实）

| 项 | 单价 |
|---|---|
| 标准存储 | **0.118 元/GB/月**（50 GB 容量包 4.13 元/月 ≈ 0.083/GB）|
| 外网下行流量 | **0.5 元/GB** |
| 读请求 | 0.01 元/万次（可忽略）|

**规模测算**（书体积按 **1 MB/本** 估 —— 纯文本 epub 多为 0.3–2 MB；带图大书按 5 MB）

| 场景 | 总存储 | 存储费/月 | 订阅收入/月 | **占比** |
|---|---|---|---|---|
| 1,000 用户 × 20 本 × 1 MB | 20 GB | **¥2.4** | ¥25,000 | **0.01%** |
| 10,000 用户 × 50 本 × 1 MB | 500 GB | **¥59** | ¥250,000 | **0.02%** |
| 10,000 用户 × 50 本 × **5 MB**（带图大书）| 2.5 TB | **¥302** | ¥250,000 | **0.12%** |

换机下载流量：250 MB × 0.5 元/GB = **¥0.125 / 人/次** ⇒ 1 万人一年各换一次也才 **¥1,250**。

> 🔴 **结论：成本是收入的千分之一量级。**
> 这不是「能不能做」的问题，是「**配额怎么定**」的问题 ——
> 与上一轮 LLM 制卡**是同一个模式**：有真实成本 ⇒ 用**订阅配额**覆盖，而不是砍掉功能。

📌 **判据（新的）**：**「随用户数线性增长」本身不是否决理由** ——
只有「**线性增长 × 单价**」得到的**绝对金额 vs 收入占比**才能做判断。
我上一版只看了「增长形态」、没看**量级**，那不是分析，是贴标签。

### 4.3 合规：私人云存储 ≠ 在线书库（关键区分）

🔴 **分界线是「是否向公众提供」，不是「是否存储文件」。**

| | 私人云存储 ✅ **可做** | 在线书库 ⛔ **已否决** |
|---|---|---|
| 谁能访问 | **只有本人** | 所有人 |
| 内容从哪来 | **用户自己上传的** | 我们选书 / 我们提供 |
| 我们扮演 | **信息存储空间**（网盘 / iCloud 同类）| **内容提供者 / 出版者** |
| 我们做的 | 存 + 取 | 提供 + 分发 + 编排 |

⇒ ✅ **可做**：用户把自己的书放进自己的空间，只有他能取回。
⇒ 🔴 **三条红线（绝不做）**：
   ① 用户**之间**共享电子书；② 我们提供公版书库；③ 把「能看到别人的书」做成权益 ——
   那才是「**向公众提供 + 从内容直接获利**」⇒ 主动放弃避风港。

⚠️ **连带约束（措辞）**：订阅文案只能宣传「**云端存储空间**」，
   **不能**宣传「订阅可以看这些书」—— 后者会把「卖存储服务」变成「卖内容」，法律性质立刻改变。

📄 依据：`docs/review/online-ebook-subscription-compliance-2026-10-04.md`（在线书库为何被否）

### 4.4 技术方案

| 项 | 决定 | 理由 |
|---|---|---|
| **存什么** | **原始文件（epub / txt）**，不是解析后的章节 | epub 本身是压缩包 ⇒ 体积最小；端侧解析器（`epub_parser.dart`）直接复用 |
| **存哪** | **对象存储（COS）**，不是 VPS 磁盘 | VPS 只有 40 GB 且外网流量贵；COS 便宜、无限扩容 |
| **跨用户去重** | 🔴 **不做** —— 按用户隔离 | 跨用户去重会泄露「**有别人也上传了这本书**」⇒ 隐私问题 |
| **键** | `user_id` + `content_hash`（已有）| 跨设备身份 v2 已解决 |
| **换机流程** | 登录 → 书架全在 → **点开自动下载**（转圈）→ 直接读 | ✅ 真正的「不丢」；**不需要重新导入** |
| **配额** | 订阅分层：免费不同步 / 订阅 N GB | 与上一轮额度制同一模式 |
| **上传时机** | 导入后**后台**上传（不阻塞导入完成）| 导入是本地动作，上传是附带 |
| **删除** | 删书 → 同时删云端对象 | 见 §六 |

### 4.5 书单（元数据）仍要同步 —— 但它是**附带**，不再是主角

| 字段 | 体积 |
|---|---|
| `title` / `author` / `language` / `source_format` / `source_name` | ~160 B |
| `chapter_count` / `char_count` / `added_at` / `content_hash` | ~96 B |
| **合计** | **≈ 260 B / 本** |

它让书架在**下载正文之前**就能显示（体感「立刻可见」），并与已有的
`book_progress` / `claimPendingForBook` 认领机制接上。

### 4.6 实现清单（重排）

| # | 层 | 做什么 |
|---|---|---|
| 1 | 存储 | 开通 COS bucket（**私有读写**）|
| 2 | 后端 | 签发**预签名 URL**（上传 / 下载），凭证不落客户端 |
| 3 | 后端 | `sync_handlers` 加 `books`（元数据）+ `sync_book` 表 + **软删** |
| 4 | 后端 | 书籍文件走**独立端点**（不进 sync 的 JSON 通道 —— 那是给结构化数据的）|
| 5 | 端侧 | 导入后**后台上传**；书架读不到本地文件时**按需下载** |
| 6 | 端侧 | 配额检查 + 超限提示（订阅引导）|
| 7 | 合规 | 订阅文案改为「云端存储空间」措辞 |

## 四-b、⛔ 原「只同步书单」方案（**作废** · 保留作记录）

> 🔴 以下方案与理由**均已作废**（白哥 2026-10-07 推翻）。
> 保留它是为了让后来者看到「当时的判断错在哪」，**请勿据此实施**。

### 原：同步哪些字段（`book` 表）

| 字段                              | 体积              | 说明                       |
| ------------------------------- | --------------- | ------------------------ |
| `title` / `author` / `language` | ~120 B          | 书架列表要显示的就是这些             |
| `source_format` / `source_name` | ~40 B           | 「从哪个文件来的」，帮用户认出是哪一本      |
| `chapter_count` / `char_count`  | 8 B             | 进度百分比要用                  |
| `content_hash`                  | 64 B            | **跨设备身份**（已有，v2 加的）      |
| `added_at`                      | 24 B            | 排序                       |
| **合计**                          | **≈ 220 B / 本** | **50 本 ≈ 11 KB** ⇒ 完全可同步 |

### 换机体验（这是方案的价值所在）

```
① 新机登录 → 书架【立刻可见】：书名、作者、进度全在
② 点开 → 提示「正文在本机，请重新导入这本书」
③ 用户导入同一文件 → 算出 content_hash → 命中 → 进度自动认领
```

🔑 **第 ③ 步的机制已经实现**（`ebook/book_progress_sync.dart` 的 `claimPendingForBook`），  
不需要写任何新逻辑 —— 书单同步只是让用户在重新导入**之前**就能看到书架。

> 📌 判据：**「书没了」和「书在，但要重新导入」是两种体验。**  
> 前者让用户以为数据丢了，后者是一个明确的、一步就能完成的动作。

### 实现清单（供评估工作量）

| # | 层  | 做什么                                                                               |
| - | -- | --------------------------------------------------------------------------------- |
| 1 | 后端 | `sync_handlers.rs` 加 `books: Vec<BookInput>` / `BookOut` + `sync_book` 表 + upsert |
| 2 | 后端 | **按 `content_hash` 当键**（不是 `book.id` —— 那是端侧 uuid，两台设备不同）                         |
| 3 | 后端 | **软删**（同 bookmark 的教训：并集同步下硬删会复活）                                                 |
| 4 | 端侧 | `sync_service` 加 `'books'` push；pull 后写回 `book.db`                                |
| 5 | 端侧 | 合并规则：`added_at` **较早**胜（保留最早导入时间）                                                 |
| 6 | UI | 书架里「云端有条目但本地无正文」的态 + 「重新导入」入口                                                     |

## 五、⛔ 原「为什么章节正文**不能**同步」—— **整节作废**（保留作记录）

> 🔴 **2026-10-07 晚作废**（白哥推翻）。原文两条理由**都站不住**：
> ① 「上传正文 = 托管他人作品」→ **过度推导** —— 正解见 §4.3（**私人存储 ≠ 向公众提供**）；
> ② 「成本随用户数线性增长」→ **根本没算单价** —— 正解见 §4.2（实测占收入 **0.12%**）。
> **以下内容仅为记录当时的判断，请勿据此实施。**

### 原：① 合规：上传正文 = 我们在托管他人作品

用户导入的 epub **很可能是有版权的书**。个人自己读是私事；**一旦上传到我们的服务器，  
我们就在事实上变成了「在线书库」** —— 而那条线本项目**已经明确否掉**  
（NPPA 网络出版服务许可 + ICP 经营许可，个人主体不可得）。

> 🔴 这不是「体积大所以不做」，是**做了就改变产品法律性质**。  
> 与「不做在线书库」那条既定裁决是同一件事，只是入口换成了「同步」。

### ② 成本/体积：随用户数线性增长

|           | 估算                          |
| --------- | --------------------------- |
| 单本正文      | 1 – 10 MB                   |
| 10 本 / 用户 | 10 – 100 MB                 |
| 服务端       | 存储 + 流量 + 备份，**全部随用户数线性增长** |

⇒ 与「零边际成本」模型冲突 —— 与上一轮「LLM 制卡」是**同一类问题**：  
**成本不可摊薄 + 用户行为驱动 ⇒ 不该无限免费承担。**

## 六、一个需要白哥拍板的问题：删书要不要跨设备传播？

|    | 传播（软删同步）                 | 不传播                            |
| -- | ------------------------ | ------------------------------ |
| 行为 | A 机删书 → B 机书架也没了         | A 机删书 → 同步后**又回来**             |
| 代价 | B 机本地正文变成**孤儿文件**（要一并清理） | 用户看到「删了又自己回来」（同 bookmark 硬删的坑） |
| 结论 | ✅ **建议传播**               | ❌ 已有前车之鉴                       |

⇒ 建议：**软删 + 传播**，且删书时**同时清理本地章节**（否则磁盘上留下孤儿正文）。
