## 一、痕迹不在 🔴 **根因已定位**

### 1.1 证据链（可直接复核）

```
写：reader_screen._writeBackLookup(ref, {wordId, spelling})      ← 🔴 签名里没有 articleId
      → repo.recordLookup(wordId:, spelling:)                     ← 🔴 调用也没传
读：user_word_repository.lookupsForArticle(articleId)
      → SQL: WHERE le.article_id = ?1                             ← 按文章过滤
```

- `recordLookup({wordId, spelling, articleId, sentence, position})` —— **`articleId` 是可选参数**
- `_writeBackLookup` 的签名只有 `{String? wordId, required String spelling}` —— **根本不接收它**
- 两个调用点（词库内 / 词库外）**都没传**
- `git log -S "articleId: widget.articleId" -- reader_screen.dart` → **空 = 历史上一行都没传过**

⇒ **`lookup_event.article_id` 写进去的是 `null`** → `WHERE le.article_id = ?1` 永不匹配
⇒ **`lookups` 恒为空** → 痕迹恒不显示。

### 1.2 🔑 为什么「之前一直是好的」—— 这个疑问也有答案

`articleLookupsProvider` 是 **`27e533f`（端侧接入服务端内容池）** 才引入的。
在那之前阅读页用的是 **Step 3.4a 的 mock 正文 + 写死的 lookups** —— **那时痕迹当然显示**。
接入真实数据源时，这个 `articleId` 的缺口就埋下了，只是**没有人专门去看痕迹**，所以没暴露。

🔑 这正是 S4 的**副作用价值**：换渲染方式时我要求白哥「专门验痕迹」→ **把一个沉睡的缺口照出来了**。

### 1.3 旁证：S4 的编码/渲染链本身是好的

我用 `id=1444` 的**真实正文**跑了一个纯 Dart 探针（复刻 `gpt_markdown` 的 `maskInlinePatterns`）：

| 环节 | 结果 |
|---|---|
| 注入标记（`injectTraceMarkers`）| ✅ 56 个 fresh + 16 个 reviewing（= 36 个词）|
| mask（解析前提升为哨兵）| ✅ 36 个哨兵 |
| 还原（`expandInlinePatterns` 的逻辑）| ✅ **36/36 全部还原成功，0 失败** |

⇒ 「标记 → 哨兵 → 还原」全链路可行。**缺的只是上游数据**（`tiers` 为空）。

### 1.4 修复方案

**方案 A（推荐）**：把 `articleId` 沿调用链接下去
```dart
// reader_screen：_lookupWord 是顶层函数 → 加一个具名参数
Future<void> _lookupWord(..., {required int articleId})
  → _writeBackLookup(ref, articleId: articleId, wordId: ..., spelling: ...)
  → repo.recordLookup(articleId: articleId, ...)
```
- 改动面：`reader_screen.dart` 1 个文件（3 处签名/调用）+ 已有可选参数无需改 repository
- 风险：极低（只多写一个已有列）
- ⚠️ **存量 `lookup_event` 的 `article_id` 仍是 NULL** → 老数据无法回填（无从得知当时的文章）→ **痕迹从「修复后新查的词」开始生效**

**方案 B**：改读取侧（不按 article 过滤）
- ❌ 不可行 —— 「痕迹」的语义就是「**这篇**文章里我查过的词」，全局标记会到处乱标

**方案 C**：补一条断言（**应随方案 A 一起做**）
- 断言「`recordLookup` 的调用点必须传 `articleId`」—— 否则它会安静地再退化一次
- 依据：本项目既有判据「**光修 bug 不够，要补接线断言**」

## 四、转义没消化 🔴 **根因已定位（S4 相关）**

### 4.1 现象（用白哥指的那篇实测）

`id=1444 HTTP QUERY Method: A Simple Guide`（S3 后重抓，**已是 Markdown 格式**），正文实际内容：

```
Most developers are familiar with HTTP methods like GET, POST, PUT, PATCH, and DELETE\.
The \"QUERY\" method is designed for read-only requests…
\{  \"city\": \"Noida\",  \"minAge\": 25, …
```

实测**全文含 97 个反斜杠**。

### 4.2 根因：产出侧与消费侧「对转义的理解」不一致

| 侧 | 行为 |
|---|---|
| **产出侧**（后端 `dom_smoothie`）| 输出**标准 CommonMark 转义**（`\.` `\"` `\{` `\}` …）—— 句号、引号、花括号**本来都不需要转义**，它是保守地全转 |
| **消费侧**（端侧 `gpt_markdown` 1.3.0）| 🔴 源码原话：`Only \| is unescaped: a general \X rule would change how \*, \_ and friends render across every document.`<br>（`plusparse/inline_parser.dart:297-303`）|

⇒ **CommonMark 规定 `\` + ASCII 标点 = 该标点的字面值**（反斜杠被吃掉）。
   而 `gpt_markdown` **只实现了 `\|` 这一种** → 其余 `\X` **原样显示** → 白哥看到反斜杠。

### 4.3 🔴 我的责任（如实写）

选包时我核对了：API 签名、能力覆盖（围栏 / 内联代码 / 标题）、依赖栈、体积。
**漏了一项**：**它是否符合 CommonMark 的转义规则**。
而这一项恰好是**产出侧大量使用**的东西（dom_smoothie 的风格就是全转义）。

📌 判据（应进 skill）：**核对「包支持某项语法」时，要连「它的容错/边缘规则」一起核** ——
「支持 Markdown」不等于「符合 CommonMark」。**产出侧用了标准写法，消费侧只实现子集**，就会静默显示错。

### 4.4 修复方案（三选一）

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| **A. 端侧前置消化** | 渲染前把 `\<ASCII标点>` → `<标点>`（**必须跳过代码块/行内代码/URL** —— 那里 `\` 有意义）| 不动后端；产出侧保持标准 Markdown | 需要正确的分区扫描（**我们已有现成框架**：`injectTraceMarkers` 的扫描器就是这个模式）|
| **B. 后端后处理** | 剥掉**不必要**的转义（`\.` `\"` `\{` `\}`…），保留语法位的（`\*` `\_` `\#`）| 端侧零改动 | 要精确判断「哪个位置需要转义」，容易误伤；且**后续换渲染器时要回滚** |
| **C. 换渲染器** | 换一个符合 CommonMark 的包 | 根治 | 成本最大；1.3.0 的其他能力（懒渲染 / 流式）已适配 |

**我倾向 A**：`\X` 的消解规则简单（ASCII 标点表），且分区逻辑可复用已有扫描器；
**B 的隐患**是「后端替消费侧做决定」，将来换渲染器又要撤。

⚠️ **两方案都需要先扩断言**：拿 `id=1444` 的真实正文当 fixture，断言「渲染前文本里不再有不必要的 `\`」，**且代码块内的 `\` 原样保留**。

## 七、TTS 坏了（单词 / 例句朗读）✅ **根因已确认：语速超范围**（非 S4）

> 🆕 **2026-10-02 17:3x 定案。** 白哥两条反馈把答案钉死了：
> ① 点喇叭后**变成停止图标** ② **拖动语速配置后就好了**
> ⇒ **变量 = 语速值**。下面是完整的因果链与修复方案。

### 7.0 🎯 结论（一句话）

**`_speechRate` 默认 1.5 超出了 `flutter_tts` 自己声明的合法范围（flutter 侧 max = 1.5 → Android 3.0），
导致引擎接受朗读请求但不产生声音；而插件把这个失败静默吞掉了。**

### 7.0b 🔑 两条反馈如何定位到它（推理链，无猜测）

| 反馈 | 推出的信息 |
|---|---|
| **点喇叭后变「停止图标」** | 看代码：`state = TtsState.playing` 在 `speak()` **之前**设；`speak` 返回非 1 会**改回 stopped**。<br>⇒ 图标停在「停止」= **`speak` 返回了 1** = **引擎接受了朗读请求**（不是插件没初始化、不是引擎拒绝）|
| **拖过语速后就好了** | ⇒ 唯一被改动的**输入变量是语速值** ⇒ **语速就是根因** |

**两条合起来**：引擎接受了 → 但无声 → 且与语速强相关。

### 7.0c 🔴 为什么这个失败「完全静默」（读到了插件源码级证据）

`flutter_tts-4.2.5/android/.../FlutterTtsPlugin.kt`：

```kotlin
"setSpeechRate" -> {
    setSpeechRate(rate.toFloat() * 2.0f)    // 🔴 Android 侧乘 2
    result.success(1)                        // 🔴 硬编码成功 —— 永不报错
}

private fun setSpeechRate(rate: Float) {
    tts!!.setSpeechRate(rate)                // 🔴 Android 的返回值（ERROR/SUCCESS）被丢弃
}
```

⇒ **三层静默叠加**：
1. Android 引擎的 `setSpeechRate` 返回 ERROR → **被插件丢弃**
2. 插件对 Dart **硬编码 `success(1)`** → Dart 侧以为成功
3. 我们的代码**没有任何范围校验**（全库无 `clamp`、无 `getSpeechRateValidRange`）
⇒ **全程零报错、零异常**，只是没声音。**「静默失败」的教科书案例。**

### 7.0d 🔑 为什么「之前一直是好的」—— 有确定解释

| 时间 | `_speechRate` 默认值 |
|---|---|
| 06-26 ~ 07-10 | **1.0** |
| **07-11（`c49673c`）起** | 🔴 **1.5** |

**语速持久化在 `SharedPreferences('tts_speech_rate')`**，而代码是：

```dart
_speechRate = prefs.getDouble('tts_speech_rate') ?? 1.5;   // 🔴 读不到才用默认
```

⇒ 完整时间线（**与全部现象自洽**）：

```
07-11 之前装过 App  → prefs 写入 1.0（当时的默认）→ 一直正常
07-11 代码把默认改成 1.5  → 但 prefs 里已有 1.0 → 【继续用 1.0】→ 仍然正常
                                      ↑ 这就是「一直好」的原因：老值掩盖了坏默认
我要求「装之前先卸载旧包」（清单 §0.3）
        → SharedPreferences 被清空
        → 首次读取拿不到值 → 落到默认 1.5 → 🔴 无声
白哥拖动语速 → 写入一个安全值 → ✅ 恢复
```

### 7.0e 🔴 这不是「偶发」—— 它对新用户是**必现**的

| 场景 | 结果 |
|---|---|
| **全新安装 / 卸载重装**（prefs 为空）| 🔴 **必然落到默认 1.5 → 必然无声** |

### 7.2 修复方案（需你批准 · 三处一起改）

#### ① 🔴 加**范围钳制**（**这是唯一可靠的防线**）

为什么必须有：**插件永不报错**（§7.0c）⇒ 只能靠我们自己保证值合法。

```dart
// 依据：flutter_tts 4.2.5 的 getSpeechRateValidRange() 自述（flutter 侧）
//   min: 0 · normal: 0.5 · max: 1.5      ← 它把 Android 1.0 映射为 flutter 0.5
const double kSpeechRateMin = 0.1;   // 不用 0（0 = 完全不读）
const double kSpeechRateMax = 1.5;   // 🔴 库声明的上限，别超
const double kSpeechRateDefault = ???;  // ← 见 ③
```

- **写入时钳制**：`set speechRate(v) { _speechRate = v.clamp(min, max); ... }`
- 🔴 **加载时也钳制**：`init()` 读到 prefs 的值后 clamp —— **这条解决「设备上已存的坏值」**（你这台现在就是这种状态：值是他拖动后的，但别人设备上可能还存着 1.5）

#### ② Slider 范围跟着改（`profile_screen.dart`）

| | 现在 | 改为 |
|---|---|---|
| `min` | 0.1 | 0.1（不变）|
| `max` | 🔴 **2.0**（超库上限 33%）| **1.5** |
| `divisions` | 19 | 按新范围重算（如 `(1.5-0.1)/0.1` = 14）|

#### ③ 默认值取哪个 —— **需要你定**

| 选项 | flutter 侧 | → Android | 说明 |
|---|---|---|---|
| **A** | **1.0** | 2.0 | = **07-11 之前的默认**，也是你长期在用的值 → **用户感知不变**。⚠️ 但它正好在 Android 原生文档的**上限边缘** |
| B | 0.5 | 1.0 | = **库声明的 `normal`**（= Android 正常语速）。**最稳**，但比你现在习惯的**慢一倍** |
| C | 0.75 | 1.5 | 折中（1.5 倍速）|

🔴 **我倾向 A**（与你长期在用的值一致 = 不改变当前体验），
**但如果你觉得语速可以慢一点，B 是最安全的**（完全在原生范围内，不留边缘风险）。

#### ④ 附带：给插件调用加**有界超时**（共同缺陷，与本次根因无关但同类）

```dart
await _tts.stop().timeout(const Duration(seconds: 3));
```

原因：插件在 `ttsStatus == null` 时会把调用**挂起且永不回调**（`FlutterTtsPlugin.kt:276`）——
一旦发生，UI 就**永久停在转圈、无报错、无出口**。
📌 与「静默失败」同族；本项目已有判据「时序要等条件、且必须有界」。

### 7.4 📌 本轮教训（值得沉淀）

**① 卸载重装 = 模拟新用户，会暴露「被持久化状态掩盖」的默认值缺陷**

这次的触发条件**就是我要求「装之前先卸载旧包」**（清单 §0.3）。
⇒ **判据**：**要求用户「卸载重装」之前，先想一遍「哪些状态会被清空、清空后回到的默认值是否安全」。**
（我不能回避这一点 —— 是我的操作指令把缺陷触发了。虽然它本来就会在新用户身上必现。）

**② 默认值缺陷会被「老用户的持久化值」长期掩盖**

⇒ **判据**：**改默认值时要同时检查两条路径** ——「新用户（无 prefs）走默认」与「老用户（有 prefs）走存储值」。
只测老设备（或只测自己的设备）会漏掉新用户必现的问题。

## 九、本次调查用到的可复用方法（值得沉淀）
