## 七、本轮踩到 / 记下的两条（都属「工具给假结论」家族）

### 7.1 🔴 报数错误：盘点脚本**重复计算**了目录与其内容

第一版盘点用的思路是「列 `data/` 下的条目 + 递归算大小」，结果**同时列了
`backups`/`curriculum` 目录**和**它们内部的每个文件** → 体积被算了两遍 → 报 **1588 MB**，
实际 **1061 MB**。

🔑 **判据**：**「容器与内容同时入表」时，必须明确问「我在算并集还是加总？」** ——
这类错误**不报错、只给错数**（同「口径差一层」家族）。
✅ 正确做法：**要么只列顶层并 `du -sh`**，要么**只列叶子**。
本轮与后续数字全部改用 `du -sh` 实测。

### 7.2 🔴 差点误判「文件被写坏」：**终端输出编码 ≠ 文件编码**

批量加横幅后，用 `head -4 <file>` 检查，**有两篇显示成 `鉀� **鏈�鏂囧凡浣滃簾**`**
（典型 mojibake）→ 第一反应是「我的 Python 脚本把 UTF-8 文件写坏了」。

**用三种独立方式交叉验证后确认：文件是好的**，是 **bash（Git Bash）终端用 GBK
解读了 UTF-8 输出**：

| 方式 | 结果 |
|---|---|
| `Read` 工具 | ✅ 正常中文 |
| Python 独立读（不经终端） | ✅ `首行含⛔: True`，内容正常 |
| `git diff --stat` | ✅ **87 insertions / 78 deletions**（若编码漂移会是**整文件**变红）|

🔑 **判据（已入 skill 家族）**：
- **不能用 `head`/`cat` 的输出判断文件编码** —— 它经过终端编码这一层。
- 判「文件是否被改坏」的**可靠三招**：① 用能自行处理编码的工具读（`Read`）②
  **绕开终端**用脚本读并断言关键内容 ③ 看 `git diff --stat` 的**规模**
  （整体重写 vs 局部修改）。
- ⚠️ **尤其危险的是「反向假结论」**：若当时直接 `git checkout` 恢复，
  就会**把已经加好的横幅和脱敏全部丢掉**，而且会以为自己「修好了一个 bug」。

📌 与既有判据同族：**工具/写法错 → 静默给假结论**。这是第 N 次，且这次差点导致**错误回滚**。
