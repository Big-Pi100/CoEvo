📌 **这降低了紧急度，但不改变「必须吊销」的结论**：

- DeepSeek 的 API Key **不会自动过期**（除非手动吊销）⇒ 那些 key **可能至今有效**
- 任何人都能拿它调用 → **烧白哥的额度 / 计入账单**
- ⚠️ **无法确认它们是否已失效** ⇒ 按「归零型风险用低成本手段主动控制」处理

### 归零型 vs 罚款型

| 类型 | 本例 |
|---|---|
| 🔴 **归零型**（不可逆 / 堵死后续路径） | 改公开后若 key 仍有效 ⇒ **任何人可无限调用**，且**无法事后追溯** |
| 🟡 罚款型 | 单纯的额度消耗（可充值恢复）|

⇒ 归零型那一面（**公开即不可逆**）决定了：**必须在改公开之前处理完**。

## 九、判据沉淀

- 🔴 **「仓库改公开」是**高影响动作**，动手前必须审计历史** ——
  它不只是「让别人看到当前代码」，而是**把整个历史一次性公开**。
  📌 同族：**任何「可视性 / 权限」变更都要连带审查「历史 / 缓存 / 副本」**。
- 🔴🔴 **「审计历史」与「审计当前」是两个独立动作**（本报告第一版的教训）——
  不能用「历史扫过了」代替「当前也扫过了」；
  ⚠️ **扫到一半中断 ≠ 扫描完成**（当时 `SIGTERM` 就是信号，我忽略了）。
- 🔴 **「删除了」≠「已消失」** —— git 层面与数据层面同一条判据。
- 🔑 **扫描历史时的判据**：**「出现过某字符串」≠「它是真值」** ——
  必须**看实际内容**（本次：`AKID` 命中是 `AKIDfake_...`）。
- 🔑 **哈希比对是判断「泄漏值是否生产在用」的安全手段** ——
  既不暴露值，又能精确回答「是不是同一个」（比"看前缀"强：所有 DeepSeek key 都以 `sk-` 开头）。
- 🔑 **区分「在磁盘」与「在 git」** —— 未跟踪的文件不会被公开，但**仍是泄漏面**（本报告 A vs B）。
- 🔑 **`.gitignore` 只防「某类文件名」，防不了「把密钥写进文档/脚本」** ——
  本报告的 A 正是这种情况（3 个 `.md` 文档，`.gitignore` 管不到）。
- 🔑 **修复要分「止血」与「根治」**：**轮换凭据是根治**（防已看过的人），**清历史只是防未来公开**。
- 🔑 **轮换前先确认「该密钥有没有数据后果」** ——
  PII 密钥换了旧数据不可读；**API 调用凭据换了只是换凭据**（无数据影响）⇒ 两者风险等级不同。
