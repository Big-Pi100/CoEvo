# Git 历史敏感信息审计（2026-10-05）

> **触发原因**：白哥定「出包时临时把仓库改公开」（绕过 GitHub Actions 额度耗尽）。
> 🔴 **改公开 = 连 git 历史一起公开** ⇒ 动手前**必须**先审计历史里有没有敏感数据。
> 📌 这不是「多此一举」—— **仓库可视性一变，历史里所有曾提交过的内容都变成公开的**，
> 而「删除文件」这个动作**不会**把内容从历史里删掉（`git rm` 只是新 commit 里不再有它）。

## 二、泄漏详情

| 项 | 内容 |
|---|---|
| 文件 | `backend/.env` |
| 引入 | `bb127e3`（**first commit**，2026-05-08）|
| 删除 | `97dfd8a`（MVP_DONE，2026-05-13）—— `1 file changed, 3 deletions(-)` |
| 🔴 **现状** | **已不在 HEAD**，但**仍在历史里**（`git show bb127e3:backend/.env` 可读出） |
| 泄漏内容 | `DEEPSEEK_API_KEY=` 一个 35 字符的 key（`sk-` 前缀，DeepSeek 标准格式）|
| **已暴露时长** | **约 5 个月**（2026-05-08 至今） |

### 为什么「删除了」仍算泄漏

`97dfd8a` 的删除**只让新 commit 不再包含它**。历史 commit `bb127e3` 里那个 blob **永久存在** ——
任何人 clone 后 `git show bb127e3:backend/.env` 就能读到。

⇒ **「已删除」≠「已消失」**（本项目的「删数据 ≠ 不再产生」是同一族判据，这次换成了 git 层面）。

## 三、风险定级：为什么不是「已经删了就算了」

**先用哈希确认它是否还在用**（不暴露值）：

| | 长度 | SHA256 前 12 位 |
|---|---|---|
| 泄漏的 key（git 历史） | 35 | `e022273dc3ae` |
| **服务器 `/opt/coevo/.env` 在用的** | 35 | `e63bb048272c` |

⇒ **两者不同** ⇒ 服务器用的是**另一个 key**，泄漏的这个**不是生产在用的**。

📌 **这降低了紧急度，但不改变「必须吊销」的结论**：

- DeepSeek 的 API Key **不会自动过期**（除非手动吊销）⇒ 那个 key **可能至今有效**
- 任何人都能拿它调用 → **烧白哥的额度 / 计入账单**
- ⚠️ **无法确认它是否已失效** ⇒ 按「归零型风险用低成本手段主动控制」的原则处理

### 归零型 vs 罚款型

| 类型 | 本例 |
|---|---|
| 🔴 **归零型**（不可逆 / 堵死后续路径） | 若改公开后 key 仍有效 ⇒ **任何人可无限调用**，且**无法事后追溯是谁用的** |
| 🟡 罚款型 | 单纯的额度消耗（可充值恢复） |

⇒ 归零型那一面（**公开即不可逆**）决定了：**必须在改公开之前处理完**。

## 六、修复方案

**分两阶段**（关键：第二阶段只在「要改公开」时才需要，不必现在承担代价）。

### 阶段 1 · 吊销 Key（🔴 必做，无论是否改公开）

| 谁 | 做什么 |
|---|---|
| **白哥** | 登录 DeepSeek 控制台 → API Keys → **找到那个旧 key 并吊销**（若已不在列表 ⇒ 说明早前已轮换，那更好）<br>⚠️ **不要**吊销服务器正在用的那个（哈希 `e63bb04…`） |

⏱ 约 2 分钟。**这一步做完，泄漏的实际风险就归零了**（无论历史是否干净）。

> 🔑 **为什么吊销是治本**：清历史只能防「未来公开时可见」，
> 但**无法防「过去 5 个月里已经看过的人」**（若仓库曾被访问、或被自动化爬取）。
> ⇒ **只有轮换凭据能真正止住**。

### 阶段 2 · 清历史（**改公开之前**做，现在不必）

**前置条件已满足** ✅：`backend/.env` **不在 HEAD**（已被 .gitignore + 删除）
⇒ `filter-repo --path backend/.env --invert-paths` **只清历史，不动工作区**
（📌 若该路径在 HEAD 上还有文件，`--path` 会把它**一起删掉** —— 这条要先查，已在 skill 里记为铁律 2）

**代价（必须提前知道）**：

| 影响 | 说明 |
|---|---|
| 🔴 **所有 commit hash 重写** | 历史变成「另一条链」 |
| 🔴 **5 个 tag 需重建** | `v0.1.0`~`v0.1.4`（均在 2026-10-03）—— 指向旧 hash，需重新打 |
| 服务器 / 其他克隆 | 需**重新 clone**（旧 clone 无法直接 pull，因为历史无共同祖先） |
| ✅ 部署链路 | **不受影响** —— CI 靠 **tag 名**触发，不依赖 hash（重建 tag 即可） |
| ⚠️ 若仓库曾公开过 | GitHub 的 fork / 缓存可能仍留有旧对象（`filter-repo` 管不到） |

**步骤**（详见 skill `git-history-purge`，六步）：
1. 诊断体积构成
2. 止血（本项目已完成 ✅）
3. **备份**（tar `.git`）+ **逐行快照**（事后验证「内容没变」的唯一手段）
4. 生成 `--path` 清单（按**内容特征**反查所有路径，不只记一个目录）
5. 执行 `git filter-repo --path backend/.env --invert-paths`
6. **逐项验证**（清理前后 HEAD 逐行一致）→ `force push`

## 八、判据沉淀

- 🔴 **「仓库改公开」是一个**高影响动作**，动手前必须审计历史** ——
  它不只是「让别人看到当前代码」，而是**把整个历史一次性公开**。
  📌 同族：**任何「可视性 / 权限」变更都要连带审查「历史 / 缓存 / 副本」**。
- 🔴 **「删除了」≠「已消失」** —— git 层面与数据层面同一条判据（本项目已有「删数据表」六动作）。
- 🔑 **扫描历史时的判据**：**「出现过某字符串」≠「它是真值」** ——
  必须**看实际内容**（本次：`AKID` 命中是 `AKIDfake_...` —— 我自己写的假密钥）。
- 🔑 **哈希比对是判断「泄漏值是否生产在用」的安全手段** ——
  既不暴露值，又能精确回答「是不是同一个」（比"看前缀"强：所有 DeepSeek key 都以 `sk-` 开头）。
- 🔑 **修复要分「止血」与「根治」**：**轮换凭据是根治**（防已看过的人），**清历史只是防未来公开**。
  只做后者会以为"安全了"，其实过去 5 个月的暴露无法撤销。
