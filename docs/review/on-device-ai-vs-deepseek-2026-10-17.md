# 【技术评估】iOS 端侧 AI 能否替代 DeepSeek API

*2026-10-17 · 依赖：Apple 官方文档（TN3193 / WWDC25 session 286）+ 2026-10 中国区上线进展的多方报道 + 项目内实测（prompt 模板 token 量、部署目标、LLM 调用点）*
*⭐ 结论：**现在不能替代**。三重硬阻塞 + 一处"质量待实测"。*

---

## 零、先纠正一个概念：Siri **不是** AI 接口

| 你以为的 | 实际是什么 | 能生成词卡吗 |
|---|---|---|
| Siri 能当 LLM 用 | 开发者接口是 **App Intents / SiriKit** —— 让 Siri 调你的 app 功能，或你的 app 触发意图 | ❌ **不能**。它是**意图框架**，不是文本生成接口 |
| `SiriIntelligence` / 系统自带对话能力 | 那是 Apple 自己的 UI 能力，**没有对第三方开放生成接口** | ❌ 不能 |

真正的端侧 LLM 接口只有一个：**Foundation Models framework**（iOS 26 起）。

---

## 一、Foundation Models framework 是什么（官方事实）

| 项 | 数据 | 来源 |
|---|---|---|
| 出现时间 | iOS 26 / iPadOS 26 / macOS 26（2025-09） | WWDC25 |
| 模型规模 | 约 **3B 参数**（2–4 bit 混合量化，均值 3.7 bit/weight） | Apple 公开数据 |
| 上下文 | **4096 tokens / 会话**（含 instructions + prompt + 工具定义 + 模型回答，**全部计入**） | TN3193（2026-03-31 更新） |
| 中文支持 | ✅ 支持（iOS 26.1 起 16 种语言，含简体/繁体） | `SystemLanguageModel.default.supportedLanguages` |
| 成本 | **零**（无推理服务） | — |
| 离线 | ✅ 完全离线，数据不出设备 | — |
| 结构化输出 | ✅ `@Generable` + `@Guide`，**类型保证**（比让模型"吐 JSON 再解析"可靠） | WWDC25 |
| 设备门槛 | **iPhone 15 Pro 及更新** / M1 iPad / M1 Mac | Apple |
| 可用性检查 | 必须 `SystemLanguageModel.default.availability` 分支处理（模型可能未下载完） | — |

> ⚠️ **一处不确定**：有 2026 年的报道称 iOS 27 把上下文提到 **8192**，但同批来源里另一篇仍写 4096。
> ⇒ **以运行时 `SystemLanguageModel.default.contextSize` 为准**，别信博客数字。

## 二、🔴 三重硬阻塞（本项目视角）

### 阻塞 1：**中国大陆区不可用**（最致命）

Apple Intelligence 至今**未在中国大陆正式上线**：

| 时间 | 事件 |
|---|---|
| 2026-06（WWDC26）| Apple 明确：**中国大陆暂不提供** |
| 2026-07-08 | 通过网信办生成式 AI 备案（`Shanghai-AppleZhiNeng-…`）|
| 2026-09-29 | 取得上线许可 |
| 2026-10-15 | 库克在上海确认「**10 月底发测试版**」，首批仅：实时翻译 / 书写工具 / 照片清除 |
| 2026-12（预计）| 随 **iOS 27.3** 正式推出；核心能力由**阿里 Qwen** 提供 |
| — | 🔴 **Siri AI 明确不在中国上线**（监管要求）|

我们的 App 是**中国区、中文用户、仅 iOS** ⇒ 端侧模型能力在我们主战场**用不了**。
（有技术博客直接写明 Foundation Models "not for accounts in mainland China"。）

### 阻塞 2：上下文预算**刚好卡边，零余量**

实测我们的词卡 prompt 模板 `backend/prompts/wordlib_contract.md`：

```
文件字节        11580
中文字符        93
其余字符        11124
→ 估算 tokens   3099      （Apple 口径：CJK 1 字 ≈ 1 token，拉丁 3.7 字符 ≈ 1 token）
```

| 预算项 | tokens |
|---|---|
| prompt 模板 | **3099**（占 4096 的 **76%**）|
| 输出上限（`max_tokens=900`）| 900 |
| **剩给「词条 + 上下文句」** | **约 97 ～ 997** |

⇒ 不是"必然爆"，而是**任何余量都没有**：

- 模板里再加一条规则 ⇒ 危险
- 想给模型几个 few-shot 例子 ⇒ 爆
- 想多轮追问（比如"这个词的例句再自然点"）⇒ 爆
- 想注册工具（tool calling）⇒ 爆

而 iOS 27 若真是 8192，这层压力会缓解 —— **但阻塞 1 仍在**。

### 阻塞 3：设备门槛 vs 我们的部署目标

| | 现在 | 用 Foundation Models 需要 |
|---|---|---|
| `IPHONEOS_DEPLOYMENT_TARGET` | **13.0** | **26.0** |
| 可用设备 | iPhone 6s 起 | **iPhone 15 Pro 起** |

⇒ 不是"抬个版本号"，是**主动砍掉绝大多数存量用户**。中国区一个个人 App 做这个取舍，代价极高。

## 三、还要问一句：**质量**（唯一必须实测、不能靠推断的）

我们的契约不是"随便说说"：

- 11.5 KB 的规则文档、8+ 个字段
- `entry_type` 必须分类（word / phrase / abbreviation…），且各有特例
- 词素拆分（prefix/root/suffix + origin + meaning）
- IPA 转写（phrase 要转整个短语）
- 严格的 JSON schema + `temperature=0.1`

**3B 模型能否稳定遵循这种多分支契约 —— 没有实测数据，我不做断言。**
但方向性判断是：DeepSeek 是百亿参数以上，**指令遵循与结构稳定性显著强于 3B**；
Apple 官方文档也明说这类模型"针对摘要 / 提取 / 分类做了优化"，**不是通用推理器**。

📌 若真要评估，唯一可信的做法：拿**同一批 20–30 个词**（含 phrase / abbreviation / 多义项特例）
分别跑 DeepSeek 与端侧，**按我们现有的校验器**判通过率 —— 不看主观感受，看 `llm_card` 的校验通过数。

## 四、✅ 但有一项端侧能力是**真的可用**：Translation framework

| 项 | 数据 |
|---|---|
| 引入 | **iOS 17.4 / 18.0**（比 Foundation Models 早得多）|
| 能力 | **端侧离线翻译**（Core ML，系统供模型）|
| 成本 | **免费**，无 API key |
| 语言包 | 首次需下载（走网络），之后离线可用 |
| 质量 | 官方博客口径：**"不错，但不是最好"**；专业场景仍建议云端 |
| 限制 | 🔴 只支持 **SwiftUI 修饰符**（`.translationTask`）⇒ Flutter 需自写 **native 插件**；🔴 **模拟器跑不了**，只能真机测 |

### ⚠️ 但它只能替代「整段翻译」，替代不了「制卡」

而**整段翻译是我们的订阅权益之一**（`translation.rs`，≤800 字符，`max_tokens=2400`）。

⇒ 白送端侧翻译 = **订阅权益贬值**。这是产品决策，不是技术决策：

| 若这么做 | 后果 |
|---|---|
| 翻译改成端侧免费 | 「订阅=云端同步+翻译额度」的卖点少一块；且质量下降（"不错"≠DeepSeek 水平）|
| 保持服务器翻译，端侧仅作兜底（离线时降级） | ✅ 我推荐的形态：**离线可用**是体验提升，**不冲击订阅** |

---

## 五、成本视角：这个动机**其实不强**

我核了调用链：**端侧从不直连 LLM**，全部走后端（`llm_card.rs` / `translation.rs`）。

而制卡已有**三层缓存**：

| 层 | 作用 |
|---|---|
| 端侧缓存 | 本机已生成的卡不再请求 |
| 服务端全局缓存（跨用户）| 同词只生成一次 |
| `word.db` | 离线兜底，随版本发布 |

⇒ **制卡是一次性成本，不是每用户每次查询都调一次**。
⇒ 「用端侧省 DeepSeek 钱」这个动机，在我们当前架构下**收益很小**（真正花钱的是翻译，而翻译恰好是端侧最不擅长的：质量 + 800 字符 × 2400 tokens 输出）。

---

## 六、结论与建议

| 功能 | 能否用端侧替代 | 判据 |
|---|---|---|
| **LLM 制卡** | ❌ **现在不能** | 中国区不可用 · 模板已吃 76% 上下文 · 设备门槛砍掉存量用户 · 3B 契约遵循待实测 |
| **整段翻译** | 🟠 **技术上能**（iOS 18 Translation） | 但会削弱订阅卖点 ⇒ 建议只作**离线兜底**，不替换 |
| **查词释义** | ❌ 不适用 | 我们本来就走 `word.db` 本地库，不调 LLM |

### 唯一值得现在做的一件事

**翻译加"离线兜底"**（端侧 Translation）—— 只在网络失败时启用，文案上不承诺质量。
但要写 native 插件，成本不低，**建议排到上架之后**。

### 🔴 重新评估的触发条件（写死，别靠记忆）

1. **中国版 Apple Intelligence 正式上线**（预计 2026-12 / iOS 27.3）**且**确认
   `SystemLanguageModel.default.availability == .available` 在**国行设备 + 中国区账号**上成立
2. **且** `contextSize` 实测 ≥ 8192（否则模板空间太紧）
3. **且** 用现有校验器跑 20–30 词的通过率，**不低于 DeepSeek 的 90%**

三条同时满足才值得动手。缺任一条 ⇒ 继续用云端。

📌 判据提醒：**「Apple 有 AI」≠「我们的用户能用」** —— 地域、设备、账号三者是独立闸门，
必须逐个验证，不能因为"最新 iPhone 能跑"就当成功能可用。
