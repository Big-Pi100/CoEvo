# 用户自定义订阅源 · 可行性评估（2026-10-07）

> **触发**：白哥问 —— 「信息流是否可以加入用户自定义订阅源，能否对订阅源进行解析」。
>
> **结论**：✅ **可以做，但必须「端侧抓 + 端侧解析」** ——
> 走服务端在**成本**与**合规**两条上都不成立（§三）。
> 端侧技术栈**已经齐备**（`xml` / `http` / `sqflite` 都已在依赖里，不用加包）。
> 主要工作量在 **正文提取**（服务端那部分是 1171 行）。
> ⚠️ **本轮未改任何代码**（可行性评估）。

---

## 一、现有信息流架构（服务端集中式）

| 组件 | 规模 | 职责 |
|---|---|---|
| `content_fetch.rs` | 1862 行 | 抓取调度 · UA 处理（**`://` 会静默断连**，实测踩过）|
| `content_rss.rs` | 1078 行 | RSS/Atom 解析（日期格式：4 个源里 3 个是 RFC 2822）|
| `content_extract.rs` | 1171 行 | **抓原网页 → 提取正文**（RSS 常只给片段）|
| `content_quality.rs` | 1300 行 | 质量检测 |
| **合计** | **5411 行** | |

源清单一律在**服务端**：`content_source` 表（seed 22 个源），用户**看不到也改不了**。

### 🔑 表里有个决定性字段

```sql
redistributable INTEGER NOT NULL DEFAULT 0
  -- 1 = 允许**全文**入库并展示；0 = **只存摘要 + 链接**（Flipboard 模式）
license           TEXT      -- public_domain | cc | news | esl
```

⇒ **连我们自己精挑的 22 个源，都要逐个标注「能不能全文入库」与「许可类型」。**

📌 **这直接决定了自定义源的正确做法**（见 §四）。

## 三、🔴 为什么**不能走服务端**（两条硬伤）

### 3.1 成本：随用户数线性增长

用户在服务端加源 ⇒ **我们用服务器替他抓** ⇒
抓取频率 × 源数 × 用户数 ⇒ 资源开销**没有上限**。

而现在 22 个源是**中心化抓一次、全体共享**，成本 **∝ 源数**（与用户数无关）。

### 3.2 合规：这一步会让我们从「工具」变成「内容提供者」

| 项 | 服务端抓（❌）| 端侧抓（✅）|
|---|---|---|
| 内容由谁获取 | **我们** | 用户自己的设备 |
| 内容是否落在我们服务器 | **是**（要入库才能发给 App）| **否**（只在用户设备）|
| 法律定性 | **内容提供者** ⇒ 需为我们抓来的侵权内容负责 | **RSS 阅读器工具**（同 Reeder / NetNewsWire）|
| ICP 备案性质 | 可能触及**经营性/内容服务** | 工具类，既有备案即可 |
| 用户加了侵权源 | 🔴 **责任在我们** | 用户自身行为（类比浏览器）|

⚠️ 与既有教训一致：记忆里「⛔ **不做在线书库**（NPPA + ICP 双证 · 个人不可得）」——
**正是同一类风险**：一旦由我们托管内容，资质门槛立刻抬高。

> 🔑 **判据：凡是"用户指定的外部内容"，不要让内容经过我们的服务器。**
> 经过服务器 = 我们成了发布者；只在两端之间 = 我们只是通道。

## 四、正确的产品定义（**照 `redistributable` 的思路**）

| | 内置源（现有）| **自定义源（新增）** |
|---|---|---|
| 谁选 | **我们**（精选 + 人工标注许可）| **用户** |
| 谁抓 | 服务端（集中一次，全体共享）| **用户设备** |
| 存哪 | 服务端库 | **只在用户设备**（不上传）|
| 版权 | 已标注 `license` / `redistributable` | ⚠️ **我们不知道** ⇒ **只展示，不托管** |
| 分级 | 有 `cefr_hint` | ⚠️ **无法预判** ⇒ 如实标注「未分级」|

**必须在产品里写清**（合规免责）：
> 「自定义源由你自行添加，内容版权归原站点所有；本应用不托管、不修改这些内容。」

### ⛔ 建议**不做**的两件事

1. **不做「源分享/源广场」** —— 那会让它变成 UGC（用户发布给别人看），
   而「不做自由文本 UGC」是已定原则（见 `ugc-comments-feasibility`），且会重新引入审核责任。
2. **不上传自定义源的内容** —— 一旦上传（比如为了跨设备同步文章），服务端又变成托管方。

## 五、端侧要做什么（**不能照搬 5411 行**）

| 模块 | 端侧怎么做 | 难度 |
|---|---|---|
| **RSS/Atom 解析** | `xml` 包，抓 `<item>` 的 `title / link / pubDate / description` | 🟢 低（~200 行；日期格式要兼容 RFC 2822 与 ISO）|
| **源列表管理** | 本地表（url / 名称 / 分类 / 添加时间）+ 增删 UI | 🟢 低 |
| **正文提取** | 🔴 **难点** —— 服务端那部分是 1171 行（含站点特例）| 🟡 **中偏大** |
| **质量过滤** | 端侧不做（或最简）| 🟢 —— 用户自选的源，质量自负 |
| **分级** | 不做（标注「未分级」）| 🟢 |
| **存储** | 本地表，**不参与同步**（除非只同步"源列表"本身）| 🟢 |

### 5.1 正文提取的三条路（按成本）

| 方案 | 做法 | 评价 |
|---|---|---|
| **① 只用 RSS 给的 description** | 不抓原网页 | 🟢 **最省**，但很多源只给片段（记忆：NPR 33/33 全是片段）⇒ 体验打折 |
| **② 端侧抓原网页 + 通用正文提取** | 移植"按密度/语义找正文块"的通用算法 | 🟡 中等，是**推荐起点** |
| **③ 用成熟包** | 找 Dart 的 readability 实现 | 🟡 需先调研质量（`readability` 类的 Dart 包成熟度未核实）|

> 🔑 **务实起点：① 先上，② 迭代**。因为自定义源是「用户自选」，
> 体验打折的责任归属清楚；而**先把能力做出来**才能验证需求是否真实存在。

## 六、风险与限制（如实列出）

| 风险 | 说明 | 处理 |
|---|---|---|
| **境外源在用户网络下不通** | 现有 22 源多为境外站（NPR 等）| ⚠️ 用户自身网络条件问题 ⇒ 做成**明确的失败提示**，别静默 |
| **源失效/改格式** | 外部源随时挂 | 每源独立失败，**不影响其它源**（现有抓取已是逐源隔离）|
| **无质量过滤** | 用户可能加到垃圾源 | 用户自负；可给"该源近 7 天抓不到内容"的提示 |
| **无难度分级** | 无法给 CEFR | 如实标注「未分级」 |
| **内容合规** | 用户可能加违规源 | 端侧不托管 ⇒ 责任在用户；产品内明示 |
| **抓取被 WAF 拦** | 端侧 UA 无法像服务端那样调优 | 用默认 UA 即可（服务端那次 UA 调优是**为特定 CDN** 做的特例）|

## 七、与订阅的关系（承接上一轮的框架）

按「**端侧抓取 ⇒ 服务器零成本 ⇒ 免费**」的判断（判据源见 `product-core-expansion-2026-10-07.md` §4.3）：

> ⚠️ **2026-10-07 晚注**：§4.3 原用的「零边际成本 ⇒ 免费」判据**已被白哥纠正并作废**
> （那是 **LLM 制卡** 的情形 —— 每次都真调 LLM）。
> 但**本节结论不受影响**：自定义源是**端侧抓取 + 端侧解析 RSS**，**不调 LLM、不占服务器**，
> ⇒ 「服务器零成本」这一条对本能力**依然成立**。

| 能力 | 归属 | 理由 |
|---|---|---|
| **自定义源 + 端侧抓取** | ✅ **免费** | **服务器零成本**（用户设备抓）⇒ 锁进付费墙没有意义；<br>且它显著提高**日活与黏性**（用户把自己的信息源搬进来）|
| **跨设备同步"源列表"** | 🟡 归**同步**（订阅）| 与现有同步权益同源（源列表是"用户配置"，属于数据资产）|

⚠️ 但注意：**同步源列表 ≠ 同步源内容**。前者是几十字节的配置，后者会让我们变成托管方。
