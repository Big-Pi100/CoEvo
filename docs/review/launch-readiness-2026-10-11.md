## 二、🔴 B · 支付（IAP）—— 你问的重点：**不只是没测试，后端配置是零**

### 2.1 实测证据（SSH 只读）

```
# 服务唯一的环境变量来源
EnvironmentFile=/opt/coevo/.env

# .env 的键名（只看名，不看值）—— 共 10 个，没有任何 IAP_*
COEVO_ADMIN_KEY / COEVO_HOST / COEVO_PII_KEY / COEVO_PORT
DEEPSEEK_API_KEY
TENCENT_SES_FROM / _REGION / _SECRET_ID / _SECRET_KEY / _TEMPLATE_ID
```

🔴 **`IAP_KEY_ID` / `IAP_ISSUER_ID` / `IAP_PRIVATE_KEY` / `IAP_ENVIRONMENT` 四个全缺。**

### 2.2 这条会导致什么（代码级因果链）

`iap_handlers.rs` 的 `iap_verify_handler` 顺序：

| 步 | 动作 | 缺配置时 |
|---|---|---|
| 1 | 鉴权（`verify_auth`）| 401 |
| 2 | `transactionId` 非空 | 400 |
| **3** | **`IapConfig::from_env()`** | 🔴 **503 `IAP 服务端未配置`** |
| 4 | 调 App Store Server API 验单 | — |

⇒ **真机哪怕购买成功、拿到 Apple 回执，上报后端也只会拿到 503** ⇒ 订阅**不会生效**
⇒ 用户付了钱、权益没开 ⇒ 这是**最坏的一类线上事故**。

> ✅ 代码本身**是对的**：缺配置时**显式 503 + 明确原因**（不让端侧误判成「这笔交易无效」）——
> 设计良好，只是**配置没做**。

## 三、🟠 C · 注销时向 Apple 撤销授权 —— **未实现，且有时效性**

| 项 | 实测 |
|---|---|
| 后端 `auth.rs` / `user_purge.rs` 调 Apple revoke 端点 | ❌ **无**（`grep revoke` 只命中 `apple_auth.rs` 的**验签**注释，没有撤销调用）|
| Apple 登录本身 | ✅ 已实现（`/api/auth/apple` 路由实测 422 · 端侧 `sign_in_with_apple` 已声明）|

### 3.1 为什么它算风险

Apple 对 **Sign in with Apple** 的要求：账号注销时须调 **REST API 撤销**该用户的 Apple token。
我们已上 Apple 登录 ⇒ 这条**适用**。

### 3.2 🔴 时效性（`pending-todos-2026-10-09` §七 已单列）

`authorizationCode → refresh_token` **只在「登录那一刻」由 Apple 返回**：

- **事后补不了** ⇒ 现在已登录过的用户，将来补功能也**永远无法撤销**他们的授权
- ⇒ 要做就**必须与登录同一轮**（或至少在提审前，让新登录的用户带上）

⚠️ **决策点**：现在做（改登录 + 注销两处，需出包）／还是先上线、接受该风险。
