## 五、🔴 本轮新踩到的两个坑（都是真实教训）

### 5.1 `cp` 覆盖运行中的二进制 ⇒ **`Text file busy`**

```
cp: cannot create regular file '/opt/coevo/bin/coevo_backend': Text file busy
```

EXT4 拒绝写「正在执行的文件」。**CI 走 rsync 所以从没遇到**（rsync 用临时文件 + rename）。
⇒ **修法：同分区 `mv`（原子 rename）** —— 运行中的进程继续持有旧的 inode，
所以**不需要先停服**，零停机。

```bash
cp /tmp/coevo_new/coevo_backend /tmp/coevo_backend.staged
chmod 755 /tmp/coevo_backend.staged
mv /tmp/coevo_backend.staged /opt/coevo/bin/coevo_backend   # ⚠️ 跨分区 mv 会退化成 copy ⇒ 又报同样的错
```

### 5.2 拿 `401` 当「新端点已注册」的判据 ⇒ **误报两条**

`POST /api/translate`（带 `{}`）返回 **422**、`POST /api/books/blob` 返回 **400** ——
我第一版脚本断言「**必须 401**」，于是**误报 2 条失败**。

**根因**：axum 的**提取器（`Json` / `Multipart`）在鉴权之前执行**：

| 情形 | 状态码 |
|---|---|
| 端点不读 body（GET / DELETE），无 token | **401** |
| 读 body，但无 `Content-Type` | **415** |
| 有 `Content-Type`，字段不全 | **422** |
| 收 multipart 却无 body | **400** |
| body 合法 | 才进 handler → **401** |

⇒ 📌 **判据只能是「非 404」**。想拿到 401 就得在验证脚本里**维护一份请求 schema 副本**，
它会随后端字段变动而漂 ⇒ **判据自己变成新的故障源**。
🔑 **「机械判据只做到「路由存在」这一层」** —— 再往下就该交给真机端到端了。
