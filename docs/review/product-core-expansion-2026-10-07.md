# 产品核心扩张 · 与订阅价值重构（2026-10-07）

> **触发**：白哥指出上一轮建议「怎么编排都不足以支持订阅」，并给出核心判断 ——
> **「我们的产品核心是制卡-FSRS 记忆，这不仅可以用来记单词，还可以用来记其他东西，
> 就像上一版的 K12 学习那样」**，并点出两个真实缺口：
> ① **英文阅读-学习产品**缺 **整段/整句翻译**；
> ② **全类别记忆产品**缺 **除单词外的其他概念制卡**。
>
> **本文**：确认核心 → 查上一版做过什么 → 评估两个缺口的改造成本 → **重构订阅价值**。
> ⚠️ **本轮未改任何代码**（战略级，先对齐）。

---

## 一、先确认核心（白哥的判断是对的，且**代码可证**）

**核心 = 「制卡 → FSRS 调度 → 复习」这台引擎，它与「记的是什么」无关。**

三条代码证据：

| 证据 | 位置 | 说明 |
|---|---|---|
| FSRS **只吃一个字符串 id** | `fsrs_service.dart:418` `cardId: _stableId(s.wordId)`，注释写明「**fsrs 只用它做标识，不参与算法**」 | 参数是「id」，不是「单词」 |
| **取卡已有回落机制** | `word_query_service.dart:267` `ext:` 前缀 → 回落查 `external_word_cache` | 已证明「词库外的内容能进学习闭环」|
| **合成 id 机制已存在** | `external_word_id.dart`：词库外词 = **`ext:<拼写>`** | 「非词库内容」**已在用**，无需改表结构 |

⇒ **FSRS 从来就不是「背单词算法」，是「间隔重复调度器」。**
现在把它用在单词上，那是**用法**，不是**能力边界**。

## 二、上一版（K12 / LinguaF）做过什么 —— 我们去掉了什么

依据 `docs/architecture/prebuilt-schema-refactor.md`（2026-06-09，V2.2 定稿）：

```sql
prebuilt_cards (                       -- 通用卡片注册表（父表）
  id, card_type,                       -- 🔑 concept / vocabulary / poem / timeline …
  domain,                              -- 🔑 硬枚举：science/language/literature/humanities
  subject, grade_band,
  front,                               -- 🔑 所有子卡的「统一名称字段」
  difficulty
)
prebuilt_science_cards     → definition / key_elements / applications / **formula(LaTeX)** / **graph(7 种图)** / source
prebuilt_language_cards    → pronunciation / pos / definitions / **level(CEFR)** / structure_meta
prebuilt_literature_cards  → full_text / **translation** / …
```

**关键结构（当时已解决、现在丢了的三件事）**：

1. **卡片有「类型」**（`card_type`）与「学科域」（`domain`），按域路由到不同子表
2. **`front` 是统一名称** —— vocabulary 的词 / concept 的概念名 / literature 的标题 / humanities 的节点名
3. 🔑 **CP1 自定义卡**：`user_cards.prebuilt_card_id IS NULL` 即自定义卡，
   **与预置卡共用同一个 `card_memory`（FSRS）** —— 取卡查询用 `UNION ALL` 合并

> **这说明**：当年「用户自己制卡」与「预置内容制卡」**跑在同一台引擎上**，
> 且自定义卡的**列结构与预置卡对齐**（设计原则 1「不引入两套 schema」）。
>
> ⇒ 上一版的核心体验是：**从内容里提取概念 → 自动/手动制卡 → FSRS 记忆**，
> 卡片可以是概念、词汇、诗词、时间线，支持 **LaTeX 公式**与 **7 种图表**。
> 📌 与记忆里那条「**LaTeX（未重接 · 34 篇）**」对上了 —— 那是它的遗留。

**现版本退化成**：`card_review_state.word_id` + `spelling` + 卡片形状
`{front, ipa, entry_type, sections}`（**`ipa` 是固有字段**）⇒ **只装得下"单词"**。

## 三、缺口评估

### 3.1 缺口 ①：整段 / 整句翻译

| 项 | 内容 |
|---|---|
| **现状** | 只有**划词**（单词级）。阅读器里没有句/段翻译入口 |
| **要什么** | 选中文本 → 翻译（中英对照）|
| **实现** | 新端点（如 `POST /api/translate`）+ 前端选中菜单加一项；**复用已有的 compliance 闸门**（`compliance` 模块本就是"在线生成内容"的前置检查）|
| **成本** | 🟢 **低**（LLM 调用 + 一层 API + 一个 UI 入口）|
| **🔴 成本性质** | **每次调用都真花钱** ⇒ **这是全项目继"LLM 制卡"之后第二个有真实边际成本的服务** |
| **产品风险** | ⚠️ **整段翻译会削弱阅读本身** —— 用户直接看译文就"读完"了，但没学到。<br>⇒ 设计上必须**按需触发**（选中才翻，不默认展开、不做整篇一键翻译）|
| **合规** | ✅ 已具备（`compliance` 闸门 + 内容合规扫描 skill）|

### 3.2 缺口 ②：非单词制卡（**产品定位扩张**）

**改造成本逐层评估**（这是本报告最有价值的部分）：

| 层 | 要不要改 | 依据 |
|---|---|---|
| **FSRS 调度** | ❌ **零改动** | 只认 id 字符串（`_stableId(wordId)`）|
| **复习队列** | ❌ **零改动** | 按 `next_review_at` 排序，与内容无关 |
| **同步机制** | 🟡 **加一张表的 push/pull** | `sync_handlers.rs` 已是"多表 + 每表上限"的结构，加一张是**既有模式** |
| **内容取卡** | 🟡 **加一个来源分支** | 现有 `word.db` → `ext:` 回落 `external_word_cache`；再加一级回落即可（同 `cardById` 既有写法）|
| **端侧新表** | 🟡 新增 `user_card`（front / back / 可选字段）| 参照 `external_word_cache` 的写法 |
| **卡片渲染** | 🟢 **可复用** | `external_word_cache` 存的形状**与 `word.db.card.content` 一致** ⇒ 自定义卡沿用同一形状，`ipa` 留空即可 |
| **制卡 UI** | 🟡 **新做**（正/反面输入）| 现在只有"划词制卡" |

⇒ **结论：核心引擎（FSRS + 复习 + 调度）完全不用动**，
   工作量集中在 **一张新表 + 取卡回落 + 一个制卡 UI + 同步加一表**。

📌 这印证了架构早年的一个决定是对的：**`ext:` 合成 id + 内容形状统一** ⇒
   「换个内容来源」不需要动引擎。当年为"词库外的词"做的抽象，正好是通用制的接口。

## 四、🔑 订阅价值重构（白哥说"编排不足以支持订阅"—— 对）

### 4.1 为什么"编排现有功能"必然失败

因为**编排不产生新价值** —— 免费层已给全量，重排只是把同一块蛋糕换个摆法。
订阅必须卖**免费层给不了的东西**，而那只能是两类：

| 类别 | 例子 | 为什么免费给不了 |
|---|---|---|
| **A · 每次都要花钱的能力** | 整段翻译 · 实时 LLM 制卡 | **成本随使用量增长**，免费给 = 我们无限贴钱 |
| **B · 数据资产的安全与延续** | 云同步（换机不丢）| 需要持续的服务器成本，且**用户越攒越在乎** |

### 4.2 归属建议（**与白哥可能的直觉相反，请重点看**）

| 能力 | 归属 | 理由 |
|---|---|---|
| 单词卡（划词） | 免费 | 基础体验 · 边际成本≈0 |
| **任意内容制卡** | 🔴 **免费** | **见下（关键判断）** |
| **整段/整句翻译** | ✅ **订阅** | 每次真花钱 ⇒ 正当性最硬 |
| 云同步（已有）| ✅ 订阅 | 数据资产不丢 · 持续服务器成本 |

### 4.3 🔴 为什么「任意内容制卡」应该**免费**（而不是订阅）

这是本轮最重要的战略判断，三条理由：

1. **它零边际成本** —— 内容由用户自己输入，不调 LLM、不占服务器算力。
   **把零成本的功能锁进付费墙，只会阻止用户增长，换不来收入。**
2. **它是用户群扩张的杠杆** —— 产品定位从「英语学习者」→「**所有想记住东西的人**」。
   用户基数每扩大一分，付费转化的基数就大一分。
3. **它让"数据资产"增值，从而抬高订阅（同步）的价值** ——
   用户记的东西越多（单词 + 概念 + 句子），越不能承受丢失 ⇒ **同步的付费意愿随之上升**。

> 📌 **一句话**：**用"免费通用制卡"换用户与数据，用"翻译 + 同步"收钱。**
> 前者是**获客与留存**，后者是**变现** —— 两条线不该混。

### 4.4 这与既定的「免费全量」冲突吗？**不冲突**

「免费全量」是 2026-10-01 对**已有功能**的决定（取消生词本上限）。
本轮新增的**翻译**是**新能力**、且有**真实成本** ⇒ 归订阅**不与那条决定矛盾**，
因为它不减少任何已有免费功能（对照表上不会有任何一行从 ✅ 变 ❌）。

## 五、落地顺序建议

| 序 | 做什么 | 为什么是这个顺序 |
|---|---|---|
| **1** | **任意内容制卡**（免费）| 定位扩张的第一块砖；且它是"从阅读中制卡"差异化的载体 |
| **2** | **整段/整句翻译**（订阅）| 第一个真正有成本依据的订阅权益 |
| **3** | 云同步**重新包装**（把"同步"改成"记录永不丢失"）| 0 成本，但要在有足够数据资产时才有力 |
| **4** | **对照表**（白哥最初要的）| ⚠️ **必须放最后** —— 前 3 步做完后，订阅列才有 3 行以上，对照表才是"放大器"而非"自曝其短" |

### 差异化要点（避免变成"另一个 Anki"）

🔑 **我们的制卡入口是"阅读"** —— 从正在读的文章里划词/划句/划概念 ⇒ 一键成卡。
这是 Anki 没有的场景，也是"英文阅读-学习产品"与"全类别记忆产品"**两者的接缝**：
**读什么，就记什么；记什么，就在复习里巩固。**

## 六、风险与取舍（如实列出）

| 风险 | 说明 | 缓解 |
|---|---|---|
| 通用制卡让产品**定位变模糊** | 从"英语 App"变成"记忆工具"，可能削弱搜索/推荐中的定位 | 主标题仍是英语阅读，通用制卡作为**能力**而非**主打** |
| 整段翻译**削弱学习效果** | 用户看译文 = 假性阅读 | 按需触发（选中才翻）· 不提供"整篇翻译" |
| 自定义卡质量参差 | 用户自制的卡可能很烂 | 不评判内容，但可提供"从选中文本自动生成"的辅助 |
| 同步加表 → 工作量 | `sync_handlers.rs` 要加第 5/6 张表 | 既有模式，风险低 |
