# 产品核心扩张 · 与订阅价值重构（2026-10-07）

> **触发**：白哥指出上一轮建议「怎么编排都不足以支持订阅」，并给出核心判断 ——  
> **「我们的产品核心是制卡-FSRS 记忆，这不仅可以用来记单词，还可以用来记其他东西，  
> 就像上一版的 K12 学习那样」**，并点出两个真实缺口：  
> ① **英文阅读-学习产品**缺 **整段/整句翻译**；  
> ② **全类别记忆产品**缺 **除单词外的其他概念制卡**。
>
> **本文**：确认核心 → 查上一版做过什么 → 评估两个缺口的改造成本 → **重构订阅价值**。  
> ⚠️ **本轮未改任何代码**（战略级，先对齐）。

---

## 一、先确认核心（白哥的判断是对的，且**代码可证**）

**核心 = 「制卡 → FSRS 调度 → 复习」这台引擎，它与「记的是什么」无关。**

三条代码证据：

| 证据                  | 位置                                                                                | 说明                    |
| ------------------- | --------------------------------------------------------------------------------- | --------------------- |
| FSRS **只吃一个字符串 id** | `fsrs_service.dart:418` `cardId: _stableId(s.wordId)`，注释写明「**fsrs 只用它做标识，不参与算法**」 | 参数是「id」，不是「单词」        |
| **取卡已有回落机制**        | `word_query_service.dart:267` `ext:` 前缀 → 回落查 `external_word_cache`               | 已证明「词库外的内容能进学习闭环」     |
| **合成 id 机制已存在**     | `external_word_id.dart`：词库外词 = **`ext:<拼写>`**                                     | 「非词库内容」**已在用**，无需改表结构 |

⇒ **FSRS 从来就不是「背单词算法」，是「间隔重复调度器」。**  
现在把它用在单词上，那是**用法**，不是**能力边界**。

## 二、上一版（K12 / LinguaF）做过什么 —— 我们去掉了什么

依据 `docs/architecture/prebuilt-schema-refactor.md`（2026-06-09，V2.2 定稿）：

```sql
prebuilt_cards (                       -- 通用卡片注册表（父表）
  id, card_type,                       -- 🔑 concept / vocabulary / poem / timeline …
  domain,                              -- 🔑 硬枚举：science/language/literature/humanities
  subject, grade_band,
  front,                               -- 🔑 所有子卡的「统一名称字段」
  difficulty
)
prebuilt_science_cards     → definition / key_elements / applications / **formula(LaTeX)** / **graph(7 种图)** / source
prebuilt_language_cards    → pronunciation / pos / definitions / **level(CEFR)** / structure_meta
prebuilt_literature_cards  → full_text / **translation** / …
```

**关键结构（当时已解决、现在丢了的三件事）**：

1. **卡片有「类型」**（`card_type`）与「学科域」（`domain`），按域路由到不同子表
2. **`front` 是统一名称** —— vocabulary 的词 / concept 的概念名 / literature 的标题 / humanities 的节点名
3. 🔑 **CP1 自定义卡**：`user_cards.prebuilt_card_id IS NULL` 即自定义卡，  
   **与预置卡共用同一个 `card_memory`（FSRS）** —— 取卡查询用 `UNION ALL` 合并

> **这说明**：当年「用户自己制卡」与「预置内容制卡」**跑在同一台引擎上**，  
> 且自定义卡的**列结构与预置卡对齐**（设计原则 1「不引入两套 schema」）。
>
> ⇒ 上一版的核心体验是：**从内容里提取概念 → 自动/手动制卡 → FSRS 记忆**，  
> 卡片可以是概念、词汇、诗词、时间线，支持 **LaTeX 公式**与 **7 种图表**。  
> 📌 与记忆里那条「**LaTeX（未重接 · 34 篇）**」对上了 —— 那是它的遗留。

**现版本退化成**：`card_review_state.word_id` + `spelling` + 卡片形状  
`{front, ipa, entry_type, sections}`（**`ipa` 是固有字段**）⇒ **只装得下"单词"**。

## 三、缺口评估

### 3.1 缺口 ①：整段 / 整句翻译

| 项           | 内容                                                                                               |
| ----------- | ------------------------------------------------------------------------------------------------ |
| **现状**      | 只有**划词**（单词级）。阅读器里没有句/段翻译入口                                                                      |
| **要什么**     | 选中文本 → 翻译（中英对照）                                                                                  |
| **实现**      | 新端点（如 `POST /api/translate`）+ 前端选中菜单加一项；**复用已有的 compliance 闸门**（`compliance` 模块本就是"在线生成内容"的前置检查） |
| **成本**      | 🟢 **低**（LLM 调用 + 一层 API + 一个 UI 入口）                                                             |
| **🔴 成本性质** | **每次调用都真花钱** ⇒ **这是全项目继"LLM 制卡"之后第二个有真实边际成本的服务**                                                 |
| **产品风险**    | ⚠️ **整段翻译会削弱阅读本身** —— 用户直接看译文就"读完"了，但没学到。<br />⇒ 设计上必须**按需触发**（选中才翻，不默认展开、不做整篇一键翻译）              |
| **合规**      | ✅ 已具备（`compliance` 闸门 + 内容合规扫描 skill）                                                            |

### 🎨 设计（缺口 ① · 翻译）

✅ `docs/design/visual-translation-2026-10-07.html`

🔑 **该设计稿正面处理了上表那条「削弱阅读」的产品风险**（三条手段 · 前两条是**约束**、第三条是**转化**）：

| | 手段 | 挡住的是 |
|---|---|---|
| ① | **按需触发**（无「整篇一键翻译」按钮 / 无"自动显示译文"开关）| 把「打开 → 全译 → 读完（其实读的是中文）」这条捷径**物理堵掉** |
| ② | **译文不替换原文**（浮层；关掉后正文一字未变）| 「把文章变成中文」的观感 ⇒ 翻译是**工具**不是**另一份文本** |
| ③ ⭐ | **浮层里直接「划线记住这段」** | 🔑 **把「看懂」转成「记住」** —— 让翻译从**终点**变回**中间站** |

🔑 **③ 是「制卡-FSRS」与翻译功能的接缝**：**看不懂 → 翻译 → 看懂 → 划线 → 记住** ——
   每一步都留在同一个产品里闭环。

📌 一条成本判断：**服务端不做全局缓存**（缓存的前提是"同一内容被多人命中"，
   而**每句话都是唯一的** ⇒ 跨用户命中率极低，白付一层复杂度）；
   **端侧**缓存有意义（同一用户会重复看同一句）⇒ 既省钱又瞬时。

### 3.2 缺口 ②：非单词制卡（**产品定位扩张**）

**改造成本逐层评估**（这是本报告最有价值的部分）：

| 层           | 要不要改                                   | 依据                                                                                |
| ----------- | -------------------------------------- | --------------------------------------------------------------------------------- |
| **FSRS 调度** | ❌ **零改动**                              | 只认 id 字符串（`_stableId(wordId)`）                                                    |
| **复习队列**    | ❌ **零改动**                              | 按 `next_review_at` 排序，与内容无关                                                       |
| **同步机制**    | 🟡 **加一张表的 push/pull**                 | `sync_handlers.rs` 已是"多表 + 每表上限"的结构，加一张是**既有模式**                                  |
| **内容取卡**    | 🟡 **加一个来源分支**                         | 现有 `word.db` → `ext:` 回落 `external_word_cache`；再加一级回落即可（同 `cardById` 既有写法）        |
| **端侧新表**    | 🟡 新增 `user_card`（front / back / 可选字段） | 参照 `external_word_cache` 的写法                                                      |
| **卡片渲染**    | 🟢 **可复用**                             | `external_word_cache` 存的形状**与 `word.db.card.content` 一致** ⇒ 自定义卡沿用同一形状，`ipa` 留空即可 |
| **制卡 UI**   | 🟡 **新做**（正/反面输入）                      | 现在只有"划词制卡"                                                                        |

⇒ **结论：核心引擎（FSRS + 复习 + 调度）完全不用动**，  
工作量集中在 **一张新表 + 取卡回落 + 一个制卡 UI + 同步加一表**。

📌 这印证了架构早年的一个决定是对的：**`ext:` 合成 id + 内容形状统一** ⇒  
「换个内容来源」不需要动引擎。当年为"词库外的词"做的抽象，正好是通用制的接口。

### 🔴 缺口 ② 的方案调整：不做 AI 制卡，改「划线记忆」（2026-10-07 晚 · 白哥定）

> 白哥原话：「我觉得还是**不要自由制卡**了，只做**划线记忆**，
> 用户可以**划线任何长度的内容加入记忆队列**，这样**不用调 LLM，也不用管生成质量**」

🔑 **这一步把「记别的东西」从「AI 服务」还原成「用户的一个动作」** ⇒ 三个问题一起消失：

| | v1（AI 制卡）| **v2（划线记忆）** |
|---|---|---|
| LLM 成本 | ¥0.003 / 次 | **0** |
| 生成质量 | 要管（闸门 / 合规 / 重试）| **不存在这个问题** |
| 长度 | ≤ 300 字符（成本 ∝ 长度）| **不限** |
| 免费额度 | 必须（30 张/月）| 🔴 **不需要 ⇒ 免费无限** |

⇒ 🔑 **这才是「什么都能记」真正成立的前提** ——
   v1 把通用记忆绑在 LLM 上，等于**承诺了一件需要持续付费的事**。

**✅ 复习形态（同日定）**：白哥原话「**复习的时候考默写，和单词一样**」
   ⇒ 给**首字母骨架**作提示 → 写出原文 → 判定 → 两档。
   🔑 这不是发明一种新考核，而是**把单词卡的考核搬到句子上** —— 结果页共用同一个形态。

   ⚠️ **但判定口径要比单词宽一层**：
   ① **句子级归一化要剔除标点**（单词卡对标点敏感，是为 `a.m.` / `dr.` 这类词条**刻意保留**的；
      句子用它会让「少一个逗号」判成「忘了」⇒ 灾难）；
   ② **按错词比例判，默认 5%**（`错词数 × 20 ≤ 总词数` —— 整数比较，避开浮点）——
      🔑 **实际效果：≤ 19 词 ⇒ 一个都不能错**（与单词卡同级）；20–39 词 ⇒ 最多 1 个；100 词 ⇒ 最多 5 个；
   ③ 🎛 **用户可调**（「我的 → 记忆」滑动条）—— 「多准算记住」本来就是**用户对自己要求**的差别。
      🔴 **但只管划线卡**：单词卡的答案唯一（`scale` 就是 `scale`），「多准算对」在它上面**没有意义**。

📌 **与上面那张逐层评估表的关系**：它评的是「复用 `ext:` + `word.db` 卡片形状」那条路，
   在 v2 下**部分作废** —— 划线卡没有 sections / ipa，硬套那套形状要造一堆空字段
   ⇒ 改为**取卡加一级来源分支**（`hl:<highlight_id>`，与 `ext:<拼写>` **同一套合成 id 机制**）。
   ✅ **「FSRS 完全不动」这条结论仍成立**（它只认 id 字符串）。

✅ **设计** → `docs/design/visual-generic-card-2026-10-07.html`（**v2** · 头部有 v1→v2 对照表）

### 3.3 缺口 ③：🆕 **书内标注（书签 / 划线）**（2026-10-07 白哥定：**要做**）

**现状：书里是「只读」的 —— 除了进度，什么都留不下。**

| 场景            | 信息流页                   | 书库页                              |
| ------------- | ---------------------- | -------------------------------- |
| 收藏一篇文章        | ✅ 有（`bookmark`）        | —                                |
| 「这个词我查过」的痕迹   | ✅ 有（`lookup_event` 底色） | ❌ **有意不记**（书的 id 是 uuid，不是文章 id） |
| **标记一段话**     | ❌ 无                    | ❌ **无**                          |
| **书签 / 回到某处** | —                      | ❌ 无（只有**单一**进度，且是自动的）            |
| **把一段话制成卡片**  | ❌ 无（只有划词查词）            | ❌ 无                              |

⇒ 🔴 **这是「阅读 → 记忆」闭环里最大的一块空白**：  
用户在书里读到一个好句子，**唯一能做的只有划词查单词** —— 整句 / 整段**留不下、也记不住**。

**要做三件事**：

| # | 能力            | 说明                                                |
| - | ------------- | ------------------------------------------------- |
| 1 | **书签**        | 标记位置（章 + 章内位置）· **可多条** —— 与「进度」是不同的东西（进度自动、只有一条） |
| 2 | **划线记忆**      | 标记一段文本（文章 / 书 + 字符区间）· 长期保留 · **进记忆队列**（默写考核）      |
| 3 | 🆕 **笔记**      | 挂在划线上的一句话 —— **不是独立的内容体系**。划线时或卡片里写；<br>🔴 **默写判定前不显示**（笔记里可能就写着答案）|

🔑 **关键判断：划线是通用制卡最自然的入口 —— 比划词更自然。**

| 动作                | 用户心智            | 出口        |
| ----------------- | --------------- | --------- |
| **划词**（lookup）    | 「我现在想**搞懂**这个词」 | 词卡（查词）    |
| **划线**（highlight） | 「**这段我要记住**」    | 🎯 **制卡** |

⇒ 划线的语义**天然就是「我要记它」** —— 它是「读什么就记什么」这句话的**直接落地**。

**技术要点（已核实）**：

| 项           | 决定                                                                                 | 依据                                  |
| ----------- | ---------------------------------------------------------------------------------- | ----------------------------------- |
| 位置表示        | 章 idx + **字符 offset**（`start` / `end`）                                             | 章文本是整块 `String`（`ChapterText.text`） |
| ⚠️ **已知限制** | `SelectionArea` 的 `SelectedContent` **只给明文、不给偏移** ⇒ 定位用 `indexOf(明文)` + **出现序号**消歧 | 读 Flutter SDK 确认                    |
| 渲染          | 章文本按 offset 切片 → `TextSpan`（普通 / 已划线）                                              | 与阅读页「痕迹」同一类做法                       |
| 🎨 **视觉区分** | 🔑 **形状区分优于参数**：**痕迹 = 底色浸染**（`rgba(180,67,44,.15)`）；**划线 = 下划线**（2px 朱砂）+ 淡底      | 项目已定判据；两者若同形状会互相干扰                  |
| 表           | `book_highlight` / `book_marker`（**book.db**）                                      | 与 `book_progress` 同库                |
| 同步          | **要同步**（学习资产）                                                                      | 与「书库上云」同批（§六）                       |

⚠️ **定位脆弱性要如实说**：同一段文字在一章里出现多次时，`indexOf` 可能定位到错误位置。  
缓解：存 `excerpt` + `occurrence`（第几次出现）；且 `content_hash` 保证「同一本书 = 同一份文件」⇒ 文本不变。

> 🔑 这条**必须在实现时真机验证**：拿一本真实的书，划一段**重复出现**的文字，检查定位是否准确。

### 📄 设计（§3.3 的两个能力）

✅ `docs/design/visual-bookmark-2026-10-07.html`（**书签**）·
   `docs/design/visual-generic-card-2026-10-07.html`（**划线记忆 · 含笔记**）

🔑 **书签设计稿最重要的一件事：把「进度 / 书签 / 划线」三者的边界钉死** ——

| | 谁产生 | 几条 | 目的 | 要复习吗 |
|---|---|---|---|---|
| **进度** | 系统自动 | 一本书**一条**（覆盖式）| 下次回到原处 | ❌ |
| **书签** | 用户点一下 | **任意多条** | **回头找**某处 | ❌ **不进队列** |
| **划线** | 用户选一段 | 任意多条 | **记住**这段 | ✅ **进队列**（默写）|

⚠️ **两条待真机确认**：① 正文**不画**书签标记（避免与划线下划线打架）够不够；
   ② `excerpt` 用比例估算会有偏差（像素比例 ≠ 字符位置），列表能否认出是哪段。

### 🆕 笔记 —— 挂在划线上（2026-10-07 白哥加）

> 白哥原话：「再加个**笔记**，划线后用户可以自己写一个笔记，
> 可以在**划线的时候**写，也可以在**卡片里**写」

🔑 **它挂在划线上，不是另开一套内容体系** —— 这是它「轻」的原因：
**只给划线表加一个 `note` 字段**，不要新表、新列表页、新入口体系。

**两个入口的分工**：

| 入口 | 时机 | 为什么要有 |
|---|---|---|
| **划线时** | 划线后 toast 上的「写笔记」（存活 3–4 秒）| 🔑 **手感最新鲜**（刚读到、刚决定要记住）。⚠️ 但**不能是强制步骤**（否则把"一步入队"变成两步）|
| **卡片里** | 复习结果页 · 记忆列表 · 卡片详情 | 🔑 **复习时反而最想补笔记**（默不出来时正好记下"为什么没记住"）⇒ 让笔记成为**复习的一部分**，而非前置动作 |

🔴 **一条硬约束**：**默写判定之前，笔记不能显示** ——
笔记是用户自己写的，**很可能就写着答案**（"这句意思是…"）⇒ 判定前露出来 = **泄题**。
⇒ 与「原文」同一条规则：**判定后才给**。

📌 **与 2026-10-06「私密笔记不做」的关系**：**那条决定不受影响**，两者是**不同的东西** ——

| | 曾被否掉的「私密笔记」| 本稿的「笔记」|
|---|---|---|
| 挂在哪 | 文章 / 书的**任意位置**（独立内容）| **挂在一条已有的划线上** |
| 要新建什么 | 一整套笔记体系（入口 / 列表 / 编辑 / 同步）| **只加一个 `note` 字段** |
| 它是谁的 | 用户的**另一份内容** | 划线的**附属说明** |

⇒ 🔑 判据：**「不做 X」要连「X 挂在哪」一起记** ——
同一个词（"笔记"）挂在不同对象上，**是不同的功能**，不能拿旧结论一票否决。

## 四、🔑 订阅价值重构（白哥说"编排不足以支持订阅"—— 对）

### 4.1 为什么"编排现有功能"必然失败

因为**编排不产生新价值** —— 免费层已给全量，重排只是把同一块蛋糕换个摆法。  
订阅必须卖**免费层给不了的东西**，而那只能是两类：

| 类别                 | 例子               | 为什么免费给不了                  |
| ------------------ | ---------------- | ------------------------- |
| **A · 每次都要花钱的能力**  | 整段翻译 · 实时 LLM 制卡 | **成本随使用量增长**，免费给 = 我们无限贴钱 |
| **B · 数据资产的安全与延续** | 云同步（换机不丢）        | 需要持续的服务器成本，且**用户越攒越在乎**   |

### 4.2 归属建议（**与白哥可能的直觉相反，请重点看**）

| 能力          | 归属                 | 理由                                         |
| ----------- | ------------------ | ------------------------------------------ |
| 单词卡（划词）     | 免费                 | 基础体验 · 边际成本≈0                              |
| **任意内容制卡**  | 🟡 **免费额度 + 订阅扩额** | **有真实边际成本** —— 见 §4.3 **更正**（原判「免费·零成本」作废） |
| **整段/整句翻译** | ✅ **订阅**           | 每次真花钱 ⇒ 正当性最硬                              |
| 云同步（已有）     | ✅ 订阅               | 数据资产不丢 · 持续服务器成本                           |

### 4.3 🔴 「任意内容制卡」的成本性质 —— **2026-10-07 晚更正，原判断理由作废**

> 🔴 **白哥纠正**：「**任意内容制卡都要调用 LLM，并不是你说的零成本**」—— **这是对的**。  
> 本节原文把该能力判为「零边际成本」并据此判「免费」（原理由 1），**该理由全错**，保留作历史（下方为修正版）。

**❌ 原论证错在哪**

| 原文写的                                   | 实际                                      |
| -------------------------------------- | --------------------------------------- |
| 「内容由用户自己输入，**不调 LLM**」                 | 「用户输入」只是把 **生成什么** 交给用户 —— **LLM 照调不误** |
| 「零边际成本」                                | 该结论 **从来不来自 LLM 制卡**，而来自 **缓存摊薄**（见下）   |
| （§4.1 表已把「实时 LLM 制卡」列为 A 类「每次都要花钱的能力」） | 🟡 **与原文 §4.3 自相矛盾** —— 以 §4.1 为准       |

**🔑 成本模型：摊薄的唯一前提是「内容被多人共享」**

|        | 单词制卡（现有 · `llm_card.rs`） | 任意内容制卡                |
| ------ | ------------------------ | --------------------- |
| 缓存 key | `spelling`（可归一化 · 可枚举）   | 用户输入原文                |
| 跨用户复用  | ✅ **全站共享** ⇒ 一个词只付一次     | ❌ 每段内容唯一 ⇒ **每人每次全价** |
| 成本 ∝   | **唯一词数**（有自然上限 ⇒ 收敛）     | **用户行为量**（无上限 ⇒ 线性增长） |
| 边际成本   | ≈ 0                      | 🔴 **纯边际成本 · 不可摊薄**   |

⇒ 现版本的「零边际成本」是「**共享词表 + 全局缓存**」的产物，**不是 LLM 制卡的属性**。  
任意内容 **天然不具备共享前提** ⇒ 退回 **按次计费**。

**📐 单次成本**（中国区官方价 · 2026-08-17 生效 · 元/百万 tokens · 空闲时段）

| 项        | 量                                                                           | 单价（未命中 / 命中） | 成本                            |
| -------- | --------------------------------------------------------------------------- | ------------ | ----------------------------- |
| input    | `prompts/wordlib_contract.md` = **11,580 B ≈ 3.3k tokens**（**固定契约，每次重复计费**） | 1.5 / 0.05   | ¥0.00495 / ¥0.00017           |
| output   | `max_tokens=900`（实测约 600）                                                   | 4.5          | ¥0.0027                       |
| **单次合计** |                                                                             |              | **¥0.0077（未命中）· ¥0.0029（命中）** |

🔑 **prompt 是固定不变的 11.5 KB ⇒ 天然命中前缀缓存**，input 部分降 ~30×  
⇒ 实际约 **¥0.003/次**，其中 **~93% 是 output**；  
⇒ 降本优先级：**控 output（`max_tokens`）＞ 控 prompt**。  
⚠️ 高峰时段（工作日 9:00–12:00 / 14:00–18:00）单价**翻倍** ⇒ 成本 ×2。

**📈 规模化（按 ¥0.003/次）**

| 场景                     | 调用量/月   | 成本/月           |
| ---------------------- | ------- | -------------- |
| 1,000 用户 × 5 张/天       | 15 万    | ¥435           |
| 10,000 用户 × 5 张/天      | 150 万   | **¥4,350**     |
| 10,000 用户 × 50 张/天（重度） | 1,500 万 | 🔴 **¥43,500** |

> ⚠️ 对照订阅收入：¥25/月 × **2%** 付费 × 1 万用户 = **¥5,000/月**。  
> ⇒ **「无限制免费送」下，重度用户群可以吃掉全部订阅收入。**

**✅ 修正后的归属：仍然免费，但必须改成「额度制」**

原结论「免费」**结果可能仍对，依据必须换** —— 不是「零成本」，而是「**获客杠杆**」（原理由 2、3 仍成立）：

| 能力         | 归属                      | 理由                         |
| ---------- | ----------------------- | -------------------------- |
| 单词划词制卡     | 免费 · 无限                 | 缓存摊薄，边际 ≈ 0（**此结论仍成立**）    |
| **任意内容制卡** | 🟡 **免费小额额度 + 订阅扩额/无限** | **真实边际成本** · 与「整段翻译」**同类** |
| 整段/整句翻译    | 订阅                      | 同上                         |
| 云同步        | 订阅                      | 服务器成本                      |

🔴 **原 §4.2 把「任意内容制卡」与「整段翻译」分成两类（一免费一订阅）是错的** ——  
二者 **成本性质相同**（每次真花钱），差别只在 **额度策略**。

**🔗 与 `subscription-value-assessment-2026-10-07.md` §B 的统一**

那份文档（§B）**方向本来就是对的**，且已给出正确判据：  
「**命中缓存 = 0 成本 = 免费；未命中 = 实时调 LLM = 付费**」。  
把它与本节合并，得到 **一条同时管住两种制卡的规则**：

| 情形                                 | 成本     | 归属                     |
| ---------------------------------- | ------ | ---------------------- |
| 词库命中（`word.db` 预制卡）                | 0      | 免费 · 无限                |
| 服务端全局缓存命中（跨用户复用）                   | 0      | 免费 · 无限                |
| **未命中 ⇒ 实时调 LLM**（单词兜底）            | ¥0.003 | 🟡 **额度**（免费少量 + 订阅无限） |
| **任意内容制卡**（**无缓存可言** ⇒ 等价于「永远未命中」） | ¥0.003 | 🟡 **同上**              |
| 整段 / 整句翻译                          | 同上     | 🟡 **同上**              |

> 🔑 **一句话**：**「命中缓存免费 · 实时生成走额度」** —— 单词制卡与任意内容制卡  
> **用同一条规则**，不需要发明两套。  
> 🔴 **不能因为「内容由用户输入」就当它是零成本** —— 那只是把「生成什么」交给了用户。

> 📌 **修正后的一句话**：**用「免费额度制卡」换用户与数据，用「翻译 + 同步 + 扩额」收钱。**  
> 🔑 **免费层给的是"额度"，不是"无限"** —— 这里有真实成本，无限送等于把「用户行为量」的账全揽过来。

### 4.4 这与既定的「免费全量」冲突吗？**不冲突**

「免费全量」是 2026-10-01 对**已有功能**的决定（取消生词本上限）。  
本轮新增的**翻译**是**新能力**、且有**真实成本** ⇒ 归订阅**不与那条决定矛盾**，  
因为它不减少任何已有免费功能（对照表上不会有任何一行从 ✅ 变 ❌）。

### 4.5 🔑 统一的成本框架（本文档的判据层 · 2026-10-07 晚补）

白哥同日两次纠正，合起来是一条完整判据：  
**成本要如实算，但它决定的是「怎么定价」，不是「做不做」。**

| 成本类型                      | 实例                          | 归属                   |
| ------------------------- | --------------------------- | -------------------- |
| **缓存摊薄后 ≈ 0**             | 词库命中制卡 · 端侧计算（朗读 / 复习）      | 免费 · 无限              |
| **可摊薄 · 成本 ∝ 内容量**（不是用户量） | 服务端抓信息流（∝ 源数，与用户数无关）        | 免费                   |
| **不可摊薄 · 用户行为驱动**         | 任意内容制卡 · 整段翻译（**¥0.003/次**） | 🟡 **免费小额额度 + 订阅扩额** |
| **存储型 · 线性但单价极低**         | 书库上云（COS **0.118 元/GB/月**）  | 🟡 **订阅配额分层**        |

🔴 **不能只看「是否随用户数线性增长」** —— 那是**形态**，必须 × **单价** 再算**占收入比例**：

| 场景     | 线性增长后的成本                      | 占订阅收入     | 结论         |
| ------ | ----------------------------- | --------- | ---------- |
| 书库正文上云 | 1 万人 × 2.5 TB = **¥302/月**    | **0.12%** | ✅ **不是问题** |
| 任意内容制卡 | 1 万人 × 50 张/天 = **¥4.35 万/月** | **1740%** | 🔴 **真问题** |

⇒ **两条都「线性增长」，结论完全相反** ⇒ 形态本身不含结论。  
⇒ 📌 判据：**把「增长形态」×「单价量级」→ 再算占收入的比例**，缺任何一项都不成判断。

| # | 判断 | 不这么做会怎样 |

| 1 | 🔴 **`blob_size` 不出现在 push 的 `DO UPDATE SET` 里** | 一台**离线很久的旧设备**推一次书单，就能把「云端已备份」标回「没有」⇒ 用户在大陆设备上看到云标记消失、以为备份丢了，而**文件明明还在** |

🔑 **三处判断**：

1. 🔴 **解析必须抽成「零依赖的纯函数」** —— 否则 `401` / `403` / 缺字段 / 非 JSON / 空数组
   这些分支**只能在真机上验**（要各造一次真实响应）。抽出后**一行字符串**全测。
   📌 判据：**能脱离外部依赖验证的逻辑，就别让它依赖**。
2. 🔴 **`401` 绝不能混进「失败」** —— 401 的正确反应是「去登录」，而"失败"是「重试」；
   混在一起 ⇒ 用户会反复重试一个**永远不会成功**的动作。
3. **缓存命中时不显示额度行** —— 没调接口 ⇒ 服务端没回 `quota`；
   显示「本月已用 0 次」是**假信息**（用 `used = -1` 哨兵值表达"未知"）。

⚠️ **一处偏离设计稿**（已回标）：「生成中」改成**浮层内的行内转圈**，不用全屏遮罩 ——
翻译只等 **2–4 秒**，而全屏遮罩的语义是「跳到了另一个界面」，与本功能§2 的首要约束
「**不打断阅读**」相冲突。

✅ **验证**：解析 **28/0** · `analyze_inproc` **error=0 / warning=0**（158 文件）· 全量回归绿。
🔴 **证伪**：把 `401` 合并进普通失败（最常见的退化）⇒ **1 项红**。

⏳ **还差**（当时）：浮层里的**来源标题** · 未登录时的**一键跳登录** —— ✅ **已在开发步 11 补齐**。

✅ **开发步 11（2026-10-08）：翻译端侧收口 —— 来源标题 + 未登录出口**

这一轮补的是**「有实现、无接线」**与**「无出口」**两类问题（都不是崩溃，而是**功能静默地不完整**）。

| 落点 | 内容 |
|---|---|
| ✏️ `HighlightSource` | 🆕 `title`（可空）—— 🔑 与其他字段**性质不同**：那几个是**定位划线**必需的，这一个**只用于展示** |
| ✏️ `reader_screen.dart` | 传 `title: item.title`（**文章标题**）|
| ✏️ `book_reader_screen.dart` | 传 `title: ch.bookTitle`（**书名** —— 与顶栏同一口径，「翻章时它不该变」）|

| ✏️ `translation_sheet.dart` | 未登录态由**单按钮**改成**两个出口**（`_Action` 列表）|
| 🆕 `verify_translation_wiring.dart` | **12 项**结构断言 · 已进 CI |

🔴 **发现的一个「有实现、无接线」**：`showTranslationSheet` 从 10-07 起就有 `sourceLabel` 参数、
浮层也把它渲染成顶栏那句「翻译 · 来自 XXX」—— **但两个阅读页都没传** ⇒ 这一整块 UI **从未显示过**。
· analyzer **不报**（可空参数不传是合法的）
· 真机也**看不出少**（「本来就不该出现的一句话没出现」**不像 bug**）
⇒ 与 `verify_auth_entry`（登录入口被误删）是**同一类**：只有结构断言守得住。

🔴 **一处设计冲突的处理**：设计稿「未登录」态画的是**一句文字指引**，没有按钮 ⇒
用户读到「登录后可翻译」却**无处可去**。但加「去登录」又会**违反本功能 §2 的首要约束「不打断阅读」**
（跳走会丢掉阅读位置）。
⇒ **两条都要满足**：给**两个平级出口** —— <b>继续阅读</b>（关闭）/ <b>去登录</b>（主要，因为
用户点翻译就是**明确想用这个功能**），且**不做自动跳转**。

📌 **两条判据**：
1. 🔑 **可空参数 = 「接了线才算完成」** —— 参数有了、UI 有了、**没人传**，等于没做；
   而它**不报错、看不出少**。⇒ 每加一个「可空但应该有值」的参数，**配一条结构断言**。
2. 🔑 **「无出口」比报错更糟** —— 报错至少告诉用户「此路不通」；只给文字指引而不给按钮，
   用户会反复点翻译、反复看到同一句话。⇒ **错误/受限态必须有可达的下一步**。

✅ **验证**：接线断言 **12/0** · `analyze_inproc` **error=0 / warning=0**（158 文件）· 全量回归绿。
🔴 **证伪**（三处独立注入）：删书名 `title` ⇒ **①-1 红** · 把 `title` 传成 `articleId` ⇒ **①-2 红** ·
删「去登录」动作 ⇒ **②-1/②-2/②-3 红**（共 5 项红、退出码 1），随后 3/3 恢复。

⚠️ **信息流页划线的能力边界**（探针实测，已如实标注在设计稿）：
跨 `**粗体**` / 链接 / 行内代码时，下划线**在定界符处断开**（两侧照画）；
**整段落在代码块里** ⇒ 一个标记都不插（有意 —— 那里不能放控制字符）。

📌 菜单项的**呈现形式随项数变化**：**1–4 项**用浮动胶囊（贴选区），**≥5 项**改底部面板 ——  
同一个数据源、两种呈现，加功能时只改列表（见 `visual-selection-menu-2026-10-07.html` §5）。


### 5.2 差异化要点（避免变成「另一个 Anki」）

🔑 **我们的制卡入口是「阅读」** —— 从正在读的文章 / **书**里划词、划句、划概念 ⇒ 一键成卡。  
这是 Anki 没有的场景，也是「英文阅读-学习产品」与「全类别记忆产品」**两者的接缝**：  
**读什么，就记什么；记什么，就在复习里巩固。**

## 六、云同步扩张：存什么、不存什么（2026-10-07 定）

✅ **设计** → `docs/design/visual-cloud-bookshelf-2026-10-07.html`

🔑 **该设计稿要解决的是一个新概念**：一本书有**三种本地性**（本地有 / 只有云端 / 正在传）。
   三态用**图标形状**区分（云 / 箭头），**不靠颜色** —— 项目只有一个强调色，压不住三态。

📌 **三个关键取舍**：① **默认态（本地有）不加任何标记**（有标记的一定有原因，否则满屏噪声）；
   ② **配额条不常驻**，用量 > 80% 才出现（低频信息不占常驻位置）；
   ③ **措辞只说「云端存储」**，绝不说「云端书库 / 这里可以找到书」（§6.1 那条分界最终落在 UI 文案上）。

| 数据                     | 现状     | 本轮                                       |
| ---------------------- | ------ | ---------------------------------------- |
| 生词本 · 收藏 · 阅读进度 · 复习事件 | ✅ 已在同步 | —                                        |
| **书单（元数据）**            | ❌      | 🆕 加（**附带** —— 让书架在下载正文前就能显示）            |

| **书内标注**（书签 / 划线）      | ❌      | 🆕 加（与书库同批）                              |

### 6.1 🔴 红线（与「不作在线书库」一致）

**私人云存储 ✅ ≠ 在线书库 ⛔** —— 分界线&#x662F;**「是否向公众提供」**：

|      | 私人云存储 ✅ 可做             | 在线书库 ⛔ 已否决  |
| ---- | ---------------------- | ----------- |
| 谁能访问 | **只有本人**               | 所有人         |
| 内容来源 | **用户自己上传的**            | 我们选书 / 我们提供 |
| 我们扮演 | 信息存储空间（网盘 / iCloud 同类） | 内容提供者 / 出版者 |

🔴 **三条线绝不碰**：① 用户**之间**共享电子书；② 我们提供公版书库；③ 把「能看到别人的书」做成权益。  
⚠️ **措辞约束**：订阅只能宣传「**云端存储空间**」，**不能**宣传「订阅可以看这些书」。

📄 逐表核实与成本量化见 `docs/review/sync-scope-extension-2026-10-07.md`

## 八、风险与取舍（如实列出）

| 风险                     | 说明                                                      | 缓解                                                                |
| ---------------------- | ------------------------------------------------------- | ----------------------------------------------------------------- |
| 通用制卡让产品**定位变模糊**       | 从「英语 App」变成「记忆工具」                                       | 主标题仍是英语阅读，通用制卡作为**能力**而非**主打**                                    |
| 整段翻译**削弱学习效果**         | 看译文 = 假性阅读                                              | 按需触发（选中才翻）· 不提供「整篇翻译」                                             |
| 自制卡质量参差                | 用户做出来的卡可能很烂                                             | 不评判内容；提供「从选中文本自动生成」的辅助                                            |
| 🔴 **AI 制卡成本随用量增长**    | 不可摊薄（¥0.003/次）⇒ 重度免费用户是**纯亏损**                          | **额度制** + 监控人均调用量（§4.3 / §4.5）                                    |
| 🆕 **划线定位的脆弱性**        | `SelectionArea` 只给明文不给偏移 ⇒ 靠 `indexOf` + 出现序号；重复文本可能定位错 | 存 `excerpt` + `occurrence` 消歧；`content_hash` 保证同书同版本。**实现时须真机验证** |
| 🆕 **书库上云被误读为「做在线书库」** | 合规观感风险                                                  | 严格**私人空间**（per-user 隔离 + 不共享 + 不检索）+ 文案只说「存储空间」                   |
| 🆕 **划线视觉与「痕迹」打架**     | 两者都是高亮，容易混淆                                             | 🔑 **形状区分优于参数**：痕迹 = 底色浸染；划线 = **下划线**                            |
