## 二、🎉 新判据的**运行时直接证据**（本轮最关键）

**服务重启后首轮抓取**（`06:35:52Z`），日志实录：

```
06:35:52 INFO content_fetch: 跳过条目（非英语词汇（英语功能词仅 7%））
          · Dev.to — Usando Raspberry Pi, rsync e inotify para um video wall de baixo custo
06:35:52 INFO content_fetch: Dev.to 拿到 12 条 · 新增 11 条
```

### 2.1 🔑 为什么这条比「日志里出现了关键字」强得多

**① 输入确实到达了闸门**（这是上一轮的教训：没看到拦截可能是上游没喂数据）

```
06:35:35 INFO content_fetch: ECNS 中国新闻网英文 拿到 100 条 · 新增 0 条
06:35:52 INFO content_fetch: Dev.to 拿到 12 条 · 新增 11 条   ← 输入到了
```

**② 🔴 数字算术自洽 —— 拦截**确实生效**，而不是「说了要拦但没拦」**

```
Dev.to 拿到 12 条  →  新增 11 条
⇒ 12 − 11 = 1 条被拦
⇒ 与日志里那 1 条「跳过条目」**正好对上**
```

**③ 用的是新判据**（旧版二进制**没有**「非英语词汇」这个变体，见 §三）

**④ 语言也换了** —— 白哥报的是**越南语**，这条是**葡萄牙语**：
⇒ 证明升级后的判据**不是只针对俄语/越南语**，而是**对拉丁语系的非英语普遍有效**
（这正是本次升级的目的：「应该过滤非英文，而非只过滤俄文」）。

### 2.2 与「存量删除」合起来才是闭环

| 步 | 动作 | 效果 |
|---|---|---|
| 1 | 升级判据 | 新内容会被拦 |
| 2 | 删存量 6 条 | 旧内容清掉 |
| 3 | **部署** | 1 生效 |

## 三、交付物级证据：生产二进制**确实含新判据**（含三重对照）

用 `grep -a`（字节级，比 `strings` 可靠）对比**新版**与 **`.prev`（旧版）**：

| 特征串 | 新版 | 旧版 | 性质 |
|---|---|---|---|
| `非 HTML 文档` | 1 | **1** | ✅ **阳性对照** —— 两版都有（v0.1.1 加的）⇒ 证明**检测器能报 1** |
| `编码乱码` | 1 | **1** | ✅ 同上 |
| `非英语词汇` | **1** | 0 | 🆕 **新判据**（差异对照）|
| `非英语文字` | **1** | 0 | 🆕 新判据 |
| `英语功能词仅` | **1** | 0 | 🆕 新判据的细节串 |

| `yourselves` | **1** | 0 | 🆕 词表 |
| `whichever` | **1** | 0 | 🆕 词表 |
| `whereupon` | 0 | 0 | ✅ **阴性对照** —— 它**不在**词表里，检测器**没有恒报 1** |

### 3.1 🔴 差点误判（如实记录）

第一次我用 `strings | grep -cx` 查，**全部返回 0** ⇒ 一度要得出「二进制里没有新判据」的**错误结论**。

**两个原因**（都是检测器的问题，不是二进制的问题）：
1. `strings` 默认按 ASCII printable 切串 ⇒ **中文多字节序列被过滤掉**
2. Rust 的 `&'static str` 在 `.rodata` 里是**连续拼接**的（`…yoursyourselvesyou've…`）
   ⇒ `grep -x`（整行匹配）**必然失败**

⇒ 改用 `grep -a`（直接把文件当文本搜字节）后全部命中 ✅

📌 **判据（本轮第 3 次同族）**：**「检测结果为 0」时，先证明检测器本身有效** ——
本次靠「阳性对照（两版都有的串）+ 阴性对照（都不在的串）」把检测器**验了一遍**，
差异对照才敢用。

## 五、⚠️ 新发现（**旧问题**，非本轮引入）：HN 源 `enabled` 仍是 1

### 5.1 现象

```
content_source: id=5  Hacker News  enabled=1     ← 应为 0
日志（每轮）: WARN content_fetch: Hacker News 失败: 未知的源类型 `hn`（目前只支持 rss）
```

### 5.2 根因：**seed 用 `ON CONFLICT DO NOTHING` ⇒ 只「新增」，不「改配置」**

`CONTENT_SEED_SQL` 末尾是 `ON CONFLICT DO NOTHING`（2026-10-03 为「让 CHECK 违规炸出来」而改）。
而 HN 弃用需要**把存量行**（库里的 id=5）的 `enabled` 从 1 改成 0 ——
`DO NOTHING` 遇到 `url` 冲突时**什么都不做** ⇒ **配置变更静默丢失**。

```
新库（全新部署）  → seed 插入 id=5 时 enabled 就是 0 ✅ 正确
老库（已部署）    → id=5 已存在 → ON CONFLICT DO NOTHING → enabled 保持 1 ❌ 错误
```

### 5.3 影响评估（**不要夸大**）

| 项 | 实际情况 |
|---|---|
| HN 还会产生内容吗 | ❌ **不会** —— 适配器已删，`未知的源类型` 直接返回错误，**未发网络请求** |
| 每轮代价 | 一条 WARN 日志（每 6 小时） |
| 内容池 | HN 的 200 条是**历史数据**（保留是有意的，见 seed 注释）|
| 真正的危害 | ① 日志噪音 ② **`enabled` 列语义与实际不符**（读表会误以为 HN 还在用）|

⇒ 严重度 **低**（不是内容/合规问题），但**它是「配置变更静默丢失」这个结构问题的实例**，
同类问题将来必然会再出现（**下次改任何源的 `enabled` / `license` / `redistributable` 都会踩**）。

### 5.4 修复选项（**未做，等你定**）

| 方案 | 做法 | 评价 |
|---|---|---|
| **🅰 迁移**（推荐） | 在迁移列表加一条 `UPDATE content_source SET enabled=0 WHERE url LIKE '%hacker-news%'` | ✅ **新库/老库都对** · 可进 CI 测试 · 与项目既有做法一致 |
| 🅱 直接改生产库 | 手工 `UPDATE ... WHERE id=5` | 最小，但**新库仍靠 seed**（靠 seed 也对）· 不改代码 ⇒ 不解决结构问题 |
| 🅲 seed 改 `DO UPDATE` | 让 seed 覆盖存量配置 | 🔴 **危险** —— 会**覆盖所有人工改动**（管理员在库里调的 enabled 会被 seed 冲掉）|

📌 ⚠️ 记忆里的既有约束：**`main.rs` 有第二份迁移列表，改 schema/迁移必查两处。**
