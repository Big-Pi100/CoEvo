## 二、🎯 最强证据：`本轮 22/22 个源成功`

```
2026-10-03T11:03:44 INFO content_fetch: 本轮 22/22 个源成功 · 新增 19 条
```

**为什么这一句比「HN 报错 0 次」强得多**：

| 证据 | 强度 | 说明 |
|---|---|---|
| 「HN 报错 0 次」 | 🟡 中 | ⚠️ **可能是假绿** —— 若首轮还没跑到 HN，它当然不报错 |
| **`22/22 个源成功`** | 🟢 **强** | 🔑 **分母是「本轮实际尝试的源数」** ⇒ HN **压根不在尝试列表里** |

🔴 **这正是上一轮的教训**：「没看到 M」≠「M 没发生」—— **必须先证明输入到达了**。
所以我**没有**停在「报错 0 次」上，而是**条件等待整轮跑完**：

```
轮询 1: 拿到记录=0  · 最后源(NPR Media)出现=0
轮询 2: 拿到记录=12 · 最后源出现=0
轮询 3: 拿到记录=22 · 最后源出现=1   ← 整轮跑完，此处才能下结论
```

而且 **22 个「拿到」记录 ↔ DB 的 `enabled=22` 互相印证** ⇒ 两个独立口径给出同一个数。

## 三、逐项验证（`verify_sources_after_deploy.py`，只读）

```
库: /opt/coevo/data/coevo.db
总行数 24（部署前 24）· 启用 22（部署前 23）

  ✅ ① HN `enabled` = 0  实得 0（部署前 1）
  ✅ ② 启用数 = 22  实得 22
  ✅ ③ 总行数不变  实得 24
  ✅ ④ 无增删行（id 集合 = 1..24）
  ✅ ⑤a HN `fail_count` 未被动      实得 1（部署前抓取失败累计，应保留）
  ✅ ⑤b HN `created_at` 未被动      实得 2026-10-01T09:13:00Z
  ✅ ⑤c HN `last_fetch_at` 未被清空 实得 2026-10-03T06:35:33Z
  ✅ ⑥ HN `updated_at` 已被 UPSERT 刷新
        last_fetch=2026-10-03T06:35:33Z  updated=2026-10-03T11:02:42Z
```

### 3.1 🔑 断言 ⑥ 是**不可省**的（防「什么都没跑」的假绿）

断言 ④⑤ 都是「**不该变的没变**」。**只验这个的话，一个根本没执行的 UPSERT 也会全绿。**

⇒ 必须配一条「**该变的变了**」：

```
HN updated_at = 2026-10-03T11:02:42Z
                           ↑
服务重启时间 = Sat 2026-10-03 19:02:42 CST = 11:02:42 UTC  ← 精确吻合
```

🔑 **两者精确吻合** ⇒ UPSERT 是在**启动那一刻**执行的。
而 `last_fetch_at` 仍是 `06:35:33Z`（几小时前抓取写的）⇒ 两者**被分别对待**，
证明「**只碰配置列、不碰运行时状态**」这个设计在**生产上真的成立**（不只是单测里）。
