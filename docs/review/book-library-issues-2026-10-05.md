## ① 导入按钮不协调 —— 根因是「两个药丸走了不同分支」

### 现状（代码事实）

| | 收藏（信息流 tab）| 导入（书库 tab）|
|---|---|---|
| 调用 | `HeaderChip(icon: bookmark_border, label: '收藏', count: N)` | `HeaderChip(icon: add, label: '导入', labelReserve: '导入中')` |
| 走的分支 | `count` 分支（**未传** `reserve`）| `reserve` 分支（**传了** `reserve`）|
| 左内边距 | `_padH` | `_iconLead` = **8** |
| 右内边距 | `_padH`（对称）| `leftPad + iconBlock` = 8 + (13+6) = **27** |
| 视觉结果 | 图标+文字+数字，左右对称 | 图标+文字，**左 8 / 右 27** ⇒ 右侧多一块空白、重心偏左 |

`widgets/header_chip.dart` 的推导逻辑（原注释）：
```
· 有图标 → 右内边距 = 左 + (13 + 6)   （文字仍居中，但图标会显得靠左）
```

🔴 **关键**：`labelReserve` 的设计目的是「**让文字居中**」（复习页的筛选药丸），
它**假定药丸右侧没有其它元素**。导入按钮借它来做「两态等宽防跳」，
副作用就是**内边距不对称** —— 这正是白哥看到的「不协调」。

📌 白哥的原话已经点到了根因：「收藏按钮后有数字，导入按钮后没有数字」——
**一个走 `count` 分支（对称），一个走 `reserve` 分支（不对称）**。

### 修复选项

| 方案 | 做法 | 评价 |
|---|---|---|
| **A ★推荐** | **让「导入中」不需要 `reserve`** —— 文案**保持不变**（仍是「导入」），用**图标变化**表达忙碌态（`Icons.add` → `Icons.hourglass_empty` 或转圈）。文案不变 ⇒ 宽度天然不变 ⇒ **不需要 `reserve`** ⇒ 内边距回到对称 | ✅ 最小改动、根因消除、与「收藏」完全同源<br>⚠️ 需确认「图标变化」的可见性够不够 |
| **B** | 修 `HeaderChip`：让「有图标 + reserve」也对称（改 `_iconLead` 公式）| ⚠️ 会改**既有组件的语义**；`labelReserve` 的「文字居中」是复习页的设计意图，改了会让那边偏 |
| **C** | 给导入加一个数字（如「导入 3」= 库里几本）| ❌ **语义错误** —— 导入是动作，不是状态计数 |

> 🔑 **推荐 A 的理由**：问题出在「为了防跳而借用了为另一个目的设计的参数」。
> A 是**消除借用**（不是让借用的副作用好看一点）。

### 代码事实

`screens/book_reader_screen.dart:219-230`：
```dart
// ⚠️ 一期用 `Text`（不可选）—— 划词查词留到下一轮（见文件头）。
//    不用 `SelectionArea` 是**有意**的：那会让用户以为能查词，
//    选了却没有菜单 ⇒ 「有出口的假象」比「没有出口」更让人困惑。
Text(ch.text, style: ...)
```
文件头（`:11-18`）：
```
// `reader_screen.dart`（1284 行）里的划词逻辑（`SelectionArea` + 防抖 + …）
// ⇒ 本轮取后者，但**不在这一轮做**。本页先给「阅读 + 翻章 + 进度 + 朗读」。
// ⏳ 下一轮：把 `reader_screen` 的划词抽成 `WordLookupSelection`
```

⇒ **这是当初有意留到下一轮的**，不是坏了。但现在真机体验上，白哥的观感就是「划词不成功」——
**功能缺失与功能坏掉，对用户是一样的**。

### 影响范围
- 书库阅读页（`book_reader_screen`）全章正文不可选、无查词
- **不影响**信息流文章（`reader_screen` 的划词正常）

### 修复选项

| 方案 | 做法 | 评价 |
|---|---|---|
| **A ★推荐** | 按原计划**抽 `WordLookupSelection` 公共组件**（从 `reader_screen` 抽出 `SelectionArea` + 防抖 + 查词弹层），信息流页改调它，书库页接入 | ✅ 「一处定义」；避免两份划词实现漂移<br>⚠️ 属重构，改动面较大（信息流页 1284 行也在动）|
| **B** | 书库页**单独**写一份划词（复制 `reader_screen` 的逻辑）| ❌ 两份实现必然漂移（本项目已有教训）|
| **C** | 先只加 `SelectionArea`（能选、能复制），查词菜单下一轮 | ⚠️ 会被误读为「能查词」（原注释正是担心这点）|

## ③ 全篇朗读不可用 —— 🔴 根因：**超平台单次朗读长度上限**

### 根因链

1. `book_reader_screen.dart:250`：
   `ref.read(ttsServiceProvider).togglePlay(ch.text)` —— 传的是**整章正文**
2. `tts_service.dart:242`：
   `_tts.speak(_cleanText(text))` —— `_cleanText` **只做字符串替换，没有截断、没有分段**
3. 🔴 **平台有单次输入上限**：
   - **Android** `TextToSpeech.getMaxSpeechInputLength()` ≈ **4000 字符**（AOSP 常量）
   - iOS `AVSpeechUtterance` 同样有实际上限
   而**一本电子书的一章通常 5,000～50,000 字符** ⇒ **必然超**
4. 🔴 **失败是静默的**：`awaitSpeakCompletion` **未开启** ⇒ `speak()` 立即返回，
   Dart 侧**收不到失败** ⇒ 与既有的「语速事故」**同一族**：
   > 「第三方库报成功」不能当作「值合法/执行成功」

### 为什么现在才发现

**这是全项目第一次长文本朗读。** 已有的朗读点**全部是短文本**：

| 位置 | 内容 | 长度 |
|---|---|---|
| `widgets/speak_button.dart:111` | 词卡（单词 / 例句）| 几十字符 |
| `profile_screen.dart:322 / 1015` | 音色试听固定句 | 十几字符 |
| **`book_reader_screen.dart:250`** | **整章正文** | **数千～数万字符** ← 🆕 |

⇒ 既有代码路径都喂短文本，**问题从未暴露**。

### 🔴 这两条是「代码事实」，第 3 条是「推断」（须真机确认）

| 层级 | 内容 | 性质 |
|---|---|---|
| 代码事实 | `_cleanText` **不截断、不分段**（已 grep 确认）| ✅ 确定 |
| 平台事实 | Android `getMaxSpeechInputLength()` ≈ 4000 字符（官方 API）| ✅ 确定 |
| **推断** | **两者相加 ⇒ 整章朗读失败** | ⚠️ **推断**，未在真机验证 |

**真机验证方法**（一次即可判定）：
1. 连 `flutter logs` / 看 Xcode 控制台，点书库朗读按钮
2. 看是否打出 `[TTS] speak gen=N: "..."`（**打出了** ⇒ 执行到了 speak）
3. 看**有没有** `[TTS] native completion`（有 = 真读完了；无 = 没读完）
4. 对照组：在词卡上点朗读（短文本）——若词卡有声而书库无声 ⇒ **坐实是长度问题**

> 📌 判据：**「检测为 0」与「有信号」两问：先证检测器有效**——
> 用「词卡能读」做**阳性对照**，才能把「书库不能读」归因到长度而非别处
> （如音频会话、`_enabled` 被关）。


`togglePlay` 的「同一文本再点 = 停止」依赖 `state == TtsState.playing`；
朗读静默失败后 `state` 已回 `stopped` ⇒ **再点仍是「播放」分支** ⇒ 用户看到的是「点了没反应」。

### 修复选项

| 方案 | 做法 | 评价 |
|---|---|---|
| **A ★推荐** | **分段朗读**：按段落/句末标点切到 ≤ 安全阈值（建议 **3000 字符**），用 TTS 的**队列**依次播完；`stop` 清空队列 | ✅ 真正实现「全篇朗读」<br>⚠️ 需处理：进度、停止、切章时清队列 |
| **B** | 只**截断**到上限（读开头就停）| ❌ 与「全篇朗读」的承诺不符，用户会以为读完了 |
| **C** | 超长时**提示**「本章过长，暂只支持分段朗读」| ⚠️ 最省事，但功能仍不完整（等于把问题告诉用户）|

> 🔑 **推荐 A**，并附一条**兜底**：因为 `speak()` 静默返回，
> 分段方案必须**自己验证「真的读了」**（例如开启 `awaitSpeakCompletion` 或依赖
> `setCompletionHandler` 推进到下一段）—— 否则分段也是「报成功但没声」。
