## 一、🔴 两处必须先纠正的直觉（否则会丢数据）

### 1.1 「清空缓存」**不能无条件**

| 做法 | 后果 |
|---|---|
| 🔴 **无条件 `DELETE FROM external_word_cache`** | **未回流的词**（`hit_count < 门槛`）卡内容没了 → 复习页 `cardById` 查不到 → **用户的复习计划里出现空卡** |
| ✅ **只删「已确认回流」的** | 已回流的词有新家（word.db）→ 缓存可删；未回流的**原样保留** |

⇒ **「清空」= 算法清空（收敛掉的才删），不是 `TRUNCATE`。**
   用户的 |缓存| 会随回流**单调递减**，最终趋于 0 —— 这才是白哥要的效果，且不丢卡。

### 1.2 「收敛」是**渐进**的，不是发版即全清

只有**被回流的词**才收得动。没回流的词永远停在 `ext:`（且这是对的 —— 它还没进权威库）。
⇒ 期望管理：**每次发版，能收多少收多少**；不追求「一次清零」。

## 二、收敛算法（纯逻辑，可独立断言）

### 2.1 触发条件

`ensureWordDb`（`word_db_bootstrap.dart:152`）判定 **词库变了** → 收敛。

### 2.2 🔑 关键性质：**不需要 mapping 文件**

`ext:<spelling>` 里的 `<spelling>` **就是拼写** → 收敛时直接拿它去**新** `word.db` 查：

```sql
SELECT id FROM word WHERE spelling = ? COLLATE NOCASE LIMIT 1
```

命中 ⇒ 该词已回流 ⇒ 收敛；未命中 ⇒ 未回流 ⇒ 保留。

📌 **不需要「回流导出 ext→w 映射表」** —— 拼写本身是桥。
   ⚠️ 前提：`word.spelling` 在 word.db 里**唯一**（09-25 实测 11,523 词 **0 组冲突**）→ 需加断言守护（见 §五）。

### 2.3 步骤（伪码）

```
收敛词表 = user.db 里三张表的 word_id ∪ ，筛出 LIKE 'ext:%'
for wid in 收敛词表:
    sp    = wid 去掉 'ext:' 前缀
    newId = 新 word.db: SELECT id FROM word WHERE spelling = sp COLLATE NOCASE
    if newId is null:  continue                    # 未回流 → 保留（缓存也留）

    user.db.transaction:
        ① user_word        : wid → newId           # 冲突则合并（见 2.4）
        ② card_review_state: wid → newId           # 同上
        ③ review_log       : wid → newId           # 冲突行丢弃（重复事件）
        ④ DELETE FROM external_word_cache WHERE spelling = sp COLLATE NOCASE
```

🔴 **顺序不可换**：**先改完三表 → 再删缓存**。
   反了且中途失败 → 数据还指 `ext:` 而缓存已没 → **取不到卡**（比不收敛更糟）。

### 2.4 主键冲突（罕见但必须定规则）

| 场景 | 现在会怎样 | 规则 |
|---|---|---|
| `user_word` 里同时有 `ext:brainstorm` 与 `w011524` | `UNIQUE(word_id)` **拦不住**（两个不同 id）→ 两行并存 | 合并：保留 **`added_at` 更早**的；另一行删除；`source_sentence` 取首次 |
| `card_review_state` 同词两行 | 复习状态分裂 | 合并：保留 **`reps` 更大**的一行（学得更多的那个）；另一行删除 |
| `review_log` 改 id 后与既有行撞 `UNIQUE(word_id, reviewed_at, device_id)` | 报错 | `UPDATE OR IGNORE` → 残留的 `ext:` 行**删除**（同一设备同一时刻的重复事件无意义）|

📌 冲突概率：**只有「先查了词库外的词、后来词库更新又查了同一个词」才会出现** ——
   但**这正是回流机制生效后的常见路径**，不能当理论边界忽略。

### 2.5 幂等

收敛只处理 `LIKE 'ext:%'` 且「新库已能查到」的行 → **重跑无副作用**（第二次没有候选）。
⇒ 中途失败可以**直接下次启动重来**，不需要断点续传。

## 三、🔴 前提：必须先有「词库变了」的**确定信号**

**这是本轮最容易被漏掉的一环。**

现状（`word_db_bootstrap.dart:27-30` 自己预告过）：
> 「判断依据是**文件大小** —— 这是**启发式**……若将来真出现〔同大小不同内容〕，
> 应改为「随词库生成的**版本号文件**」。**现在不预先加**」

🔑 **『现在』这个前提已经变了**：
- 一旦有回流，**词库更新从「罕见」变成「常态」**（每次发版都可能变）
- 而收敛**依赖**「我知道词库换了」
- 🔴 若新版 word.db 大小恰好相同 → `skipped` → **词库没更新 + 用户数据没收敛** → 双错且**静默**

⇒ **`word_db.version` 从「将来的优化」升级为「收敛机制的必需前置」。**

| 方案 | 做法 | 代价 |
|---|---|---|
| ⭐ **版本文件** | 随 word.db 生成 `word_db.version`（内容如 `2026.10.1+11523`）· 端侧存一份副本 → **不一致即视为更新** | 极小（一个几字节的 asset）|
| 兜底 | 保留文件大小比较 | `versionChanged \|\| sizeChanged` → 双保险；版本文件缺失时不至于完全失能 |

📌 建议：**`needsCopy` 改成「版本不同 或 大小不同」**（两信号取并集），
   并把「版本文件缺失」当成 `unknown` 处理（此时退回纯大小比较，保留现状能力）。

## 五、断言与验收

| # | 断言 | 防的是 |
|---|---|---|
| 1 | 🔴 **`word.spelling` 在 word.db 内唯一** | 「拼写当桥」失效（否则收敛到错的 id）|
| 2 | 收敛**纯函数**：给定候选集 + 新库查询结果 → 操作集正确（含 4 种情形：未回流 / 无冲突 / user_word 冲突 / review_log 冲突）| 逻辑错 |
| 3 | 🔴 **老库升级演练**：造一个含 `ext:` 三表数据的 v_n 库 + 新 word.db → 跑 → **三表 id 全改、缓存清空、未回流行原样** | 端到端 |
| 4 | **幂等**：连跑两次 → 第二次零改动 | 中途失败可重试 |
| 5 | 🔴 **失败顺序**：注入「删缓存后抛错」→ 断言**数据未被改**（证明先改后删）| 顺序反了 |
| 6 | **未回流的词**：断言缓存行**仍在**且取卡正常 | 无条件清空 |
| 7 | `ext:` 常量**单点**：`grep -c` 全仓库应 == 定义处 1 处 + 引用处 | 两处漂移 |
| 8 | golden 快照 diff：已有 id 的拼写**零变化** | 全量重建把 id 打乱 |

> ## 🔧 新增：发版流程多两步（**必须做，否则机制形同虚设**）
>
> ```bash
> # 改完词库（data/word.db）之后：
> python scripts/gen_word_db_version.py          # ① 刷新版本指纹
> python scripts/word_db_id_snapshot.py --check   # ② 确认「只增不改」（🔴 删/改 id 必须查清）
> python scripts/word_db_id_snapshot.py --write   #    确认无误后更新基准

> ```
> ⚠️ **漏跑 ① → 端侧永远认为「词库没变」**（因为版本没更新）→ 新版词库**发不出去**，

>    同时校验版本文件，可当作兜底（它会在源/副本脱节时报红）。

> 🔴 **CI 尚未接入这些检查**（`query_verify` / `tokens_verify` 也不在 CI 里）——
>    建议在「上架前置」批次里把这几条 check 接进 CI，否则仍靠人工记得跑。
