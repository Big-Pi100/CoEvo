## 一、选型结论（结论前置）

**两级替换，全部用成熟包，零自建渲染逻辑**：

| 层 | 现在（自建） | 换成 | 版本 | 许可 | 为什么是它 |
|---|---|---|---|---|---|
| **后端提取** | `content_extract.rs` 自建启发式（640 行，只取 `<p>`、`collapse_ws` 压平一切）| **`dom_smoothie`** | 0.18 | MIT | **readability.js 的 Rust 移植**（Mozilla 那个，Firefox 阅读模式同源）· **15 万下载/月** · 活跃维护（2026-06）· 内建 `TextMode::Markdown` · **实测两个症状都治好**（§十一）· **与项目现有 html5ever 同版本**（§1.1）|
| **端侧渲染** | `splitParagraphs` 纯文本逐段 `Text` | **`gpt_markdown`** 升级 1.0.9 → **1.3.0** | BSD-3 | 依赖**已在项目里** · 内建**代码块语法高亮 + 语言标签 + 复制按钮** · 内联代码样式 · 表格 · 图片 · **`SliverGptMarkdown` 长文档懒渲染** |
| ~~HTML→MD~~ | — | ~~`htmd`~~ | — | — | ❌ **实测不需要**（§11.2：它没有正文提取能力，直接对全页用会把 CSS 也转进来 → 26,951 字 vs 6,519 字）；`dom_smoothie` 一步到位 |

**一句话**：后端从「自己写启发式提取」换成「Mozilla Readability 的移植」；
端侧从「纯文本逐段渲染」换成「成熟 Markdown 渲染器」。

### 1.1 🔑 一个硬理由：`dom_smoothie` 与项目现有栈**共享同一个 html5ever**

实测依赖解析结果（`cargo` 版本解析，非文档推测）：

| 包 | 依赖的 `html5ever` | 对项目的影响 |
|---|---|---|
| 项目现有 `scraper = "0.20"` | **0.27.0** | — |
| **`dom_smoothie` 0.18.2**（→ `dom_query` 0.28）| **0.27.0** | ✅ **完全复用，零重复编译** |
| `htmd` 0.1.6 | **0.39.0** | 🔴 **会同时存在两个 html5ever 版本** |

⇒ **这直接决定了 §九-3 的倾向**：
`dom_smoothie` 与现有 HTML 栈**同源同版本**（都基于 html5ever 0.27），
而 `htmd` 会引入**第二份 HTML 解析器**（编译时间 + 二进制体积 + 两套行为差异）。

🔑 **判据**：**选包不只看「它能不能做」，还要看「它与现有栈叠不叠」** ——
同版本依赖是**零成本**，不同版本是**永久成本**（每次构建都付）。

## 二、为什么「不自建」—— 本项目已有的两处自建都已出问题

这不是抽象论证，是**本项目自己的历史**：

| 自建资产 | 规模 | 现状 |
|---|---|---|
| `content_extract.rs` 的启发式提取 | **640 行** | 🔴 **本报告三个症状中的 2 个源于它**（压平预格式、丢内联代码语义）|
| `markdown_span_nodes.dart` 的自建渲染器 | **870 行** | 🔴 **零消费者（死代码）** —— 三种搜法一致确认：`RichContentBuilder` 只在自身文件内出现 |

📌 第二项正是白哥判断的佐证：**870 行自建渲染器写完就没人用** ——
自建渲染的隐性成本不只是「写」，还有「接线、维护、以及被弃置」。

🔑 **而成熟包解决的问题恰好是我们的痛点**（已从官方文档核实）：

| 我们的痛点 | 成熟包怎么解 |
|---|---|
| 预格式被压平（ASCII 树变一行）| `htmd` / `dom_smoothie` 的 Markdown 模式产出 ` ``` ` 围栏块，**保留换行缩进** |
| 内联代码裸奔（`<img>` 看着像 HTML 源码）| `gpt_markdown` 的 `InlineCodeStyle`（等宽 + 底色）|
| 长文档性能 | `SliverGptMarkdown` 只构建视口内的段 |
| 畸形 Markdown（我们数据质量参差）| `gpt_markdown` 官方称 "Graceful malformed input" |

`content_pool.body` 的语义：**「纯文本（`\n\n` 分段）」→ 「Markdown」**。

🔴 这引出一个**必须处理**的问题：**新旧混存期**。
- 老数据是纯文本 → 用 Markdown 渲染时，含 `*` `_` `#` `[` `` ` `` 的会被当语法
- ✅ 白哥已定「**重抓存量**」→ 但要**先重抓完再切渲染器**（见 §五 的顺序约束）

### 3.3 端侧（三处）

| 位置 | 现状 | 改成 |
|---|---|---|
| `reader_screen.dart:324` | `splitParagraphs(value.readableText)` | `SliverGptMarkdown(markdown, ...)` |
| `article_text.dart`（纯函数层）| `splitParagraphs` 按 `\n\n` 切 | **保留**（Markdown 渲染仍可能按块切），但**不再是主渲染路径** |
| `pubspec.yaml` | `gpt_markdown: 1.0.9` | 升到 **1.3.0** |

⚠️ **注意**：现在是**精确版本** `1.0.9`（不是 `^1.0.9`）→ 升级必须**显式改这一行**，
不会因为 `pub upgrade` 自动上去。🔑 这个钉法本身是**对的**（可复现构建），别顺手改成 `^`。

✅ **依赖干净度已核实**：`pubspec.lock` 里**没有**已废弃的 `flutter_markdown`（含间接依赖）——
所以不存在「换包后发现被别的东西拖回废弃版」那个经典坑。
（`flutter_math_fork` 是 `gpt_markdown` 的传递依赖，不是我们直接用 —— 见 `pubspec.yaml:97` 的注释。）

## 四、两个必须由白哥拍的决定

> ✅ **已拍（2026-10-02）**：决定 1 = **A 不显示图片** · 决定 2 = **B 分批重抓**。

### 决定 1 · **正文里的图片要不要显示？**

现状：`<img>` 完全丢失（提取器只取文本节点 → `<img>` 无文本 → 跳过）。

改成 Markdown 后，技术上可以保留 `![](url)`，但端侧要**加载网络图片**：

| 选项 | 代价 | 风险 |
|---|---|---|
| **A. 不显示图片**（提取时丢弃）| ¥0 | 文章里的图看不到，但**至少不会显示成乱码**（现在的情况）|
| **B. 显示图片** | 端侧加图片加载 + 缓存 | 🔴 **国内可达性**（图床常被墙）· 流量（用户是移动网络）· 需要占位/失败兜底 |

⚠️ 我的建议：**先 A**（本轮不引入图片），理由是：
本项目已定「内容源绕开版权风险」，而**图片的版权风险比文字更直接**；
且 `img` 的国内可达性不可控。若要 B，建议作为**独立批次**做，含「失败占位 + 仅 WiFi 加载」策略。

### 决定 2 · 重抓存的「执行窗口」

重抓 311 篇要**真的发 311 次 HTTP 请求**（对第三方站点）。

| 选项 | 说明 |
|---|---|
| **A. 一次性全抓** | 快，但对源站压力大、易触发限流 |
| **B. 分批慢抓**（建议）| 沿用现有 `content_fetch` 的**限量**机制（`:642` 注释「每轮限量」），分几轮跑完 |

⚠️ 无论哪种，都要先 **清空 `body_attempted_at`**（`content_fetch.rs:349` 的 `WHERE body_attempted_at IS NULL` = **只抓一次**）。

## 五、实施步骤（含顺序硬约束）

⚠️ **顺序不可颠倒**（否则出现新旧格式混存 → 渲染乱）：

```
① 后端换提取器（dom_smoothie）—— 只影响「新抓的」
      ↓
② 清 body_attempted_at + 分批重抓 311 篇（老数据变 Markdown）
      ↓   ← 这一步跑完前，端侧不许切渲染器
③ 端侧切 SliverGptMarkdown（+ 升级 gpt_markdown 到 1.3.0）
      ↓
④ 修 §3.4 那两处（兜底显式化 + 报错过滤）
```

### 🔴🔴 但上面这张图**不完整** —— 它暗示「等 ② 完成再切 ③」就够了（2026-10-02 修正）

**实际不是**：`①` 落地的那一刻，**新抓的文章就已经是 Markdown** ——
所以「等 ② 完成」并不能消除窗口，窗口从 ① 就开始了。

而端侧当前是**纯文本渲染**（`splitParagraphs`：按 `\n\n` 切段，**段内单换行 → 空格**）：

| 情况 | 结果 |
|---|---|
| 新提取器产出「代码块（多行 + 缩进）」 | 🔴 `splitParagraphs` **仍把段内换行压成空格** → 又被压平 |
| 新提取器产出 ``` / `##` / `**粗体**` | 🔴 作为**普通文字**显示出来 |

⇒ **只做 ①②（后端 + 重抓）、不跟上 ③ = 症状没治好，反而多出 Markdown 标记。**

📌 **判据（本次修正的核心）**：
**改「数据格式」时，「产出侧」与「消费侧」是一件事的两半** ——
中间的窗口**不能靠「排顺序」消除**（因为产出侧一上线就开始写新格式），
只能**明确接受它、并说明谁受影响**。

⇒ 所以正确说法不是「③ 要等 ②」，而是：
**③ 与 ①② 的窗口必须被明确交代**（本次结论：零真实用户 → 窗口可接受，
唯一受影响者是测试者本人；详见 `s3-production-execution-checklist-2026-10-02.md` §三）。

## 十一、实测结果（**已跑，非推测**）

**方式**：独立临时 Rust 项目（`C:/Users/Lenovo/ds_probe/`，**零项目侵入**），
依赖 `dom_smoothie 0.18.2` + `htmd 0.1.6`，
输入 = **三篇真实 Dev.to 页面**（本地实测抓取，非构造样本）。

### 11.1 ✅ 两个关键症状都被治好

| 验证项 | 原文 | `dom_smoothie` Markdown 输出 | 结论 |
|---|---|---|---|
| **内联代码**（案例 3）| `audit.html` 有 **32 个 `<code>`** | **64 个反引号**（32 对，**完全对上**）<br>样例：`` `<img>` `` · `` `alt` `` · `` `alt=""` `` · `` `<label for>` `` | ✅ **治好** |
| **代码块**（案例 1）| `gitstage.html` 有 **1 个 `<pre>`**（11 行、含 8 空格缩进）| ``` 围栏，**11 行全保留**，`        modified:   file.txt` **缩进原样** | ✅ **治好** |
| 标题 | `<h2>` / `<h3>` | `## ` / `### ` | ✅ |
| 引用块 | `<blockquote>` | `> Note: …` | ✅ |
| 粗体 | `<strong>` | `**working directory**` | ✅ |
| 链接 | `<a href>` | `[my first post here](https://…)` | ✅ |

**代码块实测原文（节选，证明缩进真的保住了）**：

~~~text
```

$ git add file.txt
$ echo "v2" > file.txt

⇒ **案例 1 的那棵 ASCII 树，用 `dom_smoothie` 会变成有围栏、有缩进的代码块**（而不是压成一行）。

### 11.2 🔴 `htmd` 直接对全页用是**错的**（实测推翻）

| | `dom_smoothie`（Markdown 模式）| `htmd`（直接转全页）|
|---|---|---|
| 输出长度 | **6,519 字** | 🔴 **26,951 字**（**4 倍**）|
| 开头内容 | `## The 12 HTML checks…`（正文）| 🔴 `body:has(.pageslug-aie) #topbar { display: none !important; } …`（**CSS 源码！**）|

🔑 **原因**：`htmd` 是**纯转换器**，**没有「正文提取」能力** ——
它把页面里 `<style>` 的 CSS 也一并转成了 Markdown。
⇒ **`htmd` 必须先用 `dom_smoothie` 提取正文 HTML，才能用**（两步）。

**而 `dom_smoothie` 一步到位**（提取 + Markdown 都在里面）。

### 11.3 ⚠️ 观察到的一个副作用：**过度转义**（需真机确认）

输出里有 CommonMark 的**安全转义**：

```
two keystrokes\.          ← 句号被转义（防止误判为有序列表）
1\.1\.1 \(A\)             ← 编号 + 括号被转义
\"graphic\"               ← 引号被转义
```

| 判断 | 说明 |
|---|---|
| ✅ 语义上**是对的** | Markdown 规范里 `\.` 渲染后就是 `.` —— 这是**规范要求**的转义 |
| ⚠️ **但要验证渲染器** | 若 `gpt_markdown` 不处理这类转义，用户会**看到** `1\.1\.1` |
| 🔴 **我验不了** | 需要 Flutter 环境（**跑不了**，见 `a2-*` 清单 §0.4）|

⇒ 📌 **列入真机验证点**：装机后看正文里的编号是否显示成 `1.` 而不是 `1\.`。

### 11.4 §九-3 的结论（已可定）

**不需要 `htmd`** —— `dom_smoothie` 一个包就够（且它与项目现有 `html5ever 0.27` 同版本，§1.1）。
`htmd` 的唯一优势场景（faithful 模式保留 HTML）我们用不到。

**复现方式**：`C:/Users/Lenovo/ds_probe/`（临时项目保留，`cargo run --release -- <html>`）。

## 十三、实施记录（2026-10-02 · S1 / S2 / S5 已完成）

### 13.1 与方案的差异（实际实现比方案多两处）

| 项 | 方案写的是 | 实际实现 | 为什么 |
|---|---|---|---|
| 调用签名 | `extract_to_markdown(&html)` | `extract_to_markdown(&html, Some(url))` | 带 `base_url` 才能把 Markdown 里的**相对链接绝对化**（否则 App 里点不开）|
| 图片 | 「提取时丢弃」 | **显式** `strip_markdown_images()` | 见下 |

**🔑 图片为什么是「显式剥离」而不是「靠库不输出」**：
实测 `dom_smoothie` 的 Markdown 模式**本来就不产出** `![...](...)`，
但「不显示图片」是**产品决定**，不该依赖第三方库的默认行为（库升级可能改）。
📌 判据：**决定要靠自己的代码兑现，不能靠依赖的副作用**。

**🔑 `base_url` 非法时降级重试**：`Readability::new` 对非绝对 URL 直接返回
`BadDocumentURL` → 带 url 建失败就**退回不带 url 重试**（正文照常提取，只是链接保持相对）。
📌 判据：**增强项失败不该让主体失败**（同族：端侧 `word_db.version` 读不到时退回「比文件大小」）。

### 13.2 S5 的实现（两端）

**后端**：`content_fetch.rs` 加 `is_source_error_summary()` + `sanitize_summary()`，
在 `write_items` 里对 `summary` 列清洗。
判据 = **指纹 + 长度两条一起**（只按指纹会误杀「讲编译错误的教程」——
实测构造了一个长摘要含 `syntax error`，断言它**不被误杀**）。

**端侧**：`ArticleDetail.readableText`（`String?`）→ **`renderable`**
（`({String text, ArticleTextSource source})?`）+ `_SummaryOnlyBanner`。

根因值得记一笔：原 `readableText` 的注释**恰好写着**「退到 summary 时不要当成有正文」，
但**返回类型没能力兑现那句话** → 调用方只能按「非空 = 有正文」处理 → 事故。
📌 判据：**当注释在叮嘱调用方「区分 A 和 B」，而返回类型里没有 A/B 的区别时，
那不是文档问题，是类型问题。**
