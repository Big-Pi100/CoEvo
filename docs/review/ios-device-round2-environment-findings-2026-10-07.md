## 一、问题 1｜Apple 登录报 `FormatException: Unexpected end of input (at character 1)`

### 根因：**后端未部署** —— `/api/auth/apple` 这个路由在服务器上不存在

**证据 ①**（nginx access log）：

```
16:26:40  POST /api/auth/apple   404  0    ← 404，且响应体 **0 字节**
16:27:21  POST /api/auth/apple   404  0
```

**证据 ②**（服务器上的二进制）：

```
/opt/coevo/bin/coevo_backend   →  日期 2026-10-06 18:38
grep -a "apple_user_id"  →  **0 次**   ⇒ 旧版本（不含 Apple 登录代码）
grep -a "change-email"   →  **0 次**
```

### 为什么表现为 `FormatException` 而不是明确说「404」

`auth_client.appleLogin` 的第一句就是：

```dart
final data = jsonDecode(resp.body) as Map<String, dynamic>;
```

**空 body ⇒ Dart 的 `jsonDecode('')` 抛的正是**
`FormatException: Unexpected end of input (at character 1)` ✅ 与白哥看到的完全一致。

> ⚠️ 这是个**值得记的坑**：客户端在**解析成功之前**就假定「body 一定是 JSON」，
> 于是「服务端没这个路由」被翻译成了一句**看起来像数据问题的报错**。
> 📌 判据：**`jsonDecode` 之前应先判空 / 判状态码** —— 否则 404/空响应会被误报成解析错误。

| **找回密码** | HTTP **200**，但 body 是 `{"error":"验证码发送失败，请稍后再试"}` | 🔴 **腾讯云 SES 密钥从未配置** |

### 证据（应用日志）

```
2026-10-07T06:16:24Z ERROR api_server::routes: auth_forgot_password: 发信失败 —— 邮件服务未配置
2026-10-07T08:29:20Z ERROR api_server::routes: auth_forgot_password: 发信失败 —— 邮件服务未配置
```

### 证据（服务器 `.env`）

```
$ sudo grep -o "^TENCENT_SES_[A-Z_]*" /opt/coevo/.env

```

⇒ **找回密码的发信从来没成功过**：路由在、代码对，就是**没配密钥**。

`Err("邮件服务未配置")` ⇒ 路由把它转成用户可见的「验证码发送失败，请稍后再试」。
✅ **这是设计好的行为**（不吞错、如实报）—— 否则用户会一直等一封永远不来的信。

## 二·五、问题 2 已解决（2026-10-07 17:09）—— 但中间踩了一个 region 坑

### 过程

| 步骤 | 结果 |
|---|---|
| ① 白哥填好密钥文件 → 我写进 `/opt/coevo/.env`（4 项）+ 重启 | 日志从「**邮件服务未配置**」变成 `FailedOperation.SendEmailErr` ⇒ **密钥与签名都通了** |
| ② 但发信仍失败：腾讯云让你「**检查 Region 参数**」 | `ap-guangzhou` ❌ |
| ③ 用同一对密钥对候选 region 各发一次 | `ap-hongkong` ✅ **成功** |
| ④ `.env` 加 `TENCENT_SES_REGION=ap-hongkong` + 重启 | ✅ **实测通过**（见下）|

### 🔴 region 陷阱（本轮最有价值的发现）

**代码里 `TENCENT_SES_REGION` 有默认值 `ap-guangzhou`，而本项目的 SES 资源在香港。**

📌 判据：**「有默认值」≠「默认值正确」**。
配置项有默认值只说明「不填不会崩」，**不说明「不填是对的」** ——
尤其是**地域 / 端点 / bucket / 项目 ID** 这类**描述外部资源实际位置**的配置，
代码不可能猜对，**必须核实**。

⚠️ 而我当时把它标成「留空即可，走默认值」——**是我的判断失误**（把"有默认"当成了"默认对"）。

**为什么难查**：`FailedOperation.SendEmailErr` 是**笼统错误码**，
region 不对 / 模板未过审 / 域名未验证 **三者共用它**，
Message 里只有一句「请检查 Region 参数」——**它不指向真实原因**。

**实测出的 region 覆盖范围**：

| region | 结果 |
|---|---|
| `ap-guangzhou` | `FailedOperation.SendEmailErr` |
| `ap-hongkong` | ✅ 成功 |
| 其余 6 个（sh·bj·nj·cd·sg·tokyo）| `UnsupportedRegion` ⇒ **SES 只有广州与香港** |

## 三、问题 3｜找回密码应使用**账号绑定的邮箱**（**已修**）

### 根因：`ForgotPasswordDialog` 的两个入口**都没传邮箱**

| 入口 | 场景 | 此前行为 |
|---|---|---|
| `ClaimDialog`（登录弹窗）的「忘记密码？」 | **未登录** | 让用户填 |
| 🔴 `ChangePasswordDialog`（修改密码弹窗）的「忘记密码？」 | **已登录** | **也让用户填** ← **白哥指的就是这条** |

已登录时账号邮箱是**确定的**，让用户重填不但多余，**填错了还会把验证码发到别人邮箱**
⇒ 等于开了个「往任意邮箱发码」的入口。

### 改法

`ForgotPasswordDialog` 新增两个参数：

| 参数 | 行为 | 传值方 |
|---|---|---|
| **`lockedEmail`** | 第 0 步**不显示输入框**，改为只读展示账号邮箱 | `ChangePasswordDialog`（传 `authState.email`）|
| **`initialEmail`** | **预填**（仍可编辑） | `ClaimDialog`（传登录框里刚打的邮箱）|

🔑 **为什么不给「未登录」入口也锁定**：那时系统**确实不知道用户是谁** ——
必须允许他填（他可能记错了）。锁死会让他彻底没路走。
📌 判据：**「不用填」的前提是「系统已经知道」** —— 已登录才知道，未登录只能问。
