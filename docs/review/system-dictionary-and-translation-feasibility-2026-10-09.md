# iPhone 内置词典 / 翻译能力 —— 可行性核查（2026-10-09）

> 来源：白哥提问「App Store 里的 Readon（RSS 阅读）用了 iPhone 本身的词典和翻译，就像我们现在用 TTS。能不能调用 iPhone 内置的词典和翻译？」
> 状态：🔴 **只做核查，未改任何代码**（按项目铁律：先报告 → 请示 → 再实施）

## 〇、一句话结论

| 能力 | 能不能调 | 结论 |
|---|---|---|
| iPhone **内置词典** | ❌ **不能**（拿不到词条文本） | iOS 官方只给了「弹系统词典界面」的 API，**取不到释义文本**；唯一能取文本的 `DCSCopyTextDefinition` **只有 macOS / Mac Catalyst** |
| iPhone **内置翻译** | ✅ **能** | iOS 18+ 的 `Translation` framework：**端侧 · 免费 · 离线 · 能拿到译文文本**；iOS 26+ 还有官方「无界面」入口 |

⇒ 白哥看到的 Readon 那套「内置翻译」，**几乎可以断定就是 `Translation` framework** —— 因为要在**自己的 UI** 里显示译文，只有它能给到文本（`.translationPresentation` 只能弹 Apple 的浮层）。

## 一、词典：为什么不能

三个 API 逐条核实：

| API | 平台 | 能给什么 | 能用吗 |
|---|---|---|---|
| `UIReferenceLibraryViewController(term:)` | iOS 5+ | **只弹系统模态词典页** | ⚠️ 能显示，但**拿不到文本**；Apple 文档明说「不要用来做词典 App」；UI 完全不可定制 |
| `dictionaryHasDefinitionForTerm(_:)` | iOS 5+ | 一个 `Bool` | ✅ 能查「有没有这个词条」，但**取不到内容** |
| `DCSCopyTextDefinition(...)` | **macOS 10.5+ / Mac Catalyst 13.1+** | 释义**纯文本** | ❌ **iOS 不可用**（官方平台列表里没有 iOS；iOS 上 `import CoreServices.DictionaryServices` 直接编译不过） |

- 私有 API 路线：**不可用** —— App Store 审核会拒，且我们没有企业证书。
- 系统词典数据文件（`/System/Library/...` 的 `.dictionary` 包）：在沙盒外，**读不到**。

### 口径精确化（白哥 10-09 追问后确认）

「Apple 官方能调、但对我们不可用」——这个理解**成立**，但要拆成三句才准确：

| 子问题 | 答案 | 依据 |
|---|---|---|
| 能不能**正常调用**（不违规、能过审）？ | ✅ **能** | `UIReferenceLibraryViewController` 是**官方公开 API**，弹系统词典页是完全正当的用法 |
| 能不能**拿到释义内容**（落库 / 进记忆）？ | ❌ **不能** | 没有任何返回文本的接口 —— 唯一能给文本的 `DCSCopyTextDefinition` **不是 iOS 平台的** |
| 能不能**定制界面 / 语言对 / 展示形式**？ | ❌ **不能** | 整页由系统渲染，只接受一个「词」参数，其余全不可改 |

⇒ 对**「查词 → 落库 → 复习」这条闭环**来说，它**等价于不可用**：
我们缺的不是「有个地方能看释义」，而是「**释义能变成我们卡片里的数据**」。

⚠️ 补充两条容易忽略的：

1. `dictionaryHasDefinitionForTerm(_:)` 能返回 `Bool` ⇒ 「**有没有**这个词条」是可编程的，「**是什么**」不可编程。
2. 但连这个 `Bool` 都**不稳定** —— 系统词典（中文环境下的英汉/汉英）需要用户自己到「设置 → 通用 → 词典」**手动下载**；没下载时可能查不到。

📌 **为什么 TTS 能用、词典不能**（同一个「系统能力」，结论相反）：

> TTS 我们要的是「**读出来**」这个**动作**（`AVSpeechSynthesizer` 提供），所以系统能力直接可用；
> 词典我们要的是「**释义文本**」这份**内容**，而系统只提供「显示」，**从不交出内容**。
> ⇒ 判据：**「系统能显示」≠「系统能给数据」**；能不能用，取决于我们要的是**动作**还是**内容**。

**对我们的价值**：只勉强能做「兜底出口」—— 当 `word.db` 查不到某词时，让用户**跳到系统词典**看释义。但体验割裂（系统页面、释义以英文为主、不可定制），对「中英对照词卡」帮助有限。

📌 判据：**「系统有词典」≠「第三方能读词典」** —— 平台只开放了「显示」，没开放「取用」。

## 二、翻译：能，而且值得认真看

### 能力事实（Apple 官方文档 + WWDC24）

| 项 | 值 |
|---|---|
| 框架 | `Translation.framework` |
| 版本门槛 | `.translationPresentation`（只弹浮层）iOS **17.4+**；`TranslationSession`（**能拿文本**）iOS **18.0+**；无界面初始化 `init(installedSource:target:)` iOS **26+** |
| 运行位置 | **完全端侧**（on-device），语言包与 Apple「翻译」App **共用** |
| 费用 | **免费**（Apple 不收费、无额度） |
| 语言 | 含**英语（美/英）· 中文（简体）· 中文（台湾）** ✅ |
| 数据 | **正文不出设备**（Apple 只收集 Bundle ID + 语言对做使用统计） |
| 语言包 | 首次需**用户同意下载**（几十 MB），此后**完全离线** |
| 模拟器 | ❌ **不能测**（Apple 明确：必须真机） |

### 🔴 决定工作量的技术细节

现有 Flutter 包 `apple_native_translate` 的 README 写得很直白（照抄）：

> iOS 18〜25 では `TranslationSession` を **UI 無しで作れません**（UI 無しの初期化子 `init(installedSource:target:)` は **iOS 26 以降**です）。そのため、見えない 1×1 の SwiftUI ビューを一時的に貼り、その `.translationTask` からセッションを受け取ります。

翻译成要点：

- **iOS 18–25**：必须**贴一个不可见的 SwiftUI 视图**，从它的 `.translationTask` 里拿 session。
  Apple 工程师在开发者论坛明确推荐用 `UIHostingController` 承载 SwiftUI 视图（属**官方认可**的做法），但「1×1 不可见视图」在审核观感上有轻微「取巧」嫌疑 ⇒ 审核风险**中等**。
- **iOS 26+**：官方给了无界面入口，干净（但**要求语言包已安装**，否则抛错 ⇒ 首次下载仍需 UI 上下文）。

### 中国区可用性（我们的分发区域）

- Apple 的服务在**中国大陆不被墙**；Apple「翻译」App 官方支持**中文（中国大陆）**，且支持**下载语言包后离线使用** ✅
- 语言包下载走 Apple 服务器 ⇒ 大陆网络**可下**；但**首次需网络 + 用户同意**，实际速度与成功率**必须真机实测**（无法从文档断定）。

## 三、我们的现状（对照）

| 项 | 现状 | 证据 |
|---|---|---|
| **TTS** | ✅ **已经是系统能力** —— `flutter_tts`（iOS 底层 `AVSpeechSynthesizer`），全量端侧、离线 | `app/pubspec.yaml:22`、`services/tts_service.dart` |

| **原生桥接先例** | ✅ 已有：`MethodChannel("coevo/open_with")` + `AppDelegate.swift`（含 `window?.rootViewController` 取用） | `app/ios/Runner/AppDelegate.swift` |

🔑 **白哥的类比是准确的**：TTS 用的就是系统能力。翻译目前**不是**。

## 四、换成端侧的连带影响（必须先想清）

| 维度 | 服务端 LLM（现在） | 端侧系统翻译（可选） |
|---|---|---|
| 成本 | 每次真调模型（10 次/月额度） | **0**（Apple 不收费） |
| 离线 | ❌ | ✅（下载语言包后） |
| 隐私 | 正文**出境**到模型服务商 | **不出设备** ✅（与当初否掉方案 B 的「数据出境」顾虑完全契合） |
| 登录 | **必须登录**（能力记账） | ❌ **不需要** ⇒ 与产品原则「除生词表上限外不验证登录态」**更一致** |
| 质量 | LLM：可注入术语 / 上下文，可做学习导向定制 | 通用 NMT：句子级、**无法定制 prompt** |
| 变现 | **翻译是订阅权益的一项**（免费 10 次 → 订阅无限） | 端侧免费**无限** ⇒ 🔴 **这条权益就没了** |
| 版本门槛 | 无 | iOS 18+（用 `if #available` 分支即可，**不必提升最低版本**） |
| 首次体验 | 直接可用 | **首次需下载语言包**（同意 + 等待） |

🔴 **最重要的一条**：翻译现在是**订阅权益**。端侧化后它变成「人人免费无限」—— 这是**产品决策**，不是技术决策。

## 五、方案

### 方案 A ⭐ 混合：端侧优先 + 服务端兜底 / 增强
- iOS 18+ 且语言包就绪 ⇒ **端侧翻**（免费、离线、匿名）
- 否则 ⇒ 回落现有服务端（老机型 / 语言包未下 / 端侧失败）
- 可再分层：**端侧快翻**（免费）vs **「精翻」走 LLM**（订阅权益）—— 把订阅权益从「**能不能翻**」改成「**翻得好不好**」
- 工作量：1 个 `MethodChannel` + 约 40–60 行 Swift（照 `open_with` 先例）+ Dart 侧一个 client；**零数据改动**
- ⚠️ 必须**真机验证**（模拟器不支持）

### 方案 B 全量端侧
- 翻译全走系统 ⇒ 免费无限、离线、匿名
- 代价：**订阅权益少一项**；老机型（iOS < 18）**没有翻译**（要么放弃、要么仍留服务端 = 变回混合）

### 方案 C 保持现状（服务端 LLM）
- 不做。理由：若白哥认为「翻译质量 + 学习定制」是核心竞争力，端侧达不到那个水平。

### ❌ 不建议：引入第三方包 `apple_native_translate`
- MIT、verified publisher（8-order.co.jp），但 **0.1.x 早期版本**、**36 天前**才发布、下载量极低；README 自己承认用的是「不可见 1×1 视图」的绕法。
- 我们只需 **40–60 行 Swift** 就能拿到同样能力（且完全可控）⇒ **自写优于引入早期包**（依赖的是 Apple **官方框架**，风险更低）。
