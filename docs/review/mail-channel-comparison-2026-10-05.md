# 发信通道选型 —— vibedollar 那套 vs 腾讯云 SES

> **起因**：白哥问「邮件发送是否应该和 vibedollar 那样」
> **方法**：读 vibedollar 源码（`/e/vibedollar/mailer.py` · `mailproxy/`）+
> **实测**它的公网端点。**不凭记忆**。
> **结论先说**：技术上都可行，但**我不建议复用** —— 理由是**用户群不同**，不是技术。

---

## 〇、先讲清 vibedollar 到底是怎么发的（白哥可能在问这个）

我读了它的实现，链路是这样的：

```
vibedollar 后端（境外 VPS <OTHER_PROJECT_IP> · 新加坡）
   └─ mailer.py  ├─ 若配了 MAIL_PROXY_URL ⇒ POST 国内代理
                 └─ 否则直连 SMTP
                          ↓
   国内 VPS <VPS_IP>（与 CoEvo 同机）
   └─ mailproxy（FastAPI · 127.0.0.1:8200）
        └─ smtplib → smtp.qq.com（**QQ 邮箱**）
                          ↑ nginx 反代
   公网端点：https://pay.keyievolution.fun/api/mail/send
   鉴权：X-Mail-Token 头（与 .env 的 MAIL_PROXY_TOKEN 恒时比较）
```

### 🔴 为什么会有「代理」这一层（源码注释里的原始事故）

`mailer.py` 文件头原文：

> 生产故障修复 (2026-08): QQ 邮箱**拒绝境外 IP 发信**
> （实测日志: `502 Invalid input from <OTHER_PROJECT_IP> to qq.com`，风控）。
> 新增「国内 VPS 发信代理」模式 …

⇒ 也就是说：**QQ 邮箱 SMTP 是它的根**，只是因为服务器在境外被风控，才加了一个国内中转。

### ✅ 实测：这个代理**现在活着**（我刚查的）

| 探测 | 结果 | 说明 |
|---|---|---|
| `POST /api/mail/send`（无 token） | **HTTP 401** `{"ok":false,"error":"unauthorized"}` | 服务在跑 + 鉴权正常（fail closed） |
| `GET /api/mail/healthz` | HTTP 404 | ⚠️ **不是服务挂了** —— nginx 只反代 `/api/mail/*`，而 healthz 在根路径 `/healthz` ⇒ 前缀不匹配，属预期 |

⇒ **「复用」在技术上确实可行**，这一点我如实确认。

### 🔴 但它的发件人长这样（源码实测）

```python
msg["From"] = formataddr(("vibedollar", cfg["mail_from"]))   # mailproxy.py:120
```

且 `MAIL_FROM` 默认 = `SMTP_USER`（`mailproxy.py:74`）—— 即 **QQ 邮箱地址本身**。

⇒ 用户收到的是：**`vibedollar <某个QQ号@qq.com>`**

## 一、逐项对比

| 维度 | **vibedollar mailproxy（复用）** | **腾讯云 SES（我方已实现）** |
|---|---|---|
| **可用时间** | ✅ **现在**（服务已跑 · 实测 401） | ⏳ 域名验证 5min–2h + **模板审核 1 工作日** |
| **发件人地址** | 🔴 `xxx@qq.com` | ✅ `noreply@mail.keyievolution.fun` |
| **发件人显示名** | 🔴 **硬编码 `vibedollar`** ⇒ 要用必须**改它的生产代码** | ✅ `CoEvo`（我方可控） |
| **邮件正文格式** | 🔴 **纯文本**（`MIMEText(..., "plain")`，无 HTML） | ✅ HTML 模板（已写好，含朱砂色品牌样式） |

## 二、🔑 我的建议：**用腾讯云 SES，不要复用 mailproxy**

理由**不是技术**（技术上两边都能跑），而是这三条：

### ① 🔴 密码重置邮件来自 QQ 邮箱 = **反诈骗特征**（这是最重的一条）

| | vibedollar 的用户 | **CoEvo 的用户** |
|---|---|---|
| 来源 | Reddit（英文圈） | **中国区 App Store** |
| 看到「来自 `xxx@qq.com` 的密码重置邮件」时 | 无特别反应 | **第一反应是诈骗**（这正是国内钓鱼邮件的典型形态） |
| 后果 | 可接受 | **用户不敢点/不敢用**；且这是**账号安全**场景，不该冒这个险 |

📌 这正是项目记过的那条判据的又一次应用：
> **「换个市场」前先确认目标用户群是否跟着移动** ——
> 同一个方案（QQ SMTP），**换一批用户，结论相反**。
> 这里的「用户群差异」不是地域，是**诈骗语境**：中国大陆用户对陌生 QQ 邮箱发来的
> 「重置密码」链接/验证码，警惕性远高于英文圈用户。

### ② 🔴 复用要**改 vibedollar 的生产代码**

显示名硬编码 `"vibedollar"` ⇒ 要么改它（加参数支持多项目），要么用户看到
「vibedollar 发来的 CoEvo 密码重置邮件」——后者不可能接受。

⇒ 复用的真实成本 = **跨项目改动 + 两个项目共用一个发信服务**（耦合）。

### ③ 🔴 共享额度会被 vibedollar 的通知邮件挤掉

vibedollar 有「候选积压通知」（每账号每天 1 封）+ 注册验证码 + 找回 key，
全部走**同一个 QQ 邮箱**。个人邮箱日限额有限，加上 CoEvo 的找回密码请求 ⇒
两边互相挤压，而**故障表现是「验证码发不出去」**（用户侧静默失败）。

### ④ 而本方只差**一个工作日**

- 代码**已写完并验证**（`tencent_ses.rs` · `cargo test` 228 全绿）
- 邮件模板**已写好**（`docs/operations/tencent-ses-onboarding-2026-10-05.md` §三，直接复制）
- 唯一瓶颈 = 模板审核（1 工作日），且**是日历天，不是工作量**

## 三、不过 —— 如果你想要「立刻能测通全链路」

我理解「先复用、SES 通了再切」的诱惑：**能提前验证前后端整条链路**。
这条路我也如实给出，它需要一个前提：

| 方案 | 做法 | 代价 |
|---|---|---|
| **D1** | 改 `mailproxy` 加一个**可选** `from_name` 参数（向后兼容，默认仍是 `vibedollar`）→ CoEvo 传 `CoEvo` | 动 vibedollar 生产（**需你批准**）；邮件仍是纯文本 + QQ 发件人 |
| **D2** | 后端把「发信」抽成一个**可切换通道**（`SesSender` / `ProxySender`），配哪个用哪个 | 多写一个实现（成本低）；**但不解决①②③的本质问题** |

🔴 我的看法：**D1/D2 都是「为了早一天而引入长期负担」**。
更省事的路是——**今天就把 SES 的模板提交上去**（审核在后台跑，不占你的时间），
明天通了直接端到端验。**中间这一天，前端已经可以先验**：
「未注册邮箱明说」「6 格输入」「冷却倒计时」这些**都不依赖真发信**
（第 1 步会走到「发信失败」为止，报的是「验证码发送失败，请稍后再试」≠ 流程错）。
