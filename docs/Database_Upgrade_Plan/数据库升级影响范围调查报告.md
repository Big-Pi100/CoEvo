## 一、V2.1 新增变更

### 【变更 A】新建 `plan_templates` 表（K12 共享模板）

| 维度 | 结论 |
|------|------|
| 用途 | 存储 K12/Reading 预置计划模板，所有用户共享。支持远程课标更新。 |
| 行数预估 | ~15（14 科目 + 1 reading） |
| 代码影响 | **无历史代码影响**（纯新增）。计划初始化时从此表读取。 |
| 读路径影响 | `k12_init_handler(routes.rs:2026)` — 从 `curriculum_loader::get_plan()` 读取改为从 `plan_templates` 读取 |
| 写路径影响 | 无。模板由 `curriculum_loader` 启动时从 JSON 填充，或通过 admin API 远程更新。 |
| 测试影响 | 测试中的创建计划路径需要 mock 或初始化此表 |
| 风险等级 | 🟢 低 — 纯新增表，不影响现有功能 |

### 【变更 B】新建 `conversation_plans` 表（对话计划）

| 维度 | 结论 |
|------|------|
| 用途 | CP2 自由对话生成的计划，每个 conversation 至多一个，内容自包含 |
| 行数预估 | 随用户增长（当前 2 行待迁移） |
| 代码影响 | **新建**：`plan_handler.rs` 中的 `upsert_learning_plan()` 约 50 行需要分支：<br>- 如果 mode='structured' 且无 prebuilt 来源 → 写入 `conversation_plans`<br>- `build_plan_context()` (plan_handler.rs:832) 约 60 行需分支：有 cp1_plan 时读 conversation_plans，否则读 plan_templates |
| routes.rs 影响 | `plan_upsert_handler`（20 行）区分 plan_type |
| ws.rs 影响 | `handle_ws` 中 `build_plan_context` 调用（2 处）+ CP2 `analyze_turn_progress`（1 处）— 调用链自动适配 |
| 风险等级 | 🟡 中 — 核心逻辑分支，但分支条件清晰（按 mode + conversation 判定） |
| 关键代码 | `plan_handler.rs:832` — `build_plan_context` 需要重构为双路读取 |

### 【变更 C】新建 `user_plan_progress` 表（全域任务进度）

| 维度 | 结论 |
|------|------|
| 用途 | 所有计划（K12 + CP1）中单个任务的进度跟踪。DB 列替代 JSON task_status。 |
| 行数预估 | 每个计划 × 任务数（当前 7 个计划合计约 ~50 行） |
| 代码影响 | **新建**：需要实现 CRUD 函数 `get_progress()` / `upsert_progress()` / `batch_upsert()` |
| 替代范围 | 替代 `plan_handler.rs` 中所有 `task_status` JSON 操作（当前 102 处引用） |
| 关键路径 | `apply_plan_mutations()` (plan_handler.rs:335) — 当前解析 JSON 的 `task_status`，以后改为操作 DB 行<br>`build_plan_context()` — 合并 plan_templates/conversation_plans 结构 + user_plan_progress 状态<br>`unlock_next_cards()` — 推进任务时不再改 JSON，改 DB<br>`analyze_turn_progress()` — CP2 分析后写 progress 表 |

| 测试影响 | 3 个 e2e 测试文件 + e2e_runner.rs 中的测试辅助函数需适配 |
| 风险等级 | 🔴 高 — 核心状态管理从 JSON 迁移到 DB 行，涉及 plan_handler.rs ~150 行核心逻辑重写 |
| 迁移数据 | 7 行 `learning_plans.task_status` JSON 需展开为 ~50 行 user_plan_progress |

### 【变更 D】废弃 `learning_plans` 表

| 维度 | 结论 |
|------|------|
| 数据迁移 | 7 行数据分拆到 3 个目标：<br>- K12/Reading 计划（5行）→ `plan_templates`（如无则插入）+ `user_plan_progress`（状态）<br>- CP1 计划（2行）→ `conversation_plans`（plan_content）+ `user_plan_progress`（状态） |

| 代码影响 | 所有 `FROM learning_plans` 的 SQL 需要改为以下之一：<br>- `FROM plan_templates`（模板结构）<br>- `FROM conversation_plans`（CP1 结构）<br>- `FROM user_plan_progress`（进度）<br>- 或通过 `plan_type` 判断后分别查询 |
| 波及文件 | `plan_handler.rs`（25 处 learning_plans 引用），`routes.rs`（20 处），`admin_handlers.rs`（7 处），测试文件（3 个） |

### 【变更 E】时间字段统一 TEXT→INTEGER（22 列）

| 维度 | 结论 |
|------|------|
| 涉及表 | 16 张表，约 22 个 TEXT 时间列（详见后表） |
| 代码影响 | **大量**：所有 `chrono::Utc::now().to_rfc3339()` 改为 `.timestamp()`<br>所有 `format!("{}", now)` 改为 `now.timestamp()`<br>所有解析 TEXT→DateTime 的代码改为 `NaiveDateTime::from_timestamp_opt()` |
| 波及文件 | `plan_handler.rs`, `routes.rs`, `ws.rs`, `admin_handlers.rs`, `reading_loader.rs`, `e2e_runner.rs`, `auth.rs`, 测试文件 |
| 搜索替换 | `grep -rn "to_rfc3339\|format.*now\|NaiveDateTime\|DateTime.*parse"` 确认全量 |
| 数据迁移 | 16 张表需"先加 INTEGER 列 → 用 strftime 填充 → 删旧列 → 重命名" |
| 风险等级 | 🔴 高 — 变更范围大但模式统一，可批量替换 |
| 建议 | 与变更 C（user_plan_progress 新建）和变更 D（废弃 learning_plans）合并执行，新建表直接 INTEGER |

## 八、GitNexus 代码图谱验证（2026-06-01）

使用 GitNexus MCP 的 `context` + `impact` 工具进行了关键符号的代码图谱级验证。

### 8.1 采集数据

| 符号 | 风险等级 | 直接调用者 | 影响生产流程数 | 影响测试数 |
|------|---------|-----------|-------------|----------|
| `handle_plan_update` | 🔴 HIGH | 18 | 3 (chat_handler, process_plan_update, analyze_plan_progress) | 26 |
| `upsert_learning_plan` | 🔴 HIGH | 1 (handle_plan_update) | 3 (同上，深度2层) | 27 |
| `build_plan_context` | 🟢 LOW | 1 (analyze_turn_progress) | 0 | 1 |
| `unlock_next_cards` | 🟢 LOW | 2 (analyze_plan_progress, analyze_turn_progress) | 1 | 6 |
| `k12_init_handler` | 🟢 LOW | 0 (REST 端点，框架路由) | 0 | 0 |
| `reading_init_handler` | 🟢 LOW | 0 (REST 端点，框架路由) | 0 | 0 |

### 8.2 验证结论

| 验证项 | 手工分析结果 | GitNexus 验证 | 差额 |
|--------|------------|--------------|------|
| `build_plan_context` 调用者 | ws.rs + routes.rs | 生产仅 `analyze_turn_progress` 调用（ws.rs/routes.rs 通过该函数间接调用） | ✅ 一致 |
| `handle_plan_update` 影响面 | plan_handler + routes + 测试 | 26 个调用者，3 个生产流程 | ✅ 一致 |
| `upsert_learning_plan` 调用链 | `handle_plan_update` → `upsert_learning_plan` | 确认仅此一条路径 | ✅ 一致 |
| `unlock_next_cards` 调用者 | `analyze_plan_progress` + `analyze_turn_progress` | 确认这两个 | ✅ 一致 |
| `k12_init_handler` / `reading_init_handler` | 通过 `routes()` 宏注册 | 无代码级调用者（框架路由） | ✅ 一致 |
| **遗漏的生产路径** | - | 无新增发现 | ✅ 覆盖完整 |

### 8.3 关键洞察

1. **核心重构瓶颈是 `handle_plan_update` → `upsert_learning_plan` 链。** 这两个函数是计划创建/更新的唯一入口。V2.1 的分支逻辑（写 plan_templates vs conversation_plans）只需要在这两个函数内部判断，所有调用方无需感知。

2. **`build_plan_context` 只有 1 个生产调用者**（`analyze_turn_progress`）。这意味着计划上下文的读取路径重构可以集中在一个地方完成。ws.rs 和 routes.rs 中对 `build_plan_context` 的调用（共 3 处）会自动继承修改后的行为。

3. **最大的测试影响面**：`handle_plan_update` 波及 26 个测试函数。但其中 19 个是 `#[ignore]` 的 live e2e 测试，实际需要改的 lib test 约 7 个。

4. **无遗漏路径**：所有涉及 `learning_plans` 的读写入口已通过 context + impact 双重验证完整覆盖。
